## 리팩터링이란

**리팩터링(refactoring)**은 소프트웨어의 **겉보기 동작은 그대로 둔 채**, 코드를 이해하고 고치기 쉽도록 **내부 구조를 바꾸는** 일이다. 명사로는 그런 개별 기법(함수 추출, 변수 인라인 등)을, 동사로는 그 기법들을 연달아 적용해 코드를 재구성하는 행위를 가리킨다.

동작이 바뀌면 리팩터링이 아니다. 버그 수정이나 기능 추가와 섞지 않는다는 점이 핵심이다.

## 핵심 원칙

| 원칙 | 내용 |
| --- | --- |
| 기능을 넣기 쉬운 구조부터 | 새 기능을 넣기 불편한 구조라면, 먼저 넣기 쉬운 모양으로 리팩터링한 다음 기능을 추가한다 |
| 테스트가 먼저 | 리팩터링 전에 믿을 수 있는 테스트를 준비한다. 테스트는 결과를 스스로 판정(자가 진단)해야 한다 |
| 작게 바꾸고 매번 확인 | 아무리 작은 수정이라도 바꾼 뒤에는 테스트한다. "컴파일 → 테스트 → 커밋"을 작은 단위로 반복한다 |
| 두 개의 모자 | 기능 추가 모자를 썼을 때는 기존 코드를 고치지 않고 기능만 더한다. 리팩터링 모자를 썼을 때는 기능을 더하지 않고 구조만 바꾼다. 둘을 자주 바꿔 쓰되, 지금 어느 모자를 썼는지 늘 의식한다 (켄트 벡의 비유) |
| 3의 법칙 | 처음엔 그냥 한다. 비슷한 일을 두 번째 하면 일단 넘어간다. 세 번째 하게 되면 리팩터링한다 |
| 성능은 다듬은 뒤에 | 반복문을 쪼개는 등 리팩터링이 성능을 떨어뜨릴까 걱정되더라도 먼저 구조를 정리한다. 잘 다듬어진 코드라야 성능 개선도 쉽다. 정말 느려졌다면 그다음에 측정하고 개선한다 |

## 왜 하나

- 설계가 좋아진다. 시간이 지나며 무너지는 구조를 계속 바로잡는다.
- 코드를 이해하기 쉬워진다. 다음에 읽을 사람(미래의 나 포함)의 시간을 아낀다.
- 구조가 드러나면 버그가 잘 보인다.
- 결과적으로 프로그래밍 속도가 빨라진다. 좋은 코드인지 가늠하는 가장 확실한 기준은 **얼마나 수정하기 쉬운가**다.

## 코드에서 바로 써먹는 습관

책의 첫 예제(공연료 청구서 프로그램)에서 나온 작은 습관들이다.

- 함수의 반환값을 담는 변수는 항상 `result`라고 이름 붙인다. 역할이 바로 보인다.
- JavaScript 같은 동적 타입 언어에서는 매개변수 이름에 타입을 드러낸다. 역할이 뚜렷하지 않은 매개변수는 `aPerformance`처럼 부정관사를 붙인다.
- 한 번만 쓰는 임시 변수는 밖에 두지 말고 쓰는 자리에 바로 넣는다(**변수 인라인**). 함수 추출이 쉬워진다.

## 정리

- 리팩터링은 동작을 유지한 채 구조만 바꾸는 일이다. 기능 추가와 같은 커밋에 섞지 않는다.
- 테스트가 안전망이다. 작은 단계마다 테스트를 돌린다.
- 기능 추가 전에 구조부터 정리하고, 같은 일을 세 번째 할 때 리팩터링한다.
- 성능은 깨끗한 코드 위에서 측정한 뒤 개선한다.
