> elsewhen의 「[project-guidelines](https://github.com/elsewhencode/project-guidelines)」(JavaScript 프로젝트 모범 사례 모음)를 바탕으로, 도구는 2026년 기준으로 고쳐 재구성한 노트다.

## 규칙을 미리 정하는 이유

새 프로젝트는 백지에서 시작하지만, 사람이 늘고 시간이 지나면 **같은 결정을 사람마다 다르게 내린 흔적**이 유지 비용이 된다. 규칙은 그 결정을 한 번에 내려 두는 일이다. 규칙마다 **이유**를 함께 적어 두면, 맞지 않는 상황에서 규칙을 고칠지 판단할 수 있다. 이 노트는 영역별 체크리스트이고, 각 영역의 원리는 연결된 개념 노트에 있다.

## 1. Git

| 규칙 | 이유 |
| --- | --- |
| 작업은 기능 브랜치에서, `main`(또는 `develop`)에 직접 푸시하지 않고 PR로 | 미완성 코드가 안정 브랜치를 더럽히지 않고, PR이 리뷰와 토론의 자리가 된다 |
| `main`·`develop`을 보호 브랜치로 설정 | 되돌릴 수 없는 실수를 플랫폼 차원에서 막는다 |
| PR 전에 최신 기준 브랜치로 **대화형 리베이스**하고 충돌을 내 쪽에서 해결 | 머지 커밋 없는 깨끗한 이력, 충돌 없는 PR |
| 리베이스 후 푸시는 `--force-with-lease` | 남이 그사이 올린 커밋을 덮어쓰지 않는다 |
| PR 전에 빌드·테스트·스타일 검사 통과 | 기능 브랜치가 실패하면 합친 뒤에도 실패한다. 포맷 수정이 실제 변경에 섞이지 않는다 |
| 머지한 브랜치는 로컬·원격 모두 삭제 | 죽은 브랜치가 목록을 어지럽히고, 같은 브랜치를 두 번 합치는 실수를 막는다 |
| 공용 `.gitignore`(OS 파일, 에디터 설정, 의존성 폴더, 빌드 결과) | 올리면 안 되는 파일이 섞이지 않는다 |

- 작고 일관된 변경만 골라 담으려면 `git add -p`로 변경 덩어리를 하나씩 보며 고른다.
- 원격에서 지워진 브랜치를 로컬에서 한꺼번에 정리: `git fetch -p` 후 `git branch -vv`에서 `: gone]`인 브랜치를 지운다.
- 흐름의 종류(기능 브랜치, Git Flow, 트렁크 기반)는 [[branching-strategies|브랜치 전략]], 리베이스와 스쿼시는 [[merge-squash-rebase|merge, squash, rebase]]에 있다.

**커밋 메시지**: 제목과 본문을 빈 줄로 나누고(`git shortlog`가 제목만 보여 준다), 제목은 50자·본문은 72자에서 줄바꿈, 제목은 마침표 없이 명령형으로, 본문에는 **어떻게가 아니라 무엇을, 왜**를 쓴다. 세부는 [[commit-convention|커밋 컨벤션]]에 있다.

## 2. 문서

- README는 템플릿으로 시작하고(설치, 실행, 테스트, 배포, API 레퍼런스), 프로젝트가 바뀌면 함께 고친다. 저장소가 여러 개면 서로의 README에 링크를 건다.
- 주석으로 나쁜 코드를 변명하지 않고, 깨끗한 코드를 핑계로 주석을 아예 빼지도 않는다. 근거가 된 이슈·토론 링크는 주석에 남긴다.
- 코드가 바뀌면 주석도 고친다. **주석 처리한 옛 코드 블록은 지운다.** 이력은 Git이 갖고 있다([[js-comments|JavaScript 주석]]).
- 작은 할 일은 `// TODO:`, 큰 일은 이슈를 열고 `// TODO(#3456)`처럼 번호를 단다. 번호를 강제하는 린트 규칙을 둘 수 있다.

## 3. 환경

| 규칙 | 이유와 방법 |
| --- | --- |
| `development`·`test`·`production` 환경을 나눈다 | 환경마다 데이터·토큰·API·포트가 다르다. 개발에서는 예측 가능한 가짜 API를, 분석 도구는 운영에서만 켠다 |
| 배포별 설정은 **환경 변수**에서 읽고 코드에 상수로 두지 않는다 | 코드가 언제든 공개돼도 안전해야 한다. `.env`는 `.gitignore`에 넣고, 필요한 변수 목록은 `.env.example`로 커밋한다 |
| 앱 시작 전에 환경 변수를 **검증**한다 | 빠진 값이나 형식 오류를 시작 시점에 알려 몇 시간의 추적을 아낀다. Zod·Joi 같은 스키마로 검사한다 |
| 설정 파일은 `config/`에 목적별(DB, API)로 나누되 **환경별 파일은 만들지 않는다** | 배포 환경이 늘 때마다 파일이 늘어 확장되지 않는다. 값은 환경 변수가 넣는다 |

**개발 환경을 맞춘다.**

- Node.js 버전은 `package.json`의 `engines`와 `.nvmrc`에 적는다. 패키지 매니저 버전은 `packageManager` 필드로 고정한다([[package-managers|패키지 매니저]]).
- 도구는 전역 설치 대신 프로젝트 의존성으로 두고 `npx`·npm 스크립트로 부른다. 동료 컴퓨터에 같은 도구가 깔려 있다고 기대하지 않는다.
- 가능하면 Docker 이미지로 개발·CI·운영 환경을 통일한다.
- 의존성은 lock 파일(`package-lock.json`, `pnpm-lock.yaml`)을 커밋해 모두가 같은 버전을 받게 하고, CI에서는 `npm ci`로 lock 그대로 설치한다.

## 4. 의존성

| 할 일 | 도구 |
| --- | --- |
| 지금 직접 쓰는 패키지 목록 보기 | `npm ls --depth=0` |
| 더는 쓰지 않는 패키지 찾기(번들 크기만 키운다) | `depcheck`, `knip` |
| 들이기 전에 사용량·릴리스 주기·관리자 수 확인 | npm 다운로드 통계, `npm view <패키지>` |
| 낡은 의존성 확인과 갱신 | `npm outdated`, `npm-check-updates`. 릴리스 노트를 읽고 **하나씩** 올려 문제가 생기면 원인을 좁힌다 |
| 알려진 취약점 확인 | `npm audit`, Snyk, Dependabot·Renovate |

덜 알려진 패키지는 쓰기 전에 팀과 상의한다. 기여자가 많아도 관리자가 수정을 빨리 합치지 않으면 소용없다. 들일지 말지의 판단 기준은 [[small-modules|작은 모듈 철학]]에 있다.

## 5. 테스트

- 테스트 파일은 대상 옆에 `moduleName.test.js`·`*.spec.js`로 둔다. 특정 파일에 속하지 않는 테스트만 `__tests__/` 같은 별도 폴더에 둔다.
- 운영 환경의 분석 대시보드를 테스트 데이터로 오염시키거나 운영 API의 요청 한도에 걸리지 않도록, 필요하면 `test` 모드 환경을 따로 둔다.
- 부수 효과를 바깥으로 빼고 **순수 함수**로 쓰면 비즈니스 로직을 단위로 테스트할 수 있다([[humble-object-pattern|험블 객체 패턴]]).
- 정적 타입 검사기(TypeScript)를 쓴다.
- PR 전에, 리베이스한 뒤 로컬에서 테스트를 돌린다. 실행 방법은 README에 적는다. 테스트 종류와 전략은 [[frontend-test-types|프론트엔드 테스트의 종류]]에 있다.

## 6. 구조와 이름

**역할(controllers, models)이 아니라 기능·페이지·컴포넌트 기준으로 폴더를 나누고**, 테스트를 구현 옆에 둔다.

```text
나쁜 예                      좋은 예
.                            .
├── controllers              ├── product
│   ├── product.js           │   ├── index.js
│   └── user.js              │   ├── product.js
└── models                   │   └── product.test.js
    ├── product.js           └── user
    └── user.js                  ├── index.js
                                 ├── user.js
                                 └── user.test.js
```

한 책임을 담은 작은 모듈 단위로 묶이니 파일 목록이 길어지지 않고 한눈에 찾는다. 프론트엔드에서 이 방향을 끝까지 밀고 간 모양은 [[frontend-folder-structure|프론트엔드 폴더 구조]]에 있다.

- 스크립트(bash, node)는 `scripts/`에 모은다. 빌드·DB 시드·동기화처럼 금세 여러 개가 된다.
- 빌드 결과는 `build/`(또는 `dist/`)에 두고 `.gitignore`에 넣는다. 누구나 만들 수 있는 산출물은 커밋하지 않는다.
- 이름은 검색할 수 있게, 줄임말 없이, 의미가 구별되게 짓는다. 함수 이름은 의도를 드러내는 동사구다. 파일 안에서는 **위에서 아래로 내려가며** 상위 함수를 먼저 둔다([[clean-code-functions-naming|함수와 이름 짓기]]).
- 장난스러운 이름·주석·로그는 쓰지 않는다. 코드는 다른 회사나 고객에게 넘어갈 수 있다.

## 7. 코드 스타일 강제

| 규칙 | 이유 |
| --- | --- |
| 린트를 빌드(CI)에 넣어 실패시킨다 | 빌드가 깨져야 규칙을 진지하게 다룬다. 클라이언트·서버 모두 |
| 팀이 고른 스타일 가이드를 따른다(Airbnb 등) | 가이드 자체보다 **하나로 정하는 것**이 중요하다 |
| 일부 파일은 ignore 설정으로 제외하고, 코드 속 `eslint-disable` 주석은 PR 전에 지운다 | 작업 중 잠시 끄는 것은 괜찮지만 남기면 규칙이 무력해진다 |
| `.editorconfig`로 들여쓰기·줄 끝·인코딩을 에디터 간에 맞춘다 | 에디터가 달라도 같은 기본값 |
| 에디터에서 바로 경고를 보고, 커밋 전 훅(husky + lint-staged)으로 바뀐 파일만 포맷·린트 | 저장할 때마다 손으로 돌리지 않아도 된다 |

새 프로젝트는 최신 문법을 쓰고, 오래된 프로젝트는 현대화할 계획이 아니면 기존 문법에 맞춘다. ESLint와 Prettier의 역할 분담과 flat config는 [[eslint-prettier|ESLint와 Prettier 설정]]에 있다.

## 8. 로깅

- 클라이언트의 `console.log`는 운영 빌드에 남기지 않는다. 빌드에서 제거하더라도 린트가 남은 로그를 경고하게 한다.
- 서버 운영 로그는 로깅 라이브러리(pino, winston)로 남긴다. 레벨, 타임스탬프, 구조화된 JSON, 파일 회전을 맡긴다. 로그를 모으고 찾는 체계는 [[observability|관측 가능성]]에 있다.

## 9. API

### 설계

자원 중심으로 설계한다. 자원(데이터와 그것을 다루는 메서드), 컬렉션(자원의 묶음), URL(위치)이 세 요소다. 개발자에게 익숙한 모양이라 API 내용을 몰라도 범용 클라이언트를 쓸 수 있다. 경로 모양, 이름 표기(kebab-case URL, camelCase 필드), 메서드 선택, 상태 코드, 오류 본문, 버전은 [[rest-api|REST API]]에 정리돼 있다. 목록 API는 전체 개수를 함께 주고 `limit`·`offset`을 받는다([[api-pagination|API 페이지네이션]]). 필터·정렬은 모든 자원에 처음부터 넣지 않아도 되지만, 지원하는 자원은 문서에 적는다.

### 보안

| 규칙 | 이유 |
| --- | --- |
| 토큰은 URL이 아니라 `Authorization: Bearer ...` 헤더로 | URL은 로그·브라우저 기록·Referer로 샌다 |
| Basic 인증은 HTTPS에서만 | base64는 암호화가 아니라 되돌릴 수 있는 인코딩이다 |
| HTTP 요청에는 응답하지 않거나 `403`으로 거절 | 평문 교환 자체를 없앤다 |
| 요청 한도(rate limit)를 일찍 둔다 | 시간당 수천 번 부르는 봇을 막는다 |
| 보안 헤더를 설정한다(helmet 등) | 클릭재킹·MIME 스니핑 같은 공격면을 줄인다 |
| 모든 입력을 검증하고 정규 형태로 바꾸거나 `400`으로 거절 | 잘못된 데이터가 안으로 들어오지 않는다 |
| `Content-Type`을 검사하고 JSON만 받는다. 없거나 예상 밖이면 `4XX` | `application/x-www-form-urlencoded`를 받으면 공격자가 HTML 폼으로 단순 POST를 위조할 수 있다 |
| 사용자 입력은 제대로 된 JSON 직렬화기로 인코딩 | 응답에 섞인 입력이 브라우저에서 코드로 실행되지 않게 |

세부 공격과 방어는 [[api-security|API 보안]], 인증 방식은 [[session-vs-token-auth|세션과 토큰 인증]]에 있다.

### 문서

엔드포인트마다 메서드와 경로, URL 매개변수(필수·선택과 타입), 요청 본문 예시, 성공 응답(상태 코드와 본문), **가능한 실패 응답 전부**를 적는다. 반복처럼 보여도 사용자가 추측하지 않게 한다. 인증 방법은 코드 예시로 보여 준다. OpenAPI(Swagger) 같은 명세 형식으로 쓰면 문서와 테스트·클라이언트 생성을 함께 얻는다.

## 10. 접근성

**프로젝트 시작 때** 정한다. 웹 콘텐츠는 기본적으로 접근 가능하고, 복잡한 기능을 만들며 그것을 깨뜨린다. 나중에 고치는 것보다 처음부터 지키는 편이 훨씬 싸다.

- Lighthouse 접근성 점수나 axe DevTools로 정기 점검하고 **최소 점수**를 합의한다. 탭 순서 같은 항목은 도구가 못 잡으니 손으로 확인한다.
- 접근성 린터를 설치한다: React는 `eslint-plugin-jsx-a11y`, Vue는 `eslint-plugin-vuejs-accessibility`, Angular는 `angular-eslint`의 템플릿 접근성 규칙.
- 테스트에 axe-core 검사를 넣고, Storybook을 쓰면 a11y 애드온을 켠다([[a11y-driven-testing|접근성 기반 테스트]]).
- 접근성을 갖춘 디자인 시스템(React Spectrum, Material 등)을 고려한다.
- 기본 규칙: 링크 이름이 의미를 갖게, 목록은 `ul`·`li` 짝을 맞춰, 제목 순서를 건너뛰지 않게, 글자와 배경 대비를 충분히, 이미지에 대체 텍스트를([[accessible-images-links-text|접근성 있는 이미지·링크·텍스트]]).

## 11. 라이선스

쓸 권리가 있는 자원만 쓴다. 라이브러리는 MIT·Apache·BSD 같은 허용적 라이선스를 찾고, 수정해서 쓸 때는 조건을 읽는다. 저작권 있는 이미지·영상은 법적 문제가 될 수 있다.

## 정리

- 규칙은 결정을 한 번에 내려 두는 일이고, **이유를 함께 적어야** 상황이 바뀔 때 고칠 수 있다.
- Git은 기능 브랜치 + PR + 보호 브랜치, 리베이스 후 `--force-with-lease`, 제목·본문을 나눈 커밋 메시지.
- 설정은 환경 변수로, 시작 시 검증하고, Node·매니저 버전과 lock 파일로 환경을 맞춘다.
- 폴더는 역할이 아니라 기능 기준, 테스트는 구현 옆.
- 스타일·접근성 규칙은 사람이 기억하게 두지 말고 린터·훅·CI로 강제한다.
