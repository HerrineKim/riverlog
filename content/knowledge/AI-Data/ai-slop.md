> AIE Code Summit 2026의 발표자와 참가자들이 함께 쓴 「[No AI Slop: A Manifesto](https://slopmanifesto.com/)」와 GeekNews의 [한국어 정리](https://news.hada.io/topic?id=37128)를 바탕으로 재구성한 노트다.

## 슬롭이란

**슬롭(slop)은 만드는 사람이 들인 노력보다, 받는 사람이 이해하는 데 써야 하는 노력이 더 큰 결과물**이다. 1,000줄짜리 PR, 10쪽짜리 문서, 긴 채팅 답변이 모두 해당할 수 있다.

기준은 AI 사용 여부가 아니다. 사람이 쓴 글도 슬롭일 수 있고, AI가 쓴 코드도 슬롭이 아닐 수 있다. **품질과 받는 사람의 경험을 책임지지 않은 채 출력을 그대로 넘길 때** 슬롭이 된다.

## 왜 문제가 되나

| 구조 | 설명 |
| --- | --- |
| 비용의 비대칭 | 생성 비용은 0에 가까워졌지만 검토 비용은 그대로다. 에이전트 여러 개를 돌리면 사람이 검토할 수 있는 양보다 많은 결과물이 나온다 |
| 복리로 쌓인다 | 지식 베이스, 채팅 기록, 코드에 남은 슬롭은 다음 에이전트의 입력이 된다. 에이전트는 주변에 있는 패턴을 복제한다 |
| 더하기 편향 | 같은 문제를 우회 코드로 반복해 덮고, 빼기보다 더하기가 쉬운 도구를 쓰면 양만 는다 |
| 조직의 압력 | 산출량을 요구하는 조직이 슬롭을 만든다. 개인의 게으름만으로 설명되지 않는다 |
| 의지의 침식 | 슬롭이 일상이 되면 팀이 품질을 지키려는 의지를 잃는다 |

AI는 판단을 대체하지 않고 **증폭**한다. 좋은 판단도 나쁜 판단도 더 큰 규모로 실행된다.

## 우선순위 다섯 가지

왼쪽을 오른쪽보다 앞에 둔다. 오른쪽이 가치 없다는 뜻이 아니다.

| 앞에 두는 것 | 뒤에 두는 것 |
| --- | --- |
| 성과(outcome) | 산출량(output) |
| 이해 | 속도 |
| 자기 생각 | 모델의 첫 초안 |
| 더 나은 일 | 더 쉬운 일 |
| 시스템 개선 | 출력 땜질 |

## 실천 원칙

- **모델과 일하기 전에 문제를 먼저 생각한다.** 의도가 없으면 첫 초안이 방향을 정해 버린다.
- **결과물의 책임은 사람이 진다.** AI가 얼마나 기여했든 내보낸 것의 의도와 결과는 보낸 사람의 것이다.
- **에이전트가 쓴 것은 밝히고, 중요한 부분은 보내기 전에 확인한다.**
- **사람의 주의력을 아낀다.** 받는 사람이 읽는 데 쓸 시간이 가장 비싼 자원이다.
- **검토는 위험도에 따라 고른다.** 전부를 검토할 수는 없다. 걸린 것이 클수록 더 많이 본다. 계획, 설계, 결과 가운데 일부는 계속 사람이 본다.
- **같은 실수가 두 번 나오면 시스템을 고친다.** 출력을 고치는 대신 규칙, 가드레일, 린터, 검증기를 고친다. 다만 에이전트 리뷰와 린터는 유용하지만 그것만으로 충분하지 않다.
- **슬롭을 받으면 친절하게 알린다.** 말하지 않으면 기준이 내려간다.

### 검토하지 않은 출력이 늘 나쁜 것은 아니다

원샷 프롬프트와 바이브 코딩은 레버리지가 큰 도구다. 혼자 쓰는 스크립트나 버릴 프로토타입까지 줄마다 검토할 이유는 없다. 문제가 되는 때는 쓸모 있는 제품, 유지보수할 수 있는 시스템, 다른 사람의 시간과 에너지를 해칠 때다.

## 무엇으로 성과를 재나

| 재지 않는다 | 잰다 |
| --- | --- |
| 코드 줄 수, 병합한 PR 수 | 무엇을 출시했나 |
| 토큰 사용량 | 누가 쓰고 있나 |
| 병렬로 돌린 에이전트 수 | 사용자에게 어떤 도움이 됐나 |

### 토큰맥싱

**토큰맥싱(tokenmaxxing)은 AI를 많이 쓰는 것처럼 보이려고 토큰을 낭비하거나 코드량을 부풀리는 행위**다. 토큰 사용량이나 AI 생성 코드 줄 수로 순위를 매기면 구성원은 그 숫자를 키우는 쪽으로 움직인다. 측정값이 목표가 되면 좋은 측정값이 아니게 된다는 굿하트의 법칙 그대로다.

대안은 결과 지표다. 출시 속도, 버그 감소, 고객 만족도처럼 **무엇이 달라졌는가**를 본다. 개인 역량도 생성량이 아니라 AI를 언제 쓰고 언제 쓰지 않을지 가리는 판단력으로 본다. 평가 항목에 「AI 활용도」를 하나 더하는 방식은 같은 문제를 다시 만든다.

## 슬롭과 검토 병목 사이

슬롭을 막으려고 사람이 모든 출력을 검토하면 사람이 병목이 된다. 둘 사이의 기준은 **안전장치와 가이드를 갖추고 넘기는가**다.

| 상황 | 검토 수준 |
| --- | --- |
| 혼자 로컬에서 AI로 작업한다 | 변경 내역을 직접 확인한다. 다른 검증 단계가 없다 |
| CI/CD에 자동 검증(테스트, 린터, 에이전트 리뷰)이 갖춰져 있다 | 사람이 보는 양을 줄일 수 있다 |
| 프로덕션에 나가는 코드 | 읽고 이해한 뒤 배포한다 |
| 사내용 도구, 일회성 산출물 | 동작하는지 위주로 확인한다 |

코드 생성 비용이 낮아지면 요구사항을 쉽게 받아들이게 된다. 그래서 **그만큼의 코드가 정말 필요한가**를 먼저 묻는다. 만들지 않은 코드는 검토할 필요도 없다.

판단이 사람 몫으로 남는다면 그 판단력을 기를 자리도 필요하다. AI를 쓰면서도 직접 구현해 보는 경험을 따로 쌓아야 검토할 눈이 생긴다.

## 정리

- 슬롭은 AI 사용이 아니라 책임 없는 전달의 문제다. 기준은 받는 사람이 쓰는 노력이다.
- 생성은 싸지고 검토는 그대로다. 그래서 사람의 주의력이 가장 아껴야 할 자원이 된다.
- 성과는 줄 수, PR 수, 토큰이 아니라 출시한 것과 사용자로 잰다. 사용량을 지표로 삼으면 토큰맥싱이 생긴다.
- 전부 검토하지도, 전혀 검토하지 않지도 않는다. 위험도에 따라 고르고, 반복되는 실수는 시스템에서 고친다.
