## 1. 기본 구조: 3단계 프로그레시브 디스클로저

스킬은 한 번에 다 읽히지 않는다. 필요한 만큼만 단계적으로 로딩된다. LLM 버전의 지연 로딩(lazy loading)이라고 보면 된다.

| 단계 | 내용 | 언제 읽히나 |
| --- | --- | --- |
| 1 | YAML 프론트매터 (`name`, `description`) | 항상 시스템 프롬프트에 들어감. 스킬을 쓸지 판단하는 데만 사용 |
| 2 | `SKILL.md` 본문 | 관련 있다고 판단될 때 |
| 3 | `references/` 등 링크된 파일 | 본문이 가리키고, 실제로 필요할 때 |

설계할 때 지킬 원칙은 두 가지다.

- **합성성**: 여러 스킬이 동시에 로딩될 수 있다. 내 스킬만 단독으로 쓰인다고 가정하지 않는다.
- **이식성**: Claude.ai, Claude Code, API에서 똑같이 동작한다.

### MCP와 스킬의 관계

**MCP는 주방이고 스킬은 레시피다.** MCP는 도구에 접근하게 해 줄 뿐이라, MCP만 있으면 사용자가 매번 "이 도구를 이렇게 써"라고 설명해야 한다. 스킬이 그 사용법을 담고 있으면 워크플로가 알아서 켜지고 결과도 일관된다.

## 2. 설계: description이 전부다

`description`은 Claude가 스킬을 불러올지 결정하는 **유일한 단서**다. 시스템 프롬프트에 그대로 들어가기 때문에 1024자 이내여야 하고 XML 태그를 쓸 수 없다.

반드시 두 가지를 담는다.

- **무엇을 하는가 (what)**
- **언제 쓰는가 (when)**: 사용자가 실제로 칠 법한 트리거 문구

```yaml
# 나쁜 예: 언제 써야 하는지 알 수 없음
description: 프로젝트 관리를 돕는다.

# 좋은 예: 하는 일 + 트리거 문구
description: 스프린트 계획을 세우고 태스크를 생성한다. "sprint", "스프린트 계획", "create tickets" 같은 요청에 사용.
```

### 유즈케이스 세 갈래

1. **문서·에셋 생성**: 문서, 디자인, 코드. Claude 기본 능력만으로 충분한 경우.
2. **워크플로 자동화**: 여러 단계로 된 프로세스에 검증 게이트를 넣는 경우.
3. **MCP 강화**: MCP 도구 위에 "어떻게 쓰는지"라는 워크플로 지식을 얹는 경우.

### 폴더 구조와 규칙

```text
your-skill/
├── SKILL.md      ← 필수, 파일명 정확히
├── scripts/      ← 선택: 실행할 스크립트
├── references/   ← 선택: 필요할 때 읽을 상세 문서
└── assets/       ← 선택: 템플릿, 이미지 등
```

- 폴더명은 **소문자와 하이픈만** 쓴다 (`my-skill` O, `My_Skill` X).
- 프론트매터에 `name`과 `description`은 필수다.
- `claude`, `anthropic`은 이름에 쓸 수 없는 예약어다.
- 스킬 폴더 안에 `README.md`를 두지 않는다. 설명은 `SKILL.md`나 `references/`로.

### 지시문 쓰는 법

- "처리 전에 데이터를 검증하라" 같은 모호한 말 대신, **실행할 명령**(예: `python scripts/validate.py input.csv`)을 적는다.
- 핵심 지시는 맨 위에, 자세한 내용은 `references/`로 뺀다.
- 실패했을 때 어떻게 할지(에러 처리)를 반드시 쓴다.

### 성공 기준

- **정량**: 관련 질문의 약 90%에서 스킬이 뜬다. 스킬 유무로 토큰·대화 횟수를 비교한다. API 실패 0건.
- **정성**: 사용자가 "다음엔 뭐 해요?"라고 묻지 않는다. 교정 없이 끝까지 간다. 세션이 바뀌어도 결과가 같다.

가이드 스스로도 평가 일부는 아직 체감(vibes)에 기댄다고 인정한다.

## 3. 테스트와 반복 개선

### 테스트 세 단계

1. **트리거 테스트**: 관련 질문에선 뜨고, 무관한 질문에선 안 뜨는가.
2. **기능 테스트**: 결과가 정확한가, 에러를 제대로 처리하는가.
3. **성능 비교**: 스킬이 있을 때와 없을 때 차이.

가이드가 든 비교 예시:

| 항목 | 스킬 없음 | 스킬 있음 |
| --- | --- | --- |
| 대화 횟수 | 15회 | 2회 |
| API 실패 | 3회 | 0회 |
| 토큰 | 12,000 | 6,000 |

### 처음부터 범용 스킬을 설계하지 않는다

**어려운 작업 하나를 먼저 성공시키고, 그 방법을 스킬로 뽑아낸다.** 구체적인 성공을 일반화하는 순서가 반대보다 훨씬 잘 된다.

### 증상별 대응

| 증상 | 원인 | 대응 |
| --- | --- | --- |
| 언더트리거 (안 뜸) | description에 단서 부족 | 키워드·트리거 문구 추가 |
| 오버트리거 (엉뚱할 때 뜸) | 범위가 너무 넓음 | "이럴 땐 쓰지 마라" 네거티브 트리거 추가 |
| 결과가 들쭉날쭉 | 지시가 모호함 | 지시문 다듬기, 에러 처리 추가 |

## 4. 배포

| 범위 | 방법 |
| --- | --- |
| 개인 | 폴더를 zip으로 묶어 Claude.ai에 업로드, 또는 Claude Code의 `.claude/skills/`에 넣기 |
| 조직 | 관리자가 워크스페이스 전체에 배포 (2025년 12월 도입) |
| API | `/v1/skills` 엔드포인트, `container.skills` 파라미터, Agent SDK 연동 |

- Anthropic은 스킬을 MCP처럼 **오픈 스탠다드**로 공개했다. 다른 AI 플랫폼에서도 돌아가게 하는 것이 목표다.
- 권장 공유 방식: GitHub 공개 저장소에 올리고, MCP 문서에서 스킬로 링크하고, 설치 가이드를 붙인다.
- 소개할 땐 기능보다 결과를 말한다. "YAML 프론트매터와 마크다운이 담긴 폴더"보다 "팀 워크스페이스를 몇 초 만에 세팅"이 낫다.

### 팀 공용 스킬을 패키지로 배포하기

코딩 컨벤션, 커밋 규칙, 디자인 시스템 사용법처럼 **여러 저장소가 같이 지켜야 하는 규칙**을 저장소마다 `.claude/skills/`에 복사해 두면 금방 어긋난다. 디자인 시스템을 패키지로 배포하는 것과 같은 구조([[design-system|디자인 시스템을 패키지로 배포하기]])를 스킬에도 적용한다. **중앙에서 한 번 수정하고, 각 저장소는 설치·업데이트만 한다.**

```text
skill-installer/
├── package.json
├── bin/
│   └── install.js        # skills/ 아래 파일을 대상 저장소의 .claude/skills/로 복사
└── skills/
    └── team-dev-guide/
        └── SKILL.md
```

```bash
npx @my-org/skill-installer install team-dev-guide
```

| 요소 | 역할 |
| --- | --- |
| 중앙 스킬 저장소 | 스킬의 유일한 원본. 수정은 여기서만 한다 |
| npm 패키지 + 설치 명령 | 버전이 추적되고, 각 저장소는 명령 한 줄로 `.claude/skills/<skill-name>/SKILL.md`를 받는다 |
| 자동 업데이트 PR | Renovate, Dependabot, GitHub Actions 스케줄 작업이 새 버전을 감지해 PR을 만든다. 사람이 저장소를 돌며 복사하지 않고, 변경 내역은 PR 리뷰로 확인한다 |

## 5. 실전 패턴 다섯 가지

1. **순차 워크플로**: 단계마다 검증 게이트를 둔다. 단계 간 의존성과 실패 시 롤백 방법을 명시한다.
   예: 고객 온보딩 = 계정 생성 → 결제 설정 검증 → 구독 생성 → 환영 메일.
2. **다중 MCP 조율**: 여러 서비스를 넘나든다. MCP 사이에서 데이터를 넘기고, 다음 단계 전에 검증한다.
   예: 디자인 핸드오프 = Figma 추출 → Drive 업로드 → Linear 태스크 생성 → Slack 알림.
3. **반복 개선**: 초안 → 검증 스크립트 → 수정 → 재검증 루프. 품질 기준과 **언제 멈출지**를 미리 정한다.
4. **상황별 도구 선택**: 목표가 같아도 상황에 따라 도구를 고른다(큰 파일은 클라우드 스토리지, 협업 문서는 Notion, 코드는 GitHub). 판단 기준과 선택 이유를 드러낸다.
5. **도메인 전문 지식**: 스킬의 진짜 가치. 도구 연결은 누구나 할 수 있으니, 차별점은 지식을 코드화하는 데 있다.
   예: 결제 전 컴플라이언스 = 제재 목록 확인 → 관할권 검증 → 리스크 평가 → 감사 기록.

## 6. 트러블슈팅과 최적화

### 지시를 안 따를 때

원인은 대개 셋 중 하나다. 지시가 너무 길거나, 중요한 내용이 중간에 묻혔거나, 모호하다.

- 핵심 지시를 맨 위로 올리고 `## Critical` 같은 헤더로 강조한다.
- **중요한 검증은 자연어 대신 스크립트로 만든다.** 스크립트는 매번 같은 결과를 내지만, 자연어 지시는 매번 다르게 해석될 수 있다.

### 성능

- `SKILL.md`는 **5,000단어 이내**로 두고 나머지는 `references/`로 뺀다.
- 동시에 켜진 스킬이 **20~50개**를 넘으면 성능이 떨어진다. 관련 스킬은 "팩"으로 묶는다.

## 체크리스트

- [ ] 폴더명은 소문자-하이픈, 파일명은 정확히 `SKILL.md`
- [ ] `description`에 what + when(트리거 문구), 1024자 이내, XML 태그 없음
- [ ] 핵심 지시는 맨 위, 상세는 `references/`, 본문 5,000단어 이내
- [ ] 모호한 지시 대신 실행 가능한 명령, 중요한 검증은 스크립트로
- [ ] 에러 처리 지침 포함
- [ ] 관련·무관 질문 양쪽으로 트리거 테스트
- [ ] 다른 스킬과 함께 로딩돼도 충돌하지 않는지 확인
