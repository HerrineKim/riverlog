## 왜 실시간인가

뉴스는 영화·음악·책과 달리 **생명주기가 아주 짧다.** 사용자 반응을 반영하는 데 오래 걸리면, 반영할 때쯤엔 그 기사가 더 이상 뉴스가 아니다. 글 플랫폼도 비슷하다. 브런치 글 소비의 25%가 발행 당일에, 58%가 일주일 안에 일어난다.

또 뉴스는 협업 필터링·콘텐츠 기반 필터링만으로 부족하다. 기사마다 소비 데이터가 쌓이기 전에 수명이 끝나기 때문이다. 그래서 **지금 들어오는 반응으로 바로 순위를 고치는** 방법이 필요하다.

## 멀티암드 밴딧

멀티암드 밴딧(Multi-Armed Bandit, MAB)은 승률을 모르는 슬롯머신 여러 대 중 어디에 동전을 넣을지 정하는 문제다. 승률 80%짜리 기계를 찾으려면 **탐색(exploration)**이 필요하고, 찾은 뒤에는 그 기계에 거는 **활용(exploitation)**이 이득이다. 둘의 균형이 핵심이다.

| 슬롯머신 | 추천 |
| --- | --- |
| 기계 | 콘텐츠 |
| 레버 당기기 | 콘텐츠 노출 |
| 당첨 | 클릭 |
| 승률 | 클릭률(CTR) |

카카오 토로스는 **톰슨 샘플링(Thompson Sampling)**을 쓴다. 콘텐츠마다 클릭률의 분포를 두고, 매번 그 분포에서 표본을 뽑아 가장 높은 것을 보여 준다. 노출이 적어 불확실한 콘텐츠는 분포가 넓어 가끔 뽑히고, 이것이 자연스럽게 탐색이 된다.

### 교과서 밴딧과 실제의 차이

| 현실 문제 | 대응 |
| --- | --- |
| 한 번에 여러 개를 보여 준다 | 슬롯 여러 개를 동시에 고르는 변형 |
| 반응률이 시간에 따라 변한다(비정상성) | **시간 감쇠**: 오래된 반응과 오래된 기사의 가중치를 낮춘다 |
| 화면 위치가 클릭을 좌우한다 | **위치 편향 보정**: 가능한 모든 위치에서의 선택 확률을 평균한다 |
| 이미 본 기사가 또 나온다 | **중복 회피**: 사용자가 이미 고른 기사는 가중치를 낮춘다 |
| 새 콘텐츠의 초깃값 | 콘텐츠 특성이나 카테고리 평균으로 시작한다 |
| 피드백이 늦게 온다 | 수집 지연을 줄이는 파이프라인 (아래) |

루빅스(Real-time User Behavior-based Interactive Content recommender System)는 이 보정을 넣은 **개인화 MAB**를 중심으로 여러 알고리즘을 앙상블한다. 알고리즘은 사용자 그룹 맞춤 추천과 개인화 추천 두 부류로 나뉜다.

## 클릭률을 넘어: 열독률

루빅스는 도입 후 2년 넘게 CTR을 주 지표로 썼다. 그런데 **CTR은 제목에 대한 반응일 뿐 본문을 실제로 읽었는지는 알려 주지 않는다.** 낚시성 제목이 유리해진다.

그래서 2017년 9월 **열독률 지수(DRI, Deep Reading Index)**를 더했다. 기사의 정보량(본문 길이, 이미지 수)으로 기대되는 체류 시간에 비해 실제로 얼마나 머물렀는지를 잰다. 본문 500자·이미지 1개 기사와 1,000자·이미지 5개 기사의 평균 체류 시간이 같다면 앞의 기사를 더 열심히 읽은 것이다. 야구 기사인 줄 알고 눌렀는데 e스포츠 기사였던 사례는 DRI가 −97%로 나와 **제목과 본문의 불일치**를 잡아냈다.

CTR과 DRI를 섞어 DRI 총합을 최대화하도록 랭킹을 바꾼 결과, 1인당 페이지뷰는 조금 줄었지만 1뷰당 체류 시간과 1인당 총 체류 시간은 늘었다. 끌리는 제목의 기사가 덜 추천된 대가다. **무엇을 최적화하느냐가 서비스의 성격을 바꾼다.** 이 흐름은 이후 업계 전반의 「클릭 대신 장기 가치」 목표로 이어졌다.

## 피드백 지연이 성능을 바꾼다

| 실험 | 결과 |
| --- | --- |
| 다음 뉴스, 피드백 수집 주기 비교 | 피드백 지연이 10초 이내일 때가 120초일 때보다 CTR이 1.71배 높았다 |
| 다음 뉴스, 15분 단위 시험 | 수집이 빠를수록 CTR이 올랐지만 시스템 부하와 비용도 올랐다 |

**모델만큼 데이터 최신성이 중요하다.** 다만 빠르게 할수록 비싸므로 성능과 효율 사이에서 지점을 정한다.

## 실시간 추천 시스템 구조

루빅스의 2016년 구조는 지금도 실시간 추천의 기본형이다.

```text
사용자 노출·클릭 이벤트
   → Kafka (대량 메시지를 복제해 안전하게 저장)
   → Spark Streaming (스트림 처리, 결과를 학습에 반영)  ─┐
   → Spark·Hive 배치 (실시간일 필요 없는 집계)           ─┴→ 결합해 랭킹
   → 무상태 추천 서버 (Scala Future·Actor로 비동기 병렬)
   → Couchbase (분산 NoSQL, 노드 추가·복제가 쉬움)
```

| 목표 | 설계 |
| --- | --- |
| 반영 속도 | 사용자 피드백이 **수 초 안에** 다음 추천에 반영된다 |
| 응답 속도 | 디스크·네트워크 IO 최소화, 불변 데이터로 락 없이 병렬 처리. 요청 99%를 3ms, 99.9999%를 150ms 안에 처리했다 |
| 확장성 | 인스턴스를 무상태로 만들어 수평 확장. 오픈 후 요청이 60배 늘어 피크 20만 QPS를 처리했다 |
| 장애 격리 | Mesos·Marathon·Aurora로 죽은 프로세스 자동 재시작, 의존 구성 요소 장애 시 준비된 폴백 값으로 응답, 상시 통합 테스트와 카카오톡 즉시 알림. 가용성 99.998% |

Scala와 Spark를 고른 이유는 기술적 우위보다 **팀에 Scala에 익숙한 개발자가 많아서**였다. 학습 부담이 줄어든다. 지금은 Spark Streaming 대신 Flink나 Kafka Streams, Mesos 대신 Kubernetes가 흔하지만 구성 요소의 역할은 같다.

## 실험이 본체다

브런치는 2015년 유사글 추천을 도입한 뒤 **매일 3~5개의 실험 버킷을 만들고 지우며** 모델을 다듬었다. 다른 서비스에서 성공한 모델이 그대로 통하지 않기 때문이다.

### A/B 테스트 설계

- **같은 시간에 사용자를 나눠** 다른 로직을 보여 준다. 오프라인 로그는 사용자가 실제로 본 것에 대한 반응만 있고, 전후 비교에는 트렌드·새 콘텐츠·시간대 효과가 섞인다.
- 새 로직에는 트래픽의 5~10%를 준다. 이기면 그것이 새 기준이 되고 다음 실험을 시작한다.
- 토로스는 버킷 규칙을 언제든 추가·삭제·변경하고, 노출 비율을 0~100% 사이로 조절하며, **사용자 기준** 또는 **트래픽 기준**으로 버킷을 배정한다. CTR 같은 지표는 실시간으로 본다.

### UX 편향을 걷어 낸 인기 콘텐츠

신규 사용자·신규 글의 콜드 스타트에는 인기 콘텐츠가 대안이다. 그런데 「많이 본 글」은 메인 화면에 노출된 글일 가능성이 크다. 인기가 콘텐츠 품질이 아니라 **노출 위치의 결과**인 것이다. 토로스는 노출 기회를 최대한 공평하게 맞춘 뒤 반응을 비교해 인기 글을 고른다. 이렇게 고른 인기 글은 댓글·공유가 더 많았고, 추천에 쓰면 성과 지표가 50~70% 높았다.

### 브런치 추천의 두 갈래

| 자리 | 1단계 | 2단계 |
| --- | --- | --- |
| 유사글 | 글 특징 추출: CBF(주제어가 잘 맞지만 읽음 수 0인 글도 섞임) + CF(인기 있으면서 비슷한 글) | MAB로 탐색·활용하며 CTR 높은 글 선택 |
| 첫 화면 맞춤 추천 | 타기팅: XGBoost 회귀로 예측 CTR 상위 K개 + 편향 없는 인기 글 + 통계적으로 추천 가치가 있는 글 | 랭킹: ALS·word2vec 같은 CF. 분산·증분 학습으로 피드백을 수 분 안에 반영하고, 요청 시점에 행렬 분해를 한 번 더 해 최신 취향을 넣는다 |

신규 글은 발행 30분 안에 CBF 특징부터 뽑고, 반응이 쌓이면 CF 특징을 더한다. 노출·클릭 피드백은 Kafka 스트림으로 바로 반영한다.

## 알고리즘과 공정성

뉴스 추천은 여론에 영향을 주므로 기술만의 문제가 아니다. 카카오는 2016년 루빅스 알고리즘을 외부 저널리즘 전문가가 살피는 미디어자문위원회를 만들었고, 2017년 핵심 서비스의 알고리즘을 학술지(사이버커뮤니케이션학보)에 공개했다. 루빅스 도입 후 첫 화면에 배치되는 뉴스의 종류는 3.5배, 카테고리별 노출 기사는 최대 5.5배 늘었다고 발표했다. 같은 첫 화면을 모두에게 보여 주던 편집에서, 관심사별로 다른 기사가 보이는 구조로 바뀌었다.

## 정리

- 수명이 짧은 콘텐츠는 밴딧으로 탐색과 활용을 오가며 실시간으로 순위를 고친다.
- 실제 밴딧에는 시간 감쇠, 위치 편향, 중복 회피, 초깃값, 피드백 지연 보정이 필요하다.
- CTR만 최적화하면 낚시 제목이 이긴다. 체류·열독 같은 깊이 지표를 함께 본다.
- 피드백 수집은 빠를수록 좋지만 비용과 맞바꾼다.
- 추천 개발의 본체는 버킷 A/B 테스트를 매일 돌리는 실험 문화다.
