> 당근마켓 전무익의 「[딥러닝 개인화 추천](https://medium.com/daangn/%EB%94%A5%EB%9F%AC%EB%8B%9D-%EA%B0%9C%EC%9D%B8%ED%99%94-%EC%B6%94%EC%B2%9C-1eda682c2e8c)」·「[딥러닝 추천 시스템 in production](https://medium.com/daangn/%EB%94%A5%EB%9F%AC%EB%8B%9D-%EC%B6%94%EC%B2%9C-%EC%8B%9C%EC%8A%A4%ED%85%9C-in-production-fa623877e56a)」(2019), 네이버 AiRS·AiTEMS 발표 자료(2017), LINE 「[Timeline의 새로운 도전 1편](https://engineering.linecorp.com/ko/blog/a-new-challenge-for-line-timeline-1/)」(2020)을 바탕으로, 이후의 변화는 당근의 2026년 공개 내용으로 보강해 재구성한 노트다.

## 왜 딥러닝으로 가나

행렬 분해 라이브러리만으로 실시간 개인화 피드를 만들면 세 가지가 막힌다.

- 학습 데이터가 늘면 메모리 사용량이 급격히 커지고 학습이 느려진다.
- 사용자를 ID 하나로만 표현해서 지역·시간 같은 다른 정보를 넣기 어렵다.
- 요청마다 빠르게 추천을 계산하는 구조가 고려돼 있지 않다.

이 문제를 푼 대표 설계가 유튜브의 「[Deep Neural Networks for YouTube Recommendations](https://research.google/pubs/pub45530/)」(2016)다. 이후 핀터레스트 홈 피드, 당근 피드, 네이버 AiTEMS 모두 같은 뼈대를 쓴다.

## 2단계 구조

아이템이 많으면 사용자 한 명에 대해 모든 아이템의 점수를 계산할 시간이 없다. 그래서 **빠르고 거칠게 추린 뒤, 좁혀진 후보만 정밀하게 정렬한다.**

```text
전체 아이템 (수십만~수억)
   │  1단계 후보 생성(candidate generation)
   │   사용자 벡터 · 아이템 벡터의 내적 → 유사 벡터 검색으로 수백 개
   ▼
후보 수백 개
   │  2단계 랭킹(ranking)
   │   사용자·아이템·문맥 특성을 모두 이어 붙인 신경망 → 선호도 점수
   ▼
최종 추천 수십 개 (+ 다양성·중복 제거·비즈니스 규칙)
```

| 단계 | 입력 | 출력 | 특징 |
| --- | --- | --- | --- |
| 후보 생성 | 최근 소비 이력, 지역 등 일부 특성 | 사용자 벡터 → 가까운 아이템 수백 개 | 원리는 행렬 분해와 같다. 사용자 벡터를 신경망으로 만든다는 점만 다르다 |
| 랭킹 | 사용자·아이템·문맥 특성 전부 | 아이템별 점수 | 내적이 아니라 신경망 출력으로 점수를 내는 회귀 모델이다 |

### 후보 모델 학습: 다음 아이템 맞히기

당근의 첫 모델은 **사용자가 본 글 목록을 문장처럼 보고, 다음에 볼 글을 예측하는** 언어 모델식 학습이었다.

| 항목 | 내용 |
| --- | --- |
| 입력 | 최근 본 글 ID 50개, 지역, 다음 글을 본 시간 |
| 정답 | 다음에 본 글 ID |
| 학습 | 네거티브 샘플링 + 이진 교차 엔트로피 (word2vec과 같은 요령) |
| 평가 | MAP와 Top 50 적중. 3일 로그로 학습하고 다음 날로 시험했더니 50개를 추천하면 약 12%가 맞았다 |

- 지역은 따로 모델을 나누지 않고 **조건으로 넣었다.** 동네끼리 보이는 범위가 겹치고 사용자가 두 동네를 오가기 때문이다. 그 결과 옥수동에서 아기 용품을 보던 사용자와 인테리어 소품을 보던 사용자는 처음 가 본 서초동에서도 각자 취향대로 추천을 받았다.
- 중고 거래 글은 **최신 글 소비가 압도적**이다. 사용자가 본 글의 70%는 등록 후 7.3시간 이내였다. 인기 글은 금방 예약·거래 완료가 되기 때문이다. 모델도 학습 데이터처럼 최신 글을 추천하는 경향을 보였다.
- 처음에는 후보 모델만 붙여 배포하고 A/B 테스트로 개선했다. 랭킹 모델은 다음 단계로 미뤘다. 복잡한 시스템은 **단계로 쪼개 빨리 내보내는** 편이 낫다.

### 서빙: 네트워크의 뒷부분을 벡터 검색으로 바꾼다

학습 때는 네거티브 샘플링 덕에 계산이 가볍지만, 예측 때는 사용자 벡터와 **모든 글 벡터의 내적**을 구해야 한다. 내적은 결국 가까운 벡터 찾기이므로 **근사 최근접 이웃(ANN) 검색**으로 바꿀 수 있다.

```text
앱 서버 → 추천 서버
  1. Redis에서 사용자의 최근 본 글 50개 조회
  2. TensorFlow Serving: 네트워크 앞부분만 실행해 사용자 벡터 생성
  3. faiss 서버(gRPC): 사용자 벡터와 가장 가까운 글 ID 200개
  → 전체 0.01초 이하, CPU만으로 충분, 오토스케일링
```

faiss 인덱스는 데이터가 많아지면 느려지고 메모리를 많이 쓰므로 배포 전에 인덱스를 학습(양자화·클러스터링)해 둔다. 오늘날에는 faiss 외에 ScaNN, HNSW 기반 라이브러리, 벡터 DB가 같은 역할을 한다.

### 학습·배포 파이프라인

추천 모델은 새 글이 계속 들어오므로 **주기적으로 다시 학습하고 배포**해야 한다. 당근의 2019년 파이프라인은 하루 두 번 다음 순서로 돌았다.

```text
BigQuery 이벤트 로그 → 필요한 열만 모은 중간 테이블(비용 절감) → CSV
  → 전처리(TensorFlow Transform: ID 사전, 희귀 ID 제거, TFRecord)  … Dataflow 14대 병렬, 18분
  → 학습(Cloud ML Engine) → 글 임베딩 추출
  → faiss 인덱스 학습  ∥  모델을 S3로 복사
  → ECS 서비스 재시작으로 새 모델 반영
```

- 워크플로는 처음에 Airflow로 짰다가 DAG 변환 작업이 번거로워 **Kubeflow Pipelines**로 옮겼다. 반복 실행(Recurring runs)은 웹에서 설정할 수 있지만 파이프라인을 바꿀 때마다 손으로 다시 등록해야 해서, 문서화되지 않은 Pipelines API로 배포 스크립트를 만들었다.
- 전처리를 모델 그래프 안에 넣으면 서빙 때 같은 전처리를 다시 짤 필요가 없다. 학습과 서빙의 전처리 불일치(training-serving skew)를 막는 방법이다.
- 학습은 GCP, 서비스는 AWS 서울 리전에 있어 모델 파일을 S3로 옮겨 서빙했다.

당시 쓴 도구 중 Cloud ML Engine은 이후 **Vertex AI**로 통합됐고, Kubeflow Pipelines는 v2 SDK로 바뀌었다. 구조(수집 → 전처리 → 학습 → 임베딩·인덱스 → 배포)는 그대로다.

## 순서를 보는 모델: RNN 세션 추천

협업 필터링은 과거 클릭을 근거로 하므로 **방금 나온 뉴스**를 추천하기 어렵고, 한 이슈를 깊게 파고드는 소비도 잘 못 잡는다. 네이버 AiRS는 2017년 뉴스 추천에 순환 신경망(RNN)을 붙였다.

- Doc2Vec으로 기사마다 벡터를 만든다.
- 사용자가 읽은 순서대로 벡터를 이어 시퀀스를 만든다. 몇 분 안에 이어 읽은 기사는 같은 맥락(세션)으로 본다.
- RNN이 다음에 읽을 기사를 예측한다. 같은 맥락의 새 기사가 들어오면 바로 추천할 수 있다.
- **CF가 다양성을, RNN이 깊이와 최신성을** 맡는 하이브리드다. 이 연구는 CIKM 2017에 「Deep Neural Networks for News Recommendations」로 발표됐다.

지금은 RNN 자리를 트랜스포머 기반 순차 추천(SASRec, BERT4Rec 계열)이 주로 차지한다. 「다음 아이템 예측」이라는 문제 설정은 같다.

## 여러 신호를 합치는 추천

| 사례 | 무엇을 합쳤나 | 효과 |
| --- | --- | --- |
| 네이버 AiTEMS (2017~) | 쇼핑뿐 아니라 검색·뉴스·네이버TV·스포츠 이용 이력, 상품명·카테고리·가격·판매자·이미지(CNN 벡터) | **구매 이력이 없어도** 추천한다. 야구장을 검색하고 야구 영상을 본 사용자에게 야구 용품을 보여 준다. 인기 대신 취향과 상품 속성을 맞추므로 신규 판매자의 상품도 노출된다 |
| LINE Discover (2020) | 포스트마다 텍스트·이미지·비디오·소비 이력 네 가지 벡터 | 코사인 유사도로 각각 비슷한 포스트를 찾고 하나로 정렬한다 |

AiTEMS도 수억 개 상품에서 사용자 그룹 취향에 맞는 후보를 먼저 고르고, 신경망이 개인별로 최종 선택하는 2단계 구조다.

## 2026년의 흐름

당근의 추천은 2021년 클릭률 정렬에서 시작해 다음 순서로 바뀌었다.

| 시기 | 변화 |
| --- | --- |
| 2022 | 후보를 단계적으로 좁히는 다단계 구조, 사용자·글을 대조 학습(contrastive learning)으로 임베딩하는 후보 모델(투 타워와 비슷한 구조), 서비스별로 설정만 바꿔 쓰는 공통 랭킹 파이프라인 |
| 2023 | 클릭만 보지 않는 가치 함수: 최신성, 관심도, 채팅 시작, 체류 시간을 함께 보고 부정 피드백은 내린다. 후보 출처도 인구 통계·활동 기반으로 넓혔다 |
| 2024~2025 | 중고 거래 추천을 모임·알바·부동산 등 모든 서비스로 일반화, 「동네」 자체를 데이터로 모델링 |
| 2026 | 큰 **파운데이션 추천 모델**과 의외의 발견(serendipity)을 목표로 한다. LLM은 학습 데이터 생성과 알고리즘 일부에 쓰고, 모델이 커져 서빙은 실시간에서 준실시간으로 옮겨 간다 |

추천 대상이 반경 몇 km 안으로 제한되는 지역 서비스는 후보 풀이 작아 정교한 개인화가 더 어렵다. 업계 전반도 같은 방향이다. 후보 생성 → 랭킹 뼈대는 유지하되 **랭킹 목표를 클릭에서 장기 가치로 넓히고**, 아이템·사용자 표현에 LLM 임베딩을 쓰며, 여러 서비스가 하나의 큰 추천 모델을 공유한다.

## 정리

- 아이템이 많으면 후보 생성(빠르게 수백 개) → 랭킹(정밀하게) 2단계로 나눈다.
- 후보 모델은 「최근 본 것으로 다음 것 맞히기」로 학습하고, 서빙은 사용자 벡터 + ANN 검색으로 바꿔 수 밀리초에 끝낸다.
- 추천은 한 번 만들고 끝나지 않는다. 수집 → 전처리 → 학습 → 인덱스 → 배포를 자동으로 반복하는 파이프라인이 본체다.
- 순서 모델은 최신 콘텐츠와 세션 맥락을, 크로스오버·멀티모달 신호는 콜드 스타트를 푼다.
- 복잡한 시스템은 후보 모델만 먼저 내보내고 A/B 테스트로 키운다.
