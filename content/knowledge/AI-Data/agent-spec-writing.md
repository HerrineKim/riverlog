## 에이전트용 스펙이란

**에이전트용 스펙**은 코딩 에이전트가 추측하지 않고 일하도록 무엇을, 왜, 어디까지, 어떻게 확인할지를 적은 문서다(`SPEC.md`, `AGENTS.md`, 계획 문서 등). 에이전트는 회의에서 맥락을 주워듣지 못하고 세션이 바뀌면 기억을 잃는다. 그래서 사람 팀원에게는 말로 전해지던 것을 글로 남겨야 한다.

좋은 스펙은 두 가지 긴장 사이에 있다. **너무 모호하면** 에이전트가 빈칸을 그럴듯한 추측으로 채우고, **너무 길면** 지시 하나하나가 덜 지켜진다. 그래서 「충분히 구체적으로, 그러나 맥락을 넘치게 하지 않게」가 목표다.

스펙을 먼저 쓰고 버전 관리하는 개발 방식 전체(스펙 기반 개발, Spec Kit·Kiro 같은 도구, 그 장단점)는 [[claude-code-workflows#스펙 기반 개발(SDD)의 전제와 한계|Claude Code 개발 워크플로]]에 있다. 기획서를 행동·데이터 단위 태스크로 나누는 법은 [[bdd-sdd-task-design|BDD·SDD로 기획서를 태스크로 나누기]]에 있다. 이 노트는 **스펙 문서 안에 무엇을 어떻게 쓰는가**를 다룬다.

## 쓰는 순서: 비전은 사람이, 세부는 에이전트가 초안

```mermaid
flowchart LR
  a["사람: 짧은 제품 요약 (목표·사용자·성공 기준)"] --> b["에이전트: 읽기 전용 계획 모드로 코드 탐색·질문"]
  b --> c["에이전트: 상세 스펙 초안"]
  c --> d["사람: 검토·환각 수정·승인"]
  d --> e["스펙 저장, 작업 단위로 나눠 구현"]
  e --> f["테스트·리뷰에서 드러난 빈틈"]
  f --> d
```

1. **목표부터 짧게 쓴다.** 누가 쓰는가, 무엇이 필요한가, 성공하면 어떤 상태인가를 제품 요약(brief) 수준으로 적는다. 아직 구체적 기술 요구가 없으면 세부는 에이전트가 초안을 쓰게 한다.
2. **읽기 전용으로 계획하게 한다.** Claude Code의 계획 모드(Plan Mode)처럼 파일을 바꾸지 못하는 상태에서 코드를 탐색하고, 모호한 점을 되묻고, 아키텍처·보안·테스트 관점을 검토하게 한다. 계획에 오해의 여지가 없어질 때까지 실행으로 넘어가지 않는다.
3. **초안을 검토한다.** 에이전트가 쓴 스펙에도 지어낸 API나 엉뚱한 범위가 섞인다. 구현 전에 고치는 편이 훨씬 싸다.
4. **승인한 스펙을 파일로 남긴다.** 세션이 바뀌어도 같은 기준을 다시 넣을 수 있다.

## 무엇을 담나

### 목표와 비목표

| 항목 | 내용 |
| --- | --- |
| 목표(goal) | 이 작업이 끝나면 사용자에게 무엇이 달라지나 |
| 비목표(non-goals) | 이번에 하지 않는 것. 에이전트는 범위를 스스로 넓히는 경향이 있어 「하지 않는 것」을 적어야 멈춘다 |
| 합격 기준(acceptance criteria) | 끝났다고 판정하는 조건. 「`npm test`가 통과한다」, 「빈 목록이면 안내 문구를 보인다」처럼 출력이나 동작으로 확인할 수 있게 쓴다 |
| 제약(constraints) | 쓸 스택과 버전(「React 프로젝트」가 아니라 「React 19, TypeScript, Vite」), 성능·호환 조건, 지켜야 할 기존 인터페이스 |

### 여섯 핵심 영역

GitHub가 에이전트 설정 파일 2,500여 개를 분석해 잘 동작하는 파일의 공통점으로 꼽은 영역이다. 넘기기 전 체크리스트로 쓴다.

| 영역 | 적을 것 |
| --- | --- |
| **명령어** | 플래그까지 포함한 실행 가능한 명령(`npm test`, `pytest -v`, 빌드·린트). 문서 앞쪽에 둔다 |
| **테스트** | 테스트 실행 방법, 프레임워크, 파일 위치, 기대하는 커버리지 |
| **프로젝트 구조** | 소스·테스트·문서가 어디에 있나 |
| **코드 스타일** | 설명 여러 문단보다 실제 코드 조각 하나가 낫다 |
| **Git 작업 방식** | 브랜치 이름, 커밋 형식, PR 조건 |
| **경계** | 에이전트가 건드리면 안 되는 것. 가장 흔하고 효과적인 제약은 「비밀 값을 커밋하지 않는다」였다 |

### 경계: 항상 / 먼저 묻기 / 절대 금지

「하지 마라」 목록 하나보다 세 단계로 나눈 경계가 낫다. 에이전트가 승인 없이 해도 되는 일과 멈춰야 할 지점이 분명해진다.

| 단계 | 뜻 | 예 |
| --- | --- | --- |
| **항상(Always)** | 묻지 않고 매번 한다 | 커밋 전에 테스트를 돌린다, 스타일 가이드의 이름 규칙을 따른다, 오류를 모니터링 서비스에 기록한다 |
| **먼저 묻기(Ask first)** | 사람이 승인해야 한다 | DB 스키마 변경, 새 의존성 추가, CI/CD 설정 변경 |
| **절대 금지(Never)** | 무조건 멈춘다 | 비밀 값·API 키 커밋, `node_modules/`·`vendor/` 수정, 승인 없이 실패하는 테스트 삭제 |

글로 적은 경계는 지켜질 확률을 높일 뿐이다. 「절대 금지」 중 기계로 막을 수 있는 것은 권한 규칙이나 훅으로 강제한다([[ai-coding-guardrails|AI 코딩 실무 가드레일]]).

### 예시와 도메인 지식

- **입출력 예시**: 기대하는 입력과 출력, 오류 응답의 JSON 모양처럼 형식을 예로 보인다.
- **에이전트가 추론하기 어려운 사실**: 다대다 관계, 라이브러리의 함정, 사내 관례처럼 코드만 봐서는 알 수 없는 지식을 적는다.
- **불확실할 때의 행동**: 「모르면 추측하지 말고 묻는다」 같은 기본 행동을 정한다. 긴 세션에서는 이런 지침이 흐려지므로 다시 상기시킨다.
- **세부 수준은 난이도에 맞춘다.** 간단한 작업에 긴 스펙을 주면 오히려 헷갈린다. 어려운 작업만 자세히 쓴다.

## 큰 스펙을 나눠 싣는다

**지시가 많을수록 각 지시가 지켜질 확률이 떨어진다**(지시의 저주, curse of instructions). 요구사항 수십 개를 한 프롬프트에 몰아넣으면 일부가 조용히 빠진다. 그래서 스펙은 하나로 쓰되 에이전트에게는 조각으로 준다.

| 방법 | 설명 |
| --- | --- |
| 작업 단위로 쪼개기 | 독립적으로 테스트할 수 있는 작은 태스크로 나누고 한 번에 하나씩 맡긴다 |
| 영역별 스펙 | 백엔드·프론트엔드처럼 나눠 그 작업에 필요한 부분만 넣는다 |
| 요약 목차 | 섹션마다 핵심 요약과 「전체는 §4.2 참조」 같은 참조를 둔 목차를 맥락에 두고, 원문은 필요할 때 읽게 한다 |
| 서브에이전트 | DB·API·화면처럼 나눠 각자 자기 맥락 창과 스펙 조각을 갖게 한다 |
| 병렬 에이전트 | 겹치지 않는 일(한쪽은 구현, 한쪽은 테스트)만 병렬로. 두 에이전트가 같은 파일을 쓰지 않게 한다 |
| 새 세션 | 큰 기능이 바뀌면 세션을 새로 열고 스펙에서 다시 시작한다 |
| `// TODO` 미니 스펙 | 코드 안에 남긴 TODO 주석을 하나씩 채우게 한다 |

태스크 사이의 의존 관계는 스펙에 적어 둔다. 그래야 무엇을 병렬로 돌려도 되는지 에이전트와 사람이 같은 판단을 한다.

## 검증을 스펙에 넣는다

- **자기 점검**: 끝난 뒤 결과를 스펙과 대조해 못 채운 요구를 나열하게 한다.
- **테스트를 합격 기준으로**: 통과해야 할 테스트나 언어와 무관한 적합성 테스트 묶음(YAML 등)을 스펙의 성공 기준에 연결한다. 구현이 바뀌어도 같은 테스트로 판정한다.
- **LLM 판정자**: 스타일·가독성·아키텍처처럼 테스트로 잡기 어려운 기준은 다른 에이전트나 다른 프롬프트가 스펙에 비춰 검토한다. 판정자를 설계하는 법은 [[evaluation-driven-development|평가 주도 개발]]에 있다.
- **사람이 마지막 거름망**: 테스트를 통과했다고 옳은 것은 아니다. 스펙은 맞췄는데 결과가 이상하면 코드가 아니라 스펙을 고치고 다시 맡긴다. 설명할 수 없는 코드는 커밋하지 않는다.

## 살아 있는 문서로 유지한다

- **스펙은 코드와 함께 커밋한다.** 결정이 바뀌면 스펙을 먼저 고치고 에이전트에게 바뀐 점을 다시 알린다. 에이전트도 Git 이력과 diff로 무엇이 바뀌었는지 읽는다.
- **빈틈은 스펙에 되돌려 넣는다.** 테스트·리뷰에서 에이전트가 반복해서 헷갈린 지점은 다음 스펙 작성의 체크리스트가 된다. 실행 기록(trace)을 보면 어떤 지시를 잘못 읽었는지 찾을 수 있다.
- **맥락은 가볍게.** 5K 토큰이면 충분한 일에 20K 토큰을 넣지 않는다. 초안·반복 작업은 저렴한 모델에, 계획과 핵심 판단은 상위 모델에 맡긴다.

## 흔한 실수

| 실수 | 결과 | 대신 |
| --- | --- | --- |
| 「더 잘 되게 해 줘」 같은 막연한 목표 | 에이전트가 붙잡을 기준이 없다. 실패한 설정 파일 대부분의 원인 | 목표·합격 기준·명령어를 구체적으로 |
| 문서 묶음을 요약 없이 통째로 넣기 | 맥락이 넘치고 중요한 지시가 묻힌다 | 요약 목차, 검색(RAG), 필요한 조각만 |
| 테스트 통과를 완료로 간주 | 보안·유지보수성 문제가 그대로 남는다 | 사람 리뷰를 합격 기준에 넣는다 |
| 프로토타입 방식을 운영 코드에 그대로 | 스펙·테스트·리뷰 없이 쌓인 코드 | 탐색은 가볍게, 운영 코드는 스펙과 검증을 갖춰 |
| 여섯 영역 중 일부 누락 | 명령어를 몰라 테스트를 못 돌리거나, 경계를 몰라 금지 파일을 고친다 | 넘기기 전 체크리스트로 점검 |

## 정리

- 목표는 사람이 짧게, 세부는 에이전트가 읽기 전용 계획 모드에서 초안을 쓰고 사람이 검토한다.
- 스펙에는 목표·비목표·합격 기준과 명령어·테스트·구조·스타일·Git·경계의 여섯 영역을 담는다.
- 경계는 항상 / 먼저 묻기 / 절대 금지로 나누고, 기계로 막을 수 있는 금지는 도구로 강제한다.
- 지시가 많을수록 덜 지켜진다. 스펙은 하나로 쓰되 작업 단위 조각으로 싣는다.
- 스펙은 코드와 함께 커밋하고, 검증에서 드러난 빈틈을 되돌려 넣는 살아 있는 문서다.

좋은 스펙은 긴 스펙이 아니라 에이전트가 추측할 자리를 남기지 않는 스펙이다.
