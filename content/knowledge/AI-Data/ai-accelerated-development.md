## 핵심: 코딩은 일의 일부다

개발자의 시간은 코딩보다 그 바깥에서 더 많이 쓰인다. 회사 전체가 빨라지려면 모든 단계에 AI가 들어가야 한다.

```text
리서치 → 스펙 논의 → 아키텍처 설계 → 구현 → QA·디버깅 → 운영·장애 대응 → 코드 리뷰 → 채용
                                      ▲
                          흔히 "코딩"이라 부르는 부분
```

이 방식에서 일의 산출물은 **코드 + AI에게 먹일 자료**(요구 사항, 규칙, 도메인 지식)다. 둘을 함께 버전 관리하고 함께 키운다.

AI 소식은 몇 달이면 절반이 바뀐다. 매번 따라잡기보다 **어느 정도 대중화되어 정리된 도구와 방법을 받아 쓰는 편이 투자 대비 효과가 크다.** 바뀌는 것은 모델 이름이고, 아래 원칙은 오래 간다.

## 리서치: 고민을 아웃소싱한다

잘 모르는 분야의 문제(예: 광고주별 예산 배분 같은 제약 최적화)도 추론 모델에게 문제 정의의 빈틈을 지적하고 채우게 하면 풀 수 있는 형태가 된다. 결정 변수, 제약 조건, 목적 함수처럼 정형화하고 코드로까지 옮기게 한다. 복잡한 주제의 조사에는 딥 리서치 기능이 특히 강하다.

| 요령 | 방법 |
| --- | --- |
| 거대한 한 방 질문 | 고급 추론 모델은 짧은 핑퐁보다 **상세한 스펙을 담은 긴 질문 하나**에 더 잘 답한다 |
| 질문도 AI와 만든다 | 긴 질문을 사람이 쓰기는 힘드니, 빠른 대화형 모델과 주고받으며 질문을 다듬고 완성본을 추론 모델에 넣는다 |
| 도메인 지식 문서 | 질문마다 회사 맥락을 타이핑할 수 없다. 도메인 지식을 정리한 한 페이지 문서를 두고 첨부하거나, 사내 위키를 MCP로 연결해 참조하게 한다. 문서가 최신으로 관리되는지가 관건이다 |

## 기획: PRD → 태스크 리스트 → 구현

나중에 코딩 에이전트에게 맡기려면 지시가 명확하고 자세해야 한다. 그 지시를 쓰는 일도 AI에게 맡긴다.

```text
1. "이런 걸 만들 거야. 제품 요구 사항(PRD)을 써 줘"     → prd.md
2. "이 PRD로 세부 작업 목록을 만들어 줘"                → tasklist.md
3. 두 파일을 프로젝트에 두고, 규칙 파일에서 항상 참조하게 한다
4. "Day 1 작업 시작" 식으로 잘라서 맡긴다
```

- PRD는 긴 글을 잘 쓰는 모델로 만들고, 이상하면 대화하며 고친다.
- 기간을 주면 날짜별 할 일로 나눠 주어 잘라서 지시하기 편하다.
- 원하는 라이브러리가 따로 없으면 **대중적인 라이브러리**를 쓰게 한다. 학습 데이터에 많이 나온 것일수록 코드 품질이 좋다.
- "주니어 개발자에게 줄 수준으로" 요청하면 작업이 더 잘게 쪼개진다.

## 바이브 코딩의 현실적인 패턴

바이브 코딩은 **작성자가 뒤바뀐 방식**이다. 예전에는 사람이 짜고 AI가 도왔다면, 이제는 AI가 짜고 사람이 돕는다. 취지는 AI의 빠른 작성 속도로 전체를 여러 번 반복해 결과에 빨리 닿는 것이다. "코드베이스가 없을 때만 된다", "디버깅하다 죽는다"는 비판도 맞는 구석이 있어서, 답은 양극단 사이에 있다. 기존 코드베이스에서 쓸 만한 패턴은 이렇다.

| 역할 | 내용 |
| --- | --- |
| AI | 코드의 대부분을 짜고, 오류도 다시 고쳐 쓴다. 사람이 손으로 고치는 것보다 AI가 다시 쓰는 편이 빠르다 |
| 사람 | 구조를 검토하고, **바뀐 코드는 모두 읽고**, 문제를 찾아 자세히 보고하고 수정 방향을 권한다 |
| 리팩터링 | 수백 줄 쌓일 때마다 작은 리팩터링을 시킨다. 큰 리팩터링을 한 번에 맡기면 자주 망가진다 |
| 파일 크기 | 컨텍스트 창을 생각하면 큰 파일 하나보다 작은 파일 여럿이 유리하다 |

AI 개발이 지속 가능한지는 지시의 크기와 규칙의 양에서 갈린다.

| 지시 방식 | 결과 |
| --- | --- |
| 포괄적 요구 + 규칙 없음 | 한 번에 바뀌는 양이 커서 "도대체 뭘 한 거야"가 된다 → AI를 포기하고 손코딩으로 돌아간다 |
| 세세한 단일 요구 + 풍부한 규칙 | 변경량이 사람이 검토할 수 있는 크기다 → AI 개발이 계속된다 |

## Rule-Growing Development

TDD에서 테스트와 코드가 함께 자라듯, AI와 일할 때는 **규칙과 코드가 함께 자란다.**

```text
TDD:   테스트를 쓴다 → 코드를 쓴다 → 테스트와 코드가 함께 자란다
RGD:   AI에게 시킨다 → 이상한 행동을 관찰한다 → 원하는 방향의 규칙을 더한다 → 규칙과 코드가 함께 자란다
```

- 규칙에는 코딩 스타일뿐 아니라 그 프로젝트에 필요한 지식도 담는다.
- 규칙 파일(`CLAUDE.md`, `AGENTS.md`, `.cursor/rules/` 등)은 팀 저장소에서 버전 관리한다. 파일 위치와 범위는 [[claude-code-guide|Claude Code 활용 가이드]]에 있다.
- **"하지 마"보다 "이렇게 해"를 잘 따른다.** 금지와 바른 방향을 함께 쓴다. 예: "문제를 풀려고 사용하는 LLM 모델 버전을 바꾸지 마라. 바꿔야 하면 작업을 멈추고 사용자에게 확인하라."
- 한국어로 써도 되지만 영어로 쓰면 지시를 미묘하게 더 잘 따르는 경향이 있다. 적용 경로(glob)를 지정하면 더 잘 적용된다.

### 규칙에 자주 넣는 것

| 범주 | 예 |
| --- | --- |
| 변경 범위 | "가능한 한 간단한 해법을 쓴다", "시킨 것만 고친다", "구조 자체는 바꾸지 않는다". 간단하게 하라는 말은 표현을 바꿔 여러 번 강조해야 지킨다 |
| 실행 환경 | dev·test·prod 구분, 환경별 실행 방법. 기본으로는 환경을 고려하지 않아 잘 망가진다 |
| 패키지·도구 | 패키지 관리자(pip인지 uv인지), 가상 환경을 먼저 활성화할 것, 테스트 프레임워크. 빠지면 엉뚱한 곳에 패키지를 설치한다 |
| 라이브러리·버전 | 자주 쓰는 라이브러리와 기준 버전. 명시하지 않으면 학습 때 많이 본 구버전 문법이나 너무 대중적인 선택으로 간다 |
| DB | 스키마, 샘플 데이터, 샘플 쿼리를 별도 파일로 둔다. SQL 작성이 크게 나아진다 |
| 금지 영역 | "테스트 코드는 건드리지 않는다", "API 이름과 파라미터는 바꾸지 않는다", "데이터를 임의로 마이그레이션하지 않는다". 테스트가 충분히 쌓이면 제한을 풀고 리팩터링을 맡겨도 된다. 자세한 원칙은 [[ai-coding-guardrails\|AI 코딩 실무 가드레일]] |
| 황금률 | 구현 세부가 확실하지 않으면 항상 개발자에게 묻는다 |

규칙 파일을 따로 고칠 짬은 잘 나지 않는다. **커밋할 때 필요하면 규칙 파일도 함께 갱신하는 커밋 명령**을 만들어 두면 저절로 최신이 된다.

## AI가 코드를 찾는 방식을 고려한다

코딩 도구는 코드베이스 전체를 읽지 못하고 관련 조각을 골라 읽는다. 조각을 임베딩해 지시와 비슷한 부분을 찾는 방식(Cursor 등)이든, 검색 명령으로 파일을 훑는 방식(Claude Code 등)이든 **적중률은 100%가 아니다.**

| 문제 | 대처 |
| --- | --- |
| 이름이 실제 의미와 다르면 관련 코드를 못 찾는다(예: `transaction` 테이블이 실은 실명 인증 기록) | 의미를 밝히는 주석·docstring을 코드 곁에 둔다. 사람보다 AI에게 더 중요하다 |
| 파일 이름이 `A.py`, `page.py` | `user_identity_check.py`처럼 길고 구체적으로 짓는다 |
| 이미 있는 함수를 못 찾고 새로 만든다(가장 흔한 실수) | "철저히 찾아보고 정말 없을 때만 새로 만들라"고 지시하거나, 아는 함수는 이름을 짚어 고치게 한다 |
| 거대한 데이터 파일이 인덱싱돼 문제를 일으킨다 | `.cursorignore` 같은 무시 목록에 넣는다 |

## 증상이 아니라 원인을 고치게 한다

AI는 근본 원인 대신 증상만 없애는 해결책을 고를 때가 있다. 메모리를 과하게 쓰는 문제에 효율적인 자료 구조 대신 메모리 할당을 늘리고, 재시도 횟수를 늘리고, 경고를 지운다. 테스트가 실패하면 테스트를 지우고, 점수가 낮으면 기준을 낮춘다. 해결책을 지켜보다가 이런 우회가 보이면 금지하는 규칙을 더한다.

## 세션, 테스트, 되돌리기

- **세션은 중간중간 새로 연다.** 맥락이 길어질수록 모델의 성능이 떨어지는 현상은 여전하다. 긴 맥락에서 글자 그대로 일치하지 않는 정보를 찾는 능력이 크게 떨어진다는 측정도 있다([NoLiMa](https://arxiv.org/abs/2502.05167)). 이전 대화의 요약을 넘겨 주는 기능을 쓰면 새 세션도 맥락을 잇는다.
- **테스트 코드를 함께 쓰게 한다.** 고치다 보면 A를 고치면 B가 망가지고 B를 고치면 A가 이상해진다. 코드베이스에 있는 테스트가 가드레일이 되어 엉뚱한 방향을 막아 준다. AI 시대에 테스트는 오히려 더 중요해졌다. 다만 테스트 변경은 사람이 모두 눈으로 확인한다.
- **커밋을 평소보다 자주 한다.** 커밋하지 않았다면 도구의 체크포인트·되돌리기 기능을 쓴다.

## 에이전트형 도구로 맡기기

에디터에 붙은 도구는 **좋은 도구를 쥐여 주는** 느낌이라 일하는 사람은 여전히 나다. Claude Code 같은 에이전트형 도구는 **좋은 주니어를 붙여 주는** 느낌이라 나는 그들을 부린다. 자율성과 작업 완수율이 높아 "시켜 놓고 지켜보기"가 된다.

- **개발 밖의 일도 맡긴다.** 로컬 머신과 상호작용하므로 파일 내용을 읽고 이름 바꾸기, 사진을 EXIF 날짜별로 정리하기, 보고서 묶음 요약, 지난주 Git 이력 정리, 남의 코드 변경 의도 추론 같은 일을 시킨다.
- **반복 작업은 명령으로 등록한다.** 이슈 번호만 주면 문제를 파악해 고치고 PR까지 보내는 식이다.
- **병렬화가 쉽다.** 창을 여러 개 띄우면 그만큼 빨라진다. 작업마다 git worktree로 폴더를 나누면 저장소를 다시 받지 않고도 동시에 작업할 수 있고, worktree 명령을 몰라도 에이전트에게 시키면 된다. 원격 서버에서 일한다면 tmux로 세션을 유지한다(iTerm2는 `tmux -CC`로 네이티브 창처럼 쓴다).
- **프론트엔드도 맡길 수 있다.** Playwright MCP로 브라우저를 조작하게 한다. 규칙 파일에 자세한 가이드를 두고, 서버에서 돌릴 때는 headless 모드를 명시한다.
- **자주 쓰는 MCP는 사용자 단위로 설치하고 허용한다.** 승인 요청이 너무 잦으면 `~/.claude/settings.json`의 허용 목록에 서버 이름(`mcp__context7`처럼 별표 없이)을 넣어 그 서버의 도구를 모두 허용한다.

## 데이터 분석과 학습에도

- **분석 자동화**: 메신저에서 질문하면 쿼리를 짜고, 사내 분석 도구에 대시보드를 만들고, 링크를 돌려주는 봇을 만들 수 있다. "가입 후 유료 아이템을 산 사용자는 잔존율이 높은가? 잔존은 가입 2주 뒤에도 로그인하는 것으로 정의한다"처럼 비즈니스 정의까지 말로 주면 쿼리, 추출, 시각화까지 이어진다.
- **외국어 문서 읽기**: LLM을 번역 엔진으로 쓰는 대역(원문·번역 병기) 번역 확장을 쓰면 번역 품질을 원문과 바로 비교할 수 있다. "IT 전문가 입장에서 번역" 같은 페르소나를 주면 전문 용어 오역이 준다. 영어 영상에는 대역 자막을 붙인다.
- **읽기 전에 거른다**: 먼저 AI 요약으로 읽을 가치가 있는지 판단하고, 어려운 부분은 페이지를 띄운 채 AI와 대화하며 이해한다.
- **입으로 지시한다**: 음성 받아쓰기 도구로 말하면 긴 프롬프트도 타이핑보다 훨씬 쉽게 쓴다. API 키를 연결해 쓰는 도구는 월 구독보다 싸게 높은 정확도를 낼 수 있다.

## 사람의 역할

### 깐깐한 시니어가 된다

AI는 얼개는 잘 잡지만 논리 오류는 잘 못 잡는다. "이건 이렇게 잘못됐으니 이렇게 고쳐야 한다"고 말할 수 있는 **코드를 면밀히 읽는 능력**은 여전히 필요하다. 이 검토도 AI가 돕는다.

| 요청 | 효과 |
| --- | --- |
| 악플(혹평) 요청 | 가장 효과가 좋다 |
| 다른 관점 요청 | 놓친 설계 대안 |
| 잠재 오류 추정 | 리뷰 전 위험 지점 |
| 근거와 출처 요청 | 그럴듯한 오답 거르기 |
| 놓친 이슈 요청 | 빠진 요구 사항 |

### AI가 맡을 수 있는 일의 길이

| 연구 | 결과 |
| --- | --- |
| [SWE-Lancer](https://arxiv.org/abs/2502.12115)(OpenAI, 2025) | 실제 프리랜서 과제 100만 달러어치를 시켰을 때, 직접 구현하는 과제(IC SWE)보다 여러 제안 중 나은 것을 고르는 관리자 과제(SWE Manager)에서 성공률이 높았다 |
| [METR 작업 길이](https://arxiv.org/abs/2503.14499)(2025) | AI가 50% 확률로 완수하는 작업의 길이(사람 기준 소요 시간)가 약 7개월마다 두 배로 늘었다. 측정 당시 최고 모델이 사람이 1시간 가까이 걸리는 작업 수준이었다 |

결론은 둘이다. **한 번에 맡기는 작업을 AI가 감당할 크기 안으로 쪼개야** 성공률이 오른다. 사람에게도 오래 걸리는 일을 통째로 맡기면 운에 맡기는 셈이다. 그리고 AI가 더 긴 일을 맡을수록 사람이 맡는 일의 단위도 커진다.

AI 도구가 오히려 개발을 느리게 했다는 연구도 있다. 다만 참여자 대부분이 도구에 익숙하지 않았고 작업 방식도 AI에 맞게 바뀌지 않은 상태였다. **도구만 얹지 말고 일하는 방식 자체를 AI 친화적으로 재편해야** 효과가 난다. 효율과 별개로, AI와 일하면 반복 작업에서 오는 짜증이 줄어든다는 장점도 있다.

### 트레이드오프 사이의 선택자

곧 개발자 한 명이 수많은 에이전트를 부리며 코딩하게 된다. AI는 최신 스포츠카와 튼튼한 트럭 같은 선택지를 만들어 줄 수 있지만, **옳고 그름이 아니라 옳음과 옳음 사이에서 고르는 일**은 사람의 몫이다.

## 정리

- 코딩뿐 아니라 리서치·기획·검토·학습 모두에 AI를 넣는다. 산출물은 코드 + AI에게 먹일 자료다.
- 고급 모델에는 상세한 긴 질문을 한 번에 준다. 질문과 PRD·태스크 리스트도 AI와 함께 만든다.
- AI가 짜고 사람은 구조 검토, 변경 읽기, 문제 보고를 맡는다. 지시는 작게, 리팩터링도 작게 한다.
- 이상한 행동을 볼 때마다 규칙을 더해 규칙과 코드를 함께 키운다. 금지와 바른 방향을 같이 쓴다.
- AI가 코드를 찾을 수 있게 의미 있는 주석과 이름을 쓰고, 중복 함수와 증상만 고치는 해결책을 경계한다.
- 세션은 자주 새로, 테스트는 가드레일로, 커밋은 자주 한다. 작업은 AI가 감당할 길이로 쪼갠다.
- 사람은 깐깐한 리뷰어이자 트레이드오프 사이의 선택자가 된다.
