## 세 단계와 하나의 원칙

AI로 소프트웨어를 만드는 방법은 세 번 중심을 옮겼다. 각 전환은 앞 단계가 약속을 지키지 못한 데서 시작했다.

| | 프롬프트 엔지니어링 | 컨텍스트 엔지니어링 | 하네스 엔지니어링 |
| --- | --- | --- | --- |
| 시기 | 2022–2024 | 2025 | 2026– |
| 핵심 질문 | 무엇을 말할까 | 어떤 정보를 줄까 | 어떤 시스템을 만들까 |
| 비유(메일) | 완벽한 메일 쓰기 | 받은편지함 관리 | 메일 시스템 설계 |
| 비유(OS) | 명령어 한 줄 | RAM 관리 | 운영체제 전체 |
| 핵심 지표 | 응답 품질(주관적) | KV 캐시 적중률 | 작업 완료율, 작업당 비용 |
| 실패 모드 | 감으로 하는 프롬프팅, 비결정성 | 컨텍스트 오염, 중간 정보 유실 | 오케스트레이션 버그, 보안 사고 |
| 필요한 역량 | 언어 감각 + 도메인 지식 | 정보 설계 | 시스템 설계 + 보안 |

관통하는 원칙은 **엄밀함의 이동(relocating rigor)**이다. 엄밀함은 사라지지 않고 더 높은 추상화 층으로 옮긴다. 설계 문서가 자동화 테스트로, 컴파일러 타입 검사가 런타임 테스트 스위트로 옮겨 갔듯, AI 개발에서도 코드 작성 → 컨텍스트 설계 → 시스템 설계로 옮겨 간다. 그래서 "AI에게 코드를 맡기면 엄밀함을 잃는다"는 비판은 반만 맞다. 엄밀함을 둘 자리를 옮기지 않으면 잃는다.

엄밀함을 옮기는 세 원칙은 이렇다.

- **불변 조건은 기계가 강제하는 규칙으로 쓴다.** "양수만 받는다"를 주석이 아니라 타입이나 단언(assertion)으로 검사한다.
- **실패는 즉시, 크게 드러나야 한다.** 조용한 에러는 나중에 더 큰 문제로 돌아온다.
- **엔지니어의 일은 타이핑에서 의도 명세와 결과 검증으로 바뀐다.**

세 단계는 서로 대체하지 않고 **포함**한다. 좋은 하네스에도 좋은 컨텍스트가, 좋은 컨텍스트에도 좋은 프롬프트가 필요하다. 프롬프트 엔지니어링은 죽은 것이 아니라 하네스의 하위 모듈이 됐다.

## 1. 프롬프트 엔지니어링

**모델에 보내는 지시문의 품질이 결과를 정한다**고 보는 접근이다. 자연어 지시가 곧 프로그램이 되는 패러다임(Software 3.0)에서 출발했다.

### 핵심 기법

| 기법 | 아이디어 | 의의와 한계 |
| --- | --- | --- |
| 생각의 사슬(Chain-of-Thought) | "단계별로 생각해 보자"로 풀이 과정을 쓰게 한다 | 산술·상식·기호 추론 성능이 크게 오른다 |
| ReAct | 생각(Thought) → 행동(Action) → 관찰(Observation)을 번갈아 반복 | 외부 도구로 모르는 것을 찾아 환각을 줄이고, 추론 과정이 투명해진다. **오늘날 모든 코딩 에이전트의 원형 루프** |
| 생각의 나무(Tree-of-Thought) | 여러 추론 경로를 동시에 탐색하고 막히면 되돌아간다 | 문제 하나에 API 호출 수십 번. 비용이 폭증한다 |
| Self-Refine, Reflexion | 생성 → 자기 피드백 → 수정. 실패 경험을 말로 기록해 다음 시도에 쓴다 | 피드백 품질이 모델 자신의 능력에 묶인다. 학생이 자기 시험지를 채점하는 격 |

### 네 가지 에이전틱 디자인 패턴

Andrew Ng이 정리한 실무 프레임워크다.

| 패턴 | 내용 | 안정성 |
| --- | --- | --- |
| 반성(Reflection) | 결과를 스스로 비평·수정. 다른 페르소나("시니어 리뷰어 관점에서")로 검토하면 품질이 오른다 | 가장 안정적 |
| 도구 사용(Tool Use) | 검색·코드 실행·DB 조회를 **언제 쓸지 모델이 정한다**. 챗봇과 에이전트를 가르는 지점 | 안정적 |
| 계획(Planning) | 큰 작업을 하위 작업으로 분해 | 계획은 그럴듯해도 실행에서 무너지기 쉽다 |
| 멀티 에이전트 협업 | 코더·리뷰어·테스터 에이전트가 역할을 나눈다 | 가장 미성숙하지만 잠재력이 크다 |

**모델을 바꾸지 않아도 모델 바깥의 패턴을 바꾸면 성능이 뛴다.** 약한 모델을 에이전틱 워크플로로 감싸면 강한 모델의 제로샷보다 나은 경우가 있다. 이것이 "모델 밖의 시스템이 중요하다"는 첫 신호였다.

워크플로와 에이전트는 구분한다. **워크플로**는 흐름이 미리 정해진 파이프라인(생성 → 리뷰 → 테스트)이고, **에이전트**는 LLM이 다음 행동을 스스로 고르는 자율 프로세스다. 우열은 없다. 원칙은 **가능한 한 단순하게 시작하기**다. 워크플로로 충분하면 에이전트를 쓰지 않는다.

### 한계: 프롬프트가 완벽해도 볼 수 없으면 모른다

프로젝트가 커지면 "기존 유틸 함수를 재사용하라"고 아무리 써도 에이전트가 새 함수를 만든다. 유틸 파일이 컨텍스트 창에 없으면 존재를 모르기 때문이다. **프롬프트 문제가 아니라 컨텍스트 문제다.** 측정·테스트 없이 시행착오로 프롬프트를 고치는 **블라인드 프롬프팅(blind prompting)**도 한계였다. 모델은 비결정적이라 "Please" 한 단어, 줄바꿈 하나에도 결과가 바뀐다.

### 바이브 코딩이라는 극단

코드를 읽지 않고, 에러는 복사해 붙이고, 돌아가면 끝내는 방식이 **바이브 코딩(vibe coding)**이다. 프롬프트 엔지니어링의 논리적 극단이다. 원래 주말 프로젝트용이라는 단서가 붙었지만 실무로 번졌고, 데모에서 빛나던 MVP가 운영에서 무너지는 **숙취**가 뒤따랐다. 아무도 읽지 않은 코드는 아무도 고칠 수 없다.

> LLM이 모든 코드를 썼더라도 사람이 리뷰하고 테스트했다면 그것은 바이브 코딩이 아니다. — Simon Willison

핵심은 **누가 코드를 썼느냐가 아니라 엄밀함이 어디 있느냐**다. 바이브 코딩은 엄밀함의 세 원칙을 모두 어긴다.

## 2. 컨텍스트 엔지니어링

**다음 단계를 풀 수 있도록 컨텍스트 창을 딱 맞는 정보로 채우는 기술**이다. 질문이 "무엇을 말할까"에서 "무엇을 보여 줄까"로 바뀐다.

### LLM을 운영체제로 보기

| 전통 OS | LLM OS |
| --- | --- |
| 커널 | LLM 추론 엔진 |
| RAM(작업 메모리) | 컨텍스트 창. 토큰 단위로 관리 |
| 파일 시스템 | RAG·벡터 DB. 필요한 것만 꺼내 주입 |
| 시스템 콜 | 도구 호출·API |
| 프로세스 관리 | 멀티 에이전트 오케스트레이션 |

프롬프트는 OS에 치는 명령 한 줄이다. 성능은 **RAM(컨텍스트 창)에 무엇을 올리느냐**가 정한다. 필요한 파일이 마운트되지 않은 디스크에 있으면 `ls`를 아무리 정교하게 쳐도 소용없다.

컨텍스트 창에 들어가는 재료는 다섯 가지다. 시스템 프롬프트, 사용자 입력, 대화 기록, 도구 결과, 검색한 지식.

### 네 가지 전략: Write · Select · Compress · Isolate

컨텍스트 엔지니어링은 정보를 많이 넣는 일(context stuffing)이 아니다. 양보다 **신호 대 잡음 비**를 최적화한다.

| 전략 | 하는 일 | 예(고객 지원 에이전트) |
| --- | --- | --- |
| 쓰기(Write) | 시스템 프롬프트를 명확하고 구조적으로 쓴다 | 역할, 환불 정책 30일, 기술 문제는 티켓 생성 |
| 고르기(Select) | 지금 필요한 것만 넣는다 | "주문 취소" 요청에는 FAQ 전체가 아니라 취소·환불 문서만 |
| 압축(Compress) | 지난 맥락을 요약한다 | 20턴 대화의 앞 15턴을 "X 상품 환불 요청, 영수증 확인, 배송비 문의"로 |
| 격리(Isolate) | 다른 컨텍스트로 떼어 위임한다 | 기술 문제 진단은 서브에이전트에게. 로그가 메인 대화를 덮지 않는다 |

**중간 정보 유실(lost in the middle)**: 긴 컨텍스트 한가운데 묻힌 정보는 정확도가 크게 떨어진다. "컨텍스트가 40%를 넘으면 멍청해지는 구간"이라는 경험칙도 있다. 많이 넣을수록 좋다는 직관과 반대다.

### 저장과 표현을 나눈다

컨텍스트는 원시 데이터를 쏟아 놓은 것이 아니라 **더 큰 상태 시스템 위의 컴파일된 뷰**다.

- **저장과 표현 분리**: 전체 대화·도구 결과는 세션에 원본 그대로 두고, 매 턴 모델에 보낼 작업 컨텍스트는 필요한 것만 골라 새로 조립한다. DB의 테이블과 뷰 관계와 같다.
- **명시적 변환 파이프라인**: "시스템 프롬프트 주입 → 관련 기록 선택 → 도구 결과 요약 → 토큰 예산 확인"처럼 이름 붙은 단계를 정해진 순서로 돌린다. 즉흥적인 문자열 이어 붙이기가 아니다.
- **기본 범위 제한**: 서브에이전트에게는 전체 대화가 아니라 맡은 일에 필요한 것만 준다. 컨텍스트 창 버전의 최소 권한 원칙이다.

### KV 캐시 적중률이 운영 지표다

LLM은 토큰마다 어텐션의 Key·Value를 계산한다. 요청의 **앞부분(prefix)이 이전 요청과 같으면** 그 부분은 캐시를 재사용한다. 캐시를 읽는 토큰은 일반 입력보다 훨씬 싸다(Claude API에서는 기본 입력 단가의 10분의 1). 반대로 **앞부분의 토큰 하나만 바뀌어도 그 뒤 캐시가 전부 무효**가 된다.

```text
컨텍스트 창
├─ 안정된 앞부분(stable prefix): 시스템 프롬프트, 정체성, 도구 정의, 장기 요약
└─ 변하는 뒷부분(variable suffix): 최신 사용자 입력, 새 도구 결과
```

그래서 운영에서는 프롬프트의 "품질"보다 **안정성**이 더 중요하다. 실무 원칙은 이렇다.

| 원칙 | 내용 |
| --- | --- |
| 앞부분 고정 | 시스템 프롬프트와 도구 정의를 최대한 바꾸지 않는다. 타임스탬프 같은 가변 값을 앞에 넣지 않는다 |
| 도구 목록을 실행 중에 바꾸지 않는다 | 추가·삭제 대신 활성/비활성 상태로 토글한다 |
| 통제된 다양성 | 같은 입력에 같은 행동을 반복하며 루프에 빠지면, 앞부분은 건드리지 않고 응답 형식이나 표현을 살짝 바꿔 새 시도를 유도한다 |
| 운영 우선 | 파인튜닝보다 컨텍스트 개선이 몇 시간 단위로 훨씬 빨리 돈다 |
| 모델 교체에 살아남는 하네스 | 컨텍스트 관리 시스템은 특정 모델에 묶지 않는다 |
| 구조화된 출력 | 에이전트 간 통신과 도구 결과는 자유 텍스트 대신 JSON 같은 구조로 |
| 사람 개입 지점을 처음부터 | "승인은 나중에 붙이자"가 아니라 설계 단계에서 넣는다 |

### 에이전트 인프라

| 요소 | 역할 |
| --- | --- |
| MCP(Model Context Protocol) | LLM과 외부 도구·데이터의 연결 표준. 도구 쪽에 MCP 서버를 한 번 만들면 MCP를 지원하는 모든 클라이언트가 같은 방식으로 붙는다(AI의 USB). 2025년 말 Linux Foundation 산하 Agentic AI Foundation으로 이관됐다. 에이전트 ↔ 에이전트 통신 표준으로는 A2A가 있다 |
| 스킬(Skills) | 여러 도구 호출을 묶은 재사용 워크플로. 앞부분에는 이름과 한 줄 설명만 두고, 필요할 때 전체 정의를 뒷부분에 불러온다(지연 로딩). 캐시를 지키면서 능력을 늘리는 방법 |
| 서브에이전트 | 격리 전략의 구현. 메인 컨텍스트를 깨끗하게 유지한다 |
| 스웜(Swarm) | 중앙 조정자 없이 에이전트끼리 일을 넘기는(handoff) 패턴 |
| 최신 문서 주입 | 모델은 학습 이후 정보를 모르는 전향성 기억상실 상태다. 코드를 쓰기 전에 검증된 최신 API 문서를 가져와 넣는다(Context Hub 등) |
| 외부 메모리 | 파일(CLAUDE.md, 프로젝트 노트), 벡터 DB, 세션 간 JSON 상태. 오래된 대화는 단계적으로 압축한다(오래된 메시지 버리기 → 도구 결과만 압축 → 전체 요약) |

### 한계: 컨텍스트는 필요조건일 뿐이다

- **단일 턴에 갇힌다.** 컨텍스트 기법은 "이번 호출에 무엇을 넣을까"에 집중한다. 에이전트는 수십 번 연쇄 결정을 한다. 15턴째에 이미 압축된 3턴째 결과가 필요하면? 컨텍스트를 완벽히 구성해도 그것을 소비하는 루프가 엉망이면 **시스템 문제**다.
- **에러 복구가 없다.** 도구 호출 실패, 환각, 비용 급증에는 별도 장치가 필요하다. 무료 → 저가 → 고가 순으로 시도하는 비용 인식 복구, 같은 실수 반복을 감지해 멈추는 수확 체감 감지, 연속 실패 시 자동 정지하는 서킷 브레이커.
- **보안을 다루지 않는다.** 무엇을 넣을지는 다루지만 무엇을 막을지는 다루지 않는다.

## 3. 하네스 엔지니어링

> 에이전트가 실수할 때마다, 그 실수가 구조적으로 다시 일어날 수 없도록 시스템을 바꾼다.

프롬프트를 고치는 것이 아니라 **에이전트를 둘러싼 규칙·도구·제약·피드백 루프를 바꾸는 일**이다.

```text
에이전트 = 모델 + 하네스
```

하네스는 **에이전트에서 모델을 뺀 전부**다. 모델이 CPU라면 하네스는 운영체제(컨텍스트 관리, 도구 관리, 권한 통제, 에러 복구)다. 말이 아무리 힘세도 고삐와 마구가 없으면 밭을 갈 수 없다. 에이전트의 정의 "목표를 이루려고 루프 안에서 도구를 실행하는 LLM"에서 핵심은 **루프**이고, 하네스는 그 루프를 통제한다.

### 하네스의 네 사분면

| | 사전 유도(feedforward) | 사후 교정(feedback) |
| --- | --- | --- |
| **결정적** | **가이드**: AGENTS.md, `.cursorrules`, 코딩 컨벤션 | **계산형**: 컴파일러, 타입 검사, 린터, 구조 테스트 |
| **비결정적** | **지시문**: 역할 정의, 행동 제약, 퓨샷 예시 | **추론형**: LLM-as-judge, 의미 수준 코드 리뷰 |

- **가이드**는 비용이 거의 없지만 강제력이 없다. 에이전트가 무시할 수 있다.
- **계산형 피드백**은 가이드를 무시해도 기계적으로 잡는다. 커스텀 린터로 아키텍처 규칙을 강제하면 사람 리뷰어를 대신한다. 자율성의 핵심 축이다.
- **지시문**은 결정적 규칙이 못 잡는 뉘앙스("불확실하면 확인을 구하라")를 다룬다.
- **추론형 피드백**은 컴파일은 되지만 의미가 틀린 코드를 잡는다.

운영 하네스는 네 사분면을 겹겹이 쌓는다(심층 방어). 운영에서 성공하는 "AI 에이전트" 대부분은 마법 같은 자율 존재가 아니라 **핵심 지점에 LLM을 끼운 잘 설계된 전통 소프트웨어**다. 결정적 게이트의 필요성은 [[ai-era-developer|AI 시대 개발자의 역할]]의 「하네스와 오라클」에도 있다.

### 실전 패턴

| 패턴 | 구조 | 교훈 |
| --- | --- | --- |
| 계획자·생성자·평가자 분리 | 계획자가 짧은 요청을 제품 스펙으로 확장 → 생성자가 기능을 하나씩 스프린트로 구현(스프린트마다 컨텍스트 초기화) → 평가자가 Playwright E2E로 UI·API·DB 상태를 기준표로 채점, 미달이면 구체 피드백과 함께 반려 | **에이전트는 자기 결과를 정확히 평가하지 못한다.** 만드는 쪽과 판정하는 쪽을 나눈다(GAN의 생성자·판별자처럼). 계획자에게 지나치게 구체적인 기술 지시를 주면 오류가 연쇄된다. 비용은 수십 배 늘지만, 사람이 사후에 고치던 비용을 시스템의 사전 검증으로 옮긴 것이다 |
| 사람은 코드 대신 환경을 만든다 | 수동 코드 0줄로 대규모 코드베이스를 생성한 팀이 한 일은 세 가지: ① 슬랙·사람 머릿속에만 있던 결정을 레포 안 마크다운·코드로 ② 문서만으로는 무시되므로 커스텀 린터·구조 테스트로 기계적 강제 ③ 문서를 한꺼번에 쏟지 않고 지도를 주고 찾아가게(점진적 공개) | **에이전트가 볼 수 없는 지식은 존재하지 않는다.** "1000쪽 매뉴얼이 아니라 지도를 줘라." 에이전트가 실수하면 에이전트를 탓하지 말고 하네스를 고친다 |
| 랄프(Ralph) 루프 | PRD를 정의하고, 모든 항목이 끝날 때까지 코딩 에이전트를 반복 실행. 매 반복은 깨끗한 컨텍스트로 시작하고 상태는 git 기록·`progress.txt`·`prd.json`에 둔다 | 기억을 컨텍스트 창이 아니라 **파일 시스템**에 둔다. 컴파일·테스트·린트처럼 프로그램으로 검증 가능한 검사가 많을수록 오래 자율로 돈다 |

자율 루프 설계는 [[loop-engineering|루프 엔지니어링]], 생성·검증 루프를 디자인 시스템에 적용한 예는 [[design-system-agent-harness|디자인 시스템을 아는 화면 생성 에이전트 설계하기]]에 있다.

### 보안: 치명적 삼요소와 2의 규칙

에이전트가 다음 셋을 **동시에** 가지면 보안 사고는 시간문제다. 이를 **치명적 삼요소(lethal trifecta)**라고 한다.

1. 신뢰할 수 없는 입력을 처리한다(외부 웹, 메일, 사용자 입력)
2. 민감한 시스템·데이터에 접근한다(개인정보, 내부 API, DB)
3. 상태를 바꿀 수 있다(메일 발송, 파일 삭제, API 호출)

프롬프트 인젝션 한 번으로 회사 데이터가 빠져나갈 수 있다. **2의 규칙(Rule of Two)**은 이를 실행 규칙으로 바꾼다. **셋 중 최대 둘만 동시에 허용하고, 셋 다 필요하면 사람의 승인을 거친다.**

| 허용 | 막는 것 | 예 |
| --- | --- | --- |
| 외부 입력 + 민감 데이터 | 상태 변경 | 변경은 사람 승인 후 |
| 외부 입력 + 상태 변경 | 민감 데이터 | 샌드박스에서만 |
| 민감 데이터 + 상태 변경 | 외부 입력 | 내부 데이터만 다룬다 |

이 가드레일은 기능 제약이 아니라 **신뢰의 전제 조건**이다.

### 하네스는 걷어 낼 수 있어야 한다

모델이 좋아지면 하네스의 "똑똑한" 로직 일부는 쓸모없어진다. 이전 모델용 에러 복구 로직의 절반이 다음 모델에서는 짐이 될 수 있다. 하네스 설계는 **무엇을 만들까만큼 무엇을 쉽게 뗄 수 있게 할까**의 문제다. 오늘의 과잉 설계는 내일의 모델 업데이트에 족쇄가 된다.

## 다음에 옮겨 갈 자리

- **감독 에이전트(guardian agent)**: 배포 직전 다른 에이전트가 실시간으로 "규정 위반"을 막는다. 엄밀함이 실행에서 감독으로 옮긴다.
- **평가 엔지니어링**: 벤치마크 점수보다 실제 작업 완료율과 실패에서 회복하는 방식이 중요해진다. 컴파일 여부는 기계가 판단하지만 "글이 잘 읽히나", "디자인이 아름다운가" 같은 검증 불가능한 보상은 LLM-as-judge로 평가하되 평가자 편향이 남는다. 자세한 방법은 [[evaluation-driven-development|평가 주도 개발]]을 본다.
- **지식 엔진**: 코드에 남지 않는 "왜 이 아키텍처를 골랐나", "반년 전에 왜 롤백했나"를 코드 그래프·커밋 기록·세션 메모리로 엮어, "이 함수를 고쳐"가 아니라 "이 함수가 왜 이렇게 생겼는지 이해하고 고쳐"를 가능하게 한다.

## 정리

- 프롬프트 → 컨텍스트 → 하네스로 옮겨 온 것은 **엄밀함이 놓이는 자리**다. 각 단계는 앞 단계를 버리지 않고 포함한다.
- 프롬프트가 완벽해도 필요한 정보가 컨텍스트 창에 없으면 소용없다. 컨텍스트는 양이 아니라 **신호 대 잡음 비**와 **앞부분 안정성(KV 캐시)**으로 설계한다.
- 컨텍스트가 완벽해도 그것을 소비하는 루프가 엉망이면 실패한다. 하네스는 결정적·비결정적 × 사전·사후의 네 사분면을 겹쳐 쌓는다.
- 만드는 쪽과 판정하는 쪽을 나누고, 볼 수 없는 지식은 레포에 넣고, 실수는 하네스를 고쳐 구조적으로 막는다.
- 외부 입력·민감 데이터·상태 변경 중 **둘까지만** 허용하고, 모델이 좋아지면 걷어 낼 수 있게 만든다.

영어는 여전히 중요하지만, 이제 시스템 그 자체가 아니라 **시스템의 한 부품**이다.
