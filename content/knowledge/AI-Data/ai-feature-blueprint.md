## AI 시스템 블루프린트란

**AI 시스템 블루프린트(AI system blueprint)**는 새 AI 기능을 만들기 전에 "왜·어떻게·얼마나 책임 있게"를 한 장에 그리는 틀이다. 모델 선택이나 인프라부터 고르면 큰 그림을 놓치기 쉽다. 블루프린트는 세 관점으로 나뉜다.

```text
기회 (Opportunity)    왜 만드나
  ├─ 유스케이스: AI로 풀 가치가 있는 사용자 과제
  └─ 가치: 사용자 이득 + 제품·비즈니스 이득
솔루션 (Solution)     어떻게 작동하나
  ├─ 데이터: 모델이 배우고 참고하는 재료
  ├─ 지능: 모델과 주변 구성 요소
  └─ UX: 가치를 사용자에게 전달하는 화면
거버넌스 (Governance)  책임 있게 만드나
  └─ 프라이버시 · 공정성 · 신뢰와 투명성 · 안전 · 이의 제기 경로
```

AI는 불확실성과 위험을 들여온다. 그래서 **결정적(deterministic) 방식으로 풀 수 없는 문제에만 AI를 쓴다.** 회사 지시나 유행 때문에 붙인 "AI를 위한 AI"는 쓸모가 없다. 좋은 기능은 사용자 필요에서 나오고, 전달한 가치로 평가된다.

## 기회: 유스케이스와 가치

### 가치의 다섯 범주

아이디어는 AI가 주는 가치의 범주(AI 기회 트리)로 낸다. 아래로 갈수록 복잡도·위험·영향이 커진다.

| 범주 | 하는 일 | 예 |
| --- | --- | --- |
| 인사이트(Insights) | 의사 결정을 돕는다 | 검색 트렌드 분석, 내부 제품 데이터 분석 |
| 편의(Convenience) | 마찰을 없앤다 | 스마트 필터, 자동 완성 |
| 자동화(Automation) | 반복 작업을 대신한다 | 폼 자동 채우기, 사기 탐지 |
| 증강(Augmentation) | 복잡하거나 창의적인 일을 돕는다 | 시각 요약, 대체 일정 제안 |
| 개인화(Personalization) | 개인의 필요에 맞춘다 | 맞춤 추천, 맞춤 업셀 |

처음에는 **영향이 작은 것부터** 한다. 내부용 인사이트로 제품을 안에서 개선하고, 기존 UX 부채를 AI로 줄이고, 경험이 쌓이면 노출을 늘린다. 다만 가벼운 개인화처럼 위험은 낮고 효과가 큰 기회도 있다.

### 사용자 여정에 배치하기

페르소나를 정하고 사용자 여정의 단계마다 범주별 아이디어를 채우면 기회가 표로 보인다. 항공권 예약 서비스라면 이렇다.

| 여정 | 인사이트 | 편의 | 자동화 | 증강 | 개인화 |
| --- | --- | --- | --- | --- | --- |
| 발견 | 트렌드 | 스마트 필터 | | | 맞춤 영감 |
| 탐색 | | | | 시각 요약 | 적응형 제안 |
| 결정 | 가격 예측 | | | 신뢰도 점수 | |
| 예약 | | 폼 자동 완성 | 사기 탐지 | | |
| 예약 후 | | 스마트 알림 | 자동 재예약 | | 맞춤 업셀 |

아이디어의 출처는 세 가지다. 사용자의 명시적 불편, 팀 내부 제안(사용자 검증이 꼭 필요하다), 경쟁사(대상과 맥락이 다르니 일찍 검증한다).

### 가치는 숫자로

가치는 사용자 이득과 비즈니스 이득 양쪽이다. 건강한 제품에서는 둘이 같이 움직인다. 만족·신뢰처럼 무형의 가치라도 **처음에는 대략이라도 수치로 추정**해야 우선순위를 정하고 이해관계자를 설득할 수 있다. 엉뚱한 기회를 고르는 것이 AI 프로젝트가 실패하는 대표 원인이다.

## 솔루션: 데이터 · 지능 · UX

### 데이터

데이터는 AI의 연료이고, 시스템 성능의 상한이다. 쇼핑몰 자연어 검색이라면 이런 데이터가 쓰인다.

| 종류 | 예 |
| --- | --- |
| 정형 | 상품명, 색상, 사이즈, 카테고리, 재고 |
| 비정형 | 상품 설명, 리뷰, FAQ |
| 동의어 목록 | "스니커즈" = "러닝화" |
| 사용자 신호 | 클릭, 체류 시간, 장바구니 담기, 구매 |
| 시각 | 상품 이미지 → 유사 이미지 검색 인덱스 |

- **신호 대 잡음비가 높은 소수의 소스부터** 시작하고 점점 넓힌다.
- 원시 데이터는 바로 넣지 못한다. 정제·전처리를 거쳐 행동 시퀀스나 임베딩처럼 AI가 다루기 좋은 모양으로 바꾼다.
- 사전 학습 모델이 기본이 된 지금은 **양보다 질**이 중요하다.
- 데이터는 학습·파인튜닝, 평가, 운영(드리프트 감시·피드백 수집) 모든 단계에 쓰이는 살아 있는 자산이다. 사용할수록 데이터가 쌓이고 제품이 좋아지는 **데이터 플라이휠**은 차별화 요소가 된다.

### 지능

지능 층은 모델 하나가 아니라 여러 부품의 조합이다. 자연어 상품 검색이라면 개체명 인식으로 `color=red`, `season=winter` 같은 속성을 뽑고, 문장 임베딩과 시맨틱 검색으로 후보를 찾고, 작은 재순위(re-ranking) 모델로 정렬한다.

- **AI는 생성형·LLM만이 아니다.** 많은 과제는 더 작고 특화된 모델이 빠르고 싸다.
- 실제 시스템은 **복합 AI 아키텍처(compound AI architecture)**다. 모델 + 데이터베이스 + API + 가드레일이 함께 동작한다.
- 리더보드 1위를 쫓지 말고 문제에 맞는 지능을 고른다. 예측형과 생성형의 차이는 [[predictive-vs-generative-ai|예측형 AI와 생성형 AI]]에 정리했다.

### UX

결정적 소프트웨어는 같은 입력에 같은 출력을 낸다. AI는 거의 같은 질문에도 다른 답을 내고, 환각도 한다. 기존 제품에 AI를 넣을 때는 **처음엔 사용자에게 드러나는 불확실성을 최소화**한다. 자연어 검색을 기존 검색창에 조용히 통합하고, "AI 검색 켜짐"과 감지한 속성(트레일·겨울·빨강)을 짧게 보여 주는 식이다. 노출 정도별 패턴은 [[ai-ux-patterns|AI 기능의 UX 패턴]]에서 다룬다.

## 거버넌스

거버넌스는 컴플라이언스가 아니라 신뢰와 채택을 얻는 설계 원칙이다. 자연어 검색에 적용하면 이렇다.

| 항목 | 장치 |
| --- | --- |
| 프라이버시 | 개인화 데이터는 옵트인 전까지 기기에만, 언제든 끌 수 있게 |
| 공정성 | 판매자별 노출이 균형 잡혔는지 감사 |
| 신뢰·투명성 | 결과가 왜 위에 왔는지 설명 |
| 안전 | 금지 품목 같은 위험 질의는 가드레일로 차단 |
| 이의 제기(Recourse) | AI 제안 닫기, 나쁜 결과 신고, 키워드 검색으로 되돌리기 |

출력을 완전히 통제할 수는 없지만, 가드레일과 피드백 루프를 설계하고 문제가 생기면 대응할 책임은 만드는 쪽에 있다. 자세한 내용은 [[responsible-ai-governance|책임 있는 AI]]에 있다.

## 아이디어를 구체화하고 우선순위 정하기

### 1. 블루프린트로 스펙 쓰기

아이디어마다 블루프린트를 한 장씩 채운다. 보통 기회는 PM이, 솔루션은 개발자가 채운다. 개발자의 주된 책임은 **비용·노력·위험 추정**이다.

### 2. 노력과 비용 평가

| 축 | 질문 |
| --- | --- |
| 데이터 준비도 | 필요한 데이터가 있나? 정제·라벨링이 얼마나 필요한가? |
| 모델 성숙도 | 맞는 사전 학습 모델이 있나, 직접 학습해야 하나? |
| 지연 시간 | 기능이 매끄럽게 느껴지려면 얼마나 빨라야 하나? |
| 통합 복잡도 | 백엔드·API·UI·외부 도구 등 연결할 시스템이 몇 개인가? 접점이 많을수록 비용과 위험이 커진다 |
| 운영 비용 | 호출당 비용 × 월 사용량. 프로토타입에서 싸던 기능이 사용자 수천 명에서 비싸진다 |

사용자가 치르는 숨은 비용도 센다. AI는 불확실성과 실수를 들여오고, 클라이언트 AI는 사용자의 대역폭·저장 공간·배터리를 쓴다. 스마트 필터처럼 LLM API 프롬프트 파싱으로 끝나는 기능은 가볍고, 개인화 예약 비서처럼 전용 데이터 파이프라인·예약 API·사람 검토가 필요한 기능은 무겁다. **가치는 높고 마찰은 낮은 것부터** 한다.

### 3. 실패 모드 추정

| 실패 모드 | 증상 |
| --- | --- |
| 환각(Hallucination) | 그럴듯하지만 없는 것을 만든다 (존재하지 않는 항공편) |
| 편향(Bias) | 학습 데이터의 부당한 일반화를 재현·증폭한다 |
| 콜드 스타트(Cold start) | 신규 사용자·신규 항목은 데이터가 없어 가치를 못 준다 |
| 성능 저하(Drift) | 현실 데이터가 학습 분포에서 멀어져 정확도가 떨어진다 |

개인화 기능을 만들자는 요구가 있어도 관심사 신호를 모으는 데이터베이스가 없다면 엉뚱한 추천만 나오고 사용자는 떠난다. 데이터 가용성은 가치 추정 단계에서 이미 반영해야 한다. 실패했을 때는 어디서 왜 실패했는지 사용자에게 알려, 입력을 바꾸면 되는지 판단할 수 있게 한다.

### 4. 프로토타입

추정은 처음엔 정밀도가 낮다. 새 기술일수록 **조사보다 만들어 보는 쪽이 빨리 배운다.** 작게 내놓고, 관찰하고, 계속 다듬는다.

- **끝에서 끝까지 일찍 만든다.** 모델 정확도만이 아니라 데이터 → 지능 → UX 전체 흐름을 시험한다. 앱의 모든 기능일 필요는 없다.
- **지름길부터.** API와 사전 학습 모델로 가치를 먼저 확인한다.
- **전부 기록한다.** 입력·출력·사용자 수정을 남겨 흔한 실패와 치명적 문제를 찾는다.
- **실제 데이터로 시험한다.** 지저분한 진짜 사용자 행동을 담는다.
- **피드백과 제어 장치를 넣는다.** 오류 신고, 결과 확인·수정.

바이브 코딩한 검증 안 된 프로토타입을 그대로 프로덕션에 붙여 넣지 않는다. 프로토타입은 가치를 검증하는 도구이고, 코드베이스 통합과 사용자 안전 테스트는 따로 한다.

## 정리

- AI 기능은 **기회 → 솔루션(데이터·지능·UX) → 거버넌스** 순서로 그린다.
- 결정적 방식으로 풀 수 없는 사용자 문제에만 AI를 쓰고, 가치는 대략이라도 숫자로 잡는다.
- 아이디어는 가치 범주 × 사용자 여정 표로 내고, 영향이 작고 마찰이 낮은 것부터 한다.
- 개발자는 데이터 준비도·모델·지연·통합·운영비와 실패 모드를 추정하는 사람이다.
- 추정은 끝에서 끝까지 이어진 프로토타입과 로그로 검증한다.

AI 기능의 성패는 모델보다 **어떤 문제를 골랐나**에서 먼저 갈린다.
