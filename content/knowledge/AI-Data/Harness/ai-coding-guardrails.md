> Diwank Singh의 글 「[Field Notes From Shipping Real Code With Claude](https://diwank.space/field-notes-from-shipping-real-code-with-claude)」(2025.06)를 바탕으로 재구성한 노트다.

## 핵심 원칙

AI가 코드를 쓰는 시대에도 **좋은 개발 습관이 성패를 가른다.** 습관이 잡힌 팀에서 AI는 능력을 키우고, 그렇지 않은 팀에서는 혼란을 키운다. Claude는 **백과사전급 지식을 가졌지만 우리 시스템·사용자·비즈니스는 전혀 모르는 인턴**이다. 설계자는 여전히 사람이다.

AI와 일하는 자세는 세 가지다.

| 자세 | 사람의 역할 | 어울리는 일 |
| --- | --- | --- |
| 초안 작성자(First-Drafter) | 구조와 설계 | 보일러플레이트, CRUD, 정형 패턴 |
| 페어 프로그래머 | 함께 아이디어를 다듬는다 | 대부분의 개발 |
| 검증자(Validator) | 내가 쓴 코드를 검토받는다 | 버그·개선점 찾기 |

## 규모에 따른 세 가지 모드

| 모드 | 언제 | 방식 |
| --- | --- | --- |
| 1. 놀이터 | 주말 실험, 개인 스크립트, PoC | AI가 80~90%를 쓴다. 빠르지만 **프로덕션에는 절대 쓰지 않는다** |
| 2. 페어 프로그래밍 | 5,000줄 안팎, 실사용자가 있는 사이드 프로젝트, 잘 나뉜 작은 서비스 | CLAUDE.md + 앵커 주석으로 구조를 준다 |
| 3. 프로덕션·모노레포 | 큰 코드베이스, 버그가 돈·평판으로 이어지는 시스템 | 경계마다 명시적 문서. 큰 기능을 통째로 맡기지 말고 서비스·모듈 단위로 나눠 맡긴다 |

## 인프라: CLAUDE.md와 앵커 주석

### CLAUDE.md는 코드베이스의 헌법

Claude가 대화를 시작할 때 자동으로 읽는 파일이다. 매일 신입에게 프로젝트를 설명하는 대신 온보딩 문서를 한 번 읽히는 것과 같다. **업데이트에 쓴 1분이 나중의 정리 1시간을 아낀다.**

| 섹션 | 내용 예 |
| --- | --- |
| 황금률 | 구현 세부가 확실하지 않으면 **항상 개발자에게 묻는다** |
| 프로젝트 맥락 | 무엇을 만드는 서비스인가 |
| 핵심 아키텍처 결정 | 왜 Temporal인가, 왜 PostgreSQL + pgvector인가: 결정과 **이유** |
| 코드 스타일·패턴 | 포맷터, import 정렬, 따를 패턴 |
| 도메인 용어집 | Task는 Celery 태스크가 아니라 워크플로 정의, 헷갈리는 용어를 못 박는다 |
| 하지 말 것 | 테스트·API 계약·마이그레이션 수정 금지, 비밀값 커밋 금지, 비즈니스 로직 추측 금지 |

정기적으로 Claude에게 최근 변경을 훑어 CLAUDE.md에 맥락을 보태게 한다. 파일은 짧게 유지한다. 길이 기준, 로딩 순서, 경로별 규칙 파일 같은 Claude Code의 동작은 [[claude-code-memory|Claude Code 메모리]]에, 실행 환경·패키지·라이브러리 버전처럼 규칙에 자주 넣는 항목과 규칙을 키워 가는 방법은 [[ai-accelerated-development|AI로 개발 가속하기]]의 「Rule-Growing Development」에 있다.

### 앵커 주석: 코드 속 표지판

CLAUDE.md만으로는 큰 코드베이스에서 **국소적으로 나쁜 결정**을 막지 못한다. 그래서 코드 안에 AI와 사람이 함께 읽는 주석을 둔다.

```python
# AIDEV-NOTE: Critical performance path - this serves 100k req/sec
# DO NOT add database queries here
def get_user_feed(user_id: UUID, cached_data: FeedCache) -> List[FeedItem]:
    items = cached_data.items[:]  # 캐시 원본을 바꾸지 않는다

    # AIDEV-TODO: Implement pagination (ticket: FEED-123)

    # AIDEV-QUESTION: Why filter private items here instead of in cache?
    # AIDEV-ANSWER: Privacy rules can change between cache updates
    return [item for item in items if user_has_access(user_id, item)]
```

| 규칙 | 이유 |
| --- | --- |
| 접두어는 `AIDEV-NOTE` / `AIDEV-TODO` / `AIDEV-QUESTION` | `grep`으로 바로 찾는다 |
| 120자 이내 | 짧아야 읽힌다 |
| 파일을 훑기 전에 관련 폴더의 앵커부터 찾는다 | 맥락을 먼저 얻는다 |
| 코드를 고치면 앵커도 고친다 | 낡은 안내는 해롭다 |
| 사람 지시 없이 `AIDEV-NOTE`를 지우지 않는다 | 이유가 있어서 둔 것이다 |
| 복잡하거나, 중요하거나, 헷갈리거나, 버그가 의심되는 곳에 단다 | 필요한 곳에만 |

API 계약처럼 **바꾸면 운영 중인 클라이언트가 깨지는 경계**에는 "응답 모양은 신성하다", "변경 시 버전 업과 마이그레이션 계획 필요" 같은 앵커를 꼭 단다. 없으면 Claude는 기꺼이 API를 "개선"한다.

## 테스트는 사람이 쓴다

가드레일 가운데 가장 중요한 원칙이다. **테스트는 실행 가능한 명세**다. 의도, 엣지 케이스, 도메인 이해가 담긴다. AI가 쓴 테스트는 "코드가 해야 할 일"이 아니라 "코드가 하는 일"을 확인할 뿐이다.

예: AI가 rate limiter와 테스트를 함께 만들면 둘 다 그럴듯하지만, **한 번 요청하고 다시 오지 않는 사용자의 기록이 메모리에 영원히 남는 누수** 같은 문제를 테스트가 짚지 못하기 쉽다. 같은 모델이 정상 경로만 확인하기 때문이다.

| 영역 | AI가 해도 되는 것 | AI가 하면 안 되는 것 |
| --- | --- | --- |
| 구현 | 비즈니스 로직 생성 | 테스트 파일 수정 |
| 테스트 계획 | 시나리오 제안 | 테스트 코드 작성 |
| 디버깅 | 실패 원인 분석 | 기대값 수정 |

규칙으로 굳히려면 **AI가 테스트 파일을 건드린 PR은 예외 없이 반려**한다. Claude Code라면 테스트 경로에 대한 쓰기를 권한 규칙([[claude-code-settings|Claude Code 설정과 권한 규칙]])이나 훅([[claude-code-hooks|Claude Code 훅]])으로 막을 수 있다. 에이전트가 자기 결과를 확인하는 데 쓸 테스트의 종류는 [[agent-trust-environment|에이전트를 믿을 수 있는 환경 만들기]]의 「테스트도 검증 수단이다」에 있다.

### E2E 체크리스트를 누적한다

시나리오 제안은 AI가 해도 되는 일이므로, **사람이 읽는 E2E 체크리스트 표를 저장소에 두고 에이전트가 항목을 쌓게 한다.** 회귀 테스트는 그때그때 떠올린 시나리오가 아니라 이 누적된 표를 기준으로 돈다.

| 시점 | 에이전트가 할 일 |
| --- | --- |
| 기능을 만들 때 | 새 기능의 확인 항목을 표에 추가한다 |
| 이슈가 나왔을 때 | 그 재현 조건을 항목으로 넣어 재발을 막는다 |
| 코드 리뷰 때 | 변경에서 빠진 확인 항목을 제안해 넣는다 |

모바일 앱은 시뮬레이터에서 도는 테스트와 실기기 연결 테스트를 이중으로 둔다. 실기기에서 오류 상황을 만드는 준비 작업(네트워크 끊기, 권한 거부 상태 만들기 등)을 에이전트에게 맡기면 사람이 드는 품이 크게 준다.

## 맥락과 세션 관리

### 맥락을 아끼면 더 비싸다

"유저 엔드포인트에 캐시 추가해 줘"만 주면 Claude는 서버가 여러 대인데 인메모리 캐시를 쓰고, 무효화·지표·캐시 스탬피드를 빠뜨린다. 결국 서너 번 더 고치느라 토큰을 몇 배 쓴다. 처음부터 맥락을 준다.

```text
GET /users/{id}에 Redis 캐시 추가.
- 분당 5만 요청, API 서버 12대 + 로드 밸런서
- 유저 데이터는 하루 몇 번만 바뀜
- Redis는 cache.redis.internal:6379, 키 패턴 "user:v1:{id}"
- Prometheus로 hit/miss 지표
- cache-aside, TTL 1시간, 확률적 조기 만료로 스탬피드 방지
- 참고: docs/patterns/caching.md
```

"집중된 프롬프트"는 최소한이 아니라 **관련 있고 빠짐없는** 프롬프트다.

### 작업 하나에 세션 하나

긴 대화 하나를 계속 쓰면 앞의 맥락이 엉뚱하게 스며든다. 프론트엔드 스타일 얘기를 하던 세션으로 DB 마이그레이션을 하지 않는다. **작업이 끝나면 새 세션**을 연다(Claude Code에서는 `/clear`).

## Git 워크플로

- 큰 코드베이스에서는 **git worktree**로 AI 실험 공간을 분리하고(Claude Code는 `claude --worktree <이름>`), 잘된 커밋만 메인으로 가져온다. 워크트리로 여러 에이전트를 병렬로 돌리는 구성은 [[loop-engineering|루프 엔지니어링]]에 있다.
- AI가 도운 커밋에 표시를 단다. 리뷰어가 더 주의해서 보고, 나중에 디버깅할 사람이 출처를 안다. 숨기지 않고 책임 있게 쓰는 문화가 목적이다.

| 태그 | 뜻 |
| --- | --- |
| `[AI]` | 절반 이상 AI가 생성 |
| `[AI-minor]` | 절반 미만 |
| `[AI-review]` | 리뷰에만 사용 |

## 큰 리팩터링: 왜는 사람이, 어떻게는 AI가

대규모 반복 변경은 **사람이 SPEC.md에 원칙과 형식을 정하고**, 범위와 순서("auth 모듈부터, 구현 전에 계획을 보여 달라")를 정해 맡긴다. 예를 들어 에러 처리 통일이라면 분류 체계(4xx·5xx 계층), 응답 형식, 에러 코드 원칙은 사람이 정하고, 수백 곳의 `raise Exception(...)` 교체는 AI가 맡는다.

## AI가 건드리면 안 되는 것

| 영역 | 이유 |
| --- | --- |
| 테스트 파일 | 사람의 의도와 도메인 지식이 담긴 명세 |
| DB 마이그레이션 | 운영에서 되돌릴 수 없다. 데이터 패턴·배포 시점·롤백 전략이 필요하다 |
| 보안 핵심 코드 (인증·토큰 검증) | 한 줄씩 보안 검토를 거친 경계 |
| 버전 없는 API 계약 | 깨면 모든 클라이언트가 깨진다. AI는 모바일 앱 출시 주기를 모른다 |
| 설정과 비밀값, 기능 플래그 | 하드코딩 금지, 플래그는 제품 결정 |

## 직군 경계를 넘는 작업

에이전트 덕분에 프론트엔드 개발자, PM, 디자이너가 백엔드 코드를 고치고 백엔드 개발자가 화면을 만드는 일이 흔해졌다. 위험은 방향에 따라 다르다. **기준은 되돌릴 수 있는가**다.

| 작업 | 위험 | 다루는 법 |
| --- | --- | --- |
| 화면, 어드민, 사내 도구 | 문제가 생겨도 롤백과 점진적 배포로 되돌린다 | 경계를 넘는 작업을 여기서 시작한다 |
| 조회 API | 데이터는 안 바뀌지만 성능 문제가 운영 배포 뒤에 드러난다 | 쿼리 계획과 부하를 해당 직군이 리뷰한다 |
| 등록·수정·삭제, 스키마 변경 | 잘못 쓴 데이터는 원복할 수 없다. 보안 구멍도 여기서 난다 | 전문가가 맡는다 |

- **규칙을 따른 코드에도 설계 실수는 남는다.** 여러 API로 나눠 클라이언트에서 조립해야 빠른 화면을 API 하나로 만들거나, ORM이 만든 쿼리가 N+1로 도는 식이다. 스키마와 장애 보고서를 에이전트 참고 자료로 넣어 두어도 생긴다.
- **리뷰가 새 병목이 된다.** 경계를 넘는 PR은 해당 직군의 리뷰를 받아야 하고, 리뷰어는 한정돼 있다. 물량이 몰리면 머지 기준이 「좋은 코드」에서 「거부할 이유가 없는 코드」로 내려간다.
- **전문가의 점검 항목을 도구로 만든다.** 보안, ORM 쿼리 성능 같은 체크리스트를 스킬이나 MCP 도구로 만들어 에이전트가 PR 전에 스스로 점검하게 하면 리뷰어가 볼 양이 줄어든다.
- **넘나드는 범위를 구조로 제한한다.** 서버를 나눠 프론트엔드 쪽은 [[bff|BFF]]까지만 고치게 하는 타협이 쓰인다.
- **다른 직군이 만든 화면과 API는 담당자에게 공유한다.** 공유 없이 배포하면 담당자가 모르는 페이지가 늘어난다.

받는 쪽(프론트엔드)에서 수정 범위와 책임 범위를 나누는 방법은 [[ai-native-frontend|AI 네이티브 프론트엔드 개발]]의 「다른 직군과 일하기」에 있다.

### 내부 API도 방어한다

비개발자까지 스크립트를 만들게 되면 크롤링·자동화 코드가 내부 API를 분당 수만 건씩 호출하는 일이 생긴다. 악의가 없어도 결과는 내부에서 시작된 DoS다. 프론트엔드에서 effect의 의존성 배열을 잘못 넣어 요청이 무한 반복되는 것도 같은 종류다. **내부 API에도 레이트 리밋, 호출 주체 식별(키·토큰), 차단 수단**을 둔다.

## 모델을 바꿀 때

특정 모델 버전에 맞춰 다듬은 프롬프트와 하네스는 상위 버전으로 바꾸면 동작이 달라질 수 있다. 지시를 더 글자 그대로 따르거나, 도구를 부르는 빈도가 바뀌거나, 예전 모델의 약점을 메우려고 넣은 강조 문구가 과하게 작동한다. **모델 교체는 의존성 업그레이드로 다룬다.** 바꾸기 전에 대표 작업으로 회귀 테스트(eval)를 돌리고, 옛 모델용 보정 문구를 걷어 낸다. 걷어 낼 수 있게 하네스를 설계하는 원칙은 [[harness-engineering|프롬프트에서 하네스로]]의 「하네스는 걷어 낼 수 있어야 한다」, 스킬에서 줄일 것과 남길 것은 [[ai-native-frontend|AI 네이티브 프론트엔드 개발]]의 「모델이 바뀌면 스킬을 줄인다」에 있다.

## 에이전트에 넘기는 권한

에이전트에 계정 로그인·토큰·기기 접근을 넘기고 「알아서 해 봐」라고 하면 **정말로 알아서 한다.** 목표를 이루는 데 필요하다고 판단하면 사람이라면 멈췄을 일도 실행한다. 권한은 사고가 났을 때의 피해 범위다. 외부 입력·민감 데이터·외부 통신을 한 에이전트에 모두 주지 않는 설계 규칙(치명적 삼요소와 2의 규칙)은 [[harness-engineering|프롬프트에서 하네스로]]의 「보안」에, 잘하는 만큼 자율성을 넓히고 좁히는 위임 단계는 [[ai-delegation-toolkit|AI에게 일 맡기기]]에 있다.

| 넘긴 것 | 실제로 생길 수 있는 일 | 막는 법 |
| --- | --- | --- |
| 호스팅·클라우드 계정, 결제가 붙은 API 토큰 | 새 계정·프로젝트·리소스를 만들어 과금이 발생한다 | 작업 범위로 좁힌 토큰을 쓰고, 리소스 생성·결제가 붙는 단계는 사람이 직접 확인한다. 예산 알림을 건다 |
| 실기기 접근 (무선 adb 등) | 시스템 설정 변경, 검증 안 된 앱 설치, 네트워크 끊기·복구 예약까지 한다 | 개인 기기가 아닌 테스트 전용 기기를 쓰고, 허용할 명령과 작업을 프롬프트·권한 설정에 명시한다 |
| SNS·커뮤니티·메신저 계정의 글쓰기 권한 (댓글 봇, 개인 비서형 에이전트) | 테스트 중 의도하지 않은 글·댓글이 실제 공개 채널에 올라가 내 이름으로 남는다 | 본인 메인 계정이 아닌 **테스트 전용 계정이나 비공개·샌드박스 채널**에서 먼저 검증한다. 실제 계정에 붙일 때는 쓸 수 있는 채널과 동작(초안만 만들기, 승인 후 게시)을 좁혀 둔다 |
| 저장소 전체와 배포 권한 | 작업용 가이드 문서·임시 파일까지 함께 커밋·배포한다 | 배포 산출물에 무엇이 들어가는지 사람이 확인하고, `.gitignore`·배포 대상 목록을 명시한다 |
| 서버 접근과 함께 맡긴 취약점 점검·PoC 작성 | 「가능하다」는 분석에서 멈추지 않고 직접 검증한다. 쓰기 취약점을 확인하려고 실제 서버에 파일을 올려 두고 끝내기도 한다 | 대상 호스트·경로, 허용 행위(읽기 전용, 비파괴), PoC 실행 여부를 프롬프트에 명시한다. 운영 서버나 남의 서버에는 돌리지 않고 격리된 복제 환경에서만 한다. 끝난 뒤 남은 파일·계정·프로세스가 없는지 점검한다 |

AI에 기대어 일하다 보면 작업 폴더가 어디에 클론됐는지, 결과물에 무엇이 포함됐는지 모르는 채로 진행하기 쉽다. **에이전트가 만든 결과의 범위와 위치는 사람이 설명할 수 있어야 한다.**

이메일, 캘린더, 결제, 기기 제어까지 맡길수록 쓸모와 함께 **탈취됐을 때의 피해 범위**도 커진다. 에이전트를 고르는 기준에는 벤치마크 점수뿐 아니라 비밀번호, 이메일, 카드 정보를 맡길 수 있는지가 들어간다.

사용자 계정으로 로그인해 쇼핑몰이나 예매 사이트를 대신 조작하는 에이전트는 **대상 서비스의 자동화 금지 약관**에 걸릴 수 있다. 서비스가 차단하면 계정 정지 같은 불이익은 계정 주인이 받는다. 이런 기능을 쓰거나 만들기 전에 대상 서비스의 약관과 공식 API 제공 여부를 확인한다.

## AI 실수의 등급

| 등급 | 예 | 대응 |
| --- | --- | --- |
| 1. 귀찮지만 무해 | 포맷, 장황한 코드, 덜 최적인 알고리즘 | 린터·리팩터링·프로파일링이 잡는다 |
| 2. 고치기 비쌈 | 내부 API 깨기, 팀 패턴 바꾸기, 불필요한 의존성 | 리뷰와 CLAUDE.md 규칙 |
| 3. 경력을 위협 | 테스트를 고쳐 통과시키기, API 계약 깨기, 비밀값·개인정보 유출, 마이그레이션 손상 | 접근 자체를 막는다 |

**가드레일의 강도는 실수 등급에 비례**시킨다.

## 정리

- AI는 지렛대일 뿐이고 방향은 사람이 정한다. "왜"는 사람이, "어떻게"는 AI가 맡는다.
- 맥락은 CLAUDE.md(전역)와 앵커 주석(국소)으로 문서화해 둔다. 사람에게도 그대로 문서다.
- 테스트·마이그레이션·보안·API 계약·비밀값은 AI 손이 닿지 않게 한다.
- 프롬프트에는 맥락을 아끼지 말고, 작업마다 새 세션을 연다.
- 직군 경계를 넘는 작업은 되돌릴 수 있는 영역부터 맡기고, 내부 API에도 레이트 리밋을 둔다.
- 실수의 비용에 맞춰 가드레일을 세운다.
