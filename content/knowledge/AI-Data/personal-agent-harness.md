> AI Frontier Korea EP 86 「[진짜 내 일을 해결하는 Agentic Workflow](https://www.youtube.com/watch?v=EQ-Rnx-k-Ec)」(2026.02)에서 Lablup 신정규 대표가 노정석·최승준과 나눈 대담을 바탕으로 재구성한 노트다. Claude Code 기능 설명은 공식 문서로 확인했다.

## 핵심: 결과물이 아니라 생성 장치를 만든다

에이전트에게 일을 시킬 때 대화로 결과물을 바로 받아 내면, 다음에 같은 일을 할 때 처음부터 다시 해야 한다. 대신 **그 일을 해 주는 장치(하네스)** 를 만든다. 말로 코딩하되, 코딩하는 대상이 최종 결과물이 아니라 **코딩하는 에이전트**다.

- 결과물에 직접 손대지 않는다. 고치고 싶은 곳이 보이면 결과물이 아니라 장치를 고친다.
- 고치는 일(iteration)도 직접 하지 않고 「여러 각도에서 스스로 비판하고 장치를 고쳐라」라고 시킨다.
- 남이 만든 스킬·플러그인을 잔뜩 받는 것으로는 내 일이 줄지 않는다. 그것은 그 사람의 일에 맞춘 가속 장치다. **지금 내가 하는 일을 하나씩 위탁하는 장치를 직접 만들 때** 가속이 시작된다.
- 협업에 필요한 공용 하네스(팀 작업 흐름 통일 등)는 따로 두되, 출발점은 언제나 내 일을 덜어 주는 것이다.

일반론으로서의 하네스 엔지니어링은 [[harness-engineering|프롬프트에서 하네스로]], 장치가 스스로 도는 구조는 [[loop-engineering|루프 엔지니어링]]에 정리했다. 이 노트는 한 사람이 자기 일을 위한 장치를 쌓아 가는 실전 절차를 다룬다.

## 장치를 만드는 순서

예: 유튜브 채널의 설 인사 뉴스레터와 이후 이벤트 안내 메일을 쓰는 장치.

```text
1. 탐색 질문으로 맥락 쌓기   "이 채널은 무엇을 다루나", "안내 메일에 고려할 것은?"
2. 목적 선언                 "이걸 지금 쓰려는 게 아니라, 이런 일을 자동화할 프로젝트를 셋업하려 한다"
3. CLAUDE.md 작성            대화 내용을 바탕으로 프로젝트의 기본 문서(soul document)를 만든다
4. 진행 기록 규칙            PLAN.md·PROGRESS.md에 할 일과 진행 상황을 남기고, 새로 시작하면 둘을 먼저 읽게 한다
5. 구성 요소 제안받기         필요한 에이전트·명령·스킬 아이디어만 먼저 받는다
6. 형식대로 만들기            Claude Code의 구조와 형식을 조사한 뒤 .claude/ 아래에 정확한 형식으로 만든다
7. 참고 자료 캐시             조사한 내용을 reference/ 폴더에 저장하고 에이전트·스킬이 읽어 쓰게 한다
8. 다듬기                    초안을 보고 비판·수정을 시킨다. 예전에 직접 보낸 메일을 주고 말투·구성·방향을 뽑아 장치에 반영한다
```

| 단계 | 요령 | 이유 |
| --- | --- | --- |
| 맥락 쌓기 | 원하는 것을 한 번에 시키지 않고 질문부터 몇 턴 깐다 | 모델이 탐색할 공간은 맥락으로 정해진다. 처음 몇 턴의 정렬(alignment)이 세션이 옆길로 새지 않게 한다 |
| 구성 요소 | 「만들어라」 전에 「무엇이 필요할지 제안해라」 | 바로 만들게 하면 Claude Code 형식을 모른 채 프로젝트 루트에 아무 폴더나 만든다. 하네스와 통합하려면 `.claude/` 아래 정해진 형식(YAML frontmatter + 마크다운)을 지켜야 한다 |
| 진행 기록 | 「다른 에이전트에게 넘길 자료」라고 표현한다 | 「네가 잊어버릴 테니」 같은 표현은 모델을 방어적으로 만든다. 모델이 시험받는 상황을 알아채면 행동이 달라진다는 연구도 있다. 의인화가 아니라 토큰 생성 방식에 맞춘 표현이다 |
| 참고 자료 | 조사 결과를 파일로 저장 | 매번 웹을 다시 조사하는 시간을 줄인다. 새 내용을 찾아 갱신하는 명령을 따로 둘 수 있다 |
| 새로 만든 구성 요소 | 세션을 나갔다 다시 들어온다 | 새로 만든 명령·스킬은 실행 중인 세션에 바로 잡히지 않을 수 있다 |

시간은 30분 정도 든다. 앞의 10분이 장치를 세우는 시간이고, 뒤의 20분은 사람으로 치면 「갈구는」 데, 즉 비판과 수정을 시키는 데 쓴다. 이전에는 스펙을 먼저 길게 쓰는 방식이었다면, 지금은 **문답으로 맥락을 함께 쌓으면서** 스펙을 만든다.

### 입력 습관

- **한국어로, 말로 입력한다.** 품질 차이는 크지 않고, 영어로 타이핑하는 사람이 오히려 병목이다. 다만 스킬·명령 같은 장치 파일은 영어로 만들게 하면 토큰이 절약된다.
- **존댓말을 쓴다.** 하루의 절반 이상을 AI와 말하면 말투가 사람에게도 옮는다. 사람에게 반말하는 버릇을 막기 위해서다.
- 권한 확인을 모두 끄고 돌릴 때는 **VM 안에서만** 돌린다.

## 서브에이전트와 병렬 작업

같은 작업을 잘게 나눌 수 있으면 서브에이전트로 병렬 처리한다. 많을 때는 50개까지 동시에 돈다.

- **한 에이전트가 맡을 양을 정해 준다.** 「문서 100개를 번역해라」라고만 하면 맥락이 넘쳐 터진다. 「한 에이전트당 4개씩」이라고 하면 25개가 동시에 뜬다.
- 코딩은 파일 단위로 나누는 식으로 분할 규칙을 정해 둔다.
- 명령(command)은 여러 서브에이전트를 병렬로 띄우거나 이어 붙일 수 있고, 에이전트가 명령을 부를 수도 있어 조합의 바깥 틀로 쓴다. 한동안 서브에이전트가 다시 서브에이전트를 부를 수 없어서 명령이 그 역할을 맡았고, 지금은 서브에이전트의 중첩 실행도 지원된다([공식 문서](https://code.claude.com/docs/en/sub-agents)).
- 사람이 병렬 세션을 욕심내서 여러 창을 동시에 보면 인지 부하가 급격히 커진다. 토큰 생성이 빨라지면 창을 여러 개 띄울 이유도 줄어든다.

## 사례: 사람이 코드를 쓰지 않는 개발 파이프라인

Lablup의 Backend.AI:GO는 로컬·클라우드 모델을 한 화면에서 받아 돌리고 라우팅하는 데스크톱 도구다. 장애 대응(circuit breaking), 벤치마크, 통계, 문서 번역, 이미지 생성, 여러 PC의 모델을 묶어 나눠 쓰는 기능이 「필요해서 붙이다 보니」 커졌다.

| 항목 | 내용 |
| --- | --- |
| 기간 | 2025.12.24 시작 → 2026.01.06 CES에서 첫 데모(열흘 만의 MVP) → 이후 4배 더 개발, 40일 |
| 규모 | 남은 코드 약 70만 줄, 작성한 코드 총 120만 줄, 처리한 PR 764개 |
| 토큰 | 약 130억 토큰. Claude Code Max 구독 2개를 기본으로, 모자라면 추가 결제하며 PC·VM 8대에서 돌렸다 |
| 사람의 일 | 이슈 등록, UX 수정 피드백, 보고서 읽기 |

파이프라인은 복잡한 도구가 아니라 **cron과 `claude -p`** 다.

```text
사람·AI가 GitHub 이슈 등록
  → (15분마다 cron) claude -p "/새-이슈-처리" : 새 이슈를 검증하고 현재 코드 기준 구현 계획을 짜서 큐에 넣는다
  → 다른 에이전트가 큐에서 꺼내 구현 → 테스트 → 실패하면 다른 에이전트가 고친다 → PR → 머지
  → 이슈마다 사람이 읽을 기술 보고서(tech report) 작성
```

- 이슈의 출발은 사람일 때도, AI일 때도 있다. 예를 들어 「모든 화면의 스크린샷을 찍는 기능」을 먼저 만들게 한 뒤, 그 스크린샷을 보고 개선할 점을 모두 별도 이슈로 발행하게 했다. 장치가 자기 자신을 보고 일을 만든다.
- **기술 보고서는 사람에게 공부 과제를 낸다.** 보안 평가, 성능, 품질, 내린 기술적 결정, 바뀐 코드에 더해 「이 결정을 따라가려면 무엇을 공부해야 하는지」를 적게 했다. AI의 선택을 사람이 모르는 채로 쌓이지 않게 하는 장치다.
- 오전 회의에 들어가기 전에 이슈 리뷰를 던져 두고 두 시간 뒤 나와 보니 PR 21~22개가 테스트를 거쳐 머지돼 있었다.
- 장치는 하루 한두 번 **스스로를 업데이트**한다. 여러 각도의 자기 비판 결과로 결과물이 아니라 장치를 고친다.

비슷한 흐름의 일반 원칙은 [[loop-engineering|루프 엔지니어링]], `claude -p` 사용법은 [[claude-code-guide|Claude Code 활용 가이드]]의 「자동화」에 있다.

### 비개발 직군으로 번지다

- **CFO**: 문서 작성을 대표에게 넘기면 3분이면 끝나는 일을 혼자 2시간씩 하다가, Claude Code를 30분 배운 뒤 직접 3분 안에 처리하게 됐다. GitHub를 직접 다루지 못하지만 `sync` 명령으로 커밋한다.
- **콘텐츠 담당자**: 여러 사람에게 자료를 받아 정리하는 일이 버거워 상담하러 왔다가, 일주일이 안 돼 자기 하네스를 크게 만들었다.
- 둘 다 빈 폴더에 CLAUDE.md를 만드는 것부터 시작해 30분 동안 스스로 장치를 키우는 과정을 거쳤고, 그 뒤로 일이 평온해졌다.
- **사업계획서**: 참고 문서 250여 개를 마크다운으로 바꿔 넣고, 최신 뉴스를 계속 수집해 지난 예측이 맞았는지 판단하고 수정안을 내게 한다. 사람은 토론하고, 쓰는 일은 하지 않는다.
- **CTO**: 안 되는 일은 미루라는 원칙을 받아들인 뒤, 새 모델이 나오자 다시 시도해 한글(HWP) 문서 형식을 통째로 분석해 냈다. 이후 사내에서 HWP 문서를 사람이 직접 쓰지 않는다.

조직 차원의 확산 방법은 [[organizational-ax|조직 AX]]에 따로 정리했다.

### 2개월 규칙

지금 AI로 안 되는 일은 **당장 해야 하는 게 아니면 미룬다.** 모델이 두 달마다 크게 바뀌어서, 미뤄 둔 일이 다음 모델에서는 대개 된다. 사내에 퍼뜨리기 가장 오래 걸린 개념이다.

## 병목은 계속 옮겨 간다

| 시기 | 병목 | 해법 |
| --- | --- | --- |
| 초기 | 쓸 수 있는 토큰의 양 | 토큰 사용량이 곧 IT 회사의 경쟁력이 된다. 이 프로젝트도 연말 토큰 2배 이벤트가 계기였다 |
| 6개월 전 | 머지 큐(에이전트끼리 만든 코드가 충돌) | 충돌 해결도 에이전트가 한다. 두 에이전트가 같은 소스에서 다른 기능을 동시에 개발해도 결과가 멀쩡해졌다 |
| 지금 | 생각(thinking) 토큰 | 성능을 위해 thinking 예산을 늘리면 결과는 좋아지지만 느려진다. 어려운 곳만 많이 생각하게 하는 **적응형 thinking 예산**과 그걸 조절하는 하네스가 필요하다 |
| 다음 | 추론 속도 | 지금보다 5~10배 빠른 **고속 추론**으로 반복 횟수를 늘리는 쪽이 경쟁력이 된다. 돈이 있는 곳은 속도를 사고, 없는 곳은 덜 생각하게 만든다 |

## 사람의 비용: 인지 부하와 도파민

- AI에 맡겨도 **인지 부하는 줄지 않는다.** 피드백이 쉼 없이 들어오기 때문이다. 40일 동안 3년 치 코드를 짰고, 몸은 3년 치 늙었다. 5시간 사용량이 리필될 때마다 아까워 3시간 반 돌리고 1시간 반 자는 생활을 하기도 했다.
- 에이전트 코딩은 가챠 게임처럼 즉각적인 보상을 준다. 잘되니 더 하고, 더 하면 또 잘된다. 그만큼 삶이 의존적이 되고, 그 흐름이 끊기면 제품도 사람도 떠난다.
- 기다리는 시간은 나에 대해 생각할 시간(「바이오 토큰」)이 되기도 한다.

## 소프트웨어의 가치가 옮겨 간다

| 관점 | 내용 |
| --- | --- |
| 버려지는 소프트웨어 | 쉽게 만든 소프트웨어는 유지 의지가 약하고, 비슷한 것이 수십 개씩 생긴다. 블로그 댓글이 SNS로 옮겨 가자 블로그가 접힌 것처럼, 관리되지 않는 오픈소스가 크게 늘 것이다. 소프트웨어는 넘쳐도 많이 쓰이는 소프트웨어의 수는 비슷하게 유지된다 |
| SaaS | 레베뉴 담당자가 Salesforce 대체품을 이틀 만에 만들었지만 결국 더 싼 SaaS를 샀다. 직접 안 해도 되는 일은 안 하는 게 맞기 때문이다. SaaS 시장은 남되, 지금의 승자가 1년 뒤에도 승자일지는 모른다 |
| 코드의 가치 | 코드는 목적이 아니라 로직을 구현한 수단이다. 사람이 코드를 쓰지 않는 페이스라면 코드의 가치는 0에 수렴한다 |
| 소프트웨어의 새 정의 | 로직을 처리하는 **모델 약 80%** + 모델을 감싸 결정론적으로 동작하게 하는 **로직 코드(하네스) 약 10%** + 사람·AI와의 인터페이스 약 10% |
| 하네스가 경쟁력 | Claude Code의 경쟁력은 모델이 아니라 Claude Code 자체다. 라우터로 Gemini 3 Pro를 Claude Code에 붙여도 잘 돌아간다 |
| AI를 위한 인터페이스 | 도구의 사용자는 사람이 아니라 사람에게 일을 위임받은 에이전트가 된다. 스킬을 함께 배포하고, 출력을 AI가 읽기 쉽게 하고, CLI를 몰라도 유추할 수 있는 형식으로 맞춘다 |

이 전환을 펀치 카드 → 키보드 코딩, 패키지 소프트웨어 → 웹·모바일 서비스에 이은 **세 번째 대변혁**으로 본다. 앞의 전환이 DevOps, 백엔드·프론트엔드 같은 직군을 만들었듯, 이번에는 「키보드로 코딩」에서 「의미를 전달하는 코딩」으로 바뀐다. 플랫폼 전환이라는 관점은 [[ai-platform-shift|AI 플랫폼 전환과 일의 재편]]과 이어진다.

## 관점들

다음은 합의된 사실이 아니라 대담에서 나온 관점이다.

| 주제 | 관점 |
| --- | --- |
| Claude Code와 Codex | Claude Code는 선택지를 내밀고 다음 질문을 제안하며 사람과 맞춰 가는 쪽으로, Codex는 「알아서 해 줄게」 쪽으로 진화했다. 최고치는 Codex가 높고, 편안한 쪽은 Claude Code다. 애니메이션 「사이버 포뮬러」의 아스라다(운전자와 공진화하는 AI)와 오거(사람을 믿지 않는 AI)에 빗댄다 |
| 컴퓨터공학 | 무용론과 반대로 중요성이 커진다. 컴퓨터공학은 다른 학과 출신들이 만든 신생 학문이라 변화에 가장 빨리 적응한다. 배우는 것은 프로그램이 아니라 단순한 게이트에서 복잡한 로직을 세우는 사고 구조다. 도메인 전문가가 AI를 배우는 것보다 AI를 아는 사람이 도메인을 배우는 편이 빠르다 |
| 스타트업 | 가장 나쁜 것은 정체, 가장 큰 위험은 **복제가 너무 쉽다**는 점이다. 화면 스크린샷과 기능 설명만으로 NotebookLM 클론이 나흘 만에 나왔다. 사업은 낙차가 큰 곳에 물레방아를 다는 일(「물레방아론」)이고, 시차가 가장 큰 곳은 IT 안이 아니라 AI가 맥락을 해석하게 되면서 새로 IT의 영역에 들어오는 분야다 |
| 회사의 해자 | 판이 안정되면 원가가 투명해져 다시 브랜드와 트랙 레코드가 경쟁력이 된다. 불안정한 하드웨어 위에서 수많은 예외(edge case)를 밟아 온 암묵지는 쉽게 복제되지 않는다 |

이 판단들은 두 달이면 바뀔 수 있다는 단서가 붙어 있다.

## 정리

- 결과물이 아니라 결과물을 만드는 장치를 만들고, 장치를 고친다.
- 대화로 맥락을 쌓고 → CLAUDE.md·PLAN/PROGRESS → 구성 요소 제안 → 정확한 형식으로 생성 → 참고 자료 캐시 → 비판과 수정 순서로 키운다.
- 남의 스킬을 모으기보다 지금 내 일을 하나씩 위탁하는 장치부터 만든다.
- 자동화는 cron과 `claude -p`로 충분하다. 사람이 따라갈 수 있게 보고서와 공부 과제를 남기게 한다.
- 병목은 토큰 → 머지 → thinking → 추론 속도로 옮겨 간다. 안 되는 일은 두 달 미룬다.
