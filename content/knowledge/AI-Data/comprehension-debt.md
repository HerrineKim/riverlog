> Addy Osmani의 「[The 80% Problem in Agentic Coding](https://addyosmani.com/blog/the-80-problem-in-agentic-coding/)」(2026.01, [한국어 번역](https://velog.io/@typo/80-problem-in-agentic-coding))과 Erik Johannes의 「Outsourcing thinking」(2026.01, [한국어 번역 「사고의 외주화」](https://ykss.netlify.app/translation/2026/outsourcing-thinking/))을 바탕으로, 썸원 레터(2026.07~08)가 발췌한 홍진기의 『사고외주』와 팀 하포드의 자동화 편향 논의로 보강해 재구성한 노트다.

## 이해 부채란

**이해 부채(comprehension debt)** 는 존재하는 코드와 팀이 이해하는 코드 사이의 간극이다. 코드는 돌아가고 테스트도 통과하지만, 그것이 왜 그렇게 짜였는지 설명할 수 있는 사람이 없다. 대충 훑고 머지한 기능을 사흘 뒤 설명하지 못하는 순간이 이 부채가 드러나는 때다.

기술 부채와 닮았지만 쌓이는 곳이 다르다.

| | 기술 부채 | 이해 부채 |
| --- | --- | --- |
| 어디에 쌓이나 | 코드 구조 | 사람의 머릿속(이해의 공백) |
| 보이나 | 린트·복잡도·TODO로 어느 정도 보인다 | 거의 보이지 않는다. 지표에 잡히지 않는다 |
| 언제 갚나 | 리팩터링할 때 | 장애·변경·리뷰에서 「이게 왜 이렇지」를 처음 마주할 때, 대개 가장 급한 순간에 |
| 생기는 이유 | 일부러 지름길을 택해서 | 내가 쓰지 않은 코드를 이해 없이 받아들여서 |

에이전트가 코드의 80% 이상을 쓰는 흐름에서 이 부채가 빠르게 커진다. 새 개인 프로젝트에서는 그 비율이 통하지만, 문서화되지 않은 규칙이 많은 크고 오래된 팀 코드베이스에서는 에이전트가 **가장 모를 때 가장 자신 있게** 행동한다.

## 왜 쌓이나: 실수의 모양이 바뀌었다

에이전트의 실수는 문법 오류가 아니라 서두르는 주니어 개발자의 개념 오류에 가깝다. 돌아가는 코드 속에 숨어 있어 이해 없이 보면 지나친다.

| 실수 유형 | 모습 |
| --- | --- |
| **가정의 전파** | 초반에 요구를 잘못 읽고 그 위에 계속 쌓는다. PR 몇 개가 지나 구조가 굳은 뒤에야 드러난다 |
| **추상화 비대** | 단순하게 하라고 말하지 않으면 필요 이상으로 커진다 |
| **죽은 코드 누적** | 옛 구현을 치우지 않고, 이해하지 못한 코드를 건드린다 |
| **아첨형 동의** | 불완전하거나 모순된 지시에 반박하지 않고 그대로 따른다 |

이 성향은 버그가 아니라 에이전트가 작동하는 방식에서 나온다. 규칙 파일과 계획 모드로 줄일 수는 있어도 없앨 수는 없다. 그래서 사람의 이해가 마지막 방어선이 된다.

### 생산성 역설: 병목이 리뷰로 옮겨 갔다

에이전트를 많이 쓰는 팀은 PR을 훨씬 많이 머지하지만, PR 크기와 리뷰 시간도 함께 크게 늘었다는 보고(Faros AI, DORA 2025)가 있다. 코드를 쓰는 속도가 빨라진 만큼 **이해하는 속도는 빨라지지 않았다.** 더 빠른 차를 샀는데 길이 더 막히는 셈이다. 리뷰를 건너뛰면 처리량은 지켜지지만 그 차이가 그대로 이해 부채로 쌓인다.

## 사고의 외주화

이해 부채는 코드에만 생기지 않는다. 글·기획·판단을 도구에 넘길 때도 같은 일이 일어난다.

- **똑똑한 무능함**: 결과물은 전문가 수준인데, 근거를 하나 되물으면 답하지 못한다. 결론을 직접 만지고 다듬어 본 감각이 없기 때문이다.
- **비효율이 사람을 키운다**: 자료를 찾고, 상충하는 정보를 비교하고, 문장을 여러 번 고치는 시간은 낭비처럼 보이지만 사고력이 자라는 곳이다. 글쓰기는 생각을 옮기는 일이자 생각을 **만드는** 공정이다.
- **지식은 저장과 처리가 분리되지 않는다**: 컴퓨터와 달리 사람은 머릿속에 쌓인 지식이 있어야 그것으로 생각한다. 반복 연습으로 쌓인 직관이 창의성의 재료다.
- **자동화 편향(automation bias)**: 컴퓨터가 낸 답을 의심 없이 믿는 경향이다. 알고리즘에 판단을 맡길수록 더 나은 판단을 하려는 노력을 멈추고, 판단력이 약해질수록 더 의존하는 악순환이 생긴다. 내비게이션을 믿고 바다로 차를 몬 사례가 극단적인 예다. 에이전트가 낸 diff를 「승인」 한 번으로 넘기는 습관도 같은 구조다.

외주화가 특히 손해인 경우는 다음과 같다.

| 맡기지 말아야 할 때 | 이유 |
| --- | --- |
| 앞으로 쓸 복잡한 암묵지를 쌓는 중일 때 | 직접 해 봐야 쌓인다. 주니어의 학습, 처음 보는 도메인 |
| 상대에 대한 배려·존재감을 전할 때 | 의미와 표현은 분리되지 않는다. 문장을 바꾸면 메시지가 바뀐다 |
| 과정 자체가 가치일 때 | 결과만 받으면 경험이 사라진다 |
| 대신하면 기만이 될 때 | 내 이름으로 낸 것은 내 생각이어야 한다 |
| 결과가 치명적이라 완전히 믿을 수 없을 때 | 검증할 수 있는 사람이 남아 있어야 한다 |

진짜 격차는 **AI를 잘 쓰는 사람과 못 쓰는 사람 사이가 아니라, AI로 자기 사고를 단단하게 만드는 사람과 사고의 주도권을 넘긴 사람 사이**에서 벌어진다. 같은 도구가 이해를 넓히는 데도, 이해를 피하는 데도 쓰인다.

## 이해를 지키는 방법

### 리뷰 의식

| 방법 | 내용 |
| --- | --- |
| **설명할 수 없으면 머지하지 않는다** | 다른 사람에게 설명하지 못하는 코드는 커밋하지 않는다. 리뷰의 합격 기준에 「내가 설명할 수 있다」를 넣는다 |
| **작은 PR** | PR이 커질수록 리뷰는 훑기가 된다. 에이전트 작업을 리뷰할 수 있는 크기로 쪼갠다 |
| **새 맥락에서 리뷰** | 코드를 쓴 세션이 아닌 새 세션·다른 모델에게 리뷰를 맡겨 1차 거름망으로 쓴다. 그래도 최종 이해는 사람 몫이다 |
| **자동 검사로 기계적인 것은 기계에** | CI·린트·타입·테스트가 기계적인 실수를 잡아야 사람의 리뷰가 설계와 의도에 집중한다. 반복되는 에이전트 실수는 테스트나 린트 규칙으로 만든다 |

### 설명해 보기(explain-back)

- 에이전트에게 **구현 이유와 위험 지점을 설명하게** 하고, 그 설명을 내 이해와 대조한다.
- 반대로 내가 에이전트(또는 동료)에게 **변경을 설명해 본다.** 막히는 곳이 이해 부채가 있는 곳이다.
- 낯선 코드가 나오면 넘기지 말고 **더 깊이 공부할 신호**로 받는다. AI를 답을 주는 기계가 아니라 여러 접근의 이유와 한계를 묻는 튜터로 쓴다.

### 소유 규칙

- **설계 결정은 사람이 소유한다.** 모듈 경계, API 계약, 데이터 모델은 구현 전에 사람이 정하고 문서로 남긴다. 에이전트는 그 안에서 빈칸을 채운다.
- **선언형으로 맡긴다.** 단계별 지시 대신 요구사항·성공 기준·테스트를 정하고 에이전트가 통과할 때까지 돌리게 한다. 시간의 대부분을 문제 정의와 검증에 쓴다([[agent-spec-writing|AI 에이전트를 위한 스펙 작성법]]).
- **직접 짜는 시간을 남긴다.** 일부 기능은 주기적으로 손으로 짠다. TDD, 시니어와의 페어링으로 문제 해결 감각을 유지한다. 다시 짤 수 없는 코드를 리뷰하는 것은 생각보다 쉽고 그래서 위험하다.
- **반자동으로 일한다.** 전자동 머신보다 반자동 머신을 쓰는 바리스타처럼, AI 결과에 자기 판단을 더하는 지점을 일부러 남긴다. 실행 전에 「무엇을 할지 먼저 설명해」를 요구하고 그 계획을 사람이 승인한다.

## 정리

- 이해 부채는 돌아가지만 아무도 설명하지 못하는 코드의 간극이다. 지표에 안 잡히고 가장 급할 때 청구된다.
- 에이전트의 실수는 개념 오류(가정 전파, 비대한 추상화, 죽은 코드, 아첨형 동의)라 이해 없이 보면 지나친다.
- 코드를 쓰는 속도가 빨라질수록 병목은 리뷰와 이해로 옮겨 간다.
- 사고를 넘길수록 판단력이 약해지고 더 의존하게 된다(자동화 편향). 암묵지를 쌓는 일, 내 이름으로 내는 일은 맡기지 않는다.
- 설명할 수 없으면 머지하지 않고, 설명해 보며 공백을 찾고, 설계 결정은 사람이 소유한다.

도구는 맡겨도 이해는 맡길 수 없다.
