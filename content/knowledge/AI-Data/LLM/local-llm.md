## 로컬 LLM이란

**로컬 LLM**은 공개된 가중치(open-weight) 모델을 내 컴퓨터나 사내 서버에서 직접 돌리는 방식이다. 요청이 외부 API로 나가지 않는다. 몇 년 전에는 작은 모델은 성능이 모자라고 큰 모델은 개인 장비에 안 들어가 실험에 가까웠지만, 지금은 수십억~수백억 파라미터 모델이 특정 작업에서 실무에 쓸 만한 수준이 됐다.

로컬 LLM은 두 방향으로 쓰인다.

| 방향 | 쓰임 |
| --- | --- |
| **개발 도구** | 코딩 에이전트의 일부 작업을 로컬 모델에 맡겨 비용·한도·보안 부담을 줄인다 |
| **제품 기능** | 앱 안의 요약·분류·추출·개인화를 서버 비용과 개인정보 부담 없이 기기에서 처리한다. 브라우저 안 실행은 [[client-side-web-ai\|클라이언트 사이드 웹 AI]], 클라이언트·서버·하이브리드 구조 선택은 [[web-ai-platform-choice\|웹 AI 플랫폼 고르기]]에 있다 |

## 왜 로컬인가

| 이유 | 설명 |
| --- | --- |
| **개인정보·보안** | 고객 정보, 결제 정보, 사내 코드처럼 밖으로 보내기 부담스러운 데이터를 기기 안에서 처리한다. 데이터 보존·동의·유출 문제가 줄어든다 |
| **비용** | 요청마다 과금되지 않는다. 장비 비용은 고정이고 반복 작업이 많을수록 유리하다. 구독 사용량 한도에도 걸리지 않는다 |
| **지연** | 네트워크 왕복이 없다. 짧은 요청을 자주 보내는 기능에서 체감이 크다 |
| **오프라인·안정성** | 서버 장애, API 정책 변경, 카드 만료로 기능이 멈추지 않는다 |
| **접근 통제** | 가장 강한 모델이 안전·규제 이유로 일부에게만 공개되거나 갑자기 막힐 수 있다. 내가 가진 가중치는 누가 회수하지 못한다 |

클라우드 모델을 앱에 붙이는 순간 그 기능은 네트워크·인증·비용·장애·데이터 보존에 묶인 **분산 시스템**이 된다. 로컬에서 처리하는 기능은 입력을 넣으면 기기 안에서 결과가 나오는 **함수**에 가깝다. 실패 범위가 작아지고 구조가 단순해진다.

## 메모리 어림셈과 양자화

로컬 실행의 첫 제약은 메모리다. 모델 가중치가 GPU 메모리(VRAM)나 Apple Silicon의 통합 메모리에 올라가야 빠르게 돈다.

### 양자화

**양자화(quantization)** 는 가중치를 16비트 대신 8·6·5·4비트처럼 적은 비트로 저장하는 것이다. 메모리와 대역폭이 줄어 같은 장비에 더 큰 모델이 들어가고 토큰 생성도 빨라진다. 대신 비트를 줄일수록 품질이 조금씩 떨어진다. 서버 쪽에서 양자화가 처리량을 높이는 원리는 [[llm-serving-at-scale|LLM 서빙의 병목]]에 있다.

**GGUF**는 llama.cpp 개발자가 만든 모델 파일 형식이다. 텐서와 함께 토크나이저·구조 같은 메타데이터를 한 파일에 담아 빨리 불러온다. 파일 이름의 접미사가 양자화 방식이다.

| 형식 | 가중치당 비트(대략) | 쓰임 |
| --- | --- | --- |
| F16 / BF16 | 16 | 원본에 가까움. 메모리가 넉넉할 때 |
| Q8_0 | 약 8.5 | 품질 손실이 거의 없다 |
| Q6_K | 약 6.6 | 품질 우선 |
| Q5_K | 약 5.5 | 품질과 크기의 균형 |
| **Q4_K(Q4_K_M 등)** | 약 4.5 | 가장 흔한 기본값. 체감 품질을 크게 해치지 않으면서 크기를 4분의 1 가까이로 줄인다 |
| Q3_K, Q2_K, IQ 계열 | 약 2~3.5 | 메모리가 모자랄 때. 품질 저하가 눈에 띈다 |

`_K`는 가중치를 블록으로 묶어 블록마다 배율을 두는 k-양자화, `IQ`는 중요도 행렬로 중요한 가중치를 더 정밀하게 남기는 방식이다.

### 메모리 어림셈

```text
가중치 메모리(GB) ≈ 파라미터 수(십억) × 가중치당 비트 ÷ 8
필요 메모리     ≈ 가중치 + KV 캐시(맥락 길이에 비례) + 런타임·OS 여유분

예) 9B 모델, Q4_K(약 4.5비트): 9 × 4.5 ÷ 8 ≈ 5GB  → 16GB 노트북에서 여유 있게 돈다
    27B 모델, Q4_K:            27 × 4.5 ÷ 8 ≈ 15GB → 24~32GB 이상
    70B 모델, Q4_K:            70 × 4.5 ÷ 8 ≈ 39GB → 64GB 이상
```

- **맥락이 길면 KV 캐시가 커진다.** 128K 맥락을 쓰면 가중치 외에 수 GB가 더 든다. 에이전트처럼 긴 맥락을 쓰는 용도는 여유를 크게 잡는다.
- **MoE(전문가 혼합) 모델**은 토큰마다 일부 전문가만 계산하므로 속도는 활성 파라미터 수를 따르지만, 메모리에는 전체 파라미터가 올라가야 한다. 「총 파라미터로 메모리, 활성 파라미터로 속도」를 어림한다.
- 메모리가 모자라면 일부 층을 CPU·디스크로 내릴 수 있지만 속도가 크게 떨어진다.
- 장비에 맞는 모델을 고르기 어렵다면 하드웨어를 감지해 실행 가능한 후보를 점수로 보여 주는 도구(예: llmfit)를 쓴다.

## 런타임

| 런타임 | 특징 | 맞는 경우 |
| --- | --- | --- |
| **llama.cpp** | C/C++ 추론 엔진이자 GGUF의 원조. CPU·CUDA·Metal 등 폭넓게 지원하고, OpenAI 호환 서버(`llama-server`)를 내장한다 | 세밀하게 조정하고 싶을 때, 다른 도구의 기반 |
| **Ollama** | 모델 내려받기·실행·API 서버를 명령 하나로 묶었다(`ollama run <모델>`). 기본 포트 11434. OpenAI 호환 API와 Anthropic Messages API 호환을 제공한다 | 개발자의 기본 선택, 에이전트·앱에 바로 연결 |
| **LM Studio** | GUI 앱. 모델 검색·내려받기, 채팅, 로컬 API 서버. Mac에서는 GGUF(llama.cpp)와 MLX 형식을 모두 돌린다 | GUI로 여러 모델을 비교해 볼 때 |
| **MLX** | Apple이 만든 Apple Silicon용 배열·머신러닝 프레임워크. 통합 메모리와 Metal을 직접 쓴다. `mlx-lm`으로 LLM을 돌린다 | Mac에서 속도를 끌어올릴 때 |
| **vLLM 등 서빙 엔진** | 여러 사용자의 동시 요청을 배치로 처리하는 고처리량 서버 | 사내 GPU 서버에 팀 공용으로 띄울 때 |

여러 런타임이 OpenAI·Anthropic 호환 API를 내놓으므로 **앱이나 에이전트 쪽은 주소만 바꿔 클라우드와 로컬을 오간다.** 예를 들어 Claude Code는 `ANTHROPIC_BASE_URL`을 로컬 Ollama 주소로 바꾸고 모델 이름을 지정해 로컬 모델로 돌릴 수 있다. 모델 접근 계층을 추상화해 두면 모델 교체가 쉽다.

## 무엇을 로컬에 맡기나

로컬 모델은 최상위 상용 모델처럼 복잡한 문제를 혼자 끝까지 풀지는 못한다. 대신 **작업을 작게 나눠 방향을 잡아 주면** 충분히 쓸 만하다.

| 로컬 모델로 충분한 일 | 프런티어 모델이 나은 일 |
| --- | --- |
| 요약, 분류, 추출, 재작성, 정규화 | 복잡한 아키텍처 판단 |
| 자연어 조건을 검색식·필터로 바꾸기 | 긴 맥락이 필요한 설계 |
| 계획이 잡힌 뒤의 세부 구현, 테스트 케이스 추가 | 애매한 요구사항 정리 |
| 코드 리뷰 초안, 오류 추적 보조, 자료 정리 | 처음 보는 큰 코드베이스 탐색 |
| 민감 데이터가 든 백오피스 보조(상담 이력 요약, 이상 거래 표시) | 정답이 열려 있는 고난도 추론 |

대부분의 앱 기능이 요구하는 것은 셰익스피어를 쓰는 능력이 아니라 **요약·분류·추출을 안정적으로 해내는 능력**이다. 그래서 「비싼 모델이 꼭 필요한 일」과 「로컬로 충분한 일」을 나누는 하이브리드 구성이 현실적이다. 계획·판단은 프런티어 모델, 실행·반복은 로컬 모델에 보낸다. 모델을 역할로 나누는 원칙은 [[token-efficiency|에이전트 토큰 비용 관리]]의 모델 라우팅에 있다.

## 가장 강한 모델보다 지금 쓸 수 있는 모델

야구의 **WAR(대체 선수 대비 승리 기여)** 는 「이 선수가 언제든 구할 수 있는 대체 선수보다 몇 승을 더 가져오는가」를 잰다. 모델에도 같은 질문을 던질 수 있다. 가장 강한 프런티어 모델이 일부에게만 공개되거나 비싸거나 언제 막힐지 모른다면, 그 모델의 가치는 **바로 쓸 수 있는 공개 가중치 모델 대비** 얼마나 더 나은가로 따져야 한다.

| 기준 | 프런티어 API 모델 | 공개 가중치 로컬 모델 |
| --- | --- | --- |
| 최고 성능 | 높다 | 한 세대 정도 뒤처지지만 격차가 줄고 있다 |
| 접근성 | 공급자 정책·규제에 따라 제한·중단될 수 있다 | 내려받은 가중치는 계속 쓴다 |
| 비용 | 사용량 비례 | 장비 고정비 |
| 통제 | 버전이 바뀌거나 동작이 달라질 수 있다([[llm-behavior-variability\|LLM 동작은 왜 날마다 다른가]]) | 같은 가중치·같은 설정이면 같은 모델이다 |
| 데이터 | 외부로 나간다 | 기기 안에 남는다 |

사용자는 결국 가장 강한 모델보다 **지금 쓸 수 있고, 싸고, 통제할 수 있는 모델**을 고른다. 폐쇄적 라이선스가 오픈소스 데이터베이스의 채택 명분을 키웠듯, 프런티어 모델의 제한적 공개는 공개 가중치 모델을 쓸 이유가 된다.

## 한계와 주의

- **품질 격차**: 같은 크기라도 양자화를 세게 할수록, 맥락이 길수록 품질이 떨어진다. 도구 호출(tool use) 형식을 자주 틀리는 모델은 에이전트에 붙이기 어렵다. 내 작업으로 직접 평가한다([[evaluation-driven-development|평가 주도 개발]]).
- **첫 프롬프트 처리가 느리다**: 긴 시스템 프롬프트를 쓰는 코딩 에이전트는 첫 응답까지 오래 걸린다. 디스크 KV 캐시나 프롬프트 캐시를 지원하는 런타임이 두 번째 세션부터 차이를 만든다.
- **라이선스 확인**: 공개 가중치라도 상업적 이용 조건이 모델마다 다르다(Apache 2.0, MIT, 자체 라이선스).
- **보안은 따로 챙긴다**: 로컬 API 서버를 외부에 열어 두지 않는다. 출처가 불분명한 모델 파일은 받지 않는다.

## 정리

- 로컬 LLM은 개인정보, 비용, 지연, 오프라인, 접근 안정성 때문에 쓴다. 로컬 기능은 분산 시스템이 아니라 함수에 가깝다.
- 메모리는 파라미터 × 비트 ÷ 8에 KV 캐시와 여유분을 더해 잡는다. Q4_K 계열이 흔한 기본값이다.
- llama.cpp(GGUF)가 기반이고, Ollama·LM Studio가 쓰기 쉽게 감싸며, Mac에서는 MLX가 빠르다. 호환 API 덕에 주소만 바꿔 클라우드와 오간다.
- 요약·분류·추출과 계획된 구현은 로컬에, 판단과 긴 설계는 프런티어 모델에 맡긴다.

가장 강한 모델이 아니라, 지금 안정적으로 쓸 수 있는 모델이 일을 끝낸다.
