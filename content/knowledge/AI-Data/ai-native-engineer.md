> Addy Osmani의 「[The AI-Native Software Engineer](https://addyo.substack.com/p/the-ai-native-software-engineer)」(2025.07)를 바탕으로 재구성한 노트다.

## AI 네이티브 엔지니어란

AI 네이티브 엔지니어(AI-native software engineer)는 AI를 가끔 꺼내 쓰는 도구가 아니라 **일상 업무 전체에 깔린 협업자**로 다루는 엔지니어다. 작업마다 「AI가 이걸 더 빠르게, 더 잘, 또는 다르게 할 수 있나」를 먼저 묻는다.

반복 작업(보일러플레이트, 문서 초안, 테스트)은 AI에 맡기고 사람은 문제 정의·설계·판단에 집중한다. **경험이 많을수록 AI에게 맥락을 잘 주므로 결과도 좋다.** AI는 실력을 대체하지 않고 증폭한다.

## 원칙

| 원칙 | 뜻 |
| --- | --- |
| 협업자로 다룬다 | 늘 대기하는 빠른 주니어 페어 프로그래머처럼 쓰되, 방향과 결정은 사람이 쥔다 |
| 신뢰하되 검증한다 | 결과물의 정확성·보안·가독성 책임은 끝까지 사람에게 있다 |
| 모두가 관리자다 | 직접 다 짜기보다 작업을 정의해 에이전트에게 맡기고, 감독·검토·통합한다 |
| AI가 읽기 쉬운 코드베이스 | 규칙 파일(CLAUDE.md, AGENTS.md 등), 좋은 README, 일관된 구조가 결과 품질을 올린다 |
| 증폭이지 자동 조종이 아니다 | 작게 나눠 맡기고 단계마다 검토한다. 이해 못 한 코드가 쌓이면 AI 기술 부채가 된다 |

위임의 구조와 개발자 역할의 변화는 [[ai-era-developer|AI 시대 개발자의 역할]], 실무 가드레일은 [[ai-coding-guardrails|AI 코딩 실무 가드레일]]에 있다.

## 도입 단계

1. **AI로 먼저 시작한다.** 조사·설계 비교·프로토타입을 일단 AI에 시켜 보고 얼마나 해내는지 본다. 환각 걱정은 맥락을 충분히 주고 에이전트가 스스로 실행·검증하게 하면 크게 줄어든다.
2. **도구를 미리 깔아 둔다.** 에디터 어시스턴트 하나, 코딩 에이전트 하나, 범용 채팅 하나. 손 닿는 곳에 있어야 습관이 된다.
3. **구체적으로 요청한다.** 「테스트 써 줘」가 아니라 대상의 동작, 다룰 케이스, 출력 형식을 적는다. 방법은 [[prompt-cheat-sheet|프롬프트 작성법 치트시트]].
4. **보조 코드부터 맡긴다.** 이해는 하지만 쓰기 귀찮은 코드(파서, 변환, 설정)에서 신뢰를 쌓은 뒤 핵심 로직으로 넓힌다.
5. **코딩 밖으로 넓힌다.** 커밋 메시지, PR 설명, 문서, 설계 개요, 비개발 직군에게 보낼 설명까지. 엔지니어의 가치는 타이핑이 아니라 생각·계획·소통에 있다.
6. **고쳐 가며 쓴다.** 처음부터 다시 시키지 말고 어디가 틀렸는지 짚어 수정을 요청한다. 잘 먹힌 프롬프트는 모아 둔다.
7. **항상 검증한다.** 실행하고, 테스트를 더하고, 리뷰·정적 분석을 사람 코드와 같은 기준으로 돌린다. AI가 약한 곳(정밀 계산, 도메인 특화 규칙)은 더 꼼꼼히 본다.
8. **자율성을 천천히 높인다.** 질문에 답하는 단계에서 여러 파일을 고치고 테스트를 돌리는 에이전트로 넘어간다. 자율성이 커질수록 확인 지점도 늘린다.

## 도구의 네 범주

| 범주 | 하는 일 | 예 | 쓸 때 |
| --- | --- | --- | --- |
| 에디터 어시스턴트 | 자동 완성, 파일 단위 편집, 코드 설명 | GitHub Copilot, Cursor | 기존 코드를 고치는 편집·테스트 주기 안에서 |
| 터미널·IDE 코딩 에이전트 | 계획을 세우고 여러 파일 수정, 명령 실행, 테스트까지 | Claude Code, Codex CLI, Gemini CLI, Cline | 기능 하나를 통째로 맡길 때. 계획 단계를 검토한다 |
| 비동기 백그라운드 에이전트 | 이슈를 받아 격리된 환경에서 작업하고 PR로 돌려준다 | Copilot coding agent, Codex(클라우드), Jules | 잘 정의된 작업을 여러 개 병렬로 맡길 때 |
| 프로토타이핑 도구 | 프롬프트 한 번으로 실행되는 앱 골격 생성 | v0, Bolt, Lovable, Replit | 새 아이디어·PoC를 빠르게 보여 줄 때 |

- 프로토타이핑 도구의 결과물은 **첫 초안**이다. 70% 정도는 빠르게 나오지만 나머지 30%(엣지 케이스, 성능, 실제 비즈니스 규칙)는 사람이 채운다. 흔히 「70% 문제」라고 부른다.
- 흔한 조합은 프로토타이핑 도구로 골격을 만들고, 저장소로 옮겨 코딩 에이전트로 다듬는 방식이다.
- 도구 지형은 빠르게 바뀐다. 한 도구에 매달리지 말고 범주별로 하나씩 갖추고 주기적으로 갈아 본다.

## 개발 생명 주기별 활용

| 단계 | AI에게 시킬 일 | 사람이 지킬 것 |
| --- | --- | --- |
| 요구 사항 | 기능 목록 브레인스토밍, 사용자 스토리 초안, 「이 요구 사항을 분명히 하려면 무엇을 물어야 하나」, PRD 초안 | 실제 사용자·고객에게 확인 |
| 설계 | 대안별 장단점, SQL vs NoSQL 같은 선택 근거, Mermaid 다이어그램, API 엔드포인트 초안, 「이 설계에서 무엇이 깨질 수 있나」 | 최종 결정과 근거. 명세를 먼저 쓰는 스펙 주도 개발 |
| 구현 | 스캐폴딩·설정 파일, 주석으로 적은 단계 채우기, 기존 파일을 예시로 준 일관된 모듈 생성, 리팩터링 | diff를 주니어의 PR처럼 리뷰 |
| 테스트 | 단위 테스트, 속성 기반 테스트(Hypothesis, fast-check)의 속성 찾기, E2E 시나리오 목록, 더미 데이터, 빠진 케이스 찾기 | 기대값이 의도와 맞는지. 실데이터는 익명화 |
| 디버깅·유지보수 | 스택 트레이스 해석, 원인 가설, 레거시 코드 설명, 라이브러리 버전 마이그레이션, 변경 기록·마이그레이션 가이드 초안 | 패치 후 테스트 실행 |
| 배포·운영 | Terraform·Kubernetes YAML 초안, CI 워크플로, PromQL 알림 쿼리, 장애 로그 요약, 런북 | 자격 증명·보안 그룹·비용. 안전한 환경에서 먼저 적용 |

## 검증 습관

- 그럴듯하지만 **존재하지 않는 함수·설정 키**를 의심한다. 공식 문서로 확인한다.
- 린터·타입 검사·테스트는 AI 코드에도 똑같이 돌린다.
- 인증·암호화·비밀 정보 코드는 특히 천천히 본다. 비밀 값을 AI로 만들지 않는다.
- AI에게 「이 코드에 버그나 보안 문제가 있나」를 다시 묻는 것은 빠른 1차 점검이다. 보장은 아니다.
- 에이전트에는 경계를 둔다. 의존성 추가 전 확인, 네트워크 호출 제한, 계획 모드·드라이런으로 단계별 승인.

## 팀과 윤리

| 주제 | 규칙 |
| --- | --- |
| 리뷰 | AI가 만든 코드도 사람 리뷰와 테스트를 거쳐 커밋한다. PR에 AI가 만든 부분과 쓴 프롬프트를 밝히면 리뷰어가 어디를 볼지 안다 |
| 지식 공유 | 팀 스택에 맞는 프롬프트·규칙 파일을 함께 쌓는다. 성공뿐 아니라 실패 사례도 공유한다 |
| 회의적인 동료 | 홍보보다 실제 결과(찾은 버그, 아낀 시간)로 보여 준다 |
| 데이터·보안 | 「이 코드와 맥락이 외부 서버에 기록돼도 되나」를 먼저 묻는다. 회사 정책, 엔터프라이즈 플랜·자체 호스팅 모델을 확인한다 |
| 저작권 | 라이선스 있는 코드를 그대로 베끼게 하지 않는다. 결과물의 책임은 쓴 사람에게 있다 |
| 리더의 역할 | 직접 써 보이고, 도구 비용과 실험 시간을 대고, 실패해도 괜찮은 분위기를 만든다. 업무의 중심이 작성에서 명세·검증·통합으로 옮겨 간 것을 일정과 리뷰 기준에 반영한다 |

## 정리

- 작업마다 **AI부터 시도**하고, 결과는 **사람이 검증**한다.
- 엔지니어는 점점 에이전트에게 일을 맡기고 검토하는 **관리자**가 된다.
- 도구는 에디터 어시스턴트·코딩 에이전트·비동기 에이전트·프로토타이핑 네 범주로 갖춘다.
- 요구 사항부터 운영까지 모든 단계에 쓸 곳이 있다. 다만 결정과 책임은 넘기지 않는다.
- 기초(CS, 설계, 문제 해결)가 탄탄할수록 질문이 좋아지고 답을 잘 가려낸다.
