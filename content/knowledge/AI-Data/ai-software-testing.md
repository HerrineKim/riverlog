> 고려사이버대학교 「소프트웨어 테스트」(2024-1학기) 강의 내용을 바탕으로 정리했다.

일반 소프트웨어는 사람이 규칙을 코드로 쓰고, 그 규칙이 맞는지 테스트한다(연역). AI 소프트웨어는 데이터에서 규칙을 **배우고**, 배운 모델로 처음 보는 입력을 판단한다(귀납). 규칙이 코드에 적혀 있지 않으니 "이 입력이면 이 출력"을 미리 다 정하기 어렵고, 같은 테스트 방식이 그대로 통하지 않는다.

AI가 낸 고장도 일반 소프트웨어처럼 시스템을 거쳐 사고로 이어진다. 2018년 우버 자율주행 시험차의 보행자 사망 사고, 딥페이크 사기, 생성형 AI를 이용한 피싱 메일이 그런 예다.

## AI 소프트웨어의 추가 품질 특성

AI 소프트웨어도 [[software-testing|일반 소프트웨어]]처럼 기능·성능·사용성 같은 ISO/IEC 25010 품질 특성을 만족해야 한다. 거기에 고유한 특성이 더해진다. 강의는 정보통신산업진흥원(NIPA)의 「중소SW기업 SW품질관리 가이드 – AI 시스템 테스트」(2019)의 분류를 소개했다.

| 특성 | 뜻 | 테스트에서 신경 쓸 점 |
| --- | --- | --- |
| 적응성 | 새 환경·데이터에 맞춰 동작을 바꾼다 | 바뀐 뒤에도 요구사항을 지키는지 |
| 자율성 | 사람 개입 없이 스스로 판단한다 | 사람이 개입해야 할 경계가 지켜지는지 |
| 진화 | 재학습으로 시간이 지나며 변한다 | 버전마다 회귀가 없는지 |
| 유연성 | 예상하지 못한 입력에도 대응한다 | 학습 분포 밖 입력에서의 동작 |
| 편향성 | 데이터의 치우침이 결과에 스며든다 | 집단별 성능 차이 |
| 성능 지표 | 정확도, 정밀도, 재현율 같은 통계 지표로 품질을 잰다 | 목표 수치와 평가 데이터 |
| 투명성 | 왜 그런 판단을 했는지 설명할 수 있는가 | 설명 가능성 요구 여부 |
| 복잡성 | 추론 과정이 사람이 따라가기 어렵다 | 기대 결과(오라클)를 만들기 어렵다 |
| 비결정성 | 같은 입력에도 결과가 달라질 수 있다 | 반복 실행, 허용 오차 |

성능 지표의 계산법은 [[classification-metrics|분류 모델 성능 평가 지표]]에 있다.

## AI 소프트웨어의 개발 단계와 V-모델

"제품의 품질은 그것을 만드는 프로세스의 품질이 정한다"(Watts Humphrey)는 원칙은 AI에도 적용된다. AI 부분은 V-모델 안에 별도의 작은 흐름으로 들어간다.

```text
시스템 요구사항 분석 ─────────────────────────────── 시스템·인수 테스트
  시스템 아키텍처 설계 ──────────────────────── 통합 테스트
     ├ AI 부분                                    ├ 일반 SW 부분
     │ 요구사항 분석 ─────────── 훈련 완료 모델 테스트   │ 요구사항 → 설계 → 구현
     │   훈련 데이터 준비 ─── 평가 데이터 기반 테스트    │ ← 단위·통합 테스트
     │        훈련
```

| 단계 | 할 일 | 예 (고양이 사진 분류) |
| --- | --- | --- |
| 요구사항 분석 | 문제를 정의하고 AI 품질 특성을 반영한다 | 고양이 여부만인가, 품종까지인가? 국내 품종만인가? 얼굴 사진인가 전신인가? 정확도·재현율 목표는? |
| 훈련 데이터 준비 | 요구사항을 만족할 데이터셋을 설계하고 모은다 | 품종·자세·조명별로 고르게 수집하고 라벨을 검수한다 |
| 훈련 | 모델을 고르고 학습한다 | |
| 평가 데이터 기반 테스트 | 학습에 쓰지 않은 데이터로 성능을 잰다 | 미달이면 모델 선택, 하이퍼파라미터, 데이터 양을 다시 본다 |
| 훈련 완료 모델 테스트 | 시스템에 넣은 상태로 요구사항을 검증한다 | 성능이 높게 나와도 운영 중 계속 테스트한다 |

AI 부분에서는 **데이터 품질이 곧 제품 품질**이다. 편향되거나 라벨이 틀린 데이터는 코드를 아무리 잘 짜도 고칠 수 없다. 데이터를 다루는 흐름은 [[data-pipeline-basics|데이터 파이프라인 기초]]에 있다.

## 전통 기법이 잘 안 맞는 이유

[[test-design-techniques#동등 분할|동등 분할]]은 "같은 클래스의 입력은 같게 동작한다"는 가정에 기댄다. 성적을 등급으로 바꾸는 AI 모델이 있다고 하자. 사람이 짠 코드라면 90~100점 구간에서 95점 하나만 확인해도 되지만, 모델은 학습 데이터에 없던 93점에서 엉뚱한 등급을 낼 수 있다. 구간 안의 동작이 균일하다는 보장이 없다. 또 출력이 확률적이라 "정답"을 미리 정하는 **테스트 오라클 문제**가 커진다.

## AI 테스트 기법

### 블랙박스

| 기법 | 아이디어 | 예 |
| --- | --- | --- |
| 조합 테스팅 | 입력 속성(날씨, 조명, 물체 종류)의 조합을 체계적으로 만든다 | 페어와이즈로 시나리오 조합 생성 |
| 백투백 테스팅 | 같은 입력을 여러 모델·버전에 넣고 결과를 비교한다 | 새 모델과 기존 모델의 판정이 갈리는 입력을 집중 분석 |
| 변성(Metamorphic) 테스팅 | 정답은 몰라도 **입력을 이렇게 바꾸면 출력은 이래야 한다**는 관계로 검증한다 | 사진을 살짝 회전하거나 밝기를 바꿔도 분류는 같아야 한다. 주행 영상에 비를 합성해도 조향 각도는 비슷해야 한다 |
| 탐색적 테스팅 | 학습 때 몰랐던 경우를 찾아 반복적으로 파고든다 | 입력 영역 정의 → 케이스 생성 → 시뮬레이션 실행 → 결과 확인 → 결함이면 수정 후 재실행, 필요하면 새 케이스 추가 |

변성 테스팅이 특히 쓸모 있다. 오라클이 없어도 **관계**만 정하면 테스트를 만들 수 있기 때문이다. 같은 발상은 LLM 기능에도 통한다. 질문의 표현만 바꿔도 답의 핵심은 같아야 한다는 식이다([[evaluation-driven-development|평가 주도 개발]]).

### 화이트박스

신경망 내부를 보고 커버리지를 잰다. 뉴런은 입력을 계산해 활성값을 내고, 0이면 비활성이다([[perceptron-mlp|퍼셉트론과 다층 신경망]]).

| 기준 | 무엇을 세나 |
| --- | --- |
| 뉴런 커버리지 | 테스트 데이터로 활성화된 뉴런의 비율. 비활성 뉴런을 깨우는 입력을 데이터셋에 추가한다 |
| 임계점 커버리지 | 활성값이 정해 둔 임계값을 넘은 뉴런의 비율 |
| 부호 변경 커버리지 | 활성값의 부호가 바뀌는 경우를 덮었는가 |
| 값 변경 커버리지 | 활성값이 일정 이상 크게 바뀌는 경우를 덮었는가 |

코드 커버리지를 신경망에 옮긴 발상이지만, 뉴런 커버리지가 높을수록 결함을 더 잘 찾는지는 연구자들 사이에서 논란이 있다. 참고 지표로 보는 편이 안전하다.

## 가상 환경 테스트: 디지털 트윈

자율주행이나 로봇처럼 실제 환경에서 테스트하기 위험하거나 비싼 경우, 실물을 디지털로 복제한 **디지털 트윈**을 만들어 시뮬레이션으로 테스트한다.

- 실제로 재현하기 어려운 **예외 상황**(보행자 돌발 출현, 폭우, 센서 고장)을 안전하게 시험한다.
- 여러 환경을 동시에 띄워 **병렬로** 돌린다.
- 장비와 현장 비용을 줄인다.

시뮬레이션과 현실의 차이는 남으므로, 시뮬레이션에서 찾은 위험 시나리오를 실제 시험으로 확인하는 단계를 둔다.

## 정리

- AI 소프트웨어는 일반 품질 특성에 더해 적응성·자율성·진화·편향성·비결정성 같은 특성을 테스트해야 한다.
- AI 부분은 요구사항 → 데이터 준비 → 훈련 → 평가 데이터 테스트 → 훈련 완료 모델 테스트로 진행하고, 운영 중에도 계속 테스트한다.
- 오라클을 만들기 어려우니 변성·백투백처럼 **관계와 비교**로 검증하는 기법이 중심이 된다.
- 위험한 시나리오는 디지털 트윈 시뮬레이션으로 먼저 시험한다.
