웹 서비스는 결국 "누가 요청하고, 누가 처리해서, 무엇을 돌려주는가"의 반복이다. 이 흐름과 그 규칙인 HTTP를 이해하면 Express든 NestJS든 Django든 프레임워크가 하는 일이 같은 그림 위에서 보인다.

## 웹이 작동하는 방식

1. 사용자가 브라우저 주소창에 `google.com`을 입력하면 DNS를 거쳐 해당 주소의 **서버**를 찾는다.
2. 서버에서 HTML·CSS·JavaScript 파일을 내려받아 화면을 그린다.
3. 사용자가 버튼을 누르면 이벤트가 발생하고, **프론트엔드**는 필요한 데이터를 얻기 위해 **백엔드에 API 요청**을 보낸다.
4. 백엔드는 비즈니스 로직을 처리하고(필요하면 DB 조회·저장) 결과를 보통 **JSON**으로 응답한다.
5. 프론트엔드는 받은 데이터를 UI에 맞게 가공해 보여 준다.

| 역할 | 하는 일 | 응답 형태 |
| --- | --- | --- |
| 프론트엔드 서버 | 화면(UI)에 해당하는 코드를 내려줌 | HTML/JS/CSS |
| 백엔드(API) 서버 | 데이터 처리, 인증, 저장 | 주로 JSON |
| 데이터베이스 | 데이터 영속화 | 쿼리 결과 |

## HTTP 프로토콜

HTTP(HyperText Transfer Protocol)는 HTML 문서 같은 리소스를 주고받기 위한 **요청-응답 규약**이며, 웹에서 일어나는 모든 데이터 교환의 기초다. 브라우저 개발자 도구의 Network 탭에 보이는 수많은 파일이 모두 HTTP 규칙을 지켜 서버에서 받아 온 것이다.

- **요청(Request)**: 메서드(GET, POST …), URL, 헤더, (선택) 바디
- **응답(Response)**: 상태 코드(200, 404 …), 헤더, 바디
- **Stateless**: 각 요청은 독립적이다. 로그인 상태 같은 정보는 쿠키·세션·토큰으로 따로 유지해야 한다.

### 요청 메서드

| 메서드 | 용도 | 데이터 전달 |
| --- | --- | --- |
| GET | 리소스 조회. 데이터를 가져올 때만 사용 | Query String (`?key=value&key2=value2`) |
| POST | 리소스 생성 | 요청 바디 |
| PUT | 리소스 전체 교체 | 요청 바디 |
| PATCH | 리소스 일부 수정 | 요청 바디 |
| DELETE | 리소스 삭제 | 보통 URL로 대상 지정 |

HTML `<form>`도 결국 HTTP 요청을 만드는 도구다. `action`에 전송할 URL을, `method`에 GET/POST를 지정하고, 각 `<input>`의 `name`이 key, 입력값이 value가 되어 서버로 전달된다.

## 포트(Port)

IP 주소가 "어느 컴퓨터인지"를 가리킨다면, 포트는 그 컴퓨터 안에서 **어느 애플리케이션(프로세스)인지**를 구분하는 번호다.

- 범위는 0 ~ 65535. 이미 사용 중인 포트는 다른 프로그램이 중복해서 쓸 수 없다.
- 0 ~ 1023번은 **well-known 포트**로 HTTP(80), HTTPS(443), SSH(22)처럼 주요 프로토콜에 예약되어 있고, 리눅스에서는 이 포트를 열려면 관리자 권한이 필요하다.
- 개발 서버는 보통 3000, 8000, 8080처럼 1024 이상의 포트를 쓴다. (예: `http://127.0.0.1:3000` → 내 PC의 3000번 통로로 실행 중인 React 개발 서버)

## 핵심 정리

- 프론트엔드는 화면을, 백엔드는 데이터와 로직을 담당하고 둘은 HTTP API로 대화한다.
- HTTP 요청은 메서드·URL·헤더·바디, 응답은 상태 코드·헤더·바디로 이루어진다.
- 포트는 한 컴퓨터 안의 프로세스를 구분하며 1024 미만은 시스템 예약 영역이다.
