> ByteByteGo의 System Design 101 가이드 「[How Google Authenticator Works](https://bytebytego.com/guides/how-does-google-authenticator-or-other-types-of-2-factor-authenticators-work)」, 「[Is PassKey Shaping a Passwordless Future?](https://bytebytego.com/guides/is-passkey-shaping-a-passwordless-future)」를 바탕으로, TOTP 규격(RFC 6238)과 WebAuthn 명세로 확인해 재구성한 노트다.

## 인증 요소

인증은 세 종류의 증거로 한다. **서로 다른 종류를 두 개 이상** 요구하면 다중 요소 인증(MFA)이다. 비밀번호 두 개는 같은 종류라 MFA가 아니다.

| 요소 | 의미 | 예 |
| --- | --- | --- |
| 아는 것 | 기억하는 비밀 | 비밀번호, PIN |
| 가진 것 | 소유한 기기·키 | 인증기 앱이 든 휴대폰, 보안 키, 패스키가 저장된 기기 |
| 나 자신 | 생체 정보 | 지문, 얼굴 |

## TOTP: 시간 기반 일회용 비밀번호

Google Authenticator 같은 인증기 앱의 6자리 숫자는 **TOTP(Time-based One-Time Password, RFC 6238)** 다. 서버와 앱이 같은 비밀 키를 나눠 갖고, 각자 현재 시각으로 같은 숫자를 계산한다. 네트워크로 코드를 받는 것이 아니므로 앱은 오프라인에서도 동작한다.

```text
[1단계: 등록]
사용자가 2단계 인증 켜기
서버: 비밀 키 생성 → 사용자 계정에 (암호화해) 저장
서버 → 화면: otpauth://totp/발급자:사용자?secret=...&issuer=... 를 QR 코드로 표시
인증기 앱: QR 스캔 → 비밀 키를 기기에 저장
사용자: 앱에 뜬 코드를 한 번 입력해 등록 확인

[2단계: 로그인]
앱:   코드 = HOTP(비밀 키, floor(현재 Unix 시각 / 30))  → 6자리 표시
사용자: 비밀번호 + 코드 입력
서버: 저장된 비밀 키로 같은 계산 → 일치하면 통과
```

- HOTP는 비밀 키와 카운터로 HMAC을 계산해 6자리로 자른 것이고, TOTP는 그 카운터를 **30초 단위 시각**으로 바꾼 것이다.
- 기기 시계가 조금 어긋나도 통과하도록 서버는 보통 앞뒤 한 구간 정도를 함께 허용한다.

### 안전한가

| 질문 | 답 |
| --- | --- |
| 비밀 키가 새면? | 누구나 코드를 만들 수 있다. 등록 화면은 HTTPS로만, 서버는 비밀 키를 암호화해 저장한다. 해시로는 저장할 수 없다(계산에 원본이 필요하다) |
| 6자리를 맞힐 수 있나? | 경우의 수는 100만이고 30초마다 바뀐다. 그래도 **시도 횟수 제한**이 없으면 의미가 줄어든다. 실패 횟수로 잠그고, 이미 쓴 코드는 다시 받지 않는다 |
| 피싱은? | 막지 못한다. 가짜 사이트가 비밀번호와 코드를 받아 30초 안에 진짜 사이트에 넣으면 통과한다 |

SMS 코드는 번호 이동·유심 복제 공격에 약해 TOTP보다 약한 선택지다.

## 패스키: 비밀을 공유하지 않는 로그인

**패스키(passkey)** 는 FIDO2·WebAuthn 표준의 공개키 자격 증명이다. 비밀번호와 TOTP는 모두 **서버와 사용자가 같은 비밀을 나눠 갖는다**는 약점이 있다. 패스키는 서버에 공개키만 둔다.

```text
[등록]
서버 → 브라우저: 챌린지(난수), 사이트 ID(rp.id = example.com)
기기(인증기): 생체·PIN으로 사용자 확인 → 이 사이트 전용 키 쌍 생성
기기 → 서버: 공개키 + 자격 증명 ID (개인키는 기기 밖으로 나가지 않는다)

[로그인]
서버 → 브라우저: 새 챌린지
기기: 생체·PIN으로 잠금 해제 → 개인키로 (챌린지 + 출처 정보) 서명
서버: 저장된 공개키로 서명 검증 → 로그인
```

| 성질 | 의미 |
| --- | --- |
| 서버에 비밀이 없다 | DB가 유출돼도 공개키뿐이라 로그인에 쓸 수 없다 |
| 피싱에 강하다 | 브라우저가 서명에 실제 도메인을 넣는다. 가짜 도메인에서는 그 사이트용 키가 아예 쓰이지 않는다 |
| 재사용 불가 | 매번 새 챌린지에 서명하므로 가로챈 응답을 다시 써도 소용없다 |
| 한 번에 두 요소 | 기기(가진 것) + 생체·PIN(나 자신·아는 것) |

- 키 쌍은 **기기가 만든다.** 서버가 주는 것은 챌린지와 사이트 정보뿐이다.
- **동기화 패스키**는 iCloud 키체인·Google 비밀번호 관리자 같은 계정 저장소를 통해 사용자의 여러 기기에 퍼진다. **기기 결합 패스키**는 보안 키처럼 한 기기에만 있다. 동기화는 편의를, 기기 결합은 통제를 얻는다.
- 다른 기기의 패스키는 QR 코드를 찍고 블루투스로 근접을 확인하는 교차 기기 인증으로 쓴다.
- 웹 쪽 구현(자동 완성 UI, `autocomplete="username webauthn"`)은 [[sign-in-sign-up-forms|로그인·가입 폼과 인증 입력]]에 있다.

## 고르는 기준

| 방식 | 피싱 저항 | 서버 유출 시 | 사용자 부담 |
| --- | --- | --- | --- |
| 비밀번호만 | 없다 | 해시 대입 위험 | 기억 |
| 비밀번호 + SMS | 없다 | 해시 대입 위험 | 문자 대기, 유심 공격 |
| 비밀번호 + TOTP | 없다 | TOTP 비밀 키까지 새면 위험 | 앱에서 코드 옮기기 |
| **패스키** | 있다 | 공개키뿐이라 안전 | 생체·PIN 한 번 |

## 정리

- MFA는 서로 다른 종류의 증거를 요구한다.
- TOTP는 공유한 비밀 키 + 현재 시각으로 양쪽이 같은 코드를 계산한다. 시도 횟수 제한과 비밀 키 암호화 저장이 필수이고, 피싱은 막지 못한다.
- 패스키는 사이트마다 기기에서 만든 키 쌍으로 챌린지에 서명한다. 서버에 비밀이 없고 도메인에 묶여 피싱에 강하다.
- 새로 만드는 서비스는 패스키를 기본으로, TOTP를 대안으로 둔다.
