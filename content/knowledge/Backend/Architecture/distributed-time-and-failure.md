## 분산 시스템이 어려운 이유

분산 시스템은 네트워크로 연결된 여러 컴퓨터가 하나의 시스템처럼 동작하는 것이다. 어려움은 두 가지 물리적 현실이 겹치는 데서 나온다.

| 현실 | 뜻 | 결과 |
| --- | --- | --- |
| **비동기(asynchrony)** | 메시지는 반드시 시간이 걸려 도착하고, 얼마나 걸릴지 상한이 없다 | 상대가 느린 것인지 죽은 것인지 구별할 수 없다 |
| **부분 장애(partial failure)** | 부품 일부만 고장 난다. 나머지는 계속 돈다 | 「전부 성공 아니면 전부 실패」를 가정할 수 없다 |

단일 프로세스 안에서는 함수 호출이 실패하면 즉시 알 수 있다. 원격 호출은 요청이 안 갔는지, 처리됐는데 응답만 잃었는지, 아직 처리 중인지 모른다. 그래서 재시도·멱등성·타임아웃이 분산 설계의 기본 부품이 된다.

## 분산 컴퓨팅의 8가지 착각

1994년 Peter Deutsch가 Sun에서 일곱 가지를 정리했고, 1997년 James Gosling이 여덟 번째를 더했다. 처음 분산 애플리케이션을 만드는 사람이 거의 반드시 하는 가정이며, 모두 틀린다.

| 착각 | 현실 | 설계 대응 |
| --- | --- | --- |
| 1. 네트워크는 믿을 만하다 | 스위치·전원·케이블·소프트웨어가 고장 나고, 외부 파트너 쪽은 통제할 수 없다 | 재시도, 중요한 메시지 확인 응답(ack), 중복 제거나 **멱등 메시지**, 순서에 의존하지 않기, 무결성 검증 |
| 2. 지연은 0이다 | 빛의 속도가 하한이다. 유럽↔미국 왕복은 처리 시간을 빼도 최소 약 30ms다. 대역폭이 크게 느는 동안 지연은 거의 줄지 않았다 | 원격 호출 횟수를 줄이고 한 번에 많이 보낸다. 원격 객체를 로컬처럼 잘게 부르는 「네트워크 투명성」을 경계한다 |
| 3. 대역폭은 무한하다 | 보낼 데이터도 같이 늘고, 패킷 손실이 처리량을 깎는다. 왕복 40ms·손실 0.1%·MSS 1460바이트면 TCP 처리량 상한은 약 6.5Mbps다 | 메시지 크기를 제한한다. 2번(큰 메시지)과 균형을 잡는다 |
| 4. 네트워크는 안전하다 | 경계 방어만 믿으면 한 번 뚫릴 때 내부가 다 열린다 | 처음부터 위협 모델링, 계층별 방어(제로 트러스트) |
| 5. 토폴로지는 바뀌지 않는다 | 서버가 추가·제거되고 라우팅이 바뀌며, 클라이언트는 이동한다 | 특정 IP·경로에 묶이지 않는다. DNS 이름, 서비스 디스커버리 |
| 6. 관리자는 한 명이다 | DB·네트워크·클라우드·파트너사마다 관리자가 다르고 정책(포트, 권한, 할당량)이 다르다 | 진단·모니터링 도구 제공, 계약(API)의 하위 호환 |
| 7. 전송 비용은 0이다 | 직렬화(marshaling)에 CPU와 시간이 들고, 네트워크 운영에 돈이 든다 | 직렬화 비용을 지연 예산에 넣는다. 클라우드의 데이터 전송(egress) 요금을 설계에 넣는다 |
| 8. 네트워크는 균질하다 | OS·언어·장비·프로토콜이 섞여 있다 | 독점 프로토콜 대신 표준 형식(HTTP, JSON, Protocol Buffers) |

## 장애는 일상이다

규모가 커지면 드문 장애도 매일 일어난다. MTBF(평균 고장 간격)가 30년인 아주 튼튼한 서버도 1만 대를 모으면 **하루에 한 대꼴로 죽는다.** 그래서 대규모 시스템은 장애 허용 소프트웨어를 피할 수 없다.

Google이 2009년에 공개한 「새 클러스터의 전형적인 첫해」는 이 규모 감각을 보여 준다.

| 사건 | 빈도 | 영향 |
| --- | --- | --- |
| 개별 머신 고장 | 약 1,000회 | 한 대씩 |
| 하드 디스크 고장 | 수천 회 | 연간 디스크의 1~5%가 죽는다 |
| 랙 고장 | 약 20회 | 40~80대가 즉시 사라지고 1~6시간 뒤 복구 |
| 랙 이상(패킷 손실 50%) | 약 5회 | 죽지도 살지도 않은 상태가 가장 다루기 어렵다 |
| PDU(배전 장치) 고장 | 약 1회 | 500~1,000대가 한꺼번에 사라지고 약 6시간 |
| 과열 | 약 0.5회 | 대부분을 5분 안에 끄고 복구에 1~2일 |
| 라우터 재시작·고장, DNS 끊김 | 수십 회 | 짧은 연결 손실이 잦다 |

장애는 독립적이지 않고 **상관된다**(랙·전원·스위치 단위로 같이 죽는다). 그래서 복제본은 같은 랙·같은 전원에 두지 않는다. 대응 원칙은 이렇다.

- 카나리 요청, 다른 복제본·데이터센터로 페일오버, 이상한 백엔드를 감지해 실요청에서 빼기.
- 일부가 고장 나도 **에러 페이지보다 제한된 기능**을 보여 준다(우아한 성능 저하).
- 모든 서버가 상태 페이지, 메트릭, 요청 샘플, 온라인 프로파일링을 내보내 「느리면 왜 느린지」 알 수 있게 한다.
- 평균뿐 아니라 p99 꼬리 지연을 본다. 중복 요청이나 타임아웃으로 꼬리를 줄인다.

장애 감지(하트비트, 타임아웃)와 이중화 구성은 [[high-availability-redundancy|고가용성 이중화 구조와 장애 감지]]에 있다.

## 전역 「지금」은 없다

정보는 빛보다 빨리 움직이지 못하므로 두 컴퓨터가 같은 순간을 동시에 알 수 없다. 1나노초에 전기가 가는 거리는 약 30cm다.

NTP·GPS·원자시계로 시계를 맞출 수는 있지만 **오차를 없애지는 못한다.** 시계 자체가 온도·부하·전력에 따라 빨라지고 느려지며, 같은 랙의 위아래 서버끼리도 다르게 흐른다. 가장 공들인 사례인 Google Spanner도 GPS와 원자시계를 써서 시계 오차를 1~7ms 수준으로 묶을 뿐이다. 그래서 Spanner의 TrueTime API는 현재 시각을 한 점이 아니라 `[가장 이른, 가장 늦은]` **구간**으로 돌려준다. 불확실성을 숨기지 않고 드러내는 설계다.

여기에 장애가 더해지면 원리적인 한계가 생긴다.

| 결과 | 내용 |
| --- | --- |
| **FLP 불가능성**(1985) | 메시지 지연에 상한이 없는 비동기 모델에서는 프로세스 하나만 멈출 수 있어도 결정적 합의 알고리즘이 항상 끝난다고 보장할 수 없다 |
| **CAP 정리** | 네트워크 분할 중에는 완벽한 일관성과 완벽한 가용성을 함께 가질 수 없다 → [[database-models\|데이터베이스 모델의 CAP 정리]] |

불가능성 결과는 **특정 시스템 모델 안에서의 결론**이다. 「이 제품은 분할 중에도 일관되고 늘 가용하다」 같은 주장을 걸러 내는 잣대로 쓰되, 모델의 가정을 함께 알아야 한다. 실제 합의 프로토콜(Paxos, Raft)은 메시지 손실·노드 중단이 있는 세계에서도 **안전성**(서로 다른 결정을 내리지 않음)은 지키고, **진행**(결국 결정함)은 네트워크가 안정된 동안에만 보장하는 식으로 이 한계를 비켜 간다.

## 사건의 순서: happened-before와 논리 시계

물리 시계를 믿을 수 없다면 「무엇이 먼저였나」를 어떻게 정할까. Lamport는 시간을 **인과 관계**로 다시 정의했다.

### happened-before (→)

| 규칙 | 뜻 |
| --- | --- |
| 같은 프로세스 | 같은 프로세스에서 a가 b보다 먼저 일어나면 a → b |
| 메시지 | a가 메시지를 보낸 사건이고 b가 그 메시지를 받은 사건이면 a → b |
| 이행성 | a → b이고 b → c이면 a → c |

a → b도 b → a도 아니면 두 사건은 **동시적(concurrent)** 이다. 동시적이라는 말은 같은 시각이라는 뜻이 아니라 **서로 영향을 줄 수 없었다**는 뜻이다. 이 순서는 전체가 아닌 부분 순서(partial order)다. 특수 상대성 이론에서 관찰자마다 사건의 선후가 달라도 인과 순서만은 모두 같은 것과 같은 구조다.

### Lamport 논리 시계

각 프로세스가 정수 카운터 하나를 들고 다음 두 규칙을 지킨다.

```text
1. 사건이 일어날 때마다 C = C + 1
2. 메시지를 보낼 때 C를 함께 보낸다(T).
   받은 쪽은 C = max(C, T) + 1
```

그러면 **a → b이면 C(a) < C(b)** 가 보장된다. 시간이 같으면 프로세스 ID로 순서를 깨서 모든 사건의 **전체 순서**(total order)를 만든다.

- 역은 성립하지 않는다. C(a) < C(b)라고 a → b인 것은 아니다. 동시적인 사건도 숫자는 어느 한쪽이 작다.
- 인과 관계를 정확히 판별하려면 프로세스마다 카운터 배열을 들고 다니는 **벡터 시계**(vector clock)를 쓴다. 두 벡터를 비교해 「앞」, 「뒤」, 「동시」를 가린다. 버전 벡터는 같은 아이디어를 복제본 충돌 감지에 쓴 것이다.
- 물리 시계와 논리 시계를 섞은 **하이브리드 논리 시계**(HLC)는 실제 시각에 가까운 값을 유지하면서 인과 순서도 지킨다. CockroachDB 같은 분산 DB가 쓴다.
- 시스템 밖의 사건(사람이 전화로 알려 준 순서 등)은 논리 시계가 모른다. 외부 사건까지 맞추려면 동기화된 물리 시계가 필요하다.

### 전체 순서 = 어떤 분산 시스템이든 구현하는 법

모든 노드가 같은 순서로 같은 명령을 처리하면 같은 상태에 도달한다. 이것이 **상태 기계 복제**(state machine replication)다. 논문은 이를 분산 상호 배제(누가 먼저 자원을 쓰나) 예로 보였고, 오늘날 Raft·Paxos 기반 시스템(etcd, ZooKeeper, Kafka KRaft)이 같은 원리로 로그 순서를 합의한다.

## 조율의 비용과 피하는 법

합의 프로토콜(Paxos, Viewstamped Replication, Zab, Raft)은 논리적인 「지금」을 만들어 주지만 **계속 통신해야 한다.** 모든 사건의 순서를 조율하면 응답 지연은 최소 시스템 안 왕복 한 번(메시지 두 번)보다 짧아질 수 없고, 장애 중에는 진행이 멈출 수도 있다. 그래서 성능이 중요한 시스템은 「얼마나 적은 조율로 놀랍지 않은 동작을 줄 수 있나」를 찾는다.

| 방법 | 원리 | 대가 |
| --- | --- | --- |
| 합의(Raft, Paxos) | 과반이 같은 순서에 동의 | 왕복 지연, 과반이 살아 있어야 진행 |
| 하이브리드 논리 시계, TrueTime | 시계 불확실성을 명시하고 그만큼 기다리거나 구간으로 다룬다 | 불확실성 구간만큼 대기 |
| **CRDT**(충돌 없는 복제 데이터 타입) | 연산이 교환·결합·멱등이면 받은 순서와 상관없이 같은 상태가 된다(강한 최종 일관성) | 표현할 수 있는 연산이 제한된다 → [[collaborative-editing\|실시간 공동 편집: OT와 CRDT]] |
| 마지막 쓰기 승리(LWW) | 타임스탬프가 큰 쓰기를 남긴다 | 「마지막」이 정의되지 않으므로 **동시 쓰기 중 일부가 예측 불가능하게 사라진다** |

- 클러스터 관리(리더 선출, 멤버십)를 직접 만든 조율 코드로 풀지 않는다. 검증된 합의 구현(etcd, ZooKeeper)을 쓴다.
- 실제 데이터베이스가 분할 상황에서 약속한 일관성을 지키는지는 **Jepsen**처럼 네트워크를 일부러 끊고 이력을 검증하는 테스트로 확인한다. 이런 분석([aphyr.com의 Jepsen 글 모음](https://aphyr.com/tags/jepsen))에서 여러 DB가 문서에 적힌 보장을 어긴 사례가 드러났다.

## 정리

- 분산 시스템의 본질적 어려움은 **비동기와 부분 장애**다. 원격 호출은 실패 이유를 알 수 없다.
- 8가지 착각(신뢰성, 지연 0, 무한 대역폭, 보안, 고정 토폴로지, 단일 관리자, 전송 비용 0, 균질성)은 모두 틀린다. 재시도·멱등성·큰 메시지·표준 형식으로 대응한다.
- 규모가 커지면 장애는 매일 일어나고 서로 상관된다. 장애를 정상 경로로 설계한다.
- 전역 「지금」은 없다. 최선의 시계도 ms 단위 오차가 있으므로 순서는 논리 시계(Lamport, 벡터, HLC)나 합의로 정한다.
- 조율은 비싸다. 꼭 필요한 곳에만 합의를 쓰고, 나머지는 CRDT·멱등 연산처럼 순서가 필요 없는 설계로 뺀다.
