> Andrew Chan의 「[Crawling a billion web pages in just over 24 hours, in 2025](https://andrewkchan.dev/posts/crawler.html)」(2025)를 바탕으로 재구성한 노트다.

## 목표와 제약

크롤러가 웹이라는 그래프를 어떻게 탐색하는지(URL 프런티어, 재크롤링, PageRank)는 [[web-search-engine|웹 검색엔진의 동작]]에 있다. 이 노트는 그 크롤러를 **정해진 시간과 예산 안에 실제로 돌리는** 설계 사례다. 2012년 Michael Nielsen이 비슷한 크롤링을 한 뒤로 이런 기록이 드물어, 하드웨어와 웹이 바뀐 지금 병목이 어디로 옮겼는지 확인하려는 실험이었다.

| 항목 | 결과 |
| --- | --- |
| 페이지 수 | 약 10억 500만 |
| 시간 | 노드당 평균 활동 시간 25.5시간 |
| 비용 | 약 462달러 (2012년 Nielsen의 크롤링은 580달러 남짓) |

| 제약 | 내용 |
| --- | --- |
| HTML만 | JavaScript를 실행하지 않는다. HTML을 그대로 파싱해 `<a>` 태그의 링크만 프런티어에 넣는다. 옛 크롤링과 같은 조건으로 비교하기 위해서다 |
| **예의**(politeness) | robots.txt를 지키고, 연락처를 넣은 User-Agent를 쓰고, 요청이 오면 제외 목록에 도메인을 더한다. 동네 작은 사이트를 피하려 상위 100만 도메인 시드 목록 안에서만 돌고, 같은 도메인에는 최소 70초 간격을 둔다 |
| 장애 허용 | 멈췄다가 이어서 돌 수 있어야 한다. 크롤링은 웹의 **표본**이므로, 복구할 때 방문 기록 일부를 잃는 것은 괜찮다 |

robots.txt를 무시하고, 다른 에이전트로 위장하고, 같은 엔드포인트를 쉴 새 없이 두드리는 크롤러가 사이트 관리자에게 큰 고통을 준다. 그래서 예의가 첫 번째 제약이다. AI 학습용 수집이 늘면서 웹도 방어를 갖추기 시작했고, Cloudflare는 크롤링에 값을 매기는 pay-per-crawl을 실험 중이다.

## 설계: 기능별로 나누지 않는다

시스템 설계 면접의 교과서 답은 파싱, 페칭, 저장소, 크롤 상태를 **각각 다른 머신 풀로** 나눈다. 이 크롤러는 반대로, 모든 기능을 담은 **독립 노드 12개**가 도메인을 나눠 맡았다. 예산이 적어 작게 시작해 한 머신에 최대한 담은 뒤 늘리는 편이 맞았고, 원래 목표도 단일 머신 성능을 끝까지 짜내는 것이었다.

```text
노드 하나 (i7i.4xlarge: 16 vCPU, 128GB RAM, 25Gbps, 인스턴스 스토리지 3,750GB)
┌─────────────────────────────────────────────────────┐
│ Redis 1개: 크롤 상태                                   │
│   · 도메인별 프런티어 (가져올 URL 목록)                    │
│   · 준비 큐: 다음에 가져와도 되는 시각순으로 정렬한 도메인     │
│   · 방문한 URL + 메타데이터 + 저장 경로                    │
│   · 본 URL 블룸 필터                                    │
│   · 도메인 메타데이터 (제외 여부, robots.txt 내용과 만료 시각) │
│   · 파싱 큐                                            │
│                                                       │
│ 페처 9개 ──(가져온 HTML)──→ 파싱 큐 ──→ 파서 6개          │
│    ↑                                   │ 링크 추출       │
│    └──── 도메인 프런티어 ←─────────────────┘ 본문 저장 → 디스크│
└─────────────────────────────────────────────────────┘
× 12 노드. 시드 도메인을 노드별로 나누고, 노드 사이 통신은 없다
```

| 부품 | 동작 |
| --- | --- |
| **준비 큐** | 다음 요청 가능 시각순으로 도메인을 정렬한다. 페처는 준비된 도메인을 꺼내, 그 도메인의 프런티어에서 URL 하나를 가져오고, 도메인을 새 시각으로 다시 넣는다. 도메인당 지연이 자료 구조에 들어 있는 셈이다 |
| **블룸 필터** | URL이 프런티어에 이미 들어갔는지 빠르게 확인한다. 방문 기록과 따로 두는 이유는 프런티어에 있지만 아직 가져오지 않은 URL도 거르기 위해서다. 가끔 처음 보는 URL을 봤다고 잘못 판정하지만, 표본이라 괜찮다 |
| **페처** | 프로세스 하나가 asyncio로 코어 하나에 비동기 작업자 6,000~7,000개를 돌린다. I/O를 기다리는 일이라 동시성을 크게 올릴 수 있다 |
| **파서** | 프로세스당 비동기 작업자 80개. 파싱은 CPU를 쓰는 일이라 이 정도로 CPU가 찬다 |
| **LRU 캐시** | 페처와 파서가 robots.txt 같은 도메인 정보를 들고 있어 Redis 부하를 줄인다 |
| **지표** | 각 노드의 첫 페처가 리더가 되어 로컬 Prometheus에 지표를 쓴다. 실제 시스템이라면 노드 전체가 지표 DB 하나를 쓰는 편이 낫다 |

asyncio 같은 사용자 공간 멀티태스킹은 문맥 전환을 피해 높은 동시성을 얻는다. 원리는 [[event-loop-server|비동기 서버의 이벤트 루프]]에 있다.

### 왜 노드 12개인가

- 시드 도메인을 너무 잘게 나누면 **핫 샤드**가 생긴다. 인기 도메인을 맡은 노드는 일이 많고 다른 노드는 일찍 끝난다.
- Redis 하나에 붙는 페처·파서는 15개에서 멈췄다. Redis 초당 연산 수가 한계에 가까워졌기 때문이다.

### S3 대신 인스턴스 스토리지

교과서 답은 S3에 저장하라고 한다. 하지만 S3는 저장 용량뿐 아니라 **요청마다** 값을 받는다. 10억 페이지 × 250KB(250TB)를 하루만 들고 있어도 PUT 요청 비용이 크게 붙어, 계산하면 표준 등급 약 5,000달러, Express 등급 약 2,000달러가 나온다. 크롤링 전체 비용보다 한 자릿수 크다. PUT 비용을 빼고 하루치 보관료만 따져도 경쟁이 안 됐다. 그래서 스토리지 최적화 인스턴스(i7i)의 로컬 NVMe에 저장하고, 페이지를 잘라 용량을 맞췄다. 실제 크롤러라면 자르기보다 snappy 같은 빠른 압축을 쓰는 편이 낫다.

### 시도했다 버린 것

| 시도 | 결과 |
| --- | --- |
| SQLite·PostgreSQL에 크롤 상태 저장 | 자료 구조는 단순한데 프런티어 질의를 빠르게 만들기가 너무 복잡했다. 최근 크롤러 대부분이 Redis 같은 인메모리 저장소를 쓰는 이유다 |
| 거대한 단일 머신(i7i.48xlarge, 사실상 4xlarge 12대를 붙인 것)으로 수직 확장 | 네트워크는 충분했다. 모든 페이지가 1MB라도 하루 10억 페이지에 약 92Gbps면 된다. 그런데 프로세스 묶음(pod)을 독립으로 돌려도 전체가 초당 1,000페이지 남짓, 최종 클러스터의 노드 하나보다 조금 나은 수준이었다. 하드웨어보다 운영체제 자원 같은 소프트웨어 쪽 한계로 보인다. 시간이 다 돼 수평 확장으로 바꿨다 |

## 병목이 옮겨 갔다

| 병목 | 2012년 무렵 | 2025년 |
| --- | --- | --- |
| 네트워크 대역폭 | 학교 네트워크를 다 쓰지 않도록 크롤링 속도를 늦춰야 했다 | 노드당 25Gbps 중 약 8Gbps만 썼다. 데이터 센터 대역폭은 넘친다 |
| DNS | CMU의 크롤링 프로젝트에서 DNS 조회 처리량이 병목이었다 | 상위 100만 도메인만 돌아서인지 문제가 되지 않았다 |
| **파싱** | 쿼드코어 머신으로 충분했다 | 가장 큰 병목. 페이지가 커졌기 때문이다 |
| **SSL** | HTTPS가 드물었다 | 핸드셰이크 계산이 전체 CPU 시간의 약 25%. 네트워크보다 CPU가 먼저 찬다 |

### 파싱: 페이지가 커졌다

처음에는 파서 2개가 페처 1개(작업자 1,000개, 초당 55페이지, 그마저 일부는 놀면서)를 겨우 따라갔다. 2012년의 더 약한 쿼드코어 머신보다 처리량이 낮았다. 2012년에 인기 있던 lxml을 그대로 썼는데, 그사이 페이지가 커졌다.

- 측정한 비압축 페이지 크기 중앙값은 138KB, 평균은 242KB였다. 2012년 추정 평균 51KB의 몇 배다. (Web Almanac 2024의 중앙값 18KB와 차이가 큰데, 상위 도메인만 돌았기 때문일 수 있다.)
- **파서 교체**: HTML5 전용 C++ 파서 Lexbor를 감싼 selectolax로 바꿨다. 홍보처럼 30배는 아니었지만 크게 빨라졌다.
- **자르기**: 파서에 넘기기 전에 250KB로 잘랐다. 평균보다 크고 중앙값의 두 배 가까이라 대부분의 페이지는 통째로 들어간다.

그 결과 파서 프로세스 하나가 초당 약 160페이지를 처리했고, 노드마다 페처 9개와 파서 6개로 초당 약 950페이지를 크롤링했다.

### SSL: 페칭은 더 쉬워지고 더 어려워졌다

대역폭과 DNS는 쉬워졌지만, HTTPS가 기본이 되면서 SSL 핸드셰이크가 프로파일에서 가장 비싼 함수 호출이 됐다. Firefox에서 HTTPS로 열리는 페이지는 2014년 30%에서 2025년 80% 이상이 됐다. 그래서 **페칭도 네트워크가 아니라 CPU에 묶였다.** HTTPS 연결 과정은 [[https|HTTPS와 TLS]]에 있다.

## 큰 크롤링에서 생긴 일

본 크롤링 전 가장 큰 실험은 작은 머신 한 대로 몇 시간 돌린 것이었다. 규모가 열 배 넘게 뛰자 예상 못 한 문제가 이어졌고, 일요일 하루를 해 뜰 때부터 질 때까지 자기 크롤링의 당직을 서며 지표를 보고 고쳤다.

| 문제 | 내용 |
| --- | --- |
| 운영 실수 | 로그 로테이션을 설정하지 않아 루트 볼륨이 꽉 찼다 |
| **프런티어 메모리 폭증** | 프런티어를 모두 메모리에 둔 설계였다. 방문 기록과 HTTP 클라이언트의 메모리는 10억 페이지 기준으로 계산해 두었지만, 인기 도메인 몇 개의 프런티어가 URL 수억~수십억 개, 수십 GB로 불어나는 것은 예상하지 못했다. 중간쯤부터 노드가 하나씩 쓰러져, 응답 없는 머신을 재시작하고 프런티어를 잘라 냈다. 장애 허용 설계 덕에 재개는 쉬웠다 |

크롤러를 끝없이 붙잡아 두는 함정 사이트(tarpit)가 아닐까 의심했지만, 대부분은 yahoo.com, wikipedia.org처럼 링크가 아주 많은 인기 사이트였다. 처음 보기에 이상한 쇼핑몰 같던 「cosplayfu」도 찾아보니 정상 사이트였다. 가장 문제가 된 도메인은 제외 목록에 넣었다.

## 교과서 설계와 비교

시스템 설계 면접 해설(HelloInterview)은 「페칭 전용 머신 5대로 5일에 100억 페이지」를 대충 어림했다. 머신당 400Gbps에 30% 사용률을 가정한 숫자다.

- 사용률 가정은 맞았다. 25Gbps 중 약 8Gbps, 32%를 썼다.
- 이 크롤러는 16코어 중 9개만 페칭에 썼다. 단순 비례로 보면 페칭 전용 머신 약 6.75대로 하루 10억 페이지가 가능하고, 두 배 크기 머신이면 5일에 100억 페이지에 가깝다.
- 교과서 숫자는 크게 틀리지 않지만, 거기에 이르려면 이 크롤러보다 더 많은 최적화가 필요하다.

## 남은 과제

- **JavaScript 렌더링**: JS 없이도 웹의 상당 부분이 여전히 링크로 이어져 있었다. 그 덕에 ancientfaces.com 같은 재미있는 사이트도 발견했다. 하지만 GitHub처럼 크롤링되는 사이트도 본문이 마크업이 아니라 클라이언트에서 그릴 거대한 문자열로 들어 있는 경우가 많았다. 페이지를 실제로 렌더링해야 하는 크롤링은 같은 규모라도 훨씬 비쌀 것이다. 렌더링 방식과 크롤러의 관계는 [[seo-basics|SEO 기초]]에 있다.
- **수집한 웹의 모양**: 살아 있는 URL과 죽은 URL의 비율, HTML과 멀티미디어의 비율 같은 기본 통계도 아직 분석하지 않았다.

## 정리

- 하루 10억 페이지는 노드 12대, 약 460달러로 된다. 예의(robots.txt, 도메인당 지연, 시드 제한)가 첫 번째 제약이다.
- 기능별 머신 풀 대신 도메인 샤드마다 모든 기능을 담은 독립 노드로 갔다. 크롤 상태는 Redis(프런티어, 준비 큐, 블룸 필터)에 둔다.
- 저장은 요청당 과금되는 S3보다 인스턴스 로컬 스토리지가 한 자릿수 싸다.
- 병목은 네트워크·DNS에서 **CPU**로 옮겨 갔다. 커진 페이지의 파싱과 SSL 핸드셰이크 때문이다. 빠른 파서와 페이지 자르기로 푼다.
- 메모리 계산은 평균이 아니라 꼬리를 본다. 인기 도메인 몇 개의 프런티어가 전체를 쓰러뜨린다.
