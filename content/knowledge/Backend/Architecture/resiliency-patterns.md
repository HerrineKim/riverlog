## 복원력이란

큰 장애는 대개 작은 오류에서 시작한다. 한 의존성이 느려지면 호출자의 스레드가 묶이고, 묶인 호출자가 또 그 호출자를 느리게 만들며 눈덩이처럼 커진다(연쇄 장애, cascading failure). **복원력(resiliency)** 패턴은 실패를 없애는 것이 아니라 **실패가 번지는 범위를 줄이는** 장치다.

이 패턴들은 혼자 쓰지 않는다. 타임아웃이 있어야 재시도가 의미 있고, 재시도에는 서킷 브레이커와 백오프가 있어야 상대를 죽이지 않는다.

## 여덟 가지 패턴

| 패턴 | 하는 일 | 막는 것 | 한계 |
| --- | --- | --- | --- |
| 타임아웃(timeout) | 정해진 시간 안에 응답이 없으면 포기한다 | 느린 의존성에 자원이 무한히 묶이는 것 | 너무 짧으면 정상 요청도 끊는다. 하류 타임아웃은 상류보다 짧게 잡는다 |
| 재시도(retry) | 일시적 실패를 다시 시도한다 | 순간적인 네트워크 오류로 인한 실패 | 멱등하지 않은 작업은 중복 실행된다. 백오프 없이 하면 재시도 폭풍이 된다 |
| 서킷 브레이커(circuit breaker) | 실패율이 임계치를 넘으면 호출 자체를 막고 즉시 폴백을 준다 | 죽은 의존성을 계속 두드려 복구를 방해하는 것 | 임계치와 반열림 시험량을 잘못 잡으면 너무 쉽게 열리거나 늦게 닫힌다 |
| 속도 제한(rate limiting) | 클라이언트별 요청 빈도를 제한한다. 토큰 버킷(버스트 허용)과 리키 버킷(일정 속도로 평탄화)이 대표적이다 | 한 클라이언트가 자원을 독차지하는 것 | 정상 사용자의 순간 폭주도 막을 수 있다 |
| 부하 차단(load shedding) | 서버가 감당할 수 없을 만큼 요청이 오면 일부를 **일찍** 거절한다. 중요도가 낮은 요청부터 버린다 | 모든 요청이 다 같이 느려져 모두 실패하는 것 | 무엇을 버릴지 우선순위가 정해져 있어야 한다 |
| 벌크헤드(bulkhead) | 의존성별로 스레드 풀·커넥션 풀을 나눈다. 배의 격벽처럼 한 칸이 잠겨도 나머지는 뜬다 | 의존성 하나의 장애가 공용 자원을 다 먹는 것 | 풀이 잘게 나뉘면 전체 자원 활용률이 떨어진다 |
| 배압(back pressure) | 소비자가 처리 속도를 넘는 입력을 받지 않고 생산자에게 늦추라고 알린다 | 큐·메모리가 무한히 쌓이는 것 | 생산자도 늦출 방법(버퍼, 거절)을 갖고 있어야 한다 |
| 크래시 허용(let it crash) | 이상한 상태를 고치려 하지 않고 프로세스를 죽인 뒤 감독자가 깨끗한 상태로 다시 띄운다(Erlang 감독 트리) | 오염된 상태로 계속 도는 것 | 재시작이 빠르고 상태가 밖에 있어야 한다 |

서킷 브레이커의 세 상태(Closed·Open·Half-Open)와 구현 라이브러리는 [[high-traffic-resilience|대규모 트래픽에서 서비스를 지키는 설계]]에 있다.

## 재시도 전략: 백오프와 지터

재시도 사이의 대기 시간을 어떻게 늘리느냐에 따라 네 가지로 나뉜다.

| 전략 | 대기 시간 | 장점 | 단점 |
| --- | --- | --- | --- |
| 선형 백오프(linear) | 1s, 2s, 3s, 4s … 일정하게 늘린다 | 단순하다 | 많은 클라이언트가 같은 박자로 재시도해 부하가 몰린다 |
| 선형 + 지터(linear jitter) | 선형 대기에 무작위 값을 더한다 | 재시도 시점이 흩어진다 | 기본 간격이 천천히 늘어 고부하에서는 부족하다 |
| 지수 백오프(exponential) | 1s, 2s, 4s, 8s … 두 배씩, 상한까지 | 상대 시스템의 부하를 빠르게 줄인다 | 금방 풀릴 문제도 오래 기다린다 |
| 지수 + 지터(exponential jitter) | 지수 대기에 무작위를 더하거나 곱한다 | 부하 감소와 시점 분산을 둘 다 얻는다 | 지터가 크면 불필요하게 오래 기다리기도 한다 |

```text
지수 + 지터의 흔한 형태 (full jitter)
  sleep = random(0, min(상한, 기본값 × 2^시도횟수))
```

**기본값은 지수 백오프 + 지터 + 최대 재시도 횟수**다. 지터가 없으면 같은 순간에 실패한 클라이언트들이 같은 순간에 다시 몰려와 복구 중인 서버를 또 쓰러뜨린다(thundering herd).

## 웹 요청 오류에 대처하는 규칙

| 상황 | 규칙 |
| --- | --- |
| 4xx (클라이언트 오류) | **재시도하지 않는다.** 같은 요청은 같은 이유로 또 실패한다. 단, 429(Too Many Requests)와 408(Request Timeout)은 예외로, `Retry-After`를 지키며 기다렸다 다시 보낸다 |
| 5xx (서버 오류) | 백오프를 두고 **조심스럽게** 재시도하고, 횟수에 상한을 둔다 |
| 타임아웃·연결 끊김 | 요청이 서버에 닿았는지 알 수 없다. 멱등한 요청만 재시도한다 |

클라이언트가 늘 얌전히 재시도한다는 보장은 없다. 그래서 **서버는 스스로를 지킨다.** 서버 앞에 흐름 제어 게이트웨이를 두고 속도 제한과 서킷 브레이커를 건다. 클라이언트의 백오프와 서버의 흐름 제어를 지나서도 남는 오류가 진짜 고쳐야 할 버그다.

## 멱등성: 재시도의 전제 조건

**멱등(idempotent)** 한 작업은 여러 번 실행해도 결과가 한 번 실행한 것과 같다. 재시도가 안전하려면 그 작업이 멱등해야 한다. HTTP 메서드별 멱등성은 [[rest-api|REST API 설계 원칙]]에 있다.

| 적용할 곳 | 막아야 할 것 | 흔한 구현 |
| --- | --- | --- |
| API 요청 | 재시도로 같은 작업이 두 번 실행되는 것 | 멱등 메서드(PUT·DELETE) 사용, POST에는 `Idempotency-Key` 헤더 |
| 결제 | 네트워크 오류 후 재시도로 두 번 청구되는 것 | 요청마다 고유 키를 받아 처리 결과를 저장하고, 같은 키가 오면 저장된 결과를 돌려준다 |
| 주문 | 주문 버튼 연타로 주문이 여러 건 생기고 재고가 여러 번 빠지는 것 | 클라이언트가 만든 주문 ID에 유니크 제약 |
| DB 작업 | 같은 트랜잭션을 다시 적용해 상태가 또 바뀌는 것 | 「+1」 같은 상대 변경 대신 「값을 X로」 같은 절대 변경, upsert |
| 계정 관리 | 가입 재시도로 계정이 둘 생기거나, 비밀번호 재설정이 여러 번 실행되는 것 | 이메일 유니크 제약, 재설정 토큰을 한 번만 쓰게 하기 |
| 메시지 처리 | 큐가 같은 메시지를 다시 배달해 두 번 처리되는 것 | 처리한 메시지 ID를 기록해 중복을 거르는 멱등 소비자 |

대부분의 메시지 큐는 「적어도 한 번(at-least-once)」 배달을 보장하므로, **소비자는 같은 메시지를 두 번 받는다고 가정하고** 만든다.

## 정리

- 복원력 패턴은 실패를 없애지 않고, 실패가 번지는 범위를 줄인다.
- 모든 원격 호출에는 타임아웃을 건다. 타임아웃 없는 재시도와 백오프 없는 재시도는 장애를 키운다.
- 재시도는 지수 백오프 + 지터 + 횟수 상한으로 한다. 4xx는 재시도하지 않는다.
- 재시도하려면 먼저 멱등하게 만든다. 결제·주문·메시지 소비는 고유 키로 중복을 거른다.
