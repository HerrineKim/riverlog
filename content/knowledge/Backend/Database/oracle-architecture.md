> 고려사이버대학교 「데이터베이스 설계구축」(2023-2학기) 강의 내용을 바탕으로 정리했다.

DB 성능을 가장 크게 좌우하는 것은 디스크 I/O다. Oracle의 구조는 거의 전부 "디스크를 덜 읽고, 커밋은 빠르게, 장애가 나도 되살릴 수 있게"라는 목표에서 나온다. MySQL·PostgreSQL도 같은 문제를 비슷한 부품으로 푼다. 이름만 다르다. 엔진 일반의 처리 흐름은 [[database-internals|DB 내부 구조]]에 있다.

## 인스턴스와 데이터베이스

Oracle에서 이 둘은 다른 말이다.

| 구분 | 무엇인가 | 수명 |
| --- | --- | --- |
| 인스턴스 | 메모리(SGA) + 백그라운드 프로세스 | 시작할 때 메모리를 받고, 종료하면 반납한다 |
| 데이터베이스 | 디스크에 있는 파일 묶음 | 인스턴스가 꺼져도 남는다 |

인스턴스가 데이터베이스를 "마운트하고 연다". 보통 1:1이지만 RAC(Real Application Clusters)는 여러 서버의 인스턴스가 하나의 데이터베이스를 함께 연다.

```text
 사용자 프로세스 ──▶ 서버 프로세스(PGA)
                          │
 ┌──────────── SGA (모든 세션이 공유) ─────────────┐
 │ 버퍼 캐시 │ 공유 풀 │ 리두 로그 버퍼 │ 대용량·자바 풀 │
 └───────────────────────────────────────────────┘
     │ DBWn          │ LGWR          CKPT·SMON·PMON …
     ▼               ▼
 데이터 파일      온라인 리두 로그 ──(ARCn)──▶ 아카이브 로그
            컨트롤 파일(구조와 체크포인트 위치 기록)
```

## 메모리: SGA와 PGA

**SGA(System Global Area)** 는 인스턴스 전체가 공유하는 메모리다. 클수록 디스크 대신 메모리에서 답할 수 있는 요청이 늘어난다.

| 영역 | 담는 것 | 비슷한 것 |
| --- | --- | --- |
| 데이터베이스 버퍼 캐시 | 데이터 파일에서 읽어 온 블록. LRU 계열 정책으로 자주 쓰는 블록을 남긴다 | InnoDB 버퍼 풀, PostgreSQL shared_buffers |
| 공유 풀 | 라이브러리 캐시(파싱된 SQL·PL/SQL과 실행 계획), 데이터 사전 캐시(테이블·권한 같은 메타데이터), 결과 캐시 | MySQL엔 실행 계획 공유 캐시가 없다 |
| 리두 로그 버퍼 | 변경 내역(어느 블록의 어디가 어떻게 바뀌었나). 곧 리두 로그 파일로 내려간다 | InnoDB 로그 버퍼, PostgreSQL WAL 버퍼 |
| 대용량 풀·자바 풀 | 백업·병렬 처리용 큰 메모리, JVM용 메모리 | |

**PGA(Program Global Area)** 는 서버 프로세스마다 따로 갖는 메모리다. 정렬·해시 조인 작업 공간과 세션 정보가 여기에 들어간다. 정렬이 PGA에 다 안 들어가면 임시 테이블스페이스(디스크)로 넘친다.

공유 풀 덕분에 같은 SQL을 다시 받으면 파싱과 최적화를 건너뛴다(소프트 파싱). 그래서 값을 문자열로 이어 붙인 SQL보다 바인드 변수를 쓴 SQL이 Oracle에서 특히 유리하다. 문장 모양이 같아야 캐시를 재사용하기 때문이다([[sql-basics#파라미터 바인딩과 Prepared Statement|Prepared Statement]]).

## 프로세스

| 프로세스 | 하는 일 |
| --- | --- |
| 사용자 프로세스 | 클라이언트 쪽. 애플리케이션이 접속할 때 생긴다 |
| 서버 프로세스 | 사용자 대신 SQL을 실행한다. 버퍼 캐시에 없는 블록이면 데이터 파일에서 읽어 와 캐시에 올린다 |
| DBWn (Database Writer) | 버퍼 캐시의 변경된(dirty) 블록을 데이터 파일에 쓴다. 커밋과 상관없이 나중에 몰아서 쓴다 |
| LGWR (Log Writer) | 리두 로그 버퍼를 온라인 리두 로그 파일에 쓴다. **커밋하면 반드시 이것부터** 끝낸다 |
| CKPT (Checkpoint) | 체크포인트 시점을 기록하고 DBWn에게 쓰기를 알린다 |
| SMON (System Monitor) | 인스턴스가 비정상 종료됐다가 다시 뜰 때 복구한다. 임시 세그먼트를 정리한다 |
| PMON (Process Monitor) | 죽은 사용자 세션의 잠금과 자원을 풀고 트랜잭션을 롤백한다 |
| ARCn (Archiver) | 다 쓴 리두 로그 파일을 아카이브 로그로 복사한다(아카이브 모드일 때) |
| RECO (Recoverer) | 분산 트랜잭션이 중간에 끊겼을 때 커밋이나 롤백으로 마무리한다 |
| MMON 등 | 성능 통계를 주기적으로 모아 AWR에 쌓는다 |

연결마다 서버 프로세스를 하나씩 두는 게 기본(전용 서버)이다. PostgreSQL도 연결당 프로세스, MySQL은 연결당 스레드다. 연결이 비싸므로 앞단에 [[connection-pool|커넥션 풀]]을 둔다.

## 커밋이 빠른 이유: 로그 먼저

SQL 한 문장이 데이터를 바꾸는 흐름은 이렇다.

1. 서버 프로세스가 필요한 블록을 버퍼 캐시에 올린다(없으면 디스크에서 읽는다).
2. 블록을 메모리에서 고치고, 변경 내역을 리두 로그 버퍼에 남긴다. 되돌릴 이전 값은 언두 세그먼트에 둔다.
3. `COMMIT`하면 LGWR가 리두 로그를 디스크에 쓴다. 이게 끝나면 커밋 완료다.
4. 고친 데이터 블록은 DBWn이 한참 뒤에 데이터 파일로 내린다.

데이터 파일은 여기저기 흩어진 블록을 임의 위치에 써야 하지만, 리두 로그는 순서대로 덧붙이기만 하면 된다. 그래서 커밋할 때는 로그만 순차로 쓰고, 무거운 데이터 쓰기는 미룬다. 그 사이에 장애가 나면 재시작할 때 리두 로그를 다시 적용해(롤 포워드) 커밋된 변경을 되살리고, 커밋 안 된 변경은 언두로 되돌린다. WAL과 회복의 일반 원리는 [[transaction|트랜잭션과 회복]]에 있다.

체크포인트는 "여기까지의 변경은 데이터 파일에 다 내려갔다"는 표시다. 체크포인트가 잦으면 복구는 빠르지만 쓰기가 늘고, 드물면 반대다.

## 물리 파일

| 파일 | 역할 |
| --- | --- |
| 데이터 파일 | 테이블·인덱스 같은 실제 데이터 |
| 온라인 리두 로그 파일 | 변경 기록. 여러 그룹을 돌려 쓰고, 꽉 차면 다음 그룹으로 넘어간다(로그 스위치) |
| 아카이브 리두 로그 | 재사용되기 전의 리두 로그 사본. 시점 복구(PITR)에 필요하다 |
| 컨트롤 파일 | DB 이름, 데이터 파일·리두 로그 위치, 체크포인트 정보. 잃으면 DB를 열 수 없어 보통 여러 벌 둔다 |
| 파라미터 파일(spfile) | 메모리 크기 같은 인스턴스 설정 |

## 논리 저장 구조

SQL에서 보는 테이블과 디스크의 파일 사이에 네 단계의 논리 단위가 있다.

```text
테이블스페이스 ─(1:N)─ 데이터 파일          ← 물리
   └ 세그먼트   테이블·인덱스 하나가 차지하는 공간
       └ 익스텐트  연속된 블록 묶음. 공간이 모자라면 하나씩 더 받는다
           └ 데이터 블록  I/O의 최소 단위(기본 8KB)
```

- **데이터 블록**: 크기는 DB를 만들 때 정한다(2~32KB). 크면 한 번에 많이 읽어 I/O 횟수가 줄지만, 몇 행만 필요할 때 낭비가 생기고 같은 블록을 두고 다투는 일이 늘어난다. 작으면 반대다. 분석용은 크게, OLTP는 기본값 근처를 쓴다.
- **익스텐트**: 블록을 하나씩 할당하면 데이터가 흩어진다. 연속된 블록을 묶어 주면 순차 읽기가 빨라진다.
- **세그먼트**: 테이블 하나, 인덱스 하나, 파티션 하나가 각각 세그먼트다. 한 세그먼트는 한 테이블스페이스 안에 있지만 그 안의 여러 데이터 파일에 걸칠 수 있다.
- **테이블스페이스**: 관리 단위. 용량을 미리 잡고 자동 확장 폭을 정한다. 테이블과 인덱스를 다른 테이블스페이스(다른 디스크)에 두어 I/O를 나누거나, 오래된 데이터를 읽기 전용 테이블스페이스로 옮겨 백업을 줄이는 식으로 쓴다.

| 기본 테이블스페이스 | 용도 |
| --- | --- |
| SYSTEM, SYSAUX | 데이터 사전과 내부 관리 정보 |
| UNDO | 롤백과 읽기 일관성에 쓰는 이전 값 |
| TEMP | 메모리에 못 담은 정렬·해시 중간 결과 |
| USERS | 사용자 객체의 기본 저장 위치 |

```sql
CREATE TABLESPACE ts_orders
  DATAFILE '/u01/oradata/orders01.dbf' SIZE 100M
  AUTOEXTEND ON NEXT 10M;

ALTER TABLESPACE ts_orders
  ADD DATAFILE '/u02/oradata/orders02.dbf' SIZE 100M;   -- 다른 디스크로 늘리기

-- 안의 객체와 참조 제약, 실제 파일까지 지운다. 되돌릴 수 없다
DROP TABLESPACE ts_orders INCLUDING CONTENTS AND DATAFILES CASCADE CONSTRAINTS;
```

## 스키마와 테이블 구조

Oracle에서 스키마는 사용자 계정과 1:1이다. `HR` 사용자가 만든 객체는 `HR` 스키마에 속하고, 다른 사용자는 `HR.EMPLOYEES`처럼 접두어를 붙이거나 동의어를 만들어 쓴다. 스키마 안의 객체(테이블·인덱스·뷰·시퀀스·동의어·프로시저 등)는 [[oracle-schema-objects|Oracle 스키마 객체]]에 정리했다.

테이블은 행을 저장하는 방식에 따라 두 가지다.

| 종류 | 저장 방식 | 맞는 곳 |
| --- | --- | --- |
| 힙 구조 테이블(기본) | 순서 없이 빈자리에 넣는다. 인덱스는 행 주소(ROWID)를 가리킨다 | 대부분 |
| 인덱스 구조 테이블(IOT) | 기본 키 순서의 B-트리 안에 행 자체를 저장한다 | 기본 키로만 찾는 작은 행, 범위 조회가 잦은 테이블 |

MySQL InnoDB의 테이블은 늘 IOT 방식(클러스터드 인덱스)이고, PostgreSQL은 늘 힙이다. 같은 설계가 DBMS마다 다르게 동작하는 이유 중 하나다([[index-design|인덱스 설계와 쿼리 튜닝]]).

## 에디션

Express Edition(XE)은 무료이고 CPU·메모리·저장 용량에 상한이 있어 학습·개인용으로 쓴다. Standard Edition 2는 중소 규모, Enterprise Edition은 파티셔닝·RAC 같은 고급 기능을 모두 갖는다. 파티셔닝은 EE의 별도 옵션이라 라이선스가 따로 든다. 12c부터는 하나의 컨테이너 DB(CDB) 안에 여러 플러그형 DB(PDB)를 두는 멀티테넌트 구조가 들어왔다.

## 정리

- 인스턴스(메모리+프로세스)가 데이터베이스(파일)를 연다.
- SGA는 공유 캐시, PGA는 프로세스 전용 작업 공간이다. 공유 풀이 실행 계획을 재사용하므로 바인드 변수를 쓴다.
- 커밋은 리두 로그만 순차로 쓰고 끝낸다. 데이터 블록은 DBWn이 나중에 내린다. 복구는 리두로 앞으로, 언두로 뒤로.
- 저장은 테이블스페이스 → 세그먼트 → 익스텐트 → 블록. 테이블스페이스는 디스크 배치와 관리의 단위다.
