> Brandon Gregory의 「명확한 코드 작성법」(웹액츄얼리 번역, 2018.02)을 바탕으로 재구성한 노트입니다.

## 명확한 코드란

돌아가는 코드와 좋은 코드는 다르다. 좋은 코드는 **읽고, 이해하고, 고치기 쉽다.** 들여쓰기나 이름만으로는 부족하고, 편집기를 열기 전에 일을 어떻게 나눌지 설계해야 한다. 그 설계를 판단하는 네 가지 기준이 있다.

| 원칙 | 한 줄 요약 | 어기면 보이는 신호 |
| --- | --- | --- |
| 단일 책임 | 한 함수·클래스는 한 가지 일만 | 기능을 설명할 때 "그리고"가 들어간다 |
| 명령-질의 분리 | 값을 묻는 함수와 상태를 바꾸는 함수를 나눈다 | `getX()`를 불렀더니 무언가 저장·변경된다 |
| 낮은 결합도 | 단위끼리 덜 의존한다 | 한 곳을 고치면 여러 곳을 같이 고쳐야 한다 |
| 높은 응집도 | 관련된 것은 한곳에 모은다 | 같은 변수가 여러 함수에 흩어져 전달된다 |

## 1. 단일 책임 원칙

드릴이 나사를 박으면서 가루까지 뿜는다면, 가루가 필요 없는 곳에선 쓸 수 없다. **기능이 적은 코드 블록이 더 많은 곳에서 쓰인다.**

폼 제출 하나에 점수 계산·차트 생성·DOM 갱신을 다 넣으면, 고칠 곳을 찾기도 에러 위치를 찾기도 어렵다. 일을 함수로 나누면 제출 함수는 목차처럼 읽힌다.

```javascript
function handleSubmit(form) {
  const answers = collectAnswers(form)
  const scores = calculateScores(answers)
  renderChart(scores)
  showResult(scores)
}
```

검증이 필요해지면 `validate(answers)` 한 줄을 더하면 된다. 함수가 커지고 같은 데이터를 공유하는 작업이 여럿이면 클래스나 모듈로 묶는다. React 컴포넌트에 적용한 모습은 [[frontend-solid|프론트엔드와 SOLID 원칙]]에 있다.

## 2. 명령-질의 분리 원칙

함수는 두 종류다.

| 종류 | 하는 일 | 지킬 것 |
| --- | --- | --- |
| 질의(query) | 값을 돌려준다 | 상태를 바꾸지 않는다 |
| 명령(command) | 상태를 바꾼다 | 값을 돌려주지 않는다 |

```javascript
// 나쁨: 이름은 질의인데 데이터를 바꾸고 쿠키까지 쓴다
function getFirstName() {
  const name = input.value.toLowerCase()
  document.cookie = `firstName=${name}`
  return name
}

// 좋음: 묻기와 바꾸기를 나눈다
function getFirstName() {
  return input.value
}
function saveFirstName(name) {
  document.cookie = `firstName=${name.toLowerCase()}`
}
```

이름이 약속하지 않은 부수 효과(side effect)는 다른 값을 몰래 덮어쓰는 버그가 된다. 함수가 무슨 일을 하는지 매번 정의를 열어 확인해야 한다면 이 원칙이 깨진 것이다.

## 3. 낮은 결합도

직소 퍼즐은 맞추는 방법이 하나뿐이고, 레고는 조각을 마음대로 조합한다. 결합도(coupling)는 코드 단위끼리 의존하는 정도다. **레고처럼 느슨하게 결합된 코드**가 다양한 쓰임을 받아들인다.

높은 결합도의 신호:

- 거의 같은 함수가 여러 개 있다. 복사·붙여넣기가 잦다.
- 함수 안에 ID·선택자·설정값이 하드코딩돼 있다.
- 매개변수가 지나치게 많다.
- 한 클래스가 다른 클래스를 직접 생성해, 그 생성자가 바뀌면 같이 고쳐야 한다.

낮추는 방법:

- 하드코딩된 값을 인자로 받는다. 비슷한 위젯 셋에 함수 셋을 만들지 말고, 설정 객체를 받는 클래스 하나로 인스턴스 셋을 만든다.
- 생성자에는 여러 위치 인자 대신 **옵션 객체와 기본값**을 받는다. 매개변수가 늘어도 호출부가 깨지지 않는다.
- 의존 대상은 밖에서 넘겨받는다(의존성 주입).

## 4. 높은 응집도

방을 치우라고 하면 모든 물건을 옷장 하나에 밀어 넣는 아이가 있다. 치운 것 같지만 찾을 수가 없다. 응집도(cohesion)는 **관련된 것끼리 얼마나 모여 있는가**다.

- 여러 함수가 같은 변수를 쓰면 한 객체·클래스로 묶는다. 같은 DOM 요소 참조를 여러 함수에 넘기고 있다면 인스턴스 속성으로 둔다.
- 데이터 접근 함수, 특정 UI 요소 함수처럼 관심사별로 모듈을 나눈다. 30개 함수를 늘어놓는 것보다 이름 충돌도 준다.
- 반대로 `Common`, `utils`처럼 **관련 없는 것을 한데 모은 덩어리**는 응집도가 낮다. 클래스의 속성을 소수의 메서드만 쓰거나, 쓰이지 않는 메서드가 있다면 신호다.
- 같은 코드가 반복되면 응집도가 낮은 것이다. 비슷한 문장은 함수로, 비슷한 함수는 클래스로 묶는다.

응집도를 높이면 결합도는 대개 낮아진다. 둘이 충돌하면 **응집도를 우선한다.** 관련 코드가 한곳에 있는 편이 일상적인 수정에서 더 자주 도움이 된다.

## 정리

- 함수 설명에 "그리고"가 나오면 쪼갠다.
- 값을 돌려주는 함수는 아무것도 바꾸지 않는다.
- 하드코딩·복붙·긴 매개변수 목록은 결합도가 높다는 신호다. 옵션 객체와 주입으로 푼다.
- 같은 데이터를 쓰는 코드는 모으고, 관련 없는 코드는 떼어 놓는다.
- 네 원칙은 **나중에 읽을 사람(미래의 나 포함)을 위한 설계 기준**이다.
