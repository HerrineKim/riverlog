> Master.dev 뉴스레터 「Should you use micro-frontends?」(2026.07)와 Cam Jackson·Martin Fowler의 「[Micro Frontends](https://martinfowler.com/articles/micro-frontends.html)」를 바탕으로 재구성한 노트다.

## 마이크로 프론트엔드란

**마이크로 프론트엔드(Micro-Frontends)** 는 백엔드의 마이크로서비스 아이디어를 프론트엔드로 가져와, 하나의 큰 웹 애플리케이션을 **서로 다른 팀이 독립적으로 개발·테스트·배포할 수 있는 작은 수직 조각(feature slice)** 으로 나누는 아키텍처다.

핵심 목표는 기술적 멋이 아니라 **조직의 확장성**이다. 수십 명의 개발자가 하나의 프론트엔드 코드베이스에 몰려 충돌이 잦고 CI가 30분씩 걸리며, 한 팀의 사소한 버그가 전체 릴리스를 막을 때 배포 권한과 소유권을 팀 단위로 떼어 내기 위해 쓴다.

## 모놀리스에서 마이크로 프론트엔드까지의 단계

아키텍처는 "모놀리스 vs 마이크로 프론트엔드"의 이분법이 아니다. 실제로는 가장 적은 비용으로 현재 병목을 푸는 중간 단계가 넓게 존재한다.

```mermaid
flowchart LR
  A["단일 모놀리스"] -->|"내부 경계·규칙 정리"| B["모듈러 모놀리스"]
  B -->|"패키지 분리 (Turborepo/pnpm)"| C["모노레포 (단일 배포)"]
  C -->|"팀별 독립 배포 필요 시"| D["마이크로 프론트엔드"]
```

| 단계 | 배포 단위 | 푸는 문제 | 남는 비용 |
| --- | --- | --- | --- |
| 단일 모놀리스 | 1개 | 빠른 초기 개발, 단순한 디버깅·공유 | 파일 충돌, 경계 붕괴 |
| 모듈러 모놀리스 (FSD 등) | 1개 | 도메인 경계 확립, 결합도 감소 | 거대한 단일 빌드·배포 큐 |
| 모노레포 | 1개(또는 앱별) | 패키지 소유권 분리, 캐시된 빌드·테스트 | 배포 일정의 조직적 결합 |
| 마이크로 프론트엔드 | 팀별 N개 | **독립 배포 일정**과 기술 스택 자율성 | 런타임 통합 복잡도, 번들·UX 드리프트 |

## 통합 방식 비교

쪼갠 조각을 사용자 브라우저에서 하나의 앱으로 합치는 방법은 크게 네 가지다.

| 방식 | 동작 원리 | 장점 | 단점 |
| --- | --- | --- | --- |
| 빌드 타임 패키지 | npm 패키지로 배포해 컨테이너 앱이 재빌드 | 타입 안전, 트리 셰이킹, 단순한 런타임 | 하위 패키지 수정 시 전체 재배포 필요 (사실상 배포 결합) |
| 런타임 Module Federation / Import Maps | 각 팀이 `remoteEntry`나 ES 모듈을 별도 URL에 배포하고 셸이 동적 로드 | 진짜 독립 배포, 공유 의존성(React 등) 협상 가능 | 버전 불일치 시 런타임 오류, 번들러·캐시 무효화 관리 난이도 |
| 서버/엣지 조합 (ESI, SSR 프록시) | 라우트 또는 프래그먼트 단위로 서버·CDN에서 조립 | 초기 로딩 빠름, 페이지 단위 명확한 격리 | 페이지 내 클라이언트 상태·전환 공유가 어색함 |
| Web Components / `iframe` | 커스텀 요소나 `iframe` 경계로 격리 | CSS·JS 전역 오염 완전 차단(`iframe`) | 라우팅·접근성·모달 포커스·성능 오버헤드 큼 |

## 숨은 비용과 실패 패턴

마이크로 프론트엔드를 섣불리 도입하면 독립성 대신 **분산 모놀리스(distributed monolith)** 를 얻기 쉽다.

- **공유 의존성 지옥**: 팀 A가 React 18, 팀 B가 React 19를 쓰면 번들에 두 버전이 동시에 실리거나 Context·Hook 인스턴스가 깨진다. 결국 공유 라이브러리 업그레이드를 전 팀이 동시에 맞춰야 해서 독립 배포 이점이 사라진다.
- **UX·디자인 시스템 파편화**: 팀마다 별도 CSS·컴포넌트 버전이 쌓이면 버튼 모양, 폰트, 에러 토스트, 라우팅 전환이 페이지마다 어긋난다.
- **성능 저하**: 공통 런타임·폴리필·폰트·상태 관리 중복 로드로 초기 다운로드 크기(JS/CSS)와 TTI가 나빠진다.
- **E2E 테스트·로컬 개발의 고통**: 로컬에서 기능을 하나 보려면 5개 레포·서버를 동시에 띄워야 하고, 배포된 원격 모듈 조합에 따라 프로덕션에서만 재현되는 계약 불일치가 생긴다.

## 언제 쓰고 언제 쓰지 말아야 하나

- **쓰지 말아야 할 때**: 프론트엔드 개발자가 10~15명 미만인 팀, 제품 전체가 하나의 긴밀한 워크플로(예: 캔버스 에디터, 통합 대시보드)인 경우, 단순히 코드가 지저분해서 정리하고 싶은 경우. 이때는 [[feature-sliced-design|Feature-Sliced Design]] 같은 모듈러 모놀리스나 Turborepo 기반 모노레포가 훨씬 낫다.
- **고려할 만한 때**: 서로 다른 비즈니스 도메인을 맡은 자율 팀이 여러 개(보통 3~5개 이상)이고, 라우트·페이지 단위로 경계가 뚜렷하며, 실제로 **팀마다 다른 배포 주기**가 비즈니스 요구사항일 때다. 그 경우에도 한 화면 안에 여러 팀의 위젯을 잘게 섞기보다 **라우트(수직 페이지) 단위**로 쪼개는 편이 훨씬 덜 부서진다.

## 정리

- 마이크로 프론트엔드는 코드 구조 패턴이 아니라 **팀 간 배포 결합을 끊는 조직적 타협**이다.
- 모놀리스의 고통이 코드 결합 때문이라면 모듈러 모놀리스나 모노레포로 해결하고, 정말 팀별 독립 배포가 필요할 때만 마이크로 프론트엔드로 간다.
- 도입한다면 라우트 단위로 굵게 나누고, 공유 디자인 시스템·계약 테스트·의존성 버전 규칙을 먼저 세워야 분산 모놀리스를 피한다.
