## 좋은 코드는 남이 읽기 좋은 코드다

클린 코드는 **읽기 쉽고 고치기 쉬운 코드**다. 기준은 쓴 사람이 아니라 읽는 사람이다. 어려운 이유는 **지식의 저주(curse of knowledge)** 다. 한번 알게 된 것은 모르는 상태로 돌아가 상상할 수 없어서, 내 이름과 구조가 남에게도 명확하다고 착각한다. 혼자 일할 때 더 심하다. 코드 리뷰, 팀 컨벤션, 자동화된 테스트는 이 편향을 깨는 장치다. 좋은 코드의 특징을 말로 설명할 수 있어야 리뷰에서 "별로예요" 대신 근거 있는 피드백을 줄 수 있다.

## 가독성이 무너지는 이유

글은 언어이면서 시각 정보다. 사람은 글자를 하나씩 읽지 않고 단어·문장 단위의 **패턴**으로 읽는다. 띄어쓰기가 없거나, 의미와 상관없이 굵게·줄바꿈이 끼어들면 시각 정보와 의미가 충돌해 인지 부하가 오른다. 코드도 같다. **시각적 배치와 의미적 묶음이 일치해야** 읽힌다.

이 일치를 점검하는 틀로 게슈탈트 법칙을 빌려 쓸 수 있다. 원래는 시지각·UI 디자인 이론이지만 코드 배치에도 그대로 들어맞는다.

| 법칙 | 지각 원리 | 코드에서 |
| --- | --- | --- |
| 근접성(Proximity) | 가까이 있는 것은 한 묶음으로 보인다 | 빈 줄로 의미 단위를 가른다 |
| 공통 영역(Common Region) | 같은 영역 안의 것은 한 그룹이다 | 함수·블록·주석 레이블 안에는 관련된 것만 둔다 |
| 유사성(Similarity) | 비슷하게 생긴 것은 같은 종류다 | `use*`는 훅, `handle*`은 이벤트 핸들러라는 약속을 지킨다 |
| 연속성(Continuation) | 이어진 것은 하나의 흐름이다 | 데이터 흐름 순서대로 배치한다 |
| 폐쇄성(Closure) | 일부가 비어도 전체 형태를 알아본다 | 이름에 모든 정보를 넣지 않아도 된다 |

## 1. 좋은 모양: 빈 줄과 주석

들여쓰기·공백·따옴표 같은 모양은 Prettier 같은 포매터에 맡긴다([[eslint-prettier|ESLint와 Prettier 설정]]). 포매터가 못 하는 것은 **빈 줄과 주석**이다. 어디가 의미의 경계인지는 사람만 안다.

```js
const processOrder = (items, discountCode) => {
  // 소계
  const subtotal = items.reduce((sum, i) => sum + i.price * i.quantity, 0);

  // 세금 포함 총액
  const total = subtotal * (1 + TAX_RATE);

  // 할인
  const rate = DISCOUNTS[discountCode] ?? 0;
  return round2(total * (1 - rate));
};
```

빈 줄이 없으면 띄어쓰기 없는 문장처럼 묶음을 찾는 일을 읽는 사람이 떠안는다. 핵심은 **정말로 같은 것끼리만 붙이고, 다른 것 사이에 간격을 두는 것**이다. 그러려면 어떤 줄끼리 의미가 이어지는지 먼저 알아야 한다.

## 2. 좋은 구조: 배치와 흐름

코드는 글과 달리 위에서 아래로 한 번만 읽지 않는다. 실행 순서와 데이터 흐름을 따라 여러 방향으로 오간다. 읽는 흐름과 배치가 어긋나면 가독성이 떨어진다.

- **공통 영역 위반**: 관련 없는 변수·함수가 `username` 상태와 그 핸들러 사이에 끼어 있으면, 묶음 안에 관련된 것이 있으리라는 기대가 깨진다.
- **유사성 위반**: `handleNameImportant`가 이벤트 핸들러가 아니라 문자열 변환 함수라면, 이름이 같은 무리에 섞여 쉽게 오해된다. 일관성 없는 이름은 매번 역할을 추론하게 만든다.

### 역할로 묶을까, 로직으로 묶을까

| 방식 | 배치 | 장점 | 약점 |
| --- | --- | --- | --- |
| 역할 기준 | 훅 → 계산 값 → 핸들러 → 이펙트 | 각 블록의 정체가 분명하다 | 한 기능을 보려면 블록 사이를 오간다 |
| 로직 기준 | 카운트 관련 → 데이터 페칭 관련 | 흐름을 따라 읽고 디버깅하기 쉽다 | 길어지면 묶음이 시각적으로 흐려진다 |

둘은 배타적이지 않다. **로직 단위로 커스텀 훅을 만들어 공통 영역을 주고, 컴포넌트 본문은 그 훅을 흐름 순서대로 부르면** 둘 다 만족한다.

```tsx
// ✗ start, start2와 두 개의 useEffect: 의존 관계를 실행 순서로 추적해야 한다
// ✓ 데이터별로 묶고, 흐름이 위에서 아래로 보이게
function Profile() {
  const token = useToken();
  const userInfo = useUserInfo(token);
  return <UserView token={token} userInfo={userInfo} />;
}
```

## 3. 좋은 이름: 간결함과 예측 가능성

`calculateTotalPriceOfAllItemsInTheShoppingCart`는 설명적이지만 너무 길어 한눈에 안 들어오고, 정보가 많아 오히려 핵심을 놓친다. 상세한 항공사진보다 단순한 지도가 길 찾기에 낫다. 폐쇄성 법칙대로 **형태를 알아볼 만큼만** 남긴다. 기준은 **간결함과 예측 가능성**이다.

| 대상 | 이름이 알려 줘야 할 것 | 좋은 예 | 나쁜 예 |
| --- | --- | --- | --- |
| 변수 | 역할과 타입 | `age`, `isActive`, `users`, `userInfo` | `u`, `str`, `flag`, `arr` |
| 불리언 | 참/거짓의 의미 | `isActive`, `hasChildren` | `flag`, `check` |
| 함수 | 동작(동사) + 대상(명사) + 조건(전치사) + 맥락(형용사) | `getActiveUsersByGroup(groupId)` | `process`, `doStuff`, `handleIt` |

- **맥락이 말해 주는 것은 빼도 된다.** `cart.calculateTotal()`이면 `ShoppingCart`를 이름에 다시 넣을 필요가 없다.
- **보편적인 이름을 쓴다.** `get`·`fetch`·`load`, `create`·`add`, `remove`·`delete`처럼 자주 쓰는 동사는 이미 뉘앙스가 정해져 있다. 그 차이를 알고 팀 안에서 일관되게 쓰면 이름만 보고 동작을 예측할 수 있다([[typescript-coding-convention|TypeScript 코딩 컨벤션]]).

## 나쁜 코드는 왜 비싼가

나쁜 코드는 **의미가 모호하고**(이름과 하는 일이 다르다), **중복되고**, 불필요한 연산이 섞인 코드다. 깨끗한 코드는 그 반대다. 『클린 코드』가 인용하는 두 정의가 기준을 잘 요약한다.

- 비야네 스트롭스트룹(C++ 창시자): 논리가 단순해 버그가 숨을 곳이 없고, 의존성이 적어 고치기 쉽고, 오류를 일관된 전략으로 처리하며, **한 가지를 제대로 한다.**
- 그래디 부치(UML 공동 개발자): 단순하고 직접적이며, 설계자의 의도를 숨기지 않고, **잘 쓴 문장처럼 읽힌다.**

| 비용 | 내용 |
| --- | --- |
| 깨진 유리창 | 깨진 창 하나를 방치한 건물은 금세 더 망가진다. 코드도 지저분한 곳 옆에는 "여기는 원래 이래도 된다"는 신호가 생겨 나쁜 코드가 이어 붙는다 |
| 생산성 저하 | 한 줄 고치려면 주변을 다 이해해야 하고, 고칠 때마다 다른 곳이 깨진다. 팀이 커져도 속도는 오히려 떨어진다 |
| 기술 부채 | 빌린 시간은 이자를 붙여 돌아온다. 한계에 이르면 재설계(새 시스템)를 요구하지만, 옛 시스템을 운영하며 새 시스템을 따라잡는 일은 거의 성공하지 못한다 |

### 왜 알면서도 짜나

- **일정이 급해서.** "일단 돌아가게"를 반복하면 코드가 느려지고, 느려진 만큼 일정이 더 밀려 다시 "일단"을 부르는 악순환이 된다. 엉망인 코드는 일정을 지키는 수단이 아니라 **일정을 놓치는 원인**이다.
- **건드리기 무서워서.** 영향 범위가 넓어 고치면 어디가 깨질지 모르니 그대로 둔다. 이 두려움을 없애는 것이 테스트다([[tdd|TDD]]).

### 보이스카우트 규칙

"캠프장은 처음 왔을 때보다 깨끗하게 해 놓고 떠나라." 코드를 건드릴 때마다 **이름 하나, 중복 하나라도 처음보다 낫게** 해 두면 코드는 시간이 갈수록 좋아진다. 대청소 일정을 따로 잡는 것보다 작은 개선을 매번 하는 편이 현실적이다. 다만 동작 변경과 정리를 한 커밋에 섞지 않는다.

### 피해야 할 습관

| 습관 | 문제 | 대신 |
| --- | --- | --- |
| `while (i != 50)`처럼 정확한 값으로 종료 검사 | 증가 폭이 바뀌면(`i += 4`) 값을 건너뛰어 무한 루프 | `i < 50`처럼 **범위로** 검사한다 |
| 반복문 안에 탈출 지점을 여러 곳 | 어떤 조건에서 끝나는지 따라가기 어렵다 | 종료 조건을 한곳에 모으거나, 반복 본문을 함수로 빼 `return`을 분명히 한다 |
| 길고 깊은 반복문 | 한 화면에 안 들어와 흐름을 놓친다 | 본문을 이름 있는 함수로 추출한다 |
| 여러 일을 하는 함수 | 이름이 거짓말이 되고 재사용·테스트가 어렵다 | 함수 하나에 일 하나([[clean-code-functions-naming|클린 코드: 함수와 이름]]) |
| 입력을 검증하지 않음 | null·빈 값이 깊숙이 들어가 엉뚱한 곳에서 터진다 | 경계(공개 함수, API 응답)에서 **방어적으로** 검사하고 일찍 반환한다 |
| `null`을 반환 | 호출하는 모든 곳이 null 검사를 떠안고, 하나만 빠져도 오류 | 빈 배열·기본 객체를 돌려주거나, 실패는 예외·Result 타입으로 표현한다. TypeScript라면 반환 타입에 드러낸다 |

## 정리

- 좋은 코드의 기준은 **읽는 사람**이다. 지식의 저주를 의식하고, 리뷰·컨벤션으로 남의 눈을 빌린다.
- 가독성은 **시각적 배치와 의미적 묶음이 일치할 때** 생긴다. 게슈탈트 법칙이 그 점검표다.
- 모양은 포매터에 맡기고, 사람은 빈 줄과 주석으로 의미의 경계를 표시한다.
- 구조는 역할과 로직 중 하나를 고르기보다, 커스텀 훅 같은 공통 영역으로 둘 다 만족시킨다.
- 이름은 형태를 알아볼 만큼만 간결하게, 같은 접두어는 같은 역할로 일관되게.
- 나쁜 코드는 깨진 유리창처럼 번지고 기술 부채로 돌아온다. 건드릴 때마다 조금씩 낫게 둔다(보이스카우트 규칙).
