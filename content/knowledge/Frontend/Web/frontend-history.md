## 웹의 세대 구분

프론트엔드는 처음부터 있던 직군이 아니다. 2000년대 초에 생겼고, 웹이 바뀐 흐름과 같이 보면 이해하기 쉽다.

| 세대 | 시기 | 성격 | 필요했던 사람 |
| --- | --- | --- | --- |
| Web 1.0 | 1990년대 ~ 2004 | 정적인 사이트. 사용자는 읽기만 한다 | 웹 디자이너. 페이지 제작 기술은 단순했다 |
| Web 2.0 | 2004 ~ | 사용자가 콘텐츠를 만들고 고치는 상호작용 사이트 | 숙련된 웹 개발자 |
| Web 3.0 | 앞으로 | AI·블록체인·IoT 기반의 지능형·시맨틱 웹 | 정의가 아직 논쟁 중이다 |

## 프론트엔드를 만든 기술들

```text
1991 HTML 태그 ─ 1993 <img> ─ 1995 JavaScript ─ 1996 CSS ─ 2004~05 AJAX(Gmail, Google Maps) ─ 2010 무렵 Flash 퇴장
                                                                                                     │
                                                       트래픽·데이터 증가 → 프론트엔드 / 백엔드 분리 ◀┘
```

| 기술 | 바꾼 것 |
| --- | --- |
| `<img>` 태그 (1993) | 페이지가 풍성해졌다. 아직은 전문가가 따로 필요할 만큼 복잡하지 않았다 |
| CSS (1994 제안, 1996 공개, 1998 W3C 권고) | **문서 구조와 시각 디자인을 분리**했다 |
| JavaScript (1995) | 사용자와 페이지가 상호작용할 수 있게 했다. Web 2.0의 바탕이 됐다 |
| AJAX | 페이지 전체를 다시 불러오지 않고 **일부만 비동기로 갱신**한다. Gmail(2004)과 Google Maps(2005)가 보여 줬고, Jesse James Garrett이 이름을 붙였다. JavaScript의 위상이 크게 올라갔다 |
| Flash의 퇴장 (2010 무렵) | 그 자리를 HTML5와 AJAX가 채웠다 |

### Flash가 밀려난 이유

- 보안 취약점이 잦았다.
- 모바일에서 성능이 나쁘고 배터리를 많이 썼다.
- 스크린 리더가 읽지 못해 접근성이 떨어졌다.
- 검색 엔진이 내용을 색인하기 어려웠다.
- HTML5와 AJAX라는 표준 대안이 생겼다.

## 웹을 앱으로 만든 동력

> 이 절은 테오(teo)의 「[프론트엔드 역사와 미래, 업무 분야 ... 그리고 잘하는 프론트엔드 개발자란?](https://velog.io/@teo/frontend)」(2021.12)을 바탕으로 보강했습니다.

기술만으로 직군이 생기지는 않았다. **웹으로 돈을 벌려는 회사들이 브라우저를 앱 플랫폼으로 밀어붙였고**, 그 과정에서 화면 쪽 일이 전문 영역이 됐다.

| 흐름 | 일어난 일 | 프론트엔드에 남긴 것 |
| --- | --- | --- |
| IE 독점과 홈페이지 붐 (1995~2004) | 홈페이지가 회사의 명함이 됐다. 게시판은 솔루션을 사서 붙였다 | HTML·CSS 작업은 수요가 많았지만 로직이 거의 없어 낮게 평가받았다 |
| 구글의 "웹이 OS가 되면" | 오피스를 웹으로 옮기려 했고, 다른 벤더의 플러그인에 기대지 않으려고 JavaScript 비동기 화면(Google Maps)을 택했다 | JavaScript가 재평가됐다 |
| 웹 표준과 접근성 | 여러 브라우저 벤더가 IE·ActiveX 대신 공통 표준을 만들었다 | 크로스 브라우징·시맨틱·접근성이 디자이너와 다른 **전문 영역**이 됐다. 디자인을 표준 HTML·CSS로 옮기는 일이 별도 공정이 됐다 |
| jQuery (2006) | 쉬운 문법으로 DOM 조작·크로스 브라우징·Ajax를 한꺼번에 해결했다 | jQuery 문법의 상당수가 뒤에 표준 API(`querySelectorAll` 등)로 들어갔다 |
| 크롬과 V8 (2008) | 빠른 JS 엔진과 디버깅 도구를 갖춘 브라우저가 나왔다 | `console.log`조차 쓰기 어렵던 환경에서 **디버깅 가능한 개발**이 시작됐다 |
| Node와 npm | V8이 서버로 나가고, 모듈을 패키지로 공유하게 됐다 | 파일을 나눠 큰 프로그램을 짤 수 있게 됐고, webpack·Babel 같은 Node 기반 빌드 도구 생태계가 열렸다 |
| 페이스북의 규모 | 단일 웹 서비스가 감당할 데이터와 화면이 폭증했다 | React가 나오며 **프론트엔드 개발의 체계**가 잡혔다 |

## 프론트엔드와 백엔드의 분리

트래픽과 데이터가 커지자 한 사람이 모두 맡기 어려워졌다. 역할이 나뉘었다.

| 영역 | 맡는 일 |
| --- | --- |
| 프론트엔드 | 가공된 데이터를 받아 사용자가 보고 조작하는 화면을 만든다 |
| 백엔드 | 서버에서 데이터를 처리하고 저장한다 |

프론트엔드는 **새로 생긴 것이 아니라 거대 웹 서비스가 등장하며 자연스럽게 세분화된 것**이다. 백엔드는 대용량 데이터·배포 자동화·스케일링이라는 새 과제를 맡았고, 프론트엔드는 동적인 화면이라는 과제를 맡았다. 1인 개발이 흔하던 모바일 게임이 대형 팀 작업이 된 것과 같은 흐름이다.

### 지금의 자리와 앞으로

테오가 본 현재와 방향은 이렇다(2021년 시점의 전망이다).

- **디지털 전환**: 오프라인 사업이 온라인으로 옮겨 오면서, 데이터를 눈으로 보고 조작하는 **백오피스·관리자 도구** 수요가 크게 늘었다. 입문자가 상상하는 화려한 화면과 실제 수요가 다를 수 있다.
- **프로토타이핑의 최전선**: 설치가 필요 없고 가볍게 만들 수 있어, 스타트업이 사업을 검증하는 첫 도구가 된다.
- **데이터를 다루는 앱**: Notion·Figma·Slack처럼 웹이 문서가 아닌 애플리케이션이 됐다. 앞으로는 더 서버리스하게(로직이 프론트로 내려오고 백엔드는 인프라로), 더 앱처럼, 더 실시간으로 간다.

## 정리

- 프론트엔드는 한 사건이 아니라 **기술이 쌓이며 생긴** 영역이다.
- CSS는 구조와 표현을, AJAX는 페이지와 데이터 요청을 떼어 냈다.
- 표준 기술(HTML5·JS)이 독자 플러그인(Flash)을 대체하면서 브라우저가 앱 플랫폼이 됐다.
- 사용자가 웹에 기대하는 것이 커질수록 화면을 만드는 일도 전문화됐다.
- 구글(웹을 OS로)과 페이스북(거대한 단일 서비스)의 필요가 V8·크롬·React를 낳았고, 이것이 직군 분리를 굳혔다.
