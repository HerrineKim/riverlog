## 폼 사용성이 중요한 이유

사용자는 웹에서 대부분 읽기만 하고, 직접 입력하는 순간은 폼뿐이다. 그래서 **폼이 불편하면 사이트 전체의 인상이 나빠진다.** 좋은 폼의 조건은 하나다. **사용자의 통제권을 빼앗지 않는다.**

## 1. 브라우저 기본 동작을 지킨다

| 기본 동작 | 깨지는 흔한 원인 |
| --- | --- |
| 입력 칸에서 Enter로 제출 | `<form>` 없이 div와 클릭 핸들러로 폼을 만듦 |
| Tab·방향키로 이동 | 커스텀 컴포넌트가 포커스를 받지 못함 |
| 뒤로 가기 | 사용자는 이미 이 버튼으로 취소한다 |

**취소 버튼은 두지 않는다.** 제출 버튼 옆에 있으면 잘못 눌러 입력을 날리기 쉽고, 취소는 뒤로 가기가 이미 해 준다.

## 2. 모바일 가상 키보드를 맞춘다

`inputmode`로 칸마다 알맞은 키보드를 띄운다. 숫자 칸에 문자 키보드가 뜨면 사이트가 허술해 보인다.

| 속성 | 하는 일 |
| --- | --- |
| `type` | 데이터 형식을 정하고 **브라우저 검증까지** 켠다 |
| `inputmode` | **키보드 모양만** 바꾼다 (`numeric`, `decimal`, `tel`, `email`, `url`, `search`) |

검증을 JavaScript로 직접 한다면 `inputmode`만 쓰는 편이 간섭이 적다.

| 값의 성격 | 선택 |
| --- | --- |
| 수량·순서처럼 크기가 의미 있고 방향키 증감이 유용 | `type="number"` |
| 전화번호·주민번호처럼 숫자로 된 식별자 | `type="text" inputmode="numeric"` |

수량 1처럼 기본값이 든 칸은 **포커스 때 값을 전체 선택**해 두면 바로 덮어쓸 수 있다. 모바일에서 특히 편하다.

```js
input.addEventListener('focus', (e) => e.target.select());
```

## 3. 검증 메시지는 보이게

**아무 말 없이 제출이 안 되는 폼**이 가장 나쁘다. 무엇이 틀렸는지 알려 주고, 가능하면 해당 칸으로 포커스를 옮긴다.

- HTML 기본 검증 팝업은 놓치기 쉽다. `title`로 메시지를 바꾸고, `:user-invalid`로 오류 칸을 눈에 띄게 꾸민다. 팝업이 안 뜨는 상황도 있으니 여러 환경에서 확인한다.
- **입력 중에 바로 오류를 띄우지 않는다.** 아직 다 쓰지도 않았는데 빨간 글씨가 뜨면 불안하다. `blur`·`change` 때 처음 띄우고, 한 번 뜬 뒤에는 실시간으로 갱신한다(VeeValidate의 검증 모드가 이런 방식).
- 검증 라이브러리는 복잡한 UI에 빠르지만, 규칙이 특이하면 평범한 `if` 문이 개발자와 사용자 모두에게 더 명확할 수 있다.

```css
input:user-invalid {
  border-color: crimson;
}
```

## 4. 커서와 포커스를 빼앗지 않는다

| 하지 말 것 | 문제 | 대안 |
| --- | --- | --- |
| `alert()` 후 오류 칸으로 강제 포커스 | 포커스를 뺏고, 반복되면 사용자가 칸에 갇힌다 | 칸 옆에 인라인 메시지 |
| 입력 칸에 천 단위 쉼표를 직접 삽입 | 커서가 끝으로 튀고, NaN·앞자리 0 사라짐 같은 버그 | 입력은 그대로 두고 옆에 서식 붙은 값을 따로 표시 |
| 전화번호 하이픈 자동 삽입 | 백스페이스·방향키가 꼬인다 | 자유롭게 입력받고 하이픈은 서버에서 정리 |
| 전화번호를 칸 3개로 나누기 | 클릭·이동만 늘어난다 | 한 칸으로 받기 |

## 정리

- 폼 품질은 작은 디테일의 합이고, 하나하나는 어렵지 않다.
- 기준은 **사용자의 통제권**이다. 말 없이 막기, 포커스 뺏기, 커서 옮기기, 입력 제한은 모두 사용성을 깎는다.
- 모바일에서는 `inputmode` 한 줄이 체감 품질을 크게 바꾼다.
