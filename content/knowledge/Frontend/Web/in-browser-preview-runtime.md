> 토스 웨비나 「AI 시대, 토스 FE는 어떻게 일할까」(2026.08) 중 「AI 시대 어드민: 브라우저 안에 개발 환경 만들기」 발표([편집본](https://youtu.be/tcGKZANuUVE), [전체 영상](https://youtube.com/live/xDVbTlFfu30))를 바탕으로, esbuild·import map 동작은 공식 문서로 확인해 재구성한 노트다.

## 왜 브라우저 안에 개발 환경이 필요한가

프론트엔드 개발자는 로컬에서 dev 서버를 띄워 프리뷰를 본다. 하지만 **비개발자가 프롬프트로 화면을 만드는 제품**에서는 AI가 쓴 코드를 사용자 브라우저에서 곧바로 실행해 보여 줘야 한다. 로컬 환경이 없는 사람에게 개발 환경을 브라우저 안으로 가져와야 하는 것이다.

대표적인 예가 사내 어드민이다. 어드민 하나를 만들 때마다 같은 일이 반복된다.

```text
프로젝트 스캐폴딩 → npm 의존성 → 빌드 도구(Vite 등) → 인증 → 배포 설정 → 코드 작성·빌드·배포
+ 서버 API 준비
+ 어드민 전용: 보안, 개인정보 마스킹, 조회 기록(감사 로그), 다운로드 파일 암호화
```

어드민마다 따로 만들면 보안 규칙과 도메인 지식이 모든 어드민에 고르게 적용되기 어렵다. 비즈니스 확장 속도만큼 프론트엔드 인력이 없는 팀은 어드민을 아예 못 만들거나 서버 개발자가 따로 만들어 쓴다.

## 해법: 정책은 플랫폼, 화면은 AI

토스는 어드민을 **AI로 만드는 사내 플랫폼**으로 풀었다. 사용자가 프롬프트를 넣으면 에이전트가 어떤 어드민을 만들지 되묻고(질문 도구), 계획을 세우고, 코드를 써서 몇 분 만에 화면을 만든다. 공개 후 반년 동안 프로젝트 약 440개, 페이지 약 2,400개가 만들어졌고, 그중 실제 운영 중인 어드민이 약 120개다.

핵심은 어드민의 일을 두 층으로 나눈 것이다.

| 층 | 담당 | 내용 |
| --- | --- | --- |
| 데이터·컴플라이언스 | 플랫폼(정책) | 쓸 API를 등록하면 서버가 프록시한다. 프록시를 거치므로 마스킹, 조회 암호화 같은 정책이 자동 적용되고 호출 기록(증적)이 자동으로 남는다. 정책은 유관 부서와 함께 정한다 |
| 데이터를 보여 주는 화면 | AI(코드 생성) | AI가 등록된 API 스키마를 참고해 React 코드를 만든다. 테이블·필터·상세 페이지처럼 자주 쓰는 패턴을 미리 알려 준다 |

AI가 어떤 코드를 만들든 데이터는 플랫폼의 정책을 통과해야 하므로, 화면 생성의 자유와 보안을 분리할 수 있다. 사내에서 만든 앱을 안전하게 배포하는 다른 방식은 [[organizational-ax|조직 AX]]의 「바이브 코딩 앱의 사내 배포」, 생성 화면을 디자인 시스템에 맞추는 방법은 [[design-system-agent-harness|디자인 시스템을 아는 화면 생성 에이전트 설계하기]]에 있다.

## 프리뷰 런타임을 찾아가는 과정

| 시도 | 방식 | 문제 |
| --- | --- | --- |
| 1. 서버의 dev 서버 | 서버에 Next.js dev 서버 프로세스를 띄우고 사용자의 iframe을 연결 | PoC로는 충분했지만 **격리가 안 된다.** 한 사용자 페이지의 에러 오버레이가 같은 dev 서버를 쓰는 모두에게 번진다 |
| 2. Sandpack | 격리를 위해 실행 환경을 각 사용자의 브라우저로 옮긴다. iframe 안에 가상 환경을 띄워 코드 수정을 바로 반영하는 라이브러리 | **첫 화면까지 47초.** 브라우저 런타임에 들어온 뒤에야 패키지를 공개 레지스트리에서 받는다. 사내 패키지를 넣기도 어렵다 |
| 3. 직접 구성 | 브라우저 빌드 + 미리 준비한 패키지 + 결과 합성 | **첫 화면까지 1.3초** |

비슷한 문제를 푸는 다른 선택지로는 브라우저 안에서 Node.js 자체를 돌리는 WebContainers(StackBlitz)가 있다. 범용성은 크지만, 정해진 패턴의 화면만 빠르게 보여 주면 되는 경우에는 필요한 부분만 조합하는 편이 가볍다.

## 직접 만든 프리뷰 런타임의 구조

```text
[편집] AI·사용자가 코드 수정
   ↓
가상 파일 시스템 (메모리, 경로 → 내용 Map, 레이어별)
   ↓  esbuild 플러그인이 import를 해석해 가상 FS에서 파일을 읽는다
esbuild-wasm (브라우저에서 번들링) → ESM 번들
   ↓  bare import('react' 등)는 import map으로 해석
미리 번들해 S3에 올려 둔 패키지 조합 (패키지 조합 해시 = 캐시 키)
   ↓
iframe에 실행 결과 반영 (성공했을 때만 교체: 트랜잭션 커밋처럼)
```

### 1. 가상 파일 시스템

브라우저에는 파일 시스템이 없으므로 **파일 경로를 키로 하는 가상 파일 시스템**을 만든다. 메모리에서만 쓰고 런타임이 끝나면 사라진다. 실제 코드는 S3에 저장되고 사용자가 편집할 때마다 갱신된다.

### 2. esbuild-wasm으로 브라우저에서 번들링

[esbuild](https://esbuild.github.io/api/#browser)는 WebAssembly 빌드(`esbuild-wasm`)로 브라우저에서도 돈다. 플러그인의 `onResolve`·`onLoad` 훅에서 import 경로를 해석해 가상 파일 시스템의 내용을 돌려주면, 디스크 없이도 번들링이 된다. 결과는 브라우저가 바로 실행할 수 있는 ESM 번들이다.

### 3. 패키지는 미리 준비한다

가장 고민이 컸던 부분이다. 처음에는 고정된 패키지 조합이라 문제가 없었지만, 프로젝트마다 다른 패키지를 쓰고 싶어 하면서 조합이 동적으로 바뀌었다.

- **패키지를 하나씩 따로 번들하면 싱글톤이 깨진다.** React처럼 인스턴스가 하나여야 하는 패키지가 번들마다 따로 들어가 동작이 어긋난다. 그래서 **조합 전체를 한 단위로** 다뤄야 한다.
- **패키지 조합 해시(package set hash)**: 패키지 엔트리 목록과 lockfile(`yarn.lock`) 해시를 묶어 하나의 해시로 만든다. 같은 조합이면 같은 키다.
- 서버에서 해당 조합으로 워크스페이스를 만들고 `package.json`으로 의존성을 설치한 뒤 Vite로 번들해, **import map**과 함께 해시 키로 S3에 올린다.
- 브라우저는 import map을 보고 어떤 캐시(패키지 조합)를 쓸지 정한 뒤, esbuild-wasm 번들의 bare import를 그 URL로 연결한다. 브라우저가 bare specifier를 import map으로 해석하는 원리는 [[es-modules|모듈: export와 import]]에 있다.

### 4. 결과를 안전하게 합성한다

사용자 코드 번들과 패키지 조합을 합쳐 화면에 보여 줄 때, 빌드가 **성공했을 때만** 결과를 교체한다. 트랜잭션 커밋처럼 동작해 실패한 중간 상태가 화면에 보이지 않는다.

## 엔지니어가 한 일

새로 구현한 부분은 거의 없다. esbuild-wasm, Vite, import map, S3처럼 이미 잘 쓰이는 도구를 조합했다. 엔지니어의 일은 다음으로 정리된다.

- 제품의 요구에 맞게 **경계를 정한다.** 자주 바뀌는 것(사용자 코드)과 느리게 바뀌는 것(패키지 조합)을 나눠 인터페이스를 둔다.
- 코드가 **안전하고 빠르게** 실행될 구조(격리, 사전 번들, 캐시 키)를 만든다.
- 조직의 문제를 구조화해 AI 제품으로 만들면, 개인의 생산성(10x 개인)이 아니라 **조직 전체**가 바뀐다.

## 정리

- 비개발자용 AI 화면 생성 제품에는 브라우저 안의 빌드·프리뷰 환경이 필요하다.
- 데이터 정책은 API 프록시 플랫폼에 두고, AI에는 화면만 맡기면 생성의 자유와 보안을 분리할 수 있다.
- 서버 dev 서버는 격리가 안 되고, 런타임에 패키지를 받는 방식은 느리다.
- 가상 FS + esbuild-wasm + 조합 단위로 미리 번들한 패키지 + import map 조합으로 첫 화면을 47초에서 1.3초로 줄였다.
- 패키지는 조합 전체를 한 단위(해시)로 다뤄야 싱글톤이 깨지지 않는다.
