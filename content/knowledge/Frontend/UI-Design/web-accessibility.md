## 웹 접근성이란

색 대비와 애니메이션은 [[color-motion-accessibility|색과 움직임의 접근성]]에서 따로 다룬다.

웹 접근성은 장애가 있는 사람도 웹을 **인지하고, 이해하고, 탐색하고, 상호작용하고, 기여할 수 있게** 만드는 일이다. 대상 장애는 시각만이 아니다. 청각, 인지, 신경, 신체, 언어 장애가 모두 포함된다.

세계보건기구는 장애를 **개인의 속성이 아니라 능력과 환경의 불일치**로 정의한다(사회적 정의). 이 관점에서는 장애와 보조 기술의 경계가 맥락에 따라 달라진다.

- 휠체어를 위해 만든 인도의 경사로는 지금 유모차와 캐리어도 쓴다.
- 초기 타자기는 시각장애인 친구가 글을 쓰게 하려고 만들어졌다.
- 색맹을 위한 화면 대비 설정은 햇빛 아래에서 화면을 보는 사람에게도 쓸모 있다.

다양한 능력을 위한 설계가 모두에게 쓸모 있는 혁신으로 이어지는 일이 많다. 접근성은 소수를 위한 추가 작업이 아니라 **더 넓은 사용자를 위한 설계**다.

## 보조 기술은 웹을 어떻게 읽나

스크린 리더, 점자 디스플레이, 시선 추적 같은 대체 입력 장치가 웹을 쓰는 보조 기술이다. 그중 스크린 리더가 기술적으로 가장 까다롭다. 화면의 시각 단서 없이 "이건 버튼인가", "어떤 순서로 읽나", "제목만 훑을 수 있나"에 답해야 하기 때문이다.

| 시기 | 방식 | 한계 |
| --- | --- | --- |
| 1980년대 | 텍스트 화면 버퍼를 그대로 소리로 변환 | GUI 등장 후 쓸 수 없음 |
| 1990년대 초 | 오프스크린 모델: OS의 그래픽 명령을 가로채 휴리스틱으로 "버튼 같다"를 추측 | OS 종속적이고 추측이 자주 틀림 |
| 1990년대 후반~ | 시맨틱 웹: HTML이 구조·의미를 표현과 분리해 담고, 브라우저가 접근성 API로 넘김 | 개발자가 의미에 맞게 마크업해야 동작 |

지금 브라우저는 DOM을 파싱해 화면을 그리는 동시에 **접근성 트리(accessibility tree)**를 만든다. 트리의 노드는 role(버튼), name(버튼 텍스트), state(포커스됨) 같은 속성을 갖고, 스크린 리더는 이 값을 읽는다.

```text
HTML ──파싱──→ DOM ──┬──→ 렌더링 → 화면
                     └──→ 접근성 트리 → 접근성 API → 스크린 리더 · 점자 장치
```

- `h1`~`h6`는 heading 노드가 된다. 스크린 리더 사용자는 "다음 제목으로 건너뛰기"로 페이지를 훑는다. 실제로 가장 흔한 정보 탐색 방법이 제목 훑기다.
- 아이콘만 있는 버튼에는 `aria-label`, 이미지에는 `alt`로 name을 준다.
- 머신러닝이 이미지 대체 텍스트를 자동 생성하는 등 트리에 들어갈 데이터를 보강하기 시작했지만, 아직은 개발자가 넣는 의미가 기본이다.

시맨틱 마크업 자체는 [[semantic-html|시맨틱 HTML과 문서 구조]]에, role과 접근 가능한 이름을 테스트에 쓰는 법은 [[a11y-driven-testing|접근성 기반 UI 테스트 자동화]]에 있다. 이 방식의 약점은 개발자가 의도에 맞는 태그와 속성을 써야만 동작한다는 점이다. 그래서 **오늘날 웹 접근성의 가장 큰 장벽은 기술 한계가 아니라 인식과 우선순위의 부족**이다.

## 표준: WCAG와 그 밖의 지침

| 지침 | 대상 | 내용 |
| --- | --- | --- |
| WCAG (웹 콘텐츠 접근성 지침) | 글·이미지·폼 같은 콘텐츠 | 인지 가능·조작 가능·이해 가능·견고함 4원칙 아래 13개 지침, 성공 기준마다 A·AA·AAA 등급. 2026년 기준 최신 권고안은 WCAG 2.2(2023.10)이고, 2025년에 국제 표준 ISO/IEC 40500:2025로도 채택됐다. 법·조달 기준은 보통 AA다. WCAG 3.0은 아직 초안이다 |
| ATAG (저작 도구 접근성 지침) | HTML 편집기, CMS | 장애인도 WCAG를 지키는 콘텐츠를 만들 수 있게 하는 도구 |
| UAAG (사용자 에이전트 접근성 지침) | 브라우저, 확장 프로그램, 미디어 플레이어 | 콘텐츠를 보여 주는 쪽의 접근성 |

접근성은 법적 의무이기도 하다. 유럽 접근성법(European Accessibility Act)은 2025년 6월 28일부터 시행돼 EU에서 파는 전자상거래·은행·전자책 같은 디지털 서비스에 접근성을 요구한다. 기술 기준은 유럽 표준 EN 301 549다. 현재 효력이 있는 V3.2.1(2021)은 WCAG 2.1 AA를 따르고, WCAG 2.2 AA로 기준을 올린 V4.1.1이 2026년 9월 발행돼 EU 관보 등재(2026년 말 예정)를 기다리고 있다. 미국은 ADA와 508조, 한국은 장애인차별금지법과 한국형 웹 콘텐츠 접근성 지침(KWCAG)이 기준이다.

## 표준을 지켜도 쓰기 어려울 수 있다

WCAG를 통과한 제품을 시각장애인·전맹인과 테스트하면 이런 일이 생긴다.

- 글자는 컸지만 굵기가 너무 가늘어 읽지 못했다.
- 날짜 선택 UI를 이해하지 못해 식당 예약을 끝내지 못했다.
- 화면 확대 프로그램을 쓰는 사람은 시야 밖에 나타난 로그아웃 버튼이나 다음 단계를 찾지 못했다.
- `aria-label`이 너무 길어 페이지를 빠르게 훑을 수 없었다.

표준은 **필요조건이지 충분조건이 아니다.** 체크리스트만 보면 사람 사이의 상호작용을 놓친다. 그래서 접근성은 사용성과 함께 봐야 한다. 제이컵 닐슨의 사용성 5요소가 기준이 된다.

| 요소 | 질문 |
| --- | --- |
| 학습 용이성 | 처음 본 사람이 기본 동작을 쉽게 하나 |
| 효율성 | 익숙해진 뒤 얼마나 빨리 끝내나 |
| 기억 용이성 | 오랜만에 와도 다시 배우지 않고 쓰나 |
| 오류 | 오류가 얼마나 자주·심각하게 나고, 쉽게 복구되나 |
| 만족도 | 주관적으로 만족하나 |

## 장애인 참가자와 사용성 테스트하기

| 단계 | 할 일 |
| --- | --- |
| 목표·과제 | 디자이너·PM·개발자·QA가 함께 목표를 정한다. 보조 기술 사용자는 과제가 오래 걸리므로 중요한 과제부터 고르되, 복잡한 절차를 테스트용으로 단순화하지 않는다 |
| 일정 | 이동 동행, 보조 기술 설정 시간까지 잡는다. 세션 사이에 1시간 정도 여유를 둔다 |
| 모집 | 병원·특수학교·정보 접근 센터를 통해 찾는다. 사용 기기·브라우저·보조 기술, 녹화와 관찰자 여부, 접근 가능한 보상을 미리 알린다 |
| 환경 | 참가자가 장비를 가져오기 어려우면 NVDA·JAWS·ZoomText 같은 도구를 준비한다. 계단 없는 입구, 화장실, 안내견 자리까지 확인한다 |
| 리허설 | 일주일 전 실제 참가자와 리허설한다. 화면 공유 도구와 보조 기술의 충돌 같은 문제를 미리 잡는다 |
| 진행 | 스크린 리더 소리가 관찰을 방해하므로 참가자에게 생각을 크고 분명하게 말해 달라고 한다 |
| 결과 | 버그(스크린 리더가 버튼 상태를 알리지 않음), 콘텐츠(폼 오류를 알아채지 못함), 시각 환경(확대 시 다음 단계가 시야 밖) 문제로 나눠 보고한다. 잘된 점도 남긴다 |

테스트의 진짜 효과는 보고서보다 **관찰한 팀원의 관점 변화**다. 장애인 인권 운동의 구호 "우리 없이 우리에 대해 결정하지 말라(Nothing About Us Without Us)"는 사용자 중심 디자인과 같은 뿌리다.

## 바로 할 수 있는 다섯 가지

1. **마우스를 치우고 키보드로만 써 본다.** 포커스 표시가 항상 보이고, 포커스 순서가 논리적이어야 한다.
2. **낮은 대비를 피한다.** 눈으로 먼저 거슬리는 곳을 찾고 대비 검사 도구로 확인한다.
3. **자동 검사를 돌린다.** axe DevTools, Lighthouse, WebAIM의 WAVE, Accessibility Insights 같은 도구가 라벨 누락 같은 문제를 빨리 잡는다. 다만 자동 검사는 **일부 문제만** 찾는다. 키보드로 끝까지 할 수 있는지 같은 건 사람이 확인해야 한다.
4. **접근성 페이지를 둔다.** 취한 조치와 문제를 알릴 연락처를 밝힌다.
5. **쉬운 말로 쓴다.** 전문용어를 줄이고, 제목·문단·목록으로 나누고, 한 문단에 요점 하나를 둔다.

"월 얼마에 100% 준수"를 약속하는 오버레이 솔루션은 지름길이 아니다. 접근성에는 교육과 우선순위 외에 지름길이 없다.

## 조직 차원의 접근성

접근성은 한 팀의 체크리스트가 아니라 조직의 우선순위다.

| 원칙 | 내용 |
| --- | --- |
| 결정권자 중에 당사자를 둔다 | 장애가 있는 리더나 최고접근성책임자(CAO) 같은 역할이 있으면 우선순위가 유지된다 |
| 장애인을 위한 해결책을 확장한다 | 장애인 직원용 재택 지원 키트, 회의 앱의 "손 들기"처럼 포용을 위해 만든 것이 결국 모두에게 쓰인다 |
| 실제 사용 데이터를 본다 | 큰 글꼴·확대·고대비 설정 비율 같은 통계는 접근성 투자의 근거가 된다 |
| 당사자 네트워크를 만든다 | 장애가 있는 동료가 디자이너와 직접 이야기하면 이론 교육보다 효과가 크다 |
| 전문가를 키운다 | 모든 직군이 기준을 익힐 때까지 접근성 전문가와 교육 과정이 필요하다 |

## 정리

- 장애는 능력과 환경의 불일치다. 접근성은 결국 더 많은 사람을 위한 설계다.
- 브라우저는 시맨틱 HTML로 접근성 트리를 만든다. 의미에 맞는 마크업이 보조 기술 지원의 기본이다.
- WCAG는 최소선이다. 지켜도 쓰기 어려울 수 있으니 장애인과 직접 테스트한다.
- 자동 검사와 오버레이는 보조 수단이다. 키보드 테스트와 사람의 판단이 필요하다.
- **가장 큰 장벽은 기술이 아니라 우선순위다.**
