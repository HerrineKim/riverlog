> 고려사이버대학교 「UI/UX 디자인」(2024-2학기) 강의 내용을 바탕으로 정리했다.

## 사용성이란

**사용성(usability)** 은 사용자가 특정 상황에서 목표를 이루려고 시스템을 쓸 때 "쓰기 쉬운가"다. 국제 표준 ISO 9241-11은 세 축으로 정의한다.

| 축 | 질문 | 재는 법 |
| --- | --- | --- |
| 효과성(effectiveness) | 원하는 목표를 제대로 이뤘나 | 과업 성공률, 오류 수 |
| 효율성(efficiency) | 얼마나 적은 시간과 노력으로 이뤘나 | 완료 시간, 클릭 수, 최적 경로 대비 이동 |
| 만족도(satisfaction) | 쓰는 경험이 만족스러웠나 | 설문(SUS 등), 인터뷰 |

제이콥 닐슨(Jakob Nielsen)은 이를 실무에서 볼 속성으로 풀었다. 처음 쓰는 사람이 얼마나 빨리 익히나(**학습 용이성**), 익숙해진 뒤 얼마나 빨리 하나(**효율성**), 한동안 안 쓰다 돌아와도 기억나나(**기억 용이성**), 실수가 적고 쉽게 회복되나(**오류**), 쓰기 즐거운가(**만족도**). 여기에 피드백, 유연성(개인화), 보편성(장애와 문화 다양성), 안전성(데이터 보호)까지 사용 편의성 기준으로 넓혀 보기도 한다.

사용성의 심리학적 바탕(지각, 기억, 어포던스)은 [[interface-psychology|인터페이스 심리학]]에 있다.

### 예쁘면 너그러워진다

사람은 보기 좋은 화면의 사용성 문제에 더 관대하다(**심미적 사용성 효과**). 그래서 테스트에서 "좋아요"라는 말이 나와도 실제로 과업을 해냈는지 따로 봐야 한다. 반대로 미관을 위해 사용성을 깎으면(대비 낮은 회색 글자, 레이블 없는 아이콘) 사용자는 금방 인내심을 잃는다.

## 휴리스틱 평가

**휴리스틱 평가(heuristic evaluation)** 는 사용자 없이 UX 전문가가 정해진 원칙 목록에 비춰 화면을 점검하는 방법이다.

- 평가자 한 명은 문제의 일부만 찾는다. 닐슨의 연구에서는 **3~5명**이 각자 따로 평가한 뒤 결과를 합칠 때 비용 대비 효과가 가장 좋았다.
- 빠르고 싸서 개발 초기, 와이어프레임이나 프로토타입 단계에서 큰 문제를 미리 걸러 낸다.
- 찾은 문제마다 **심각도**를 매긴다. 흔히 0(문제 아님)부터 4(출시 전 반드시 고침)까지 다섯 단계를 쓰고, 빈도·영향·반복성(한 번 겪으면 피할 수 있나)을 함께 본다.
- 한계: 전문가의 판단이라 실제 사용자가 막히는 지점을 놓치거나, 실제로는 문제가 안 되는 것을 문제로 꼽을 수 있다. 사용성 테스트로 보완한다.

### 닐슨의 10가지 휴리스틱

1994년에 정리된 목록이 지금도 거의 그대로 쓰인다. 원칙마다 점검 질문을 붙였다.

| # | 원칙 | 점검 질문 |
| --- | --- | --- |
| 1 | 시스템 상태를 보여 준다 (Visibility of system status) | 누른 뒤 반응이 바로 오나? 지금 무엇이 진행 중이고 어디쯤인지 보이나? |
| 2 | 현실 세계와 맞춘다 (Match between system and the real world) | 사용자가 쓰는 말인가, 개발 용어인가? 아이콘과 순서가 현실의 관습과 맞나? 누르면 무슨 일이 생길지 예측되나? |
| 3 | 사용자에게 통제권과 자유를 준다 (User control and freedom) | 실수로 들어간 곳에서 빠져나갈 비상구가 있나? 실행 취소와 다시 실행이 되나? |
| 4 | 일관성과 표준을 지킨다 (Consistency and standards) | 같은 것을 같은 이름·모양·위치로 부르나? 플랫폼 관례(뒤로 가기, 링크 색)를 따르나? |
| 5 | 오류를 예방한다 (Error prevention) | 지울 수 없는 동작 전에 확인하나? 선택할 수 없는 항목이 분명히 구분되나? 입력 형식과 예시를 미리 보여 주나? |
| 6 | 기억하게 하지 말고 알아보게 한다 (Recognition rather than recall) | 앞 화면의 정보를 외워야 다음 화면을 쓸 수 있나? 메뉴와 선택지가 보이나? 관련 항목을 묶고 이름을 붙였나? |
| 7 | 유연하고 효율적이게 한다 (Flexibility and efficiency of use) | 숙련자를 위한 단축키, 바로 가기, 즐겨찾기가 있나? 자주 하는 설정을 기억하나? 시스템이 대신할 수 있는 일을 사용자에게 시키지 않나? |
| 8 | 간결하고 미적인 디자인 (Aesthetic and minimalist design) | 지금 필요 없는 정보가 필요한 정보와 경쟁하지 않나? 입력 항목이 꼭 필요한 것만 있나? |
| 9 | 오류를 알아차리고 진단하고 회복하게 돕는다 (Help users recognize, diagnose, and recover from errors) | 오류 메시지가 쉬운 말로 무엇이 왜 잘못됐는지, 어떻게 고치는지 알려 주나? 오류 코드만 띄우지 않나? |
| 10 | 도움말과 문서 (Help and documentation) | 도움말 없이 쓰는 게 최선이지만, 필요할 때 맥락에 맞는 도움을 찾기 쉬운가? 도움말과 작업 화면을 쉽게 오가나? |

이 목록은 출발점이다. 대상 제품에 맞게 항목을 고르거나 더한다. 접근성 관점의 휴리스틱은 [[accessible-design-process|디자인 단계의 접근성]]에, 문구 점검 기준은 [[ux-writing|UX 라이팅]]에, 입력 폼에 특화된 기준은 [[form-usability|폼 사용성]]에 있다.

## 사용성 테스트

**사용성 테스트(UT)** 는 실제 사용자(또는 대표 사용자)에게 과업을 주고, 수행하는 모습을 관찰하며 문제와 원인을 찾는 방법이다. 전자기기, 앱, 웹, 게임처럼 사람이 조작하는 것이라면 무엇이든 대상이 된다.

얻는 것은 두 가지다.

- **구체적인 문제와 원인**: 어느 단계에서 왜 막혔는지. 기존 버전이나 경쟁 제품과 비교하면 개선 여지도 보인다.
- **우선순위**: 문제마다 중요도를 매겨 개발 팀이 무엇부터 고칠지 빨리 정한다.

### 진행 순서

| 단계 | 할 일 |
| --- | --- |
| 1. 계획 | 이해관계자 인터뷰로 목표를 정한다. 무엇을 알고 싶은지, 어떤 방법(대면·원격, 진행자 유무)으로 할지 계획서에 적는다 |
| 2. 참가자 | 대상자 프로필(직업, 사용 경험 유무, 연령대 등)을 정하고 모집한다 |
| 3. 과제 시나리오 | 테스트할 화면 범위를 정하고, 실제 상황처럼 과제를 쓴다. "장바구니에 담긴 상품 하나를 빼고 주문하세요"처럼 목표만 주고 방법은 알려 주지 않는다 |
| 4. 진행 | 참가자가 과제를 하며 생각을 소리 내 말하게 하고(think-aloud), 진행자는 개입을 최소화한다. 시간·성공 여부·오류를 기록한다 |
| 5. 정리 | 기록을 과제별·단계별로 정리하고 사용자 발언(VOC)을 모은다 |
| 6. 분석 | 문제가 생긴 원인을 휴리스틱에 비춰 분류하고, 심각도와 개선안을 낸다 |

참가자 수는 많지 않아도 된다. 닐슨은 정성 테스트에서 **5명** 정도면 주요 문제 대부분이 나오고, 그 이상은 같은 문제가 반복된다고 봤다. 20명을 한 번에 하기보다 5명씩 고치고 다시 테스트하는 편이 낫다. 성공률이나 시간을 통계적으로 비교하려면 더 많은 인원이 필요하다.

### 무엇을 재나

| 범주 | 지표 |
| --- | --- |
| 효과성 | 과업 성공률(%), 오류 수와 유형, 오류에서 회복했는지 |
| 효율성 | 과업 완료 시간, 클릭·탭 수, 최적 경로 대비 실제 경로의 비율, 특정 기능까지 걸린 시간 |
| 학습 용이성 | 처음 시도와 반복 시도의 차이, 설명 없이 바로 쓸 수 있는 정도 |
| 일관성 | 비슷한 과업에서 같은 방식으로 조작하는지(시각·기능 일관성) |
| 만족도 | 과업 직후 난이도 한 문항(SEQ), 테스트 끝에 SUS(10문항, 0~100점) |

정량 지표는 "어디서" 문제가 생겼는지를, 관찰과 발언은 "왜" 생겼는지를 알려 준다. 둘을 함께 본다.

## 휴리스틱 평가와 사용성 테스트

| | 휴리스틱 평가 | 사용성 테스트 |
| --- | --- | --- |
| 누가 | UX 전문가 3~5명 | 실제·대표 사용자 5명 안팎 |
| 언제 | 아주 이른 단계부터 | 동작하는 프로토타입이나 제품이 있을 때 |
| 비용 | 낮다 | 모집·진행·분석에 시간이 든다 |
| 강점 | 원칙 위반을 빠짐없이 훑는다 | 실제로 막히는 지점과 이유를 본다 |
| 약점 | 실제 사용자의 행동과 다를 수 있다 | 과제로 정하지 않은 부분은 못 본다 |

먼저 휴리스틱 평가로 뻔한 문제를 걷어 내고, 남은 시간을 사용성 테스트에 쓰는 순서가 효율적이다. 리서치 방법 전체를 단계별로 고르는 법과 참가자 윤리는 [[user-research|사용자 리서치]]에, 접근성 측면의 평가 절차는 [[accessibility-evaluation|접근성 평가]]에 있다.

## 정리

- 사용성은 효과성·효율성·만족도. 학습 용이성, 기억 용이성, 오류 회복까지 본다.
- 휴리스틱 평가는 전문가 몇 명이 10가지 원칙으로 싸고 빠르게 훑는 방법이다. 문제마다 심각도를 매긴다.
- 사용성 테스트는 과제 시나리오로 실제 사용자를 관찰한다. 5명씩 반복하고, 성공률·시간·오류와 발언을 함께 분석한다.
- 예쁜 화면은 문제를 가린다. 말보다 행동을 본다.
