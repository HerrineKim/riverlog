## 디자인 시스템이란

디자인 시스템(design system)은 **팀이 제품의 목적에 맞는 디자인을 일관되게 적용하도록 정한 규칙의 묶음**이다. 버튼 모음(UI 키트)에 그치지 않고, 원칙·스타일·컴포넌트·문서와 그것을 바꾸는 절차까지 포함한다.

"바퀴를 다시 발명하지 말라"는 말처럼, 잘 만든 바퀴 하나를 언제든 가져다 쓰게 해 두고 **진짜 문제(사용자 경험)에 시간을 쓰게 하는 것**이 목적이다.

## 없으면 생기는 일

| 직군 | 문제 |
| --- | --- |
| 디자이너 | 같은 컴포넌트를 사람마다, 시기마다 조금씩 다르게 다시 그린다. 한 화면 안에서도 미세하게 다른 버튼이 쌓인다 |
| 개발자 | 디자인의 컴포넌트가 기존 것인지 새것인지 알 수 없어 매번 새로 만든다. 비슷한 컴포넌트가 여러 벌이라 수정·테스트가 번거롭다 |
| 기획자 | 작업 기간과 예외를 가늠하기 어렵고 확인할 것이 많다 |
| 사용자 | 같은 기능이 화면마다 달라 보여 사용성과 브랜드 경험이 흐려진다 |

시스템이 주는 효과는 **작업 시간 단축, 제품 전반의 일관성, 커뮤니케이션 비용 감소**다. 컴포넌트 이름만으로 소통이 끝나고, 1px 단위 디자인 QA가 줄고, 기능까지 담은 공통 컴포넌트라 버그와 기능 QA도 줄어든다. 새 구성원의 온보딩도 빨라진다. 피그마를 다룰 줄 아는 기획자·개발자가 기존 컴포넌트를 조합해 간단한 화면을 직접 만들 수도 있다.

## 구성 요소

| 층 | 내용 |
| --- | --- |
| 디자인 원칙·가이드라인 | 제품이 지향하는 원칙과, 그에 맞춰 화면을 구성하는 방법 |
| 파운데이션(스타일) | 색, 타이포그래피, 간격, 그리드, 그림자, 아이콘, UX 라이팅(보이스 톤, [[ux-writing\|UX 라이팅]]). 코드에서는 **디자인 토큰**이 된다 |
| 컴포넌트·패턴 | 버튼, 입력, 모달, 탭 등 재사용 단위와 그 조합 패턴. 모양뿐 아니라 **동작(상태, 이벤트)** 까지 정의한다 |
| 문서·거버넌스 | 사용 예, 변경 이력(누가 만들고 언제 반영했나), 새 요청을 받아들이는 절차 |

공개된 디자인 시스템(Google Material Design 3, Microsoft Fluent 2, IBM Carbon, Atlassian, Adobe Spectrum 등)은 구조와 문서화 방식을 참고하기 좋다.

## 언제 도입하나

디자인 시스템은 초기 비용이 큰 투자다. 다음을 함께 본다.

- **조직 규모와 의지**: 사람이 늘수록 비일관성이 생산성을 갉아먹는다. 구성원이 규칙을 지킬 의지가 없으면 만들어도 쓰이지 않는다.
- **로드맵과 역량**: 대규모 개편, 새 시장·채널 확장이 예정돼 있는지, 만들고 유지할 기술 역량이 있는지.
- **도입 시점**: 전면 리디자인이나 프론트엔드 프레임워크 전환처럼 **모든 화면을 다시 만드는 때**가 최적기다. 레거시를 덜 남기고 처음부터 시스템 위에 쌓을 수 있다.
- **작은 팀도 필요하다**: 디자이너가 한 명이어도 ① 반년 뒤의 나는 오늘 세운 규칙을 기억하지 못하고, ② 디자이너 혼자서는 개발된 컴포넌트의 구조까지 맞출 수 없고, ③ 개발자는 여러 명일 수 있다. 혼자 세운 규칙보다 **합의되고 기록된 규칙**이 오래간다.
- 처음부터 다 만들기보다 검증된 오픈 소스 라이브러리를 바탕으로 키우는 편이 현실적이다.

### 모양이 같아도 같은 컴포넌트가 아니다

디자이너와 개발자가 각자 "재사용 가능한 모달"을 만들어 겉모양이 똑같아도, 개발 쪽에서 왼쪽 회색 버튼을 '닫기 전용'으로 고정했다면 "왼쪽 버튼으로 알림 끄기" 같은 다음 요청에 쓸 수 없다. 컴포넌트를 고치면 기존 화면이 모두 영향을 받고, 피하려면 비슷한 모달을 또 만들게 된다. 그래서 컴포넌트는 **모양과 함께 어떤 슬롯과 동작을 바꿀 수 있는지(props)를 디자이너와 개발자가 함께 정해야** 한다.

## 구축·개편 절차

```text
1. 감사(inventory)   지금 쓰는 스타일·컴포넌트를 전부 모으고, 쓰는 것과 안 쓰는 것을 가른다
2. 목표 범위         예: 파운데이션과 공통 UI의 디자인 파일 ↔ Storybook 일치율 100%
3. 기준 합의         디자인 방향성 · 확장성 · 접근성 · 지속 관리 방식을 디자이너끼리 먼저 정한다
4. 정리·재정의       파운데이션 → 컴포넌트 순으로 줄이고 이름을 붙인다 (조금씩 나눠 합의)
5. 개발 합의         구조와 props, 무엇을 시스템에 넣고 무엇을 화면별로 둘지 정한다
6. 구현·QA          실제 서비스에 적용해 화면을 돌며 깨진 곳을 찾는다
7. 릴리스·개선       사용자가 이질감을 느끼지 않게 기존 인상은 유지하고, 버전을 올리며 계속 다듬는다
```

### 인터페이스 인벤토리: 1단계를 설득 도구로

1단계 감사는 **인터페이스 인벤토리(interface inventory)** 로 한다. 콘텐츠 인벤토리처럼, 지금 화면에 있는 **고유한 UI 패턴을 전부 스크린숏으로 모아 범주별로 묶는** 작업이다. 같은 패턴은 한 번만 찍는다. 한 페이지에 모양이 다른 버튼이 십여 개 모인 슬라이드는 말보다 강하게 시스템의 필요를 보여 준다.

| 단계 | 하는 일 |
| --- | --- |
| 사람 모으기 | 디자이너 혼자가 아니라 개발·콘텐츠·기획·PM이 **한 방에서 함께** 한다. 비일관성의 고통을 모두가 직접 겪어야 시스템을 지지한다 |
| 도구 통일 | 한 슬라이드 도구(공유 문서)에 모두 모은다. 나중에 합치기 쉽다 |
| 범주 나눠 찍기 | 사람마다 범주를 맡는다. 전역 요소(헤더·푸터), 내비게이션, 이미지 종류, 아이콘, 폼, 버튼, 제목, 블록(미디어 객체 같은 묶음), 목록, 상호작용 컴포넌트(아코디언·탭·캐러셀), 미디어, 서드파티 위젯, 광고, 메시지(알림·오류·툴팁·로더), 색, 애니메이션(화면 녹화) |
| 발표 | 범주마다 발견한 것을 보여 주고 이야기한다 |
| 다음 단계 | 결과를 패턴 라이브러리의 출발점으로 삼고, 이해관계자에게 공유한다 |

### 시각 방향을 싸게 정하는 법

3단계 기준 합의 중 디자인 방향성은 완성 시안(comp)부터 그리지 않고 정한다. 완성 시안부터 그리면 시간이 많이 들고, 한 번 그린 레이아웃에 의견이 묶인다. 그 전에 가벼운 산출물로 미감을 합의한다.

| 산출물 | 무엇을 보여 주나 | 효과 |
| --- | --- | --- |
| 20초 직감 테스트 | 관련 사이트 20~30개를 20초씩 보여 주고 1~10점으로 투표, 최고·최저·논쟁 점수를 토론 | 이해관계자의 취향 차이를 초기에 드러내 공통 미감을 찾는다 |
| 스타일 타일(style tile) | 색·글꼴·질감·아이콘 견본. 레이아웃은 없다 | 무드보드보다 구체적이고 시안보다 빠르다. 페이지가 아니라 **시스템의 재료**로 생각하게 한다 |
| 요소 콜라주(element collage) | 실제 UI 요소(버튼, 카드, 내비게이션)에 그 재료를 입힌 조각 모음 | 레이아웃 없이 실제 인터페이스 느낌을 확인한다 |

이 단계 뒤에야 브라우저 안에서 컴포넌트를 반복해 다듬는다. 디자인이 끝나고 개발이 시작되는 폭포수가 아니라, **개발도 디자인 과정의 일부**로 함께 돈다.

### 흔한 문제와 처방

| 증상 | 처방 |
| --- | --- |
| 이 컴포넌트를 어디서 쓰는지, 누가 만들었는지 매번 메신저로 묻는다 | 컴포넌트마다 용도·담당·반영 여부를 문서에 이력으로 남긴다. 메신저 대화는 휘발된다 |
| 같은 기능인데 디자이너마다 모양이 다르다 | 하나로 통합하고 변형은 variant로 표현한다 |
| 텍스트·배경 대비가 낮다 | 일반 텍스트 4.5:1(WCAG AA)을 만족하도록 색 규칙을 다시 정한다([[color-motion-accessibility\|색과 움직임의 접근성]]) |
| 브랜드 색을 컴포넌트에 직접 박아 다른 브랜드·서비스에서 쓰면 어색하다 | 컴포넌트는 `primary` 같은 의미 토큰을 참조하고, 브랜드별로 토큰 값만 바꾼다([[css-color-variables\|색상 체계 짜기]]) |
| 글꼴 굵기·크기를 그때그때 고른다 | 정보의 위계에 따른 역할별 타입 스케일을 정한다 |

### 규칙 예시

- **타이포그래피**: 가장 많이 보이는 화면에서 실제로 많이 쓰는 크기를 추리고, 단계 사이를 2px 이상 벌려 구분되게 한다. 굵기는 역할에 묶는다. `Display`·`Heading`은 Bold, `Body`·`Caption`은 Regular처럼 두세 가지로 줄인다.
- **버튼**: 모서리·높이 같은 형태를 먼저 통일한다. 이름은 색(`default`, `yellow`)이 아니라 **형태와 강조 수준**으로 짓는다. `Contained`(주요 실행), `Outlined`(보조 액션, 두 버튼 중 낮은 우선순위), `Text`(옵션처럼 가장 낮은 우선순위).
- **아이콘**: 선 굵기·모서리·격자를 맞춰 전부 다시 다듬고, `키워드-모양-색` 같은 규칙으로 이름을 지어 디자인 파일과 코드에서 같은 이름으로 찾게 한다.
- **드물게 쓰는 컴포넌트**(예: 플로팅 버튼)는 시스템에 넣지 않고 화면별로 대응할 수 있다. 시스템에는 자주, 여러 곳에서 쓰는 것부터 넣는다.

### 컴포넌트 이름과 속성 축

흩어진 컴포넌트를 통합할 때는 **무엇이 다르면 다른 컴포넌트이고, 무엇이 다르면 옵션인가**부터 정한다.

| 구분 | 기준 | 예 |
| --- | --- | --- |
| 고정 속성 → 다르면 새 컴포넌트 | 형태, 텍스트 스타일, 높이처럼 거의 바뀌지 않는 것 | 둥근 버튼과 각진 버튼은 별개 |
| 가변 속성 → 옵션(prop) | 자주 바뀌는 것. 주로 색 | 같은 버튼의 테마 색 |

버튼이라면 대개 세 축의 조합으로 정리된다.

| 축 | 값 | 영향 |
| --- | --- | --- |
| `size` | small · medium · large | 높이, 글자·아이콘 크기, 내부 여백 |
| `variant` | contained · outlined · text | 채움·테두리 같은 스타일 |
| `color` | primary · 보조 색 두세 개 | 같은 모양 안의 강조 차이 |

축마다 값을 **적게 제한**해야 「같은 목소리」를 낸다. 축이 정해지면 각 prop을 클래스나 스타일 변형으로 바꾸는 구현은 단순하다. 기존 버튼 사용법과 크게 다르지 않게 만들어야 이전(migration)이 쉽다. 크기는 높이를 고정하고 너비는 기기 폭에 맞춰 늘어나게 둔다.

이름 규칙:

- 용도보다 **형태**를 기준으로 짓고, 컴포넌트 종류(`Button`)를 이름 끝에 둔다.
- `BTN` 같은 약어를 쓰지 않는다. 짧되 필요한 정보는 다 담는다.
- 팀마다 다르게 부르던 이름을 먼저 모두 모아 하나로 정한다. 같은 대상을 다르게 부르는 것이 소통 비용의 가장 큰 원인이다.
- 눌림(pressed) 같은 상태도 컴포넌트 정의에 넣어, 화면마다 따로 확인하지 않게 한다.

다크 모드에서 기본 색이 1:1로 대응하지 않으면 **컴포넌트 전용 색 토큰**을 두기도 한다. 당장은 편하지만 컴포넌트 수만큼 토큰이 불어나므로, 결국 의미 토큰 체계로 모아야 한다. 컴포넌트의 주 사용자는 디자이너이므로 **디자이너가 설계를 주도하고 개발자가 리뷰하는** 방식이 체계를 오래 유지하기 쉽다. 디자이너가 개발 환경을 갖추고 컴포넌트 골격 코드를 직접 쓰는 팀도 있다.

## 코드로 배포하기

여러 프로젝트가 같은 버튼·색·간격을 쓰게 하려면 각 저장소에 스타일을 복사하지 말고 **한 곳에서 만들어 패키지로 배포**한다.

### 디자인 토큰

색상, 간격, 모서리, 폰트 크기, 브레이크포인트처럼 **디자인 결정을 값으로 정의**한 것이 디자인 토큰이다. 값을 Sass·CSS 파일에 두지 않고 플랫폼 중립 형식(JSON)에 한 번만 적어, 웹·iOS·안드로이드가 같은 원천에서 각자의 변수를 생성한다. Salesforce Lightning 디자인 시스템이 처음 이름 붙여 퍼뜨렸다.

```json
{
  "color": {
    "primary": { "$type": "color", "$value": "#5B5CFF" },
    "action": { "$value": "{color.primary}" }
  },
  "spacing": {
    "md": { "$type": "dimension", "$value": { "value": 16, "unit": "px" } }
  }
}
```

토큰 파일 형식은 W3C 디자인 토큰 커뮤니티 그룹(DTCG)의 [Design Tokens Format Module](https://www.designtokens.org/TR/drafts/format/)이 표준이고, 2025년 10월 첫 안정판이 나왔다. `$value`가 있는 객체가 토큰이고, `{color.primary}`처럼 다른 토큰을 참조(alias)한다. 토큰 JSON에서 CSS 변수, TypeScript 상수, 테마 객체를 자동 생성하고(예: Style Dictionary), Figma 변수와도 주고받는다. 토큰을 「결정의 인코딩」으로 보는 관점과 섣부른 시맨틱 토큰의 함정은 [[product-language-design-system|제품 언어로서의 디자인 시스템]]에 있다.

### 컴포넌트

```tsx
<Button variant="contained" size="md" loading={isSubmitting} disabled={isSubmitting}>
  저장
</Button>
```

바닥부터 만들기보다 **shadcn/ui** 같은 접근성이 검증된 컴포넌트를 가져와 토큰과 디자인을 입히는 편이 빠르다. 모바일 대응도 컴포넌트 안에 넣어 두면 화면마다 모바일 시안을 따로 그릴 일이 줄어든다.

### 중앙 저장소(모노레포)와 문서

```text
design-system/
├─ packages/
│  ├─ tokens/      # 색상, spacing, typography, radius
│  ├─ icons/       # 공통 아이콘
│  ├─ ui/          # Button, Input, Modal, Table 등
│  └─ theme/       # 테마, CSS 변수, 다크 모드
├─ apps/
│  └─ storybook/   # 컴포넌트 문서
└─ package.json
```

```javascript
// 각 프로젝트: npm install @my-org/ui @my-org/tokens
import "@my-org/tokens/css"
import { Button, TextField, Modal } from "@my-org/ui"
```

Storybook으로 컴포넌트마다 사용 예와 props를 보여 주면 디자이너·기획자도 실제 컴포넌트를 확인할 수 있다. **디자인 파일과 Storybook이 어긋나는 순간 시스템은 신뢰를 잃는다.** 개편의 출발점이 대개 이 불일치다.

AI 코딩 도구가 읽는 팀 규칙 파일(`SKILL.md`)도 같은 구조로 중앙에서 배포할 수 있다([[claude-skill-building-guide#팀 공용 스킬을 패키지로 배포하기|Claude 스킬 만들기 가이드]]).

## 정리

- 디자인 시스템은 UI 키트가 아니라 원칙·파운데이션·컴포넌트·문서와 변경 절차를 아우르는 **팀의 약속**이다.
- 작은 팀에도 필요하다. 합의되고 기록된 규칙이 사람과 시간의 차이를 메운다.
- 전면 개편·프레임워크 전환 때 도입하고, 감사 → 기준 합의 → 정리 → 개발 합의 → QA 순으로 만든다.
- 이름은 색이 아니라 역할·형태로 짓고, 컴포넌트는 모양과 바꿀 수 있는 동작을 함께 정의한다.
- 토큰 → 컴포넌트 → Storybook을 중앙에서 관리해 패키지로 배포하고, **한 번 만들고 끝이 아니라 버전을 올리며 계속 다듬는다.**
