## 기술 스택이란

기술 스택은 프로젝트에 쓰는 언어·프레임워크·DB·인프라·도구의 묶음이다. 개발은 누군가 만든 기술 위에 내 기능을 얹는 일이라, **프로젝트는 고른 스택에 의존할 수밖에 없다**. 스택은 개발 속도, 유지 보수, 팀 협업, 사람 뽑기, 장기 생존에 모두 영향을 준다.

스택은 혼자 쓰지 않는다. 누군가 문제를 느껴 새 방법을 내놓고, 비슷한 문제를 겪는 사람들이 묻고 답하며 고치는 과정에서 단단해진다. 그래서 **커뮤니티가 스택을 키운다**. 커뮤니티가 없는 기술은 막혔을 때 도움을 받을 곳이 없고, 그 인식이 다시 사람을 떠나게 하는 악순환에 빠진다.

## 유행은 어떻게 만들어지나

### 기술 수용 주기

| 성향 | 속마음 | 역할 |
| --- | --- | --- |
| 혁신가(Innovators) | "문제가 있네. 새로 만들어야겠다" | 위험을 감수하고 새 도구를 만든다 |
| 얼리어답터(Early Adopters) | "이거 좋다! 여러분 이런 게 있어요" | 발견하고 널리 알린다 |
| 초기 다수(Early Majority) | "흥미로운데 지금 나한테 필요할까?" | 비용을 따져 적절한 때 받아들인다 |
| 후기 다수(Late Majority) | "대세가 되면 그때 하자" | 증거가 쌓인 뒤 도입한다 |
| 회의론자(Laggards) | "지금 기술이면 충분해" | 기존 방식을 끝까지 지킨다. 위험 관리 역할도 한다 |

### 캐즘과 하이프 사이클

- **캐즘(Chasm)**: 얼리어답터의 열광과 대중의 수용 사이에 있는 깊은 골. 새 기술을 배우고 바꾸는 데는 비용이 들기 때문에 대부분은 **주류가 될 것 같을 때에야** 움직인다. 이 골을 넘는 기술은 드물다.
- **하이프 사이클(Hype Cycle)**: 발표 → 과대 기대 → 현실 검증 → 주류 수용. **얼리어답터가 떠들 때가 가장 시끄럽다**. 그들이 열정적으로 홍보하는 이유는 캐즘을 못 넘으면 좋아하는 기술이 사라진다는 걸 알기 때문이다.
- 프론트엔드는 jQuery → AngularJS → React·Vue·Angular → Svelte·Solid·Qwik으로 10년 넘게 거대한 하이프를 겪었고, 글 작성 시점(2024)에는 안정기로 들어섰다고 봤다. 하이프가 지난 것은 몰락이 아니라 안정이다.

### 캐즘을 넘었는지 알아보는 법

혁신가는 "이런 새 문제를 풀 수 있다"고 말한다. 주류가 된 기술은 **알려진 문제의 해결 과정이 공유된다**. 학원 커리큘럼, 취업 블로그, TIL에 등장하면 확실히 넘은 것이다.

## 고르는 기준

| 기준 | 질문 |
| --- | --- |
| 범용성과 특수성 | 우리 프로젝트에 필요한 기술인가? 기본은 보편 스택(예: TypeScript + React)으로, **뾰족한 문제에는 뾰족한 도구**를 섞는다 |
| 학습 비용 | 새로 배워야 하나, 배우기 쉬운가? 비슷한 기능이면 사람들은 결국 쉬운 쪽을 고른다 (Redux → Redux Toolkit → Zustand, 강력하지만 어려운 RxJS) |
| 커뮤니티와 지원 | 모르는 에러를 만나면 답을 찾을 수 있는가? 검색해도 안 나오는 에러의 막막함을 떠올려 보라 |
| 인력 수급 | 이미 배운 사람을 구하기 쉬운가? |
| 지속 가능성 | 오래 업데이트되고 트렌드에 맞는가? 회사는 10~20년을 본다 |

**잘 모르면 커뮤니티가 큰 도구를, 팀원이 가장 많이 아는 도구를** 고르는 게 대부분 안전하다.

### 비주류를 고르면 생기는 일

테오는 사내 자체 프레임워크와 Svelte·RxJS·자작 CSS 도구처럼 비주류 스택을 오래 썼다. 결과물에는 문제가 없었지만 대가가 있었다.

- 회사를 옮길 때 **주류 프레임워크 경험이 없다는 것**이 뼈아팠다. 경험이 있어야 이직이 되는데, 이직을 해야 경험이 쌓인다.
- 인수인계할 때 문서도 없는 자체 프레임워크를 넘기기 부담스러웠다. Svelte로 만든 프로젝트도 담당 팀이 바뀌자 React로 다시 짜였다.
- 생태계가 작으면 "이거 있나?"를 찾기 전에 직접 만들어야 하고, 베스트 프랙티스가 없다.

좋은 기술이라는 것과 회사에서 쓸 기술이라는 것은 다르다. 비주류 기술은 **사이드 프로젝트로 해 보기**에 좋다.

## 트렌드는 범주로 읽는다

**스택 숙련도와 스택 이해도는 다르다.** 숙련도는 특정 도구로 문제를 풀어 본 경험(짬)이고, 이해도는 그 도구가 어떤 범주의 어떤 문제를 풀려는지 아는 것이다. React·Vue·Angular는 모두 "DOM 직접 조작보다 데이터 기반 컴포넌트 렌더링이 낫다"는 같은 범주에 있다. 하나를 잘하면 나머지도 금방 한다.

```text
개발 언어 · 프레임워크 · 메타 프레임워크 · 상태 관리 · 서버 상태 관리
유틸리티 CSS · CSS 방법론 · 컴포넌트 라이브러리 · 디자인 시스템
패키지 관리자 · 런타임 · 번들러·빌드 도구 · 포매터 · 테스트 도구 · 문서화 도구
```

새 기술이 나오면 두 가지만 묻는다.

1. 기존 범주의 어떤 문제를 개선하려는가?
2. 전에 없던 **새 범주와 패러다임**을 만드는가? (jQuery → 프레임워크처럼) 이쪽이면 더 주의 깊게 본다.

범주마다 주류 하나를 숙련하고 나머지는 배경과 코어 컨셉만 이해해도 트렌드를 따라가기에 충분하다. 2024년 시점의 무난한 조합(TypeScript, React, Next.js, TanStack Query, Zustand, TailwindCSS, Vite, Prettier, Storybook, Playwright 등)은 바뀔 수 있으니 범주 지도만 기억한다.

## 레거시를 대하는 자세

- 기술은 **사람들이 더 이상 배우고 싶어 하지 않을 때** 레거시가 된다. 오래된 것이 곧 레거시는 아니다. 아직 쓰인다면 이유가 있다.
- 표준이 바뀌는 데는 시간이 오래 걸린다. **늦은 다수여도 괜찮다**. 다만 미루다 컴포트 존에 숨는 기술 꼰대가 되지는 않는다.
- 커리어에서 스택 전환은 최소 한두 번 온다. 불안해할 필요는 없지만 준비는 한다.
- 내 성향과 팀원의 성향이 수용 주기의 어디인지 알면 스택 논쟁이 편해진다. 성향은 틀린 게 아니라 다른 것이다.

## 정리

- 스택은 함께 쓰는 것이라 **커뮤니티와 생태계**가 기술의 수명을 정한다.
- 새 기술 대부분은 캐즘을 넘지 못한다. 가장 시끄러운 때는 얼리어답터 구간이니 조급해할 필요 없다.
- 범용성·학습 비용·커뮤니티·인력·지속 가능성으로 고르고, 모르면 다수가 쓰는 것을 쓴다.
- 도구 하나보다 **범주와 문제 인식**을 이해하면 무엇이 나와도 따라갈 수 있다.
