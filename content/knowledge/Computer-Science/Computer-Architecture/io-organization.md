## 입출력 인터페이스와 장치 컨트롤러

CPU와 주변 장치 사이의 통로를 컴퓨터 구조 교재는 **입출력 인터페이스**, 운영체제 교재는 **장치 컨트롤러**(입출력 제어기)라고 부른다. 신호 방식·전송 속도·데이터 형식의 차이를 메우고, 여러 장치의 순서와 우선순위를 조정한다.

| 역할 | 설명 |
| --- | --- |
| 통신 중개 | CPU와 입출력장치 사이를 잇고, 장치의 신호·코드를 메모리 워드로 바꾼다 |
| 오류 검출 | 장치와 주고받은 데이터의 오류를 확인한다 |
| 데이터 버퍼링 | 버퍼에 모았다가 한꺼번에 보내거나, 한꺼번에 받아 조금씩 보내 전송률 차이를 완화한다 |

| 내부 레지스터 | 담는 것 |
| --- | --- |
| 데이터 레지스터 | CPU와 장치가 주고받을 데이터. 데이터가 많은 장치는 RAM을 쓰기도 한다 |
| 상태 레지스터 | 장치가 준비됐는지, 오류가 있는지 |
| 제어 레지스터 | 장치가 수행할 일에 대한 제어 정보와 명령 |

상태 레지스터와 제어 레지스터는 장치에 따라 **상태/제어 레지스터** 하나로 합쳐 쓰기도 한다. 모든 입출력 장치는 하나 이상의 컨트롤러에 연결되고, 컨트롤러 하나에 여러 장치가 붙기도 한다.

**장치 드라이버**는 장치 컨트롤러를 감지하고 제어하는 OS 쪽 소프트웨어다. 컨트롤러가 장치와 컴퓨터를 잇는 **하드웨어 통로**라면, 드라이버는 그 컨트롤러를 어떻게 다룰지 아는 **소프트웨어 통로**다. 운영체제가 드라이버를 인식하고 실행해야 어느 회사의 어떤 장치든 쓸 수 있다. 그래서 새 장치를 연결했는데 인식되지 않으면 가장 먼저 드라이버가 설치·동작하는지를 확인한다.

## 입출력 방법

| 방법 | 동작 | CPU 부담 |
| --- | --- | --- |
| 프로그램 입출력 | CPU가 컨트롤러의 레지스터를 직접 읽고 쓴다. 쓰기 명령 → 상태 레지스터를 주기적으로 확인(폴링) → 준비되면 데이터 레지스터에 쓴다 | 큼 |
| 인터럽트 기반 입출력 | CPU는 명령만 내리고 다른 일을 하다가, 컨트롤러가 거는 인터럽트를 받아 처리한다 | 중간 |
| DMA 입출력 | DMA 컨트롤러가 장치와 메모리 사이 전송을 맡고, 끝나면 인터럽트로 알린다 | 작음 |
| 입출력 프로세서(IOP) | 자체 명령어 프로그램을 실행하는 입출력 전담 프로세서 | 가장 작음 |

### 폴링과 인터럽트

| 비교 | 폴링 | 인터럽트 |
| --- | --- | --- |
| 동작 | CPU가 장치의 상태 레지스터를 주기적으로 확인한다 | 장치가 준비되면 CPU에 신호를 보낸다 |
| 장점 | 구현이 단순하다. 이벤트가 매우 잦으면 확인할 때마다 일이 있어 낭비가 적고 지연도 짧다 | 이벤트가 드물 때 CPU가 그동안 다른 일을 한다 |
| 단점 | 이벤트가 드물면 확인이 헛수고라 CPU를 낭비한다 | 인터럽트마다 상태 저장·복원 비용이 든다. 너무 잦으면 처리만 하다 실제 일을 못 하는 인터럽트 폭주(livelock)가 생긴다 |

그래서 고속 장치는 둘을 섞는다. Linux 네트워크 스택의 **NAPI**는 첫 패킷은 인터럽트로 받고, 트래픽이 많은 동안은 인터럽트를 끄고 폴링하다가 조용해지면 인터럽트로 돌아간다. DPDK 같은 사용자 공간 네트워킹과 초고속 NVMe 저장 장치의 폴링 모드는 아예 폴링만 쓴다.

### 입출력 버퍼링

버퍼는 속도나 전송 단위가 다른 두 쪽 사이에서 데이터를 잠시 담아 두는 메모리다. 다른 곳에 원본이 있는 데이터의 사본을 빠른 곳에 두는 캐시와 달리, 버퍼는 옮기는 도중의 데이터를 담는다.

| 쓰는 이유 | 예 |
| --- | --- |
| 속도 차이 흡수 | 느린 장치가 데이터를 모으는 동안 CPU는 다른 일을 한다. 키보드 입력 버퍼, 프린터 스풀 |
| 전송 단위 맞추기 | 바이트 단위로 쓰는 프로그램과 블록 단위로 읽고 쓰는 디스크·네트워크 사이 |
| 호출 횟수 줄이기 | 작은 쓰기를 모아 한 번에 보낸다. stdio 버퍼 |
| 복사 의미 지키기 | `write` 호출이 끝난 뒤 프로그램이 자기 버퍼를 고쳐도, 이미 커널 버퍼에 복사된 데이터는 바뀌지 않는다 |

| 구조 | 동작 |
| --- | --- |
| 단일 버퍼 | 버퍼가 찰 때까지 채우고, 비우는 동안은 다음 데이터를 받지 못한다 |
| 이중 버퍼 | 하나를 채우는 동안 다른 하나를 처리해 두 일을 겹친다. 화면 출력의 더블 버퍼링 |
| 원형 버퍼(링 버퍼) | 생산자와 소비자가 같은 배열을 돌며 쓰고 읽는다. 네트워크 카드의 수신 링, `io_uring`의 제출·완료 큐 |

운영체제가 두는 stdio 버퍼와 페이지 캐시의 두 층은 [[unix-file-io|UNIX 파일 입출력]]에 있다.

### 버스 구성과 I/O 주소

| 구성 | 설명 |
| --- | --- |
| 버스를 따로 둠 | 메모리 버스와 I/O 버스가 분리된다. I/O 쪽은 IOP가 맡는 경우가 많다 |
| 공통 버스 + 제어선 분리 → **격리형 I/O**(Port-mapped) | 메모리와 I/O 주소 공간이 따로다. `IN`/`OUT` 같은 전용 명령을 쓰고, 메모리 주소 공간을 온전히 쓴다 |
| 공통 버스 + 제어선 공통 → **메모리 맵 I/O** | 메모리 주소 일부를 장치에 할당해 일반 load/store로 접근한다. 전용 명령이 없어 구조가 단순하다(임베디드에서 흔함) |

## 레지스터로 장치를 직접 다루는 예

마이크로컨트롤러에서는 장치 컨트롤러의 레지스터가 정해진 이름(주소)으로 드러나 있어, 프로그램이 그 레지스터를 직접 읽고 써서 입출력을 한다. AVR(ATmega128) 기준으로 보면 다음과 같다.

| 레지스터 | 역할 |
| --- | --- |
| `DDRx` (Data Direction Register) | 포트 x의 각 핀을 출력(1)으로 쓸지 입력(0)으로 쓸지 정한다 |
| `PORTx` | 출력으로 정한 핀에 내보낼 값을 쓴다 |
| `PINx` | 입력으로 정한 핀의 현재 값을 읽는다 |
| `SREG`의 I 비트 | 플래그 레지스터의 전역 인터럽트 허용 비트. 1이어야 외부(하드웨어) 인터럽트를 받는다 |
| `EIMSK` | 외부 인터럽트 INT0~INT7을 하나씩 허용·차단하는 마스크 |
| `EICRB` | INT4~INT7을 신호의 어느 순간(하강 에지 등)에 일으킬지 정한다 |

포트 A에 LED 8개, 포트 E의 4번 핀(INT4)에 스위치가 연결된 보드에서 스위치를 누를 때마다 LED 전체를 켜고 끄는 코드는 다음과 같다.

```c
#include <avr/io.h>
#include <avr/interrupt.h>

volatile uint8_t data = 0x00;

ISR(INT4_vect) {            // 스위치가 눌리면 실행되는 인터럽트 서비스 루틴
    data = ~data;           // 모든 비트를 뒤집는다
}

int main(void) {
    DDRA = 0xFF;            // 포트 A 8개 핀을 모두 출력으로
    DDRE &= ~(1 << PE4);    // PE4(스위치)를 입력으로
    EICRB = 1 << ISC41;     // INT4를 하강 에지에서 일으킨다
    EIMSK = 1 << INT4;      // 외부 인터럽트 중 INT4만 허용
    sei();                  // SREG의 I 비트를 1로: 인터럽트 전역 허용
    for (;;) PORTA = data;  // 현재 값을 LED로 내보낸다
}
```

`PORTA = 0b10000001`처럼 쓰면 양 끝 LED만 켜진다(1을 쓰면 켜지는 회로 기준). 운영체제가 있는 PC에서는 이 일을 장치 드라이버가 커널 안에서 하고, 사용자 프로그램은 시스템 콜로 요청한다([[system-structure|컴퓨터 시스템 구조와 인터럽트]]). 레지스터를 읽고 쓰는 맨 아래 단의 동작은 같다.

## 비동기 데이터 전송

송신과 수신이 같은 클럭을 공유하지 않을 때는 신호로 타이밍을 맞춘다. **스트로브 제어**는 한쪽이 "지금 데이터가 버스에 있다"고만 알려 상대가 받았는지 확인할 수 없다. **핸드셰이킹**은 응답 신호를 하나 더 두고, 응답이 없으면 타임아웃으로 감지한다.

| 시작하는 쪽 | 핸드셰이킹 신호 순서 |
| --- | --- |
| 송신 측 | 송신이 *data valid*를 올림 → 수신이 받고 *data accepted*를 올림 → 송신이 *data valid*를 내림 |
| 수신 측 | 수신이 *ready for data*를 올림 → 송신이 데이터와 *data valid*를 올림 → 수신이 받고 *ready for data*를 내림 |

### 비동기 직렬 전송

- 문자 하나에 **시작 비트 1개 + 데이터 비트 + 정지 비트**를 붙인다. 예: 1 + 8 + 2 = 11비트로 8비트 문자 하나. 한 비트의 시간은 1 / 전송 속도(bps)다.
- 이를 처리하는 칩이 **UART**다. 시프트 레지스터로 병렬 데이터를 직렬로 바꾸며, 송수신 모두 **이중 버퍼**라 한 문자를 보내는 동안 CPU가 다음 문자를 미리 넣어 둘 수 있다.
- 속도가 다른 두 장치 사이에는 **FIFO 버퍼**를 둔다.

| 수신 에러 | 원인 |
| --- | --- |
| 패리티 에러 | 받은 문자의 패리티가 맞지 않는다 |
| 프레이밍 에러 | 정지 비트 자리에서 정지 비트가 검출되지 않는다 |
| 오버런 에러 | CPU가 앞 문자를 읽기 전에 다음 문자가 도착해 덮어쓴다 |

## 인터럽트 처리

### 처리 순서

```text
1. 장치(컨트롤러)가 CPU에 인터럽트 요청 신호를 보낸다
2. CPU는 실행 사이클이 끝나고 다음 명령어를 인출하기 전에 요청이 있는지 확인한다
3. 인터럽트 플래그(IEN)로 지금 받아들일 수 있는지 본다 (NMI는 막을 수 없다)
4. 받아들이면 PC와 레지스터·플래그(PSW)를 저장한다
5. 인터럽트 벡터에서 서비스 루틴(ISR, 인터럽트 핸들러)의 시작 주소를 찾아 실행한다
6. ISR이 끝나면 저장한 상태를 복구해 하던 일을 이어 간다
```

장치마다 처리 방법이 달라 ISR도 장치마다 따로 있다. 처리 루틴 주소가 메모리의 고정 위치에 있으면 **비벡터 인터럽트**, 장치가 루틴의 위치(벡터 주소, VAD)를 알려 주면 **벡터 인터럽트**다.

중첩 인터럽트를 허용할 때는 4번과 5번 사이에 같거나 낮은 우선순위 요청을 마스크로 막고 IEN을 다시 켜서 더 높은 우선순위만 받아들인다. 종료할 때는 IEN을 끄고, 레지스터를 복원하고 처리한 요청 비트를 지운 뒤, 마스크를 되돌리고 복귀 주소를 PC에 넣으며 IEN을 다시 켠다.

### 우선순위 정하기

여러 장치가 동시에 요청하면 누구를 먼저 처리할지 정해야 한다. 소프트웨어로 장치를 하나씩 조사(폴링)하면 느리므로 하드웨어로 정한다.

| 방식 | 동작 |
| --- | --- |
| 데이지 체인 | 장치들을 우선순위 순으로 직렬 연결한다. CPU의 승인(acknowledge) 신호가 높은 장치부터 전달되고, 요청한 장치가 받으면 자기 VAD를 버스에 올리고 전달을 멈춘다 |
| 병렬 우선순위 | 장치마다 비트 하나인 **인터럽트 레지스터**와 개별 허용·차단용 **마스크 레지스터**를 AND해 **우선순위 인코더**에 넣으면, 가장 높은 요청의 VAD만 나온다. **IEN 플립플롭**이 전체를 켜고 끄며, CPU는 인터럽트를 인식하면 보통 IEN을 0으로 만든다 |
| PIC | 현대 PC의 **PIC(Programmable Interrupt Controller)가** 컨트롤러들의 요청을 받아 하나를 골라 CPU에 보낸다. CPU가 확인 신호를 보내면 PIC가 데이터 버스로 인터럽트 벡터를 넘긴다. 여러 개를 계층적으로 연결해 쓴다 |

정전·하드웨어 고장처럼 플래그로 막을 수 없는 최우선 인터럽트가 **NMI(Non-Maskable Interrupt)이며**, PIC를 거치지 않는다.

## DMA와 입출력 프로세서

프로그램 입출력과 인터럽트 기반 입출력에서는 장치와 메모리 사이의 데이터가 **반드시 CPU 레지스터를 거친다.** 디스크의 데이터를 메모리로 옮기려면 CPU가 컨트롤러의 데이터 레지스터를 읽어 자기 레지스터에 담고, 다시 메모리에 써야 한다. 백업처럼 큰 데이터를 옮기면 CPU가 이 복사에 묶인다. DMA는 이 복사를 CPU 대신 맡아, CPU는 입출력의 시작과 끝에만 관여한다.

DMA 컨트롤러가 **버스 요청(bus request)을** 보내고 CPU가 **버스 승인(bus grant)을** 하면, 컨트롤러가 버스를 넘겨받아 직접 전송한다. 그동안 CPU는 메모리 버스를 쓸 수 없다. CPU는 시작 주소(주소 레지스터), 워드 수(워드 카운트 레지스터), 읽기/쓰기 모드(제어 레지스터)를 설정해 시작만 시키고, 끝나면 인터럽트를 받는다.

| 전송 방식 | 동작 |
| --- | --- |
| 버스트 전송 | 버스를 잡은 동안 블록 전체를 연속 전송. 빠르지만 CPU가 오래 기다린다 |
| 사이클 스틸링 | 한 번에 한 워드만 보내고 버스를 돌려준다. CPU는 메모리 사이클 하나씩만 "도둑맞는다" |

DMA가 시스템 버스를 자주 쓰면 CPU가 그만큼 버스를 못 쓴다. 장치 컨트롤러까지 시스템 버스에 붙어 있으면, 메모리 내용을 디스크로 보낼 때 DMA 컨트롤러가 메모리에서 읽느라 한 번, 컨트롤러에 쓰느라 또 한 번, 같은 데이터로 시스템 버스를 **두 번** 쓴다. 그래서 장치 컨트롤러들을 별도의 **입출력 버스**(PCI Express 등)에 연결하고, 입출력 버스가 시스템 버스와 이어지게 한다. 메인보드의 확장 슬롯이 입출력 버스의 접점이다.

**입출력 프로세서(IOP, 데이터 채널)는** DMA 컨트롤러와 달리 **자체 명령어 프로그램**을 실행한다. 8비트 문자를 모아 32비트 워드로 만드는 것처럼 데이터 형식을 재구성하고, CPU와는 주로 메모리를 통해 소통한다. CPU가 명령을 남기면 IOP가 상태를 기록하고 DMA로 전송한 뒤 인터럽트로 알린다.

## 직렬 통신

| 주제 | 방식 | 내용 |
| --- | --- | --- |
| 에러 검출 | LRC | 블록 안 모든 문자를 XOR한 값을 덧붙인다 |
| 에러 검출 | CRC | 다항식 나눗셈(시프트 레지스터 + XOR)으로 검사 값을 만든다. 연속 비트가 깨지는 **버스트 에러**에 강하다. 다시 계산한 값이 다르면 재전송을 요청한다 |
| 전송 방향 | 단방향(simplex) / 반이중(half-duplex) / 전이중(full-duplex) | 한쪽으로만(방송) / 양방향이지만 번갈아(무전기) / 동시에 양방향(전화) |
| 링크 프로토콜 | 문자 지향 | 특수 제어 문자로 프레임 경계를 표시한다. 데이터에 같은 패턴이 나오면 오해되는 **데이터 투명성 문제**를 DLE 문자로 피하지만 번거롭다 |
| 링크 프로토콜 | 비트 지향 (HDLC 등) | 플래그 `01111110`으로 경계를 표시하고, **1이 다섯 번 연속되면 0을 끼워 넣어(비트 스터핑)** 같은 패턴을 막는다 |

## 핵심 정리

- 폴링 → 인터럽트 → DMA → IOP 순으로 CPU의 입출력 부담이 줄어든다.
- 인터럽트는 명령어 사이클 끝에서 확인하고, 상태를 저장한 뒤 벡터로 ISR을 찾아 실행하고 복구한다.
- 인터럽트 우선순위는 데이지 체인(직렬), 마스크 + 우선순위 인코더(병렬), PIC로 정한다.
- 직렬 통신은 CRC로 에러를 검출하고, 비트 스터핑으로 데이터 투명성을 확보한다.
