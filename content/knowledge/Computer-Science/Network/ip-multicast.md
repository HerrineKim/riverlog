> 고려사이버대학교 「컴퓨터네트워크」(2023-2학기) 강의 내용을 바탕으로 정리했다.

## 왜 멀티캐스트인가

유니캐스트로 N명에게 같은 영상을 보내면 송신자는 같은 패킷을 N번 만들고, 송신자 근처 링크에는 같은 데이터가 N번 지나간다. 멀티캐스트는 송신자가 **그룹 주소로 한 번만** 보내고, 경로가 갈라지는 라우터에서만 패킷을 복사한다. 링크마다 사본은 최대 하나다.

| 방식 | 송신 횟수 | 받는 대상 |
| --- | --- | --- |
| 유니캐스트 여러 번 | 수신자 수만큼 | 각 수신자 |
| 브로드캐스트 | 1번 | 같은 네트워크 전체(라우터를 넘지 않음) |
| 멀티캐스트 | 1번 | 그룹에 가입한 호스트만, 라우터를 넘어서도 |

쓰이는 곳은 IPTV, 사내 영상 송출, 금융 시세 배포, 라우팅 프로토콜끼리의 메시지(OSPF, RIPv2) 같은 곳이다. 공용 인터넷을 가로지르는 멀티캐스트는 사업자들이 거의 열어 두지 않아서, 실무에서는 한 사업자나 한 회사 망 안에서 주로 쓴다. 인터넷 전체로 퍼뜨리는 일은 [[cdn|CDN]]과 [[live-streaming|라이브 스트리밍]]의 유니캐스트 계층 구조가 대신한다. 시세 멀티캐스트의 실제 쓰임은 [[backend-latency-optimization|백엔드 지연 최적화]]에 있다.

## 멀티캐스트 주소

IPv4에서 클래스 D, 즉 `224.0.0.0/4`(224.0.0.0 ~ 239.255.255.255)가 멀티캐스트용이다. 주소 하나가 호스트가 아니라 **그룹**을 가리킨다.

| 구간 | 용도 |
| --- | --- |
| `224.0.0.0/24` | 로컬 네트워크 제어용. TTL 1로 보내 라우터를 넘지 않는다 |
| `232.0.0.0/8` | SSM(Source-Specific Multicast). 「이 송신자가 보내는 이 그룹」 단위로 받는다 |
| `239.0.0.0/8` | 관리 범위(administratively scoped). 조직 내부용, 사설 IP와 비슷한 역할 |

로컬 제어 블록에는 미리 정해진 주소가 있다.

| 주소 | 뜻 |
| --- | --- |
| `224.0.0.1` | 이 네트워크의 모든 호스트 |
| `224.0.0.2` | 이 네트워크의 모든 라우터 |
| `224.0.0.5` | OSPF 라우터 |
| `224.0.0.9` | RIPv2 라우터 |
| `224.0.0.13` | PIM 라우터 |
| `224.0.0.22` | IGMPv3 보고 수신 |

### 그룹 주소를 MAC 주소로

유니캐스트 IP는 [[network-layer|ARP]]로 MAC 주소를 묻지만, 그룹 주소에는 응답할 주인이 하나가 아니다. 그래서 이더넷은 **계산으로** 바꾼다.

- MAC 주소 앞 25비트를 `01:00:5E` + `0`으로 고정한다.
- IP 주소의 하위 23비트를 그대로 붙인다.

```text
IP   239.1.2.3 = 1110 | 1111 0 | 000 0001 0000 0010 0000 0011
                 고정    버림     하위 23비트
MAC  0000 0001 0000 0000 0101 1110 0 | 000 0001 0000 0010 0000 0011
     = 01:00:5E:01:02:03
```

IP 쪽 앞 4비트(`1110`)는 고정이라 정보가 28비트인데, MAC에 담기는 건 23비트뿐이다. 버려지는 5비트 때문에 **IP 그룹 32개가 MAC 주소 하나를 같이 쓴다.** 그래서 NIC가 받은 프레임이 정말 내가 가입한 그룹인지는 IP 계층에서 한 번 더 걸러야 한다.

## IGMP: 누가 그룹에 들어 있나

라우터는 자기 LAN에 어떤 그룹의 수신자가 있는지 알아야 그쪽으로 패킷을 내보낸다. **IGMP(Internet Group Management Protocol)** 는 호스트와 바로 옆 라우터 사이에서 이 가입 정보를 주고받는다. 라우터끼리 그 정보를 퍼뜨리는 건 별도의 멀티캐스트 라우팅 프로토콜이 맡는다.

- **질의(Query)**: 라우터가 묻는다. 모든 그룹을 묻는 일반 질의(`224.0.0.1`로), 특정 그룹만 묻는 질의, 특정 그룹의 특정 송신자만 묻는 질의(v3)가 있다.
- **보고(Report)**: 호스트가 답하거나 먼저 알린다. 그룹에 가입할 때도 보고를 보낸다. v3에서는 `224.0.0.22`로 보낸다.
- IP 프로토콜 번호 2로 캡슐화하고 TTL을 1로 두어 LAN 밖으로 나가지 않는다.
- 버전 1 → 2 → 3으로 오면서 명시적 탈퇴(v2), 송신자 지정(v3, SSM의 기반)이 추가됐다.

스위치는 원래 멀티캐스트 프레임을 브로드캐스트처럼 모든 포트로 뿌린다. 그래서 스위치가 IGMP 메시지를 엿보고 가입한 포트로만 보내는 **IGMP 스누핑**을 켜는 경우가 많다.

## 멀티캐스트 라우팅: 어떤 트리로 퍼뜨릴까

유니캐스트 라우팅은 목적지마다 최단 경로 하나면 되지만, 멀티캐스트는 송신자에서 여러 수신자로 뻗는 **트리**가 필요하다. 트리를 만드는 방식은 둘로 나뉜다.

| 구분 | 송신자 기반 트리(SBT) | 그룹 공유 트리 |
| --- | --- | --- |
| 트리 단위 | (송신자, 그룹) 쌍마다 하나 | 그룹마다 하나. 코어(랑데부) 라우터가 뿌리 |
| 경로 | 송신자에서 각 수신자까지 최단 경로 | 송신자 → 코어 → 수신자. 최단이 아닐 수 있다 |
| 지연 | 짧다 | 코어를 돌아가는 만큼 길다 |
| 확장성 | 송신자·그룹이 많으면 상태가 폭증 | 상태가 그룹 수에 비례해 가볍다 |
| 어울리는 곳 | 송신자가 적고 수신자가 촘촘할 때 | 송신자가 많고 수신자가 흩어져 있을 때 |
| 프로토콜 | DVMRP, MOSPF, PIM-DM | CBT, PIM-SM |

### 송신자 기반 트리의 전달 정책

가장 단순한 방법인 플러딩부터 하나씩 약점을 고쳐 가는 순서로 보면 이해가 쉽다.

| 정책 | 동작 | 남는 문제 |
| --- | --- | --- |
| 플러딩 | 받은 인터페이스를 뺀 모든 곳으로 보낸다 | 루프가 생기고, 멤버가 없는 망에도 간다 |
| RPF (Reverse Path Forwarding) | 송신자 주소로 유니캐스트 라우팅 테이블을 찾아, **내가 송신자에게 갈 때 쓰는 인터페이스로 들어온 패킷만** 내보낸다. 나머지는 버린다 | 루프는 없어지지만 한 네트워크가 사본을 여러 개 받을 수 있다 |
| RPB (Reverse Path Broadcasting) | 네트워크마다 부모 라우터를 하나로 정해 그 라우터만 전달한다 | 사본 중복은 없어지지만 여전히 브로드캐스트다 |
| RPM (Reverse Path Multicasting) | 처음엔 RPB처럼 뿌리고, 멤버가 없는 가지는 **가지치기(prune)**, 새 멤버가 생기면 **접목(graft)** 한다 | 주기적으로 다시 뿌리고 가지치는 비용 |

RPF의 발상은 「송신자에게 가는 최단 경로의 반대 방향으로 들어온 패킷만이 최단 경로 트리를 따라온 것」이라는 점이다. 유니캐스트 라우팅 테이블을 재활용하니 멀티캐스트용 표를 따로 계산할 필요가 없다. RPF 검사는 오늘날 PIM에서도 그대로 쓰인다.

### 프로토콜별 특징

- **DVMRP**: [[network-layer|RIP]]과 같은 거리 벡터 방식에 RPM을 얹었다. RIP의 한계(느린 수렴, 15홉 제한, 주기적 메시지로 대역폭 낭비)를 그대로 물려받았다.
- **MOSPF**: OSPF를 확장해 링크 상태 정보로 (송신자, 그룹)마다 [[dijkstra|다익스트라]] 트리를 계산한다. 가입·탈퇴마다 계산이 다시 돌아 그룹과 송신자가 적은 환경에만 맞는다.
- **CBT**: 코어 라우터 하나를 뿌리로 하는 공유 트리. 송신자는 멀티캐스트 패킷을 유니캐스트로 감싸 코어에 보내고, 코어가 벗겨서 트리로 뿌린다. 수신 측 라우터는 코어에 명시적으로 가입한다.
- **PIM(Protocol Independent Multicast)**: 이름처럼 특정 유니캐스트 라우팅 프로토콜에 묶이지 않고, 이미 있는 라우팅 테이블을 RPF 검사에 쓴다. 지금 실제로 가장 많이 쓰는 방식이다.
  - **PIM-DM(밀집 모드)**: 대부분의 라우터에 수신자가 있다고 보고 RPM 방식으로 뿌린 뒤 가지친다.
  - **PIM-SM(희소 모드)**: 수신자가 드문드문 있다고 보고 랑데부 포인트(RP)를 뿌리로 한 공유 트리로 시작한다. 트래픽이 많아지면 송신자 기반 최단 경로 트리로 갈아탈 수 있다.

## MBONE: 멀티캐스트를 모르는 라우터 건너뛰기

모든 라우터가 멀티캐스트를 지원하지는 않는다. **MBONE**은 멀티캐스트 라우터끼리를 **유니캐스트 터널**로 이어 논리적인 멀티캐스트 망을 만든 실험망이다. 멀티캐스트 패킷을 터널 반대편 라우터 주소로 향하는 유니캐스트 패킷에 통째로 넣어 보내고, 받은 쪽이 벗겨서 다시 멀티캐스트로 뿌린다. VPN 터널과 같은 캡슐화 원리다([[network-security|네트워크 보안]]).

## 핵심 정리

- 멀티캐스트는 그룹 주소(`224.0.0.0/4`)로 한 번 보내고 갈라지는 지점에서만 복사한다.
- 그룹 주소는 하위 23비트를 `01:00:5E` 뒤에 붙여 MAC으로 바꾸며, 32개 그룹이 MAC 하나를 공유한다.
- IGMP는 호스트와 옆 라우터 사이의 가입 관리, 멀티캐스트 라우팅 프로토콜은 라우터 사이의 트리 구성을 맡는다.
- 송신자 기반 트리는 지연이 짧고 상태가 무겁다. 공유 트리는 그 반대다. PIM-SM은 공유 트리로 시작해 필요하면 최단 경로 트리로 바꾼다.
- RPF는 유니캐스트 라우팅 테이블로 루프 없는 전달을 판정하는 핵심 장치다.
