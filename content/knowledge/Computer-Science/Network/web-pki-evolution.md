## 핵심: 인증서는 귀중품에서 소모품이 됐다

TLS의 원리(대칭키·공개키, 핸드셰이크, HSTS)는 [[https|HTTPS와 TLS]]에 있다. 이 노트는 그 위의 **신뢰 체계**, 즉 누가 인증서를 발급하고 브라우저가 무엇을 믿는지(웹 PKI)가 어떻게 바뀌었는지를 다룬다.

| | 예전 | 지금 |
| --- | --- | --- |
| 프로토콜 | SSL 3.0, 암호 묶음 수십 개 | TLS 1.3, 암호 묶음 5개, 전방 비밀성 강제 |
| 인증서 키 | RSA 2048 + SHA-1 서명 | ECDSA P-256 우선(RSA 2048은 호환용), SHA-256 이상 |
| 유효 기간 | 3~5년 | 200일(2026.3) → 100일(2027.3) → 47일(2029.3) |
| 발급 | 양식 작성·결제·사람의 확인, 며칠 | ACME로 기계끼리 몇 초, 무료 |
| 개인키 | 유출되면 과거 통신까지 모두 풀리는 귀중품 | 유출돼도 과거 통신은 안전. 자주 바꾸는 소모품 |
| 규칙 결정 | CA들이 거부권을 쥔 합의 | 브라우저·OS 루트 프로그램이 사실상 결정 |
| 검증 수준 | EV를 사면 주소창에 회사명 표시 | 표시 사라짐. DV면 충분 |

인터넷 곳곳에 남은 "CSR 만드는 법" 답변은 대부분 RSA 2048·SHA-1·장기 유효 기간을 전제로 해서 지금은 그대로 쓰면 안 된다. 직접 CSR을 만들 일 자체가 드물다. ACME 클라이언트나 호스팅이 키 생성부터 갱신까지 맡는다([[https-migration|HTTPS 전환]]).

## 옛 웹 PKI가 동작하던 방식

```text
루트 CA (브라우저·OS의 루트 저장소에 내장)
   └─ 중간 CA ─ 서명 → 사이트 인증서
            ↑
   CA는 매년 WebTrust 감사를 통과하면 루트 저장소에 남는다
   규칙(Baseline Requirements)은 CA/브라우저 포럼에서 합의로 바꾼다
```

- **감사의 이해 상충**: CA가 감사인을 직접 고르고 돈을 냈다. 1년에 한 번 감사만 통과하면 됐다.
- **CA/브라우저 포럼**(2005~): CA와 브라우저가 함께 최소 규칙(Baseline Requirements)을 정하는 자율 규제 기구다. 규칙을 바꾸려면 CA 쪽 표결도 통과해야 했으므로, 현상 유지로 이익을 보는 쪽이 사실상 거부권을 가졌다.
- **비싼 인증서**: 검증 수준(DV·OV·EV)에 따라 값이 달랐고, 인증서 하나가 몇 년을 갔다. 개인키를 잃으면 돈을 내고 다시 사야 했다.
- **"RSA"의 혼동**: RSA는 키 교환(TLS 1.3에서 제거), 인증서 키(타원 곡선으로 대체 중), 서명 알고리즘(아직 사용)을 모두 가리켜서 맥락마다 뜻이 다르다. 어느 RSA를 말하는지 구분해야 한다.

## 무엇이 무너뜨렸나

| 연도 | 사건 | 드러난 문제 | 결과 |
| --- | --- | --- | --- |
| 2011 | **DigiNotar 침해**: 네덜란드 CA가 뚫려 google.com 위조 인증서가 이란에서 쓰였다 | 미패치 소프트웨어·기본 비밀번호·망 분리 부재가 감사를 통과했다 | DigiNotar는 신뢰를 잃고 몇 달 만에 파산. 감사로는 CA를 믿을 수 없다 |
| 2013 | **스노든 폭로**: 암호화된 트래픽을 대량으로 저장해 두고 나중에 개인키를 얻어 푸는 감청 | 같은 개인키가 신원 증명과 세션 키 암호화를 모두 맡았다 | **전방 비밀성**(아래) 확산 |
| 2013~ | **인증서 투명성(CT)** 제안(RFC 6962) | CA가 몰래 잘못 발급해도 알 길이 없었다 | Chrome이 EV(2015), 모든 인증서(2018)에 CT 로그 기록을 의무화 |
| 2014 | **Heartbleed**: OpenSSL 버그로 서버 메모리 64KB씩을 반복해서 읽을 수 있었다 | 개인키 유출 시 과거 통신까지 위험. 수십만 장을 폐기해야 했는데 **폐기 체계가 감당하지 못했다** | 전방 비밀성 유무가 피해 규모를 갈랐다. 폐기가 믿을 수 없다는 것이 명백해졌다 |
| 2015~2017 | **SHA-1 충돌**: SHAppening(2015, free-start 충돌), SHAttered(2017, 실제 충돌) | 충돌을 만들 수 있으면 평범한 인증서와 서명이 같은 위조 인증서를 CA 몰래 얻을 수 있다 | Microsoft가 2013년에 합의 없이 2016년 이후 SHA-1 불신을 선언. 다년 인증서 탓에 충돌 증명 뒤에도 SHA-1 인증서가 한동안 유효했다 |
| 2017 | **Symantec 불신**: CT 로그로 무단 발급 수만 건이 드러났다 | 세계 최대 CA도 규칙을 어겼고, 감사는 잡지 못했다 | Chrome이 Symantec 계열 루트(VeriSign·GeoTrust·RapidSSL 등)를 단계적으로 불신. 사업은 DigiCert로 넘어갔다 |
| 2018 | **Chrome "주의 요함" 표시**: HTTP 사이트에 경고 | | HTTPS 비율이 빠르게 올랐다. 쉽게 만드는 것보다 부끄럽게 만드는 것이 더 효과적이었다 |
| 2018 | **BygoneSSL**: 도메인을 판 뒤에도 이전 주인의 인증서가 유효 | 인증서 수명이 도메인 소유권보다 길다 | 짧은 유효 기간이 위험을 크게 줄인다는 근거가 됐다 |
| 2019 | **EV 표시 제거**: 사용자가 주소창의 회사명을 보지 않는다는 연구 | EV가 실제 보안을 높이지 않는다 | Chrome·Firefox·Safari가 EV 표시를 없앴다 |

### 전방 비밀성: 신원과 암호화를 분리한다

옛 RSA 키 교환에서는 클라이언트가 세션 비밀값을 **서버 공개키로 암호화해 보냈다.** 통신을 저장해 둔 사람이 나중에 서버 개인키를 얻으면 그 키로 만든 모든 과거 세션을 풀 수 있었다.

전방 비밀성(forward secrecy)은 두 일을 나눈다.

| 일 | 맡는 것 |
| --- | --- |
| 신원 증명 | 인증서와 개인키(서명) |
| 세션 키 합의 | 세션마다 새로 만드는 일회용 키로 (EC)DHE 키 교환 |

```text
클라이언트: 비밀 a 생성 → g^a 전송          서버: 비밀 b 생성 → g^b 전송
            양쪽 모두 g^ab를 계산 (관찰자는 g^a, g^b만 보고 g^ab를 구할 수 없다: 이산 로그 문제)
```

공유 비밀은 어느 쪽도 전송하지 않는다. 개인키가 세션 키 계산에 쓰이지 않으므로 **개인키가 유출돼도 과거 통신은 풀리지 않는다.** 유출은 여전히 나쁘지만(위장 가능) 재앙은 아니게 됐고, 개인키를 자동화 도구로 옮기고 자주 바꾸는 것이 현실적인 선택이 됐다. TLS 1.3은 RSA 키 교환을 없애 전방 비밀성을 강제한다.

### 인증서 투명성(CT)

모든 공개 인증서는 발급 시 **추가만 가능한 공개 로그**에 기록되어야 하고, 브라우저는 로그 기록 증명(SCT)이 없는 인증서를 거부한다. 누구나 로그를 감시해 자기 도메인으로 발급된 인증서를 확인할 수 있다.

- 도메인 주인은 crt.sh 같은 CT 검색으로 **모르는 발급**을 찾는다. 감시 알림 서비스도 있다.
- 반대로 CT 로그는 공개 정보다. 인증서에 넣은 **내부 서브도메인 이름이 모두 드러난다.** 숨겨야 할 호스트 이름은 공개 인증서에 넣지 않거나 와일드카드·사설 CA를 쓴다.

### 폐기는 지금도 잘 안 된다

| 방식 | 동작 | 문제 |
| --- | --- | --- |
| CRL | CA가 폐기 목록 파일을 게시 | 커지고 느리고 오래된다 |
| OCSP | 인증서마다 CA에 유효한지 물어본다 | CA 서버가 자주 죽고, 어떤 사이트를 방문하는지 CA에 새어 나간다. 응답이 없으면 통과(soft-fail)시키므로 공격자가 요청만 막으면 무력하다 |
| OCSP stapling | 서버가 OCSP 응답을 받아 핸드셰이크에 붙인다 | 설정이 번거로워 널리 쓰이지 않았다 |
| 브라우저 내장 목록 | Chrome CRLSets, Firefox CRLite처럼 브라우저가 폐기 정보를 미리 받아 둔다 | CRLSets는 중요한 일부만 담는다. 브라우저마다 결과가 다르다 |

OCSP는 CA/브라우저 포럼 규칙에서 선택 사항이 됐고, Let's Encrypt는 2025년에 OCSP를 끝내고 CRL만 제공한다. 폐기를 믿을 수 없으니 **인증서 수명 자체를 짧게 해서 폐기가 필요 없게 만드는** 방향으로 간다. 폐기된 인증서를 브라우저가 막는지는 `revoked.badssl.com`으로 확인할 수 있다.

## ACME와 Let's Encrypt

Let's Encrypt는 ISRG(비영리)가 운영하는 무료 CA이고, ACME(RFC 8555)는 그 발급 절차를 표준화한 프로토콜이다. 처음부터 **무료, 짧은 수명, 사람 없는 자동화**를 목표로 했다.

```text
ACME 클라이언트 ── 주문(example.com) ──▶ CA
               ◀── 챌린지: 도메인을 통제함을 증명하라
   HTTP-01:  http://example.com/.well-known/acme-challenge/<토큰> 에 파일을 둔다
   DNS-01:   _acme-challenge.example.com TXT 레코드를 둔다 (와일드카드는 이것만)
   TLS-ALPN-01: 443 포트의 TLS 핸드셰이크로 증명한다
               ── CSR 제출 ──▶ CA ── 인증서 발급 (몇 초)
```

- CA들은 "기업은 자동화를 감당할 수 없다"고 반대했지만, Let's Encrypt는 지금 웹에서 가장 많은 인증서를 발급하는 CA다. ACME는 거의 모든 CA·호스팅·로드 밸런서가 지원하는 표준이 됐다.
- **ARI**(ACME Renewal Information, RFC 9773)로 CA가 클라이언트에게 갱신할 때를 알려 준다. 대량 폐기 사고가 나면 CA가 갱신을 앞당기도록 신호를 보낼 수 있다.
- Let's Encrypt는 6일짜리 단기 인증서도 발급하고, 기본 수명도 단계적으로 줄인다.

## 규칙을 정하는 힘이 브라우저로 옮겨 갔다

| 연도 | 일 |
| --- | --- |
| 2013 | Microsoft가 SHA-1 인증서 불신 일정을 일방적으로 발표 |
| 2013~2018 | Google이 CT 의무화를 합의 없이 Chrome에 적용 |
| 2017·2019 | 유효 기간을 1년으로 줄이자는 표결이 CA들의 반대로 두 번 부결 |
| 2020 | Apple이 398일 넘는 인증서를 더는 믿지 않겠다고 발표하고 2020년 9월 적용(다른 브라우저도 따랐다) |
| 2025 | Ballot SC-081 통과: 최대 유효 기간 200일(2026.3.15) → 100일(2027.3.15) → 47일(2029.3.15). 도메인 검증 재사용 기간도 10일까지 줄어든다 |

브라우저·OS는 각자의 **루트 프로그램**으로 어떤 CA를 넣을지 정한다. 포럼 표결이 막히면 루트 프로그램 규칙을 바꾸는 것으로 결과를 강제할 수 있고, CA가 반대하면 포럼 대신 브라우저마다 따로 감사를 받아야 한다. 이 압력으로 SC-081 같은 단축안이 통과됐다. 포럼은 남아 있지만 결정의 무게는 브라우저 쪽에 있다.

## 짧은 수명이 운영에 주는 일

수동 갱신은 1년에 한 번이면 달력 알림으로 버텼다. 47일이면 인증서 하나에 1년에 8번 이상이고, 인증서가 수십 장이면 수백 번이 된다. **수동 갱신은 끝났다.**

갱신 자동화만으로는 부족하다. 장애는 대개 **배포**에서 난다. 새 인증서를 모든 서버·장치에 맞는 형식으로 넣고 서비스를 다시 읽게 하는 일이다. 갱신은 몇 분 만에 끝났는데 모든 서버에 반영하는 데 몇 시간이 걸린 대형 서비스 장애 사례도 있다.

스크립트로 시작한 자동화는 보통 이렇게 자란다.

| 단계 | 상황 | 덧붙는 것 |
| --- | --- | --- |
| 1 | 서버 하나, certbot + cron | 끝인 줄 안다 |
| 2 | Java 서버는 키스토어 형식이 필요 | 형식 변환·복사 스크립트 |
| 3 | 와일드카드 인증서 | DNS-01용 DNS API 자격 증명이 스크립트에 들어간다 |
| 4 | 여러 노드가 한 인증서를 공유 | 공유 폴더에 인증서 파일 |
| 5 | 재시작 실패·오래된 인증서로 새벽 장애 | 만료 모니터링 |
| 6 | 보안팀이 "이 인증서들 주인이 누구냐"고 묻는다 | 소유자·위치를 적은 스프레드시트 |

이런 스크립트는 결국 **인증서 수명 주기 관리**(CLM: certificate lifecycle management)의 절반을 엉성하게 다시 만든 것이 된다. 인증서가 많다면 처음부터 이 기능을 갖춘 도구나 플랫폼을 쓴다.

| 기능 | 내용 |
| --- | --- |
| 탐색 | 어떤 인증서가 어디에 있는지 목록화(CT 로그·네트워크 스캔) |
| 발급·갱신 | ACME, ARI로 갱신 시점 자동 판단 |
| 배포 | 형식 변환, 서버·로드 밸런서·장치에 설치, 서비스 재시작 |
| 감시 | 만료·배포 실패·예상 밖 발급 알림 |
| 소유 | 인증서마다 담당자와 용도 기록 |

가장 쉬운 길은 이 일을 플랫폼에 넘기는 것이다. Vercel·Netlify·Cloudflare 같은 호스팅, 클라우드 로드 밸런서, Caddy·Traefik 같은 서버는 발급·갱신·배포를 스스로 한다.

## 다음 전환: 양자 내성 암호

충분히 큰 양자 컴퓨터는 (EC)DHE 키 교환을 깰 수 있다. 그래서 지금 저장한 트래픽을 나중에 푸는 **"지금 저장, 나중에 해독"**(harvest now, decrypt later) 위협이 다시 생긴다.

- **키 교환**은 이미 전환 중이다. X25519MLKEM768(기존 X25519 + ML-KEM 하이브리드)을 주요 브라우저와 CDN이 기본으로 협상한다([[https|HTTPS와 TLS]]).
- **인증서 서명**(ML-DSA 등 양자 내성 서명)은 서명과 인증서가 훨씬 커지는 문제 때문에 웹 PKI에 아직 들어오지 않았다. 바뀌면 다시 모든 인증서를 새로 발급해야 한다.
- 발급·배포가 자동화돼 있으면 이 전환은 설정 변경으로 끝나고, 수동이라면 또 한 번 긴 비상 작업이 된다. 짧은 수명이 강제하는 자동화가 **암호 민첩성**(crypto agility)의 기반이다.

## 정리

- 웹 PKI는 CA 침해, 대량 감청, 해시 충돌, Heartbleed, 폐기 실패를 겪으며 "CA를 믿고 감사로 확인한다"에서 "**모든 발급을 공개 기록하고, 짧게 쓰고, 자동으로 바꾼다**"로 바뀌었다.
- 전방 비밀성이 개인키를 귀중품에서 소모품으로 바꿨다. TLS 1.3이 이를 강제한다.
- CT 로그는 잘못된 발급을 드러내는 장치다. 대신 인증서에 넣은 호스트 이름은 모두 공개된다.
- 폐기는 지금도 믿을 수 없다. 그래서 수명을 줄인다: 2029년 3월부터 최대 47일.
- 갱신 자동화로 끝나지 않는다. 탐색·배포·감시·소유까지 수명 주기 전체를 자동화하거나 플랫폼에 맡긴다.
- 양자 내성 암호 전환이 다음 차례다. 자동화된 곳만 쉽게 넘어간다.
