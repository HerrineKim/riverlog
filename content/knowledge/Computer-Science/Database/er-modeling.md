> 고려사이버대학교 「데이터베이스시스템」(2024-1학기) 강의 내용을 바탕으로 정리했다.

DB 설계는 요구사항 분석 → 개념적 설계 → 논리적 설계 → 물리적 설계 순서로 간다([[sql-and-relational-algebra#DB 설계 단계|관계대수와 DB 설계]]). **개념적 설계**는 아직 어떤 DBMS를 쓸지 모르는 상태에서 "무엇을 저장하고 그것들이 어떻게 엮이는가"를 그리는 단계이고, 그때 쓰는 도구가 **ER 모델(Entity-Relationship model)** 이다. 1976년 피터 첸(Peter Chen)이 제안했고, 나중에 상위·하위 타입 같은 개념이 붙어 확장 ER 모델(EER)이 됐다.

ER 다이어그램(ERD)의 쓸모는 기술보다 소통에 있다. 현업 담당자, 기획자, 개발자가 같은 데이터를 서로 다르게 이해하고 있을 때, 그림 하나로 합의를 만든다. 테이블을 만든 뒤에 "주문 하나에 배송지가 여러 개일 수 있다"는 걸 알게 되면 비싸다. ERD 단계에서 알면 선 하나 고치면 된다.

## 세 가지 구성 요소

| 요소 | 무엇 | 첸 표기법 |
| --- | --- | --- |
| 개체(entity) | 저장하고 관리할 대상. 사람·물건 같은 물리적 개체와 강좌·주문 같은 개념적 개체 | 사각형 |
| 속성(attribute) | 개체나 관계의 성질 | 타원 |
| 관계(relationship) | 개체 사이의 연관 | 마름모 |

용어를 구분해 두면 문서를 읽기 쉽다.

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| 개체 타입 | 속성들로 정의된 틀 | 학생(학번, 이름, 학과) |
| 개체 인스턴스 | 틀에 값이 채워진 하나 | (S001, 김민선, 경영) |
| 개체 집합 | 인스턴스들의 모음 | 모든 학생 |

테이블로 치면 타입은 스키마, 인스턴스는 행, 집합은 테이블의 내용이다.

## 개체

### 무엇이 개체가 되나

요구사항 문장에서 명사가 후보다. 그중 다음을 만족하는 것만 남긴다.

1. 업무에서 관리할 필요가 있다
2. 인스턴스를 서로 구별할 식별자가 있다
3. 인스턴스가 둘 이상이고, 계속 남겨 둘 정보다
4. 속성이 하나 이상 있다
5. 다른 개체와 관계가 하나 이상 있다

"우리 병원에는 많은 의사가 근무하고 환자가 진료를 받는다"에서 후보는 병원·의사·환자·진료다. **병원**은 시스템 전체를 가리킬 뿐 인스턴스가 하나라 개체가 아니다. **진료**는 의사와 환자 사이의 행위라 관계로 본다(진료일·처방처럼 속성이 많아지면 개체로 올리기도 한다). 학번·이름은 학생을 설명하는 속성이지 개체가 아니다.

이름은 현업 용어를 쓰고, 약어를 피하고, 단수 명사로 짓고, 모델 안에서 유일하게 한다. "고객구좌"와 "고객계좌"처럼 같은 걸 두 이름으로 부르기 시작하면 테이블도 둘이 된다.

### 강한 개체와 약한 개체

| 종류 | 키 | 표기 |
| --- | --- | --- |
| 강한 개체 | 자기 속성만으로 식별된다 | 사각형 |
| 약한 개체 | 자기 속성만으로는 식별이 안 되고 소유 개체에 기대야 한다 | 이중 사각형, 식별 관계는 이중 마름모 |

직원의 부양가족이 전형적인 약한 개체다. "이름이 김지우인 부양가족"은 여러 명일 수 있지만, "사번 1001 직원의 부양가족 김지우"는 하나다. 약한 개체에서 소유 개체의 키와 합쳐야 식별자가 되는 속성(여기서는 이름)을 **부분 키**라 하고 점선 밑줄로 표시한다. 소유 개체가 사라지면 약한 개체도 의미가 없으므로 보통 삭제가 함께 전파된다.

## 속성

속성 값이 가질 수 있는 범위를 **도메인**이라 한다(이름은 20자 이하 문자열, 국가 코드는 `{KR, US, JP, …}`, 입학 연도는 2001보다 큰 정수). 도메인은 나중에 타입과 `CHECK` 제약이 된다.

| 종류 | 뜻 | 예 | 첸 표기 |
| --- | --- | --- | --- |
| 단순 속성 | 더 쪼갤 수 없다 | 성별 | 타원 |
| 키 속성 | 인스턴스를 유일하게 식별한다. 유일하고 NULL이 아니어야 한다 | 학번 | 밑줄 |
| 복합 속성 | 의미 있는 부분으로 나뉜다 | 주소(시·구·동), 이름(성·이름) | 타원에 하위 타원 |
| 다중값 속성 | 한 인스턴스가 값을 여러 개 갖는다 | 취미, 전화번호들 | 이중 타원 |
| 유도 속성 | 다른 값에서 계산된다 | 나이(생년월일에서), 부양가족 수 | 점선 타원 |

키는 속성 하나일 수도, 여러 개를 합친 것일 수도 있다. 강의실은 "건물 번호 + 호실"이 함께여야 식별된다. 슈퍼키·후보키·기본 키의 구분은 [[sql-basics#제약 조건|SQL 기초]]에 있다.

## 관계

### 카디널리티 비율

두 개체 집합 사이의 대응 방식이다.

| 비율 | 뜻 | 예 |
| --- | --- | --- |
| 1:1 | 양쪽 다 상대 하나와만 | 직원 ─ 사원증 |
| 1:N | 한쪽 하나가 상대 여럿과 | 부서 ─ 직원 |
| N:M | 양쪽 다 상대 여럿과 | 학생 ─ 과목 |

### 참여와 (최소, 최대)

비율만으로는 "반드시 있어야 하나"가 안 보인다. 그래서 각 개체가 관계에 몇 번 참여하는지를 **(최소, 최대)** 로 적기도 한다.

```text
교수 (0, 4) ── 담당 ── (1, 1) 과목
```

교수는 과목을 0~4개 맡는다(안 맡는 교수도 있다: **선택적 참여**). 과목은 정확히 한 명의 교수가 맡는다(최소가 1 이상: **필수적 참여**, 전체 참여). 필수 여부는 나중에 외래 키의 `NOT NULL`이 된다.

관계를 정할 때는 양방향으로 문장을 만들어 읽어 보면 실수가 줄어든다.

> 의사 **한 명은** 환자를 **여러 명** 진료**할 수 있다.**
> 환자 **한 명은** 의사 **한 명에게** 반드시 진료**받는다.**

### 관계의 다른 성질

- **관계도 속성을 가진다.** 성적은 학생의 것도 과목의 것도 아니고 "어떤 학생이 어떤 과목을 들었다"는 사실에 붙는다.
- **같은 두 개체 사이에 관계가 여럿일 수 있다.** 사람과 도시 사이에 "거주"와 "출생"이 따로 있다. 관계 하나가 외래 키 하나가 되므로 따로 그린다.
- **차수**: 참여하는 개체 수. 둘이면 이진, 셋이면 삼진(학생·과목·교수가 함께 엮인 강의). 한 개체가 자기 자신과 맺으면 **순환(재귀) 관계**(직원이 직원을 관리한다).

## ERD 그리는 순서

1. **개체 고르기**: 요구사항의 명사에서 후보를 모으고 위 기준으로 거른다. 처음엔 넉넉히 올리고, 동의어처럼 보여도 바로 버리지 않는다.
2. **관계 정하기**: 동사에서 찾는다. 이름을 먼저 붙이고 비율과 필수·선택을 양방향으로 정한다.
3. **골격 ERD**: 개체와 관계를 이어 전체 그림을 만들고, 중복된 개체·관계를 지운다. 가능하면 이진 관계로 표현한다.
4. **속성 붙이기**: 각 개체와 관계에 속성을 달고, 키와 카디널리티 같은 제약을 표시한다.

실무 ERD는 첸 표기법보다 까마귀 발(crow's foot) 표기법을 많이 쓴다. 속성을 사각형 안에 나열하고, 선 끝 모양으로 1·N과 필수·선택을 함께 표시해 그림이 훨씬 작다.

## ERD를 테이블로: 논리적 설계

개념 모델은 DBMS와 무관하지만, 관계형 DB에 담으려면 릴레이션(테이블)으로 옮겨야 한다. 규칙은 기계적이다.

| ER 요소 | 변환 |
| --- | --- |
| 강한 개체 | 테이블 하나. 키 속성이 기본 키 |
| 약한 개체 | 테이블 하나. 소유 개체의 기본 키를 외래 키로 가져와 부분 키와 합쳐 기본 키로 |
| 1:N 관계 | **N쪽** 테이블에 1쪽의 기본 키를 외래 키로. 관계의 속성도 N쪽에 |
| 1:1 관계 | 한쪽의 기본 키를 다른 쪽의 외래 키로. 필수적으로 참여하는 쪽에 두면 NULL이 안 생긴다 |
| N:M 관계 | 새 테이블. 양쪽 기본 키를 외래 키로 가져와 둘을 합쳐 기본 키로. 관계의 속성도 여기에 |
| 삼진 이상 관계 | 새 테이블. 참여하는 개체 모두의 기본 키를 외래 키로 |
| 순환 관계 | 같은 테이블에 자기 기본 키를 가리키는 외래 키(`manager_id → employee.id`) |
| 같은 개체 사이의 관계 여럿 | 관계마다 외래 키를 따로(`birth_city`, `residence_city`) |
| 다중값 속성 | 새 테이블. 소유 개체의 기본 키 + 그 값이 기본 키 |
| 복합 속성 | 부분들을 각각 컬럼으로, 또는 하나로 합친다 |
| 유도 속성 | 보통 저장하지 않고 계산한다 |

```sql
-- 학생 N:M 과목, 관계 속성은 성적
CREATE TABLE enrollment (
  student_id  CHAR(5)  REFERENCES student(id),
  course_id   CHAR(6)  REFERENCES course(id),
  grade       CHAR(2),
  PRIMARY KEY (student_id, course_id)
);

-- 다중값 속성: 직원의 취미
CREATE TABLE employee_hobby (
  employee_id INT          REFERENCES employee(id),
  hobby       VARCHAR(30),
  PRIMARY KEY (employee_id, hobby)
);

-- 약한 개체: 부양가족
CREATE TABLE dependent (
  employee_id INT REFERENCES employee(id) ON DELETE CASCADE,
  name        VARCHAR(30),
  relation    VARCHAR(10),
  PRIMARY KEY (employee_id, name)
);
```

다중값 속성을 `hobby1, hobby2, hobby3` 컬럼으로 펴면 안 되는 이유는 관계형 모델이 컬럼 하나에 원자값 하나만 허용하기 때문이고(1NF), 네 번째 취미가 생기면 스키마를 바꿔야 하기 때문이다([[normalization|정규화와 반정규화]]).

### 판단이 필요한 경우

**복합 속성을 쪼갤까?** 부분이 혼자서도 쓰이는지를 본다. 주소를 시·구로 나누면 "구별 고객 수"를 바로 셀 수 있다. 반대로 날짜를 연·월·일 컬럼으로 나누면 함께 있을 때만 뜻이 있는 값을 흩어 놓을 뿐이라 날짜 타입 하나가 낫다. 전화번호도 지역번호로 검색할 일이 없으면 한 컬럼이면 충분하다.

**유도 속성을 저장할까?** 원칙은 계산이다. 저장하면 원본이 바뀔 때마다 같이 고쳐야 하고, 빠뜨리면 값이 어긋난다. 그래도 저장하는 흔한 경우가 있다.

| 유형 | 예 | 이유 |
| --- | --- | --- |
| 현재 값만 따로 | 고객의 현재 등급, 현주소 | 이력 테이블을 매번 뒤지지 않으려고 |
| 집계 결과 | 주문의 총액, 직원의 부양가족 수 | 매번 합계를 내기 비싸서 |
| 대표 값 | 대표 이메일 | 여럿 중 하나를 자주 쓴다 |

이건 성능을 위해 일부러 중복을 들이는 반정규화이므로, 갱신 책임(트리거, 애플리케이션, 배치)을 함께 정해 둔다.

## 물리적 설계로

릴레이션 스키마가 나오면 물리적 설계에서 이를 특정 DBMS의 테이블 명세로 구체화한다. 컬럼마다 타입과 길이, NULL 허용, 기본값, 제약 조건(기본 키·외래 키·유니크·CHECK)을 정하고, 자주 쓰는 조회를 보고 인덱스와 파티션 같은 접근 경로를 정한다([[index-design|인덱스 설계와 쿼리 튜닝]], [[oracle-schema-objects|Oracle 스키마 객체]]). 같은 ERD라도 여기서부터는 DBMS와 트래픽에 따라 결과가 달라진다.

## 정리

- ER 모델은 개체(사각형)·속성(타원)·관계(마름모)로 데이터 구조를 그린다. 목적은 이해관계자 사이의 합의다.
- 개체는 식별자가 있고 인스턴스가 여럿이며 관계가 있는 것. 자기 키가 없으면 약한 개체다.
- 속성은 단순·키·복합·다중값·유도로 나뉜다. 관계는 비율(1:1, 1:N, N:M)과 참여(최소, 최대)로 적는다.
- 변환 규칙: 1:N은 N쪽에 외래 키, N:M과 다중값 속성은 새 테이블, 약한 개체는 소유자 키를 빌린 복합 키.
