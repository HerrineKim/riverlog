> 릴레이션의 구조와 성질, 조인의 종류, 디비전과 질의를 관계대수식으로 쓰는 예는 고려사이버대학교 「데이터베이스시스템」(2024-1학기) 강의 내용으로 보강했다.

관계대수는 관계형 데이터베이스의 질의를 연산으로 표현하는 수학적 체계이고, SQL은 그 위에 만든 표준 언어다. SQL은 "무엇을 원하는지"만 적는 비절차적 언어, 관계대수는 "어떻게 구할지"를 연산 순서로 적는 절차적 언어라는 차이가 있다.

SQL 명령어 분류(DDL·DML·DCL)와 문법, `WHERE`와 `HAVING` 같은 시험 단골 함정은 [[sql-basics|SQL 기초]]에 있다.

## 릴레이션의 구조

관계형 모델(Codd, 1970)은 데이터베이스를 **릴레이션(테이블)의 집합**으로 본다. 수학적으로 릴레이션은 각 속성 도메인의 카티션 곱의 부분집합이고, 실제로는 튜플의 집합이다.

| 용어 | 뜻 | 테이블에서 |
| --- | --- | --- |
| 릴레이션 스키마 | 릴레이션 이름과 속성의 목록. `학생(학번, 이름, 학과)` | 테이블 정의 |
| 릴레이션 인스턴스(상태) | 어느 한 시점에 들어 있는 튜플의 집합 | 지금 들어 있는 데이터 |
| 속성(attribute) | 이름 붙은 값의 칸 | 열 |
| 튜플(tuple) | 속성 값의 묶음 하나. 의미를 담는 최소 단위 | 행 |
| 도메인(domain) | 한 속성이 가질 수 있는 원자값의 집합. `점수 = 0~100의 정수` | 데이터 타입 + 제약 |
| 차수(degree) | 속성의 수 | 열 개수 |
| 카디널리티(cardinality) | 튜플의 수 | 행 개수 |

릴레이션은 집합이므로 테이블과 다른 성질이 있다.

| 성질 | 뜻 | 결과 |
| --- | --- | --- |
| 튜플의 유일성 | 똑같은 튜플이 두 번 있을 수 없다 | 모든 튜플을 구별하는 키가 반드시 있다. SQL 테이블은 기본 키가 없으면 중복 행을 허용한다는 점에서 릴레이션과 다르다 |
| 원자값 | 모든 속성 값은 더 쪼갤 수 없는 값 하나다 | 다중값·복합값을 한 칸에 넣지 않는다([[normalization\|1NF]]) |
| 튜플의 무순서 | 튜플 사이에 순서가 없다 | 순서가 필요하면 `ORDER BY`로 매번 지정한다 |
| 속성의 무순서 | 속성 사이에 순서가 없다 | 위치가 아니라 이름으로 속성을 가리킨다 |

키와 무결성 제약(개체·참조·도메인)은 [[sql-basics#제약 조건|SQL 기초]]에 있다.

## 관계대수

관계(테이블)를 입력받아 관계를 결과로 내놓는 연산들. 피연산자와 결과가 모두 릴레이션이므로 연산을 이어 붙여 식을 만들 수 있다.

### 순수 관계 연산자

| 연산 | 기호 | 의미 |
| --- | --- | --- |
| Select | σ | 조건을 만족하는 **튜플(행)** 추출, 수평 연산 |
| Project | π | 지정한 **속성(열)** 만 추출, 중복 제거, 수직 연산 |
| Join | ⋈ | 공통 속성을 기준으로 두 릴레이션을 결합 |
| Division | ÷ | R에서 S의 모든 값과 관련된 튜플을 찾아, S의 속성을 뺀 나머지만 남김 |

**조인의 종류**: 조인은 카티션 곱 뒤에 선택을 한 것(`R ⋈θ S = σθ(R × S)`)으로 정의된다.

| 조인 | 조건 | 결과 |
| --- | --- | --- |
| 세타 조인(θ-join) | 비교 연산자 `=, ≠, <, ≤, >, ≥` 중 하나 | 조건을 만족하는 튜플 쌍 |
| 동등 조인(equi join) | θ가 `=` | 조인 속성이 양쪽에 모두 남아 같은 값이 두 번 나온다 |
| 자연 조인(natural join, ⋈N) | 같은 이름의 속성끼리 `=` | 동등 조인에서 **중복 속성을 하나만 남긴다**. `π(R과 S의 속성 합집합)(σR.z=S.z(R × S))` |
| 외부 조인(outer join) | 동등 조인 + 짝 없는 튜플 보존 | 짝이 없는 쪽을 NULL로 채운다. 왼쪽·오른쪽·완전 외부 조인. SQL의 `LEFT/RIGHT/FULL JOIN`이다 |

**디비전 예**: `등록(학번, 과목번호) ÷ 과목(과목번호)`은 과목 릴레이션에 있는 **모든** 과목을 등록한 학번을 돌려준다. 과목이 `{C123}`이면 C123을 들은 학생 전부, `{C123, C124, C225}`이면 세 과목을 다 들은 학생만 남는다. 「모든 ~를 한」 질의는 SQL에 바로 대응하는 연산자가 없어 이중 `NOT EXISTS`로 쓴다([[sql-subquery|서브쿼리와 관계해석]]).

### 일반 집합 연산자

합집합·교집합·차집합은 두 릴레이션의 속성 수와 도메인이 같아야(합병 가능) 한다.

| 연산 | 결과 | 결과 카디널리티(튜플 수) |
| --- | --- | --- |
| 합집합 UNION (∪) | 두 릴레이션의 튜플을 합치고 중복 제거 | 두 카디널리티의 합 **이하** |
| 교집합 INTERSECTION (∩) | 양쪽에 모두 있는 튜플 | 작은 쪽 카디널리티 **이하** |
| 차집합 DIFFERENCE (−) | 앞 릴레이션에만 있는 튜플 | 앞(빼지는) 릴레이션 카디널리티 **이하** |
| 카티션 곱 CARTESIAN PRODUCT (×) | 모든 튜플의 순서쌍 | 두 카디널리티의 **곱** (차수는 두 차수의 합) |

### 질의를 관계대수식으로 쓰기

조회뿐 아니라 삽입·삭제도 집합 연산으로 표현된다. 같은 질의를 여러 식으로 쓸 수 있고, 그중 비용이 낮은 식을 고르는 것이 아래의 최적화다.

| 질의 | 관계대수식 |
| --- | --- |
| 모든 학생의 이름과 학과 | `π 이름,학과 (학생)` |
| C123 과목을 들은 학생의 이름과 성적 | `π 이름,성적 (σ 과목번호='C123' (학생 ⋈N 등록))` |
| 학생 한 명 삽입 | `학생 ∪ {('S600', '김명호', '컴퓨터')}` |
| 「데이터베이스」 과목 삭제 | `과목 − σ 과목명='데이터베이스' (과목)` |

두 번째 식은 조인 뒤에 거르지만, 선택을 먼저 해서 `π 이름,성적 (학생 ⋈N σ 과목번호='C123' (등록))`으로 바꿔도 결과가 같고 조인할 행이 줄어든다.

## SQL이 실행되는 과정

DBMS는 비절차적인 SQL을 받아 관계대수 같은 절차적 표현으로 바꾼 뒤 실행한다. 관계대수가 SQL의 「내부 언어」인 셈이다.

```text
SQL 문 ─▶ ① 파싱 ─▶ ② 변환 ─▶ ③ 최적화 ─▶ ④ 실행 ─▶ 결과
         문법·이름   관계대수 등    실행 계획 선택   계획대로
         검사       내부 표현으로   (인덱스·조인 순서) 읽고 계산
```

| 단계 | 하는 일 |
| --- | --- |
| 파싱 | 문법을 검사하고, 테이블·열 이름이 실제로 있는지, 권한이 있는지 확인한다 |
| 변환 | 쿼리를 관계대수 트리 같은 내부 표현으로 바꾼다. 같은 결과를 내는 여러 동등한 식으로 다시 쓸 수 있다(예: 선택 σ를 조인보다 먼저 해서 다룰 행 수 줄이기) |
| 최적화 | 통계 정보와 인덱스를 보고 비용이 가장 낮은 **실행 계획**을 고른다. 어떤 인덱스를 쓸지, 조인 순서와 방식(중첩 루프·해시·병합)을 무엇으로 할지 정한다 |
| 실행 | 계획에 따라 데이터를 읽고 결과를 돌려준다 |

고른 실행 계획은 `EXPLAIN`으로 볼 수 있다. 같은 SQL이라도 인덱스·통계에 따라 계획이 달라지므로, 느린 쿼리는 SQL 문장보다 계획부터 확인한다.

절의 **논리적 평가 순서**는 작성 순서와 다르다: `FROM`·`JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `DISTINCT` → `ORDER BY` → `LIMIT`. `SELECT`에서 붙인 별칭을 `WHERE`에서 못 쓰는 이유다. 실제 실행 순서는 최적화기가 결과가 같은 범위에서 바꿀 수 있다. 파서·옵티마이저·실행기·버퍼 관리자 같은 엔진 내부 구성 요소는 [[database-internals|DB 내부 구조]]에 있다.

## DB 설계 단계

```text
요구사항 분석 → 개념적 설계 → 논리적 설계 → 물리적 설계 → 구현
```

| 단계 | 하는 일 | 산출물 |
| --- | --- | --- |
| 개념적 설계 | 현실 세계를 추상화 | E-R 다이어그램 |
| 논리적 설계 | 특정 DB 모델(관계형)에 맞게 변환, **정규화** | 릴레이션 스키마 |
| 물리적 설계 | 저장 구조·인덱스·접근 경로 결정 | 테이블 정의서 |

### 요구사항에서 테이블까지

1. **용도 파악**: 누가 어떤 데이터를 어떻게 쓰는지 사용자 인터뷰·기존 문서·기존 시스템으로 모은다.
2. **항목 나열**: 저장할 대상(고객, 상품, 주문)과 속성을 데이터 사전(data dictionary)으로 적는다. 속성은 **쓸모 있는 가장 작은 단위**로 쪼갠다(주소를 국가·도시·도로명으로 나누면 국가별 조회가 된다). 같은 데이터를 두 테이블에 두지 않는다.
3. **테이블과 기본 키**: 대상마다 테이블을 만들고 기본 키를 정한다. 기본 키는 **유일하고, 바뀌지 않고, 늘 값이 있어야** 한다. 주문 번호는 맞고, 바뀔 수 있는 전화번호·주소는 맞지 않다. 여러 컬럼을 묶은 복합 키도 된다.
4. **관계 정하기**: 관계의 카디널리티를 보고 키를 배치한다.
5. **정규화**: 이상 현상을 없앤다([[normalization|정규화와 반정규화]]).

| 관계 | 구현 |
| --- | --- |
| 1:1 | 대개 한 테이블로 합친다. 대부분 비어 있는 선택 속성이나 접근 권한이 다른 속성만 따로 떼어 같은 기본 키로 잇는다 |
| 1:N | "1" 쪽(부모)의 기본 키를 "N" 쪽(자식)에 **외래 키**로 둔다 |
| M:N | 직접 표현할 수 없다. 두 테이블의 키를 함께 갖는 **연결 테이블(link·junction table)** 을 만들어 1:N 두 개로 나눈다(학생 ─< 수강 >─ 강의). 연결 테이블에는 수강일 같은 관계 고유의 속성도 둔다 |

관계마다 **필수인가 선택인가**(주문은 고객 없이 존재할 수 없지만 고객은 주문 없이 존재한다)도 정해 외래 키의 NOT NULL 여부로 옮긴다. E-R 다이어그램에서는 까마귀 발 표기법(crow's foot)으로 나타낸다.

## 스키마와 인덱스

- **스키마**: 데이터베이스의 구조(테이블, 컬럼, 타입)와 제약 조건, 관계를 기술한 메타데이터의 집합. 스키마는 자주 바뀌지 않는 「틀」이고, 어느 순간 들어 있는 실제 데이터는 **인스턴스**라고 한다. MySQL에서는 스키마와 데이터베이스가 같은 말이고, PostgreSQL에서는 한 데이터베이스 안에 여러 스키마(이름공간)를 둔다.
- **인덱스**: `<키 값, 레코드 주소>` 쌍으로 이루어진 자료구조로, 검색 속도를 높인다. 파일 구조는 크게 순차, 인덱스, 해싱 방식이 있다. 대부분의 RDBMS는 인덱스를 B-트리 계열(B+ 트리)로 구현한다([[data-structures|기초 자료구조]]의 균형 트리 참고). B+ 트리를 쓰는 이유는 [[database-internals#인덱스 자료 구조|DB 내부 구조]], 복합 인덱스 순서와 실행 계획 읽기는 [[index-design|인덱스 설계와 쿼리 튜닝]]에 있다.

### 3단계 스키마와 데이터 독립성

ANSI/SPARC 구조는 스키마를 보는 관점에 따라 세 층으로 나눈다.

| 층 | 무엇을 기술하나 | 예 |
| --- | --- | --- |
| 외부 스키마 | 사용자·응용 프로그램 하나가 보는 부분. 여러 개 있다(서브 스키마) | 뷰, 사용자별 권한이 걸린 컬럼 묶음 |
| 개념 스키마 | 조직 전체의 논리 구조. 모든 엔터티·관계·제약 조건. DB당 하나 | 테이블 정의, 외래 키, 무결성 제약 |
| 내부 스키마 | 저장 장치에 어떻게 놓이나. 레코드 형식, 인덱스, 파일 구성 | 인덱스, 파티션, 테이블스페이스 |

층을 나누는 목적은 **데이터 독립성**이다. 층 사이에 매핑을 두어 아래층이 바뀌어도 위층을 고치지 않게 한다.

| 독립성 | 뜻 | 예 |
| --- | --- | --- |
| 논리적 독립성 | 개념 스키마가 바뀌어도 외부 스키마·응용 프로그램은 그대로 | 테이블을 둘로 나눠도 같은 모양의 뷰를 제공하면 앱 코드는 그대로다 |
| 물리적 독립성 | 내부 스키마가 바뀌어도 개념 스키마는 그대로 | 인덱스를 추가하거나 저장 장치를 바꿔도 SQL은 그대로다 |

논리적 독립성은 물리적 독립성보다 지키기 어렵다. 컬럼을 지우거나 의미를 바꾸면 뷰로 감출 수 없는 경우가 많다.
