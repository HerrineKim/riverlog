> 개발 생명주기와 방법론, 요구공학, 구조적·객체지향 분석과 설계, 프로젝트 관리, 형상 관리 절은 고려사이버대학교 「소프트웨어공학」(2024-1학기)과 「소프트웨어 분석설계」(2023-2학기) 강의 내용으로 보강했다.

좋은 소프트웨어 설계의 핵심은 "고치기 쉽고 다시 쓰기 쉬운 구조"다. 소프트웨어 공학은 이를 정해진 비용과 일정 안에서 믿을 만한 품질로 해내는 방법을 다룬다. 무엇을 만들지 정하는 요구공학, 어떻게 나눌지 정하는 분석·설계, 제대로 만들었는지 확인하는 [[software-testing|테스트]], 그리고 이 모두를 굴리는 프로젝트 관리와 형상 관리가 큰 축이다. 시험에서는 개발 과정의 틀(생명주기 모델, 방법론), 모듈 독립성, 디자인 패턴, 모델링 도구, 관리 기법(비용 산정, 형상 관리)으로 나눠 묻는다.

## 개발 프로세스와 생명주기

**프로세스**는 고객 요구를 만족하는 제품을 만들려고 절차·방법, 도구·장비, 인력을 하나로 묶는 접착제다. "제품의 품질은 그것을 만드는 프로세스의 품질이 정한다"(Watts Humphrey)는 원칙 때문에, 계획을 세운다는 것은 곧 프로세스를 정의한다는 뜻이 된다. 단계마다 착수 기준(Entry), 할 일(Task), 검증 기준(Verification), 완료 기준(eXit)을 적어 프로세스를 정의하는 방법을 **ETVX**라고 한다.

| 용어 | 뜻 | 예 |
| --- | --- | --- |
| 개발 생명주기(SDLC) | 어떻게 개발할지를 정한 **최상위 수준의 프로세스**. 단계, 접근 방식, 마일스톤·일정·비용 산정의 기준을 준다 | 폭포수, 나선형, V-모델 |
| 개발 방법론 | 생명주기의 각 단계에서 **무엇을 어떻게 할지** 구체적으로 정한 것. 기법, 산출물 양식, 점검 항목을 준다 | UP, 애자일(스크럼, XP) |

### 생명주기 모델

접근 방식은 둘로 나뉜다. **빅뱅(Big Bang)** 방식은 요구사항부터 테스트까지 한 번에 순서대로 밟고 끝에 한 번 배포한다. **진화적(Evolutionary)** 방식은 요구·설계·구현·테스트를 작은 주기로 여러 번 돌린다.

| 모델 | 방식 | 특징 | 맞는 상황 |
| --- | --- | --- | --- |
| 주먹구구식(Build & Fix) | - | 분석·설계 없이 코딩하고 만족할 때까지 고친다. 관리·유지보수가 어려워 체계적 모델 연구의 계기가 됐다 | 아주 작은 프로그램 |
| 폭포수(Waterfall) | 빅뱅 | 이전 단계 산출물이 다음 단계 입력이다. 앞 단계가 끝나야 다음으로 가고, 고객은 후반에야 동작하는 소프트웨어를 본다 | 규모가 작고 요구사항이 명확할 때 |
| 원형(Prototyping) | 진화적 | 주요 기능만 담은 시제품을 빨리 만들어 고객과 평가하며 요구를 확정한다. 원형은 확인 뒤 버리고, 성능·보안은 보통 고려하지 않는다 | 초기에 요구사항을 알기 어려울 때 |
| 나선형(Spiral) | 진화적 | 폭포수와 원형의 장점에 **위험 분석**을 더했다. 계획 → 위험 분석 → 개발 → 고객 평가를 반복한다. 위험 분석이 틀리면 문제가 되고 관리가 복잡하다 | 비용이 크고 기간이 긴 프로젝트 |
| V-모델 | 빅뱅 | 왼쪽 개발 단계와 오른쪽 테스트 단계를 짝지어 **검증과 확인**을 강조한다. 테스트 설계를 개발과 병행한다 | 품질·안전 요구가 높은 시스템 ([[software-testing#테스트 레벨 (V-모델)\|테스트 레벨]]) |

### 방법론: UP와 애자일

**UP(Unified Process)** 는 Jacobson·Booch·Rumbaugh가 만든 객체지향 방법론이다. 유스케이스로 요구를 분석하고, 아키텍처를 중심에 두며, 위험 관리를 중시하고, 반복적·점진적으로 개발한다. 시간 순서로 네 단계를 거치되 **각 단계 안에서 요구·설계·구현·테스트가 모두 조금씩 일어난다**는 점이 폭포수와 다르다.

| 단계 | 초점 |
| --- | --- |
| 도입(Inception) | 타당성을 평가해 진행 여부를 정하고 요구사항 전체를 대략 파악한다 |
| 정련(Elaboration) | 요구 분석과 아키텍처를 확정하고 상세 설계·구현 계획을 세운다. 핵심 기능만 구현·테스트한다 |
| 구축(Construction) | 구현과 테스트에 집중한다 |
| 전이(Transition) | 배포하고 사용자 환경에서 인수 테스트와 사용자 교육을 한다 |

**애자일(Agile)** 은 변경을 받아들이고 빠른 배포를 강조하는 반복적·점진적 방법이다. 2001년 애자일 선언문은 프로세스·도구보다 개인과 상호작용을, 포괄적 문서보다 동작하는 소프트웨어를, 계약 협상보다 고객 협력을, 계획 준수보다 변화 대응을 더 중시한다. 대표 방법론은 XP, 스크럼, FDD, 린, AUP이고, 공통 실천은 짧은 반복, 데일리 스탠드업, 유저 스토리, 페어 프로그래밍, 리팩토링, 지속적 통합, TDD, 회고다. 스크럼의 **스프린트 회고**는 주기가 끝날 때 무엇을 개선할지 돌아보고 기록하는 활동이다. 폭포수와 애자일을 고르는 기준은 [[agile-sprint|애자일과 스프린트]]에 있다.

**리팩토링**은 동작은 바꾸지 않고 코드 구조를 개선하는 것이다. 중복 코드, 방대한 클래스, 장황한 메서드 같은 코드 스멜이 대상이다([[refactoring-principles|리팩터링 원칙]]).

## 요구공학

요구사항은 **문제를 풀기 위해 제품이 갖춰야 할 기능과 지켜야 할 제약**이다. **기능적 요구사항**은 시스템이 제공할 기능·서비스, **비기능적 요구사항**은 성능·보안·신뢰성 같은 제약과 품질 속성이다. 설계는 요구사항(무엇을)을 어떻게 만들지 정하는 일이고, 테스트는 만든 것이 요구사항을 지키는지 확인하는 일이라, 요구사항이 흔들리면 뒤의 모든 산출물이 같이 흔들린다. 잘못된 요구사항을 운영 단계에서 고치는 비용은 분석 단계에서 고치는 비용의 수십 배 이상으로 불어난다.

| 구분 | 누구의 말인가 | 예 (경비 정산 앱) |
| --- | --- | --- |
| 고객 요구사항 (Needs) | 고객·사용자가 바라는 것. 모호해도 된다 | "영수증 입력이 너무 번거롭다" |
| 제품 요구사항 | 개발 관점에서 구체화한 것. 검증할 수 있어야 한다 | "영수증 사진을 올리면 금액·날짜·가맹점명을 자동으로 채운다", "인식 결과는 3초 안에 보여 준다" |

고객 요구사항 하나가 제품 요구사항 여러 개로 갈라지는 것이 보통이다. 이 변환을 체계적으로 하는 공학적 방법이 **요구공학**이다.

```text
요구사항 개발                                   요구사항 관리
추출 ──▶ 분석 ──▶ 명세 ──▶ 검증 ──▶ [베이스라인] ──▶ 변경 관리
 (후보)    (합의)   (공식 문서) (일관성 확인)              추적 관리
```

개발 쪽은 요구사항을 **만드는** 일이고, 관리 쪽은 합의한 요구사항이 프로젝트 끝까지 **유지되게 하는** 일이다.

### 요구사항 추출

1. **비즈니스 이해**: 시장 동향과 현재 업무의 문제를 보고 개발 범위를 정한다.
2. **이해관계자 식별**: 사용자, 발주 고객, 운영자뿐 아니라 경쟁사, 협력 업체, 관련 법규·표준도 이해관계자다.
3. **기대사항 수집**: 인터뷰, 설문, 브레인스토밍, 마인드맵, 벤치마킹, 워크숍 중 기간·비용에 맞는 방법을 고른다.

이해관계자는 자기가 원하는 것을 정확히 말하지 못하는 경우가 많다. 한 가지 방법에 기대지 말고 여러 방법을 섞어 빈틈을 메운다. 사용자 조사 방법은 [[user-research|사용자 리서치]]에 있다.

### 요구사항 분석

- **전제 조건 식별**: 고객이 이미 정해 둔 조건. 출시 시점, 대상 시장, 지켜야 할 법규, 기존 대비 개선 목표 같은 것들이다.
- **운용 시나리오 분석**: 어떤 환경(오프라인, 저사양 단말, 야외)에서 어떤 모드(평상시, 점검 중, 장애 시)로 쓰이는지 정리한다.
- **기능·비기능 요구사항 분석**: 시스템이 **무엇을 하는지**와 **얼마나 잘 하는지**를 나눈다.

| 분류 | 묻는 것 | 예 |
| --- | --- | --- |
| 기능 | 무엇을 해야 하나 | 행위, 외부 인터페이스, 제어, 고장 감지·회피 같은 안전 기능 |
| 품질 | 얼마나 믿을 만한가 | 신뢰성, 유지보수성, 사용성, 보안, 재사용성 |
| 성능 | 얼마나 빠르고 많이 | 응답 시간, 처리량, 용량, 정확도 |
| 제약 | 무엇에 묶여 있나 | 외부 환경, 표준·법규, 조직의 비용·일정·인력 |

비기능 요구사항은 **숫자로 쓴다.** "빠르게 응답한다"는 검증할 수 없고, "사용자 요청의 95%를 2초 안에 응답한다"는 검증할 수 있다. 분석 방법은 데이터 흐름을 따라 하향식으로 쪼개는 구조적 분석과, 사용자 시나리오에서 출발하는 객체지향 분석(유스케이스)으로 나뉜다(아래 「소프트웨어 설계」).

### 요구사항 명세

분석 결과를 **소프트웨어 요구사항 명세서(SRS)** 로 정리한다. SRS의 목차는 IEEE 830(현재는 ISO/IEC/IEEE 29148이 대체)이 대표적이다. 외부 인터페이스(사용자·하드웨어·소프트웨어·통신), 기능 요구사항(정보 흐름, 프로세스 설명, 데이터 사전), 비기능 요구사항 순으로 구성한다. 표기법은 정형화 정도에 따라 셋으로 나뉜다.

| 표기법 | 수단 | 장점 | 한계 |
| --- | --- | --- | --- |
| 비정형 (Informal) | 자연어, 조직 내부의 그림 | 누구나 읽고 쓸 수 있다 | 사람마다 다르게 읽는다 |
| 준정형 (Semiformal) | DFD, UML 같은 범용 모델링 언어 | 기능·구조·동작을 같은 기호로 공유한다 | 표기법을 배워야 한다 |
| 정형 (Formal) | 수학 기호, 정형 명세 언어 | 사람과 도구가 똑같이 해석한다. 자동 검증이 가능하다 | 작성 비용이 크다. 안전 필수 시스템 위주 |

자연어 명세의 모호함을 줄이는 간단한 방법이 **EARS**(Easy Approach to Requirements Syntax)다. 문장을 몇 가지 정해진 틀에 맞춰 쓴다.

| 패턴 | 틀 | 예 |
| --- | --- | --- |
| 항상 | 시스템은 ~해야 한다 | 앱은 모든 금액을 원 단위 정수로 저장해야 한다 |
| 이벤트 | ~하면, 시스템은 ~해야 한다 | 사용자가 영수증 사진을 올리면, 앱은 3초 안에 인식 결과를 보여 줘야 한다 |
| 상태 | ~인 동안, 시스템은 ~해야 한다 | 오프라인인 동안, 앱은 입력 내용을 기기에 임시 저장해야 한다 |
| 원치 않는 상황 | 만약 ~라면, 시스템은 ~해야 한다 | 만약 인식한 금액이 100만 원을 넘으면, 앱은 사용자에게 확인을 요청해야 한다 |
| 선택 기능 | ~가 있는 경우, 시스템은 ~해야 한다 | 법인카드 연동을 쓰는 경우, 앱은 카드 승인 내역과 영수증을 자동으로 짝지어야 한다 |

틀에 맞추면 **트리거, 조건, 기대 동작**이 문장마다 드러나서 그대로 테스트 케이스가 된다.

### 요구사항 검증

요구사항 단계에는 아직 코드가 없으니 **리뷰**로 검증한다. 막연히 읽지 말고 기준별 체크리스트를 쓴다.

| 기준 | 확인할 질문 |
| --- | --- |
| 완전성 | 모든 기능과 운용 모드·환경을 다뤘나? 비기능 요구사항이 빠지지 않았나? 아직 모르는 값은 TBD로 표시했나? |
| 명확성 | 두 가지로 읽히는 문장은 없나? 서로 부딪히는 요구사항은 없나? 다이어그램 표기는 정확한가? |
| 실현 가능성 | 일정과 조직의 기술 수준 안에서 만들 수 있나? 우선순위가 정해져 있나? |
| 추적 가능성 | 요구사항마다 고유 ID가 있나? 상위의 이해관계자·시스템 요구사항과 연결되나? |

### 변경 관리와 추적

검증을 마친 요구사항은 **베이스라인**으로 확정하고(아래 「형상 관리」의 베이스라인과 같은 개념), 그 뒤의 변경은 반드시 절차를 거친다. 베이스라인 전의 수정은 아직 개발 중인 것이라 변경 관리 대상이 아니다.

```text
변경 요청 ──▶ 영향 분석 ──▶ 변경 심사 ──승인──▶ 변경 실시 ──▶ 변경 확인
 (고객·개발자)                    └──반려──▶ 요청자에게 사유 회신
```

심사 때 보는 것은 변경의 난이도, 이미 만든 산출물(설계·코드·테스트)에 미치는 영향, 일정과 비용 안에서 가능한지다. "요구한 대로 만들었는데 고객은 다른 것을 기대했다"는 상황이 되풀이되면, 변경 요청을 대화로 처리하지 말고 이 흐름에 올린다.

**추적 관리**는 요구사항과 다른 산출물 사이의 연결을 기록해서, 하나가 바뀌면 영향을 받는 곳을 바로 찾게 한다. **수직 추적**은 요구사항 → 설계 → 코드처럼 개발 단계를 따라 내려가고, **수평 추적**은 V-모델의 같은 높이끼리(고객 요구사항 ↔ 인수 테스트, 요구사항 분석 ↔ 시스템 테스트) 잇는다. 보통 **추적 매트릭스**로 관리한다.

| 요구사항 ID | 설계 | 코드 | 테스트 케이스 | 상태 |
| --- | --- | --- | --- | --- |
| REQ-OCR-001 | 영수증 인식 모듈 설계 | `receipt/ocr.ts` | TC-031, TC-032 | 통과 |
| REQ-OCR-002 | 금액 검증 규칙 | `receipt/validate.ts` | TC-040 | 실패 1건 |
| REQ-OFF-001 | 오프라인 저장소 설계 | (미구현) | 미작성 | 진행 중 |

테스트가 없는 요구사항, 요구사항이 없는 코드가 매트릭스의 빈칸으로 드러난다.

### 공공SW 사업의 요구사항 분류

국내 공공 SW 사업의 제안요청서(RFP)는 요구사항을 정해진 유형과 코드로 나눠 쓴다. 「공공SW사업 제안요청서 작성을 위한 요구사항 상세화 실무 가이드라인」의 분류는 다음과 같다.

| 코드 | 유형 | 코드 | 유형 |
| --- | --- | --- | --- |
| SFR | 기능 | COR | 제약사항 |
| PER | 성능 | PMR | 프로젝트 관리 |
| ECR | 시스템 장비 구성 | PSR | 프로젝트 지원 |
| INR | 인터페이스 | MPR | 유지관리 수행 |
| DAR | 데이터 | MHR | 유지관리 인력 |
| TER | 테스트 | CNR | 컨설팅 |
| SER | 보안 | ENR | 공사 |
| QUR | 품질 | - | - |

RFP를 읽거나 쓸 때 "SFR-012"처럼 붙은 ID가 이 코드다. 기능 요구사항만 사업마다 내용이 완전히 달라서 공통 항목 없이 상세화 수준을 정해 쓰고, 나머지 유형은 작성 항목이 어느 정도 정해져 있다. 기획서를 태스크로 쪼개는 실무 방식은 [[bdd-sdd-task-design|BDD·SDD로 기획서를 태스크로 나누기]]에 있다.

## 소프트웨어 설계

설계는 소프트웨어를 이루는 요소와 그 구조를 정하는 활동이고, 수준에 따라 둘로 나뉜다.

| 구분 | 다른 이름 | 무엇을 정하나 |
| --- | --- | --- |
| 아키텍처 설계 | 상위 설계, 예비 설계 | 구성 요소(모듈·컴포넌트) 사이의 관계로 된 전체 구조와 인터페이스 |
| 상세 설계 | 하위 설계 | 각 구성 요소 내부의 자료구조(변수 이름·타입·값)와 알고리즘 로직 |

아키텍처는 건물의 청사진 역할을 한다. 이해관계자 사이의 공통 의사소통 수단이 되고, 개발 조직의 구조와 일정·비용 예측에 영향을 주고, 변경이 생겼을 때 원인을 찾게 해 주고, 재사용할 구성 요소를 확보하는 수단이 된다. 무엇보다 **비기능 요구(품질 속성)를 반영하는 자리**다. 같은 기능이라도 모니터링 모듈을 따로 두느냐에 따라 신뢰성이 달라진다. 품질 속성의 표준 분류는 [[software-testing#소프트웨어 품질과 ISO/IEC 25010|ISO/IEC 25010]]에, 아키텍처 스타일은 [[software-architecture-patterns|소프트웨어 아키텍처 패턴]]에 있다.

### 설계 원리

| 원리 | 뜻 | 예 (만년 달력) |
| --- | --- | --- |
| 추상화 | 세부를 정하기 전에 상위 수준에서 먼저 설계한다 | 과정: "입력 → 윤년 판정 → 요일 계산 → 출력" 흐름만 먼저 정한다. 데이터: 연·월·일을 "날짜" 하나로 본다. 제어: "윤년이면 A, 아니면 B"를 "요일 계산" 한 단계로 묶는다 |
| 단계적 상세화 | 상위 설계를 점점 구체적인 설계로 나눠 내려간다 (Niklaus Wirth) | "처리"를 "입력 검증, 총 날짜 계산, 윤년 판정, 요일 결정"으로 나눈다 |
| 모듈화 | 함수와 데이터로 이루어진 독립 단위로 나눈다 | 각 단위가 이름을 갖고, 따로 컴파일되고, 다른 곳에서 재사용될 수 있어야 모듈이다 |

좋은 모듈은 정보 은닉, 높은 응집도, 낮은 결합도를 갖는다(아래 「모듈과 모듈 독립성」).

### 구조적 방법과 객체지향 방법

| 관점 | 구조적 | 객체지향 |
| --- | --- | --- |
| 출발점 | 데이터 흐름과 처리 ("어떤 처리가 일어나는가") | 사용자 시나리오와 책임 ("무엇이 책임을 지는가") |
| 분석 산출물 | 시스템 문맥도, DFD | 유스케이스 다이어그램·명세 |
| 설계 단위 | 태스크, 모듈, 함수 | 컴포넌트, 클래스, 메서드 |
| 잘 맞는 곳 | 센서·주기 처리가 많은 C 기반 임베디드·실시간 시스템 | 도메인 개념이 풍부한 업무 시스템 |

객체지향 쪽 흐름은 아래 「UML로 하는 객체지향 분석·설계」에 있다.

## 구조적 분석과 설계

구조적 방법론은 **데이터가 어디서 들어와 어떻게 바뀌어 어디로 나가는지**를 기준으로 시스템을 위에서 아래로 쪼갠다.

| 단계 | 하는 일 | 산출물 |
| --- | --- | --- |
| 요구사항 분석 | 데이터 흐름을 중심으로 기능을 분석한다 | 시스템 문맥도, 데이터 흐름도(DFD), 데이터 사전, 프로세스 명세 |
| 아키텍처 설계 | 기능을 구현할 실행 단위와 모듈을 정한다 | 태스크 모델(동적 관점), 모듈 구조(정적 관점) |
| 상세 설계 | 모듈 안의 함수 구조를 정한다 | 구조 차트 |

아래에서는 **주차장 차단기 제어 소프트웨어**를 예로 단계를 따라간다.

### 시스템 문맥도: 경계를 긋는다

만들 소프트웨어 전체를 **프로세스 하나(번호 0)** 로 두고, 주고받는 외부 개체(**터미네이터**)와 정보 흐름만 그린다. 목적은 **범위 확정**이다.

```text
 [차량 감지 센서] ──차량 진입──▶ ┌─────────────┐ ──개폐 명령──▶ [차단기 모터]
 [번호판 카메라] ──번호판 정보──▶ │ 차단기 제어 0 │ ──안내 문구──▶ [전광판]
 [타이머]  ═══주기 신호═══▶       └─────────────┘
 ──▶ 데이터 흐름   ═══▶ 제어 흐름
```

정보 흐름은 값이 중요한 **데이터 흐름**(번호판 문자열)과, **언제 일어났는지**가 중요한 **제어 흐름**(타이머 인터럽트, 차량 진입 신호)으로 나뉜다. 문맥도 옆에는 흐름마다 의미와 값의 형태, 주기를 표로 적는다(예: "차량 진입: True/False, 센서 인터럽트로 입력").

### 데이터 흐름도: 개발자가 이해할 때까지 쪼갠다

문맥도의 프로세스 0을 1, 2, 3으로, 다시 1.1, 1.2로 나눈다. 기호는 데이터 프로세스, 제어 프로세스, 데이터 흐름, 제어 흐름, **데이터 저장소**다. 한 프로세스가 출력을 여러 개 내보내면 아직 덜 쪼갠 것으로 보고 더 나눈다.

```text
번호판 정보 ──▶ (1.1 번호판 인식) ──차량 번호──▶ (1.3 출입 판정) ──개폐──▶ (2.1 모터 제어)
차량 진입   ──▶ (1.2 센서 입력)  ──진입 여부──▶      │
                                          [등록 차량 목록] (데이터 저장소)
```

최하위 프로세스에는 역할 유형과 실행 유형을 붙인다.

| 구분 | 유형 | 뜻 |
| --- | --- | --- |
| 역할 | Device | 센서·디스플레이 같은 장치를 다룬다 (데이터 프로세스) |
| 역할 | Control | 상태를 제어한다 (제어 프로세스, 상태 머신으로 명세) |
| 역할 | Function | 특정 알고리즘을 처리한다 (데이터 프로세스) |
| 실행 | Synchronous | 다른 프로세스와 맞물려 데이터를 주고받는다 (일반 함수 호출) |
| 실행 | Asynchronous | 독립적으로 돌며 이벤트에 반응한다 (인터럽트 처리) |
| 실행 | Periodic | 주기적으로 실행된다 (타이머로 5ms마다 센서 읽기) |

### 데이터 사전과 프로세스 명세

**데이터 사전**은 DFD에 나온 데이터의 이름, 설명, 값의 범위를 정의한다.

| 데이터 | 설명 | 값의 범위 |
| --- | --- | --- |
| 차량 번호 | 인식한 번호판 문자열 | 7~8자, 한글 1자 포함 |
| 진입 여부 | 차단기 앞 차량 유무 | True / False |
| 개폐 명령 | 모터에 보내는 명령 | Open / Close |

**프로세스 명세**는 최하위 프로세스마다 쓴다. 데이터 프로세스는 자연어로, 제어 프로세스는 상태 머신으로 쓴다.

```text
프로세스 ID  1.2 센서 입력
유형        Periodic Device
입력        센서 값, 타이머 신호
출력        진입 여부 (→ 1.3 출입 판정)
처리        1. 10ms마다 센서 값을 읽는다.
            2. 세 번 연속 감지되면 진입 여부를 True로 보낸다.
```

상태 머신의 전이는 `이벤트(파라미터) [조건] / 행위`로 쓴다.

```text
[닫힘] ── 판정(결과) [결과 = 허가] / "모터 열기" ──▶ [열림]
[열림] ── 진입 여부(값) [값 = False] / "모터 닫기" ──▶ [닫힘]
```

### 태스크 모델과 모듈 구조

**태스크**는 운영체제가 따로 스케줄하는 실행 단위(스레드)다. DFD의 프로세스를 그대로 태스크로 만들면 너무 많아지므로 세 단계로 줄인다.

1. **태스크 후보 식별**: 혼자 돌아야 하는 프로세스(Asynchronous, Periodic, Control)를 후보로 뽑는다.
2. **잔여 프로세스 할당**: 후보가 되지 못한 프로세스(Synchronous, Function)를 앞뒤로 이어 실행되는(절차적 응집) 후보에 붙인다.
3. **태스크 통합**: 시간 제약을 어기지 않는 선에서, 같은 타이머로 깨어나는 태스크끼리(시간적 응집) 합친다.

입력이 연달아 들어와도 잃으면 안 되는 태스크 사이에는 **비동기 메시지(큐)** 를 쓴다. 각 태스크가 어느 프로세스를 품고 있는지는 추적 관계로 남겨 둔다.

**모듈**은 구현 단위다. C라면 `.c`/`.h` 파일 하나이거나 그 묶음인 디렉터리다. 태스크를 모듈로 옮기고, 여러 모듈이 같이 쓰는 기능은 **라이브러리 모듈**로 뽑고, 함수 호출 관계로 모듈 간 의존을 그린 뒤, 모듈마다 ID·이름·설명·인터페이스를 적는다.

```text
모듈 ID   PK_001        모듈명  출입 판정
설명      번호판과 센서 입력을 종합해 출입 허가 여부를 정한다
인터페이스 Decide_Entry(): 허가 여부를 반환한다
```

공통 기능을 라이브러리로 뽑으면 재사용은 좋아지지만 의존하는 모듈이 늘어 결합도가 올라갈 수 있다. 어느 쪽이 나은지는 매번 저울질한다.

### 구조 차트

구조 차트는 모듈 안의 **함수 호출 관계와 파라미터 이동**을 계층으로 그린다. 위의 상자가 아래 상자를 호출하고, 화살표 옆에 넘기는 데이터를 적는다. 일반 호출, 비동기 호출, 반복, 조건 같은 기호가 있다.

```text
              Decide_Entry()
            ↙ 차량 번호   ↘ 진입 여부
   Read_Plate()          Read_Sensor()
     ↓                        ↓
 Normalize_Plate()       Debounce_Signal()
```

모듈 구조를 바탕으로 DFD의 흐름을 호출 구조로 옮긴 초기 구조 차트를 그리고, 기능을 더 쪼개고 공통 기능을 뽑아 최종본으로 다듬는다. 여기까지 오면 함수 이름과 시그니처가 거의 정해져서 바로 코딩으로 넘어갈 수 있다.

## 모듈과 모듈 독립성

**모듈**은 성능 향상과 수정·재사용 편의를 위해 기능 단위로 나눈 부분이다. 모듈 독립성은 **결합도는 약하게, 응집도는 강하게**, 크기는 작게 할수록 높아진다.

### 결합도와 응집도

- **결합도(Coupling)**: 모듈 간 의존 정도, 약할수록 좋다. 약한 순서로 자료 → 스탬프 → 제어 → 외부 → 공통 → 내용. 단계별 설명은 [[code-coupling|결합도를 낮추는 전략]]에 있다.
- **응집도(Cohesion)**: 모듈 내부 요소의 관련 정도, 강할수록 좋다. 강한 순서로 기능적 → 순차적 → 교환적 → 절차적 → 시간적 → 논리적 → 우연적. 단계별 설명은 [[code-cohesion|응집도를 높이는 전략]]에 있다.

### Fan-in / Fan-out

**Fan-in**은 어떤 모듈을 호출하는 상위 모듈 수(높으면 재사용성이 좋다), **Fan-out**은 어떤 모듈이 호출하는 하위 모듈 수다.

### 계층과 API

함수가 수십만 개로 늘면 함수 단위로도 관리가 안 된다. 관련 함수와 변수를 객체로 묶고, 객체 안에 다시 객체를 넣어 **계층**을 만든다. 자동차 소프트웨어라면 `Car` 안에 `Engine`, 그 안에 `CruiseControl`·`IgnitionControl`이 들어가고, 호출은 `car.engine.cruiseControl.setSpeed(55)`처럼 바깥에서 안으로 내려간다. 팀도 이 경계를 따라 나눈다.

다른 팀이 만든 모듈을 쓸 때 기댈 것은 문서와 **API(Application Programming Interface)** 다. API는 모듈이 밖에 공개하는 함수와 데이터의 목록이다. `IgnitionControl`은 `setRPM()`을 public으로 열어 크루즈 컨트롤이 부를 수 있게 하고, 점화 플러그를 직접 점화하는 함수는 private으로 닫아 자기 안에서만 부른다. **필요한 것만 골라 공개하는 것이 정보 은닉**이다. 내부를 바꿔도 API가 같으면 쓰는 쪽은 고칠 것이 없으므로, 정보 은닉은 결합도를 낮추는 실제 수단이 된다.

## 디자인 패턴 (GoF)

GoF 패턴 23개는 목적에 따라 **생성**(객체를 만드는 방식: Singleton, Factory Method, Builder 등), **구조**(객체를 조합하는 방식: Adapter, Decorator, Proxy 등), **행위**(객체가 협력하고 책임을 나누는 방식: Observer, Strategy, Template Method 등)로 나뉜다. 패턴별 비유·푸는 문제와 헷갈리는 짝은 [[gof-design-patterns|GoF 디자인 패턴]]에 있다.

## 객체지향

- 구성 요소: **객체**(데이터 + 메서드), **클래스**(공통 속성·연산을 가진 객체의 틀, 객체는 클래스의 인스턴스), **메시지**(객체 간 상호작용 수단)
- 기본 원칙: 캡슐화, 정보 은닉, 상속, 추상화, 다형성
- **럼바우(OMT) 분석 기법**: 객체 → 동적 → 기능 모델링 순서
  - 객체(정보) 모델링: 객체 다이어그램, ERD. 구조를 나타낸다
  - 동적 모델링: 상태 다이어그램. 시간에 따른 변화를 나타낸다
  - 기능 모델링: 자료 흐름도(DFD). 입력이 출력으로 바뀌는 과정을 나타낸다

## UML

다이어그램은 정적인 **구조**와 동적인 **행위**로 나뉜다. 유스케이스 다이어그램 작성법과 유스케이스 명세는 [[use-case-diagram|유스케이스 다이어그램]]에 있다.

### 구조 다이어그램

| 다이어그램 | 표현하는 것 |
| --- | --- |
| 클래스 | 클래스의 속성·연산과 클래스 사이 관계. 시스템 구조를 파악하고 문제점을 찾는다 |
| 객체 | 특정 시점의 인스턴스(객체)들과 그 관계 |
| 컴포넌트 | 실제 구현 모듈(컴포넌트) 사이의 관계와 인터페이스. 구현 단계 |
| 배치 | 결과물·프로세스·컴포넌트가 놓이는 물리적 노드와 통신 경로. 구현 단계 |
| 복합체 구조 | 클래스·컴포넌트가 복합 구조일 때 그 내부 구조 |
| 패키지 | 유스케이스·클래스 같은 요소를 묶은 패키지 사이의 관계(`<<import>>` 의존) |

### 행위 다이어그램

| 다이어그램 | 표현하는 것 |
| --- | --- |
| 유스케이스 | 사용자(Actor) 관점의 요구 기능(Use Case). 기능 모델링 |
| 시퀀스 | 객체들이 주고받는 메시지를 **시간 순서**로 |
| 커뮤니케이션 | 메시지와 함께 객체 간 **연관 관계**까지 |
| 상태 | 한 객체의 상태가 이벤트에 따라 어떻게 바뀌는지 |
| 활동 | 처리 로직이나 조건에 따른 흐름을 순서대로. 기능 모델링 |
| 상호작용 개요 | 여러 상호작용 다이어그램 사이의 제어 흐름 |
| 타이밍 | 객체 상태 변화와 **시간 제약** |

### 관계

관계 기호는 결국 코드 모양의 차이다.

| 관계 | 의미 | 표기 | 코드에서의 모습 |
| --- | --- | --- | --- |
| 연관(Association) | 서로 관련이 있음 | `A ───▶ B` 실선 | 상대를 필드로 계속 참조한다 |
| 집합(Aggregation) | 부분-전체지만 부분이 독립적으로 존재 가능 | `A ◇─── B` 빈 마름모가 전체 쪽 | 부분을 **밖에서 받아** 갖는다. 다른 객체와 공유할 수 있다 |
| 합성(Composition) | 부분이 전체에 종속 | `A ◆─── B` 채운 마름모가 전체 쪽 | 전체가 부분을 **직접 생성**해서 갖는다. 전체가 사라지면 부분도 사라진다 |
| 일반화(Generalization) | 상속 관계 | `A ───▷ B` 실선, 빈 삼각형이 부모 쪽 | `extends` |
| 실체화(Realization) | 인터페이스 구현 | `A - - ▷ B` 점선, 빈 삼각형이 인터페이스 쪽 | `implements` |
| 의존(Dependency) | 짧은 시간 동안 사용하는 관계 | `A - - > B` 점선 화살표 | 메서드 파라미터나 지역 변수로 **잠깐** 쓴다 |

```ts
class Post {
  private comments: Comment[] = [];          // 연관 (Post 1 ── 0..* Comment)
}

class Comment {
  private meta = new CommentMeta();          // 합성: 직접 생성
  constructor(private author: Member) {}     // 집합: 밖에서 받은 Member를 공유
}

class CommentCtrl {
  register(form: CommentForm) { /* ... */ }  // 의존: 파라미터로만 사용
}
```

### 클래스 다이어그램 표기

클래스 다이어그램은 업계에서 설계를 공유할 때 가장 많이 쓰는 UML이다.

| 요소 | 뜻 | 표기 |
| --- | --- | --- |
| 클래스 | 객체의 속성과 행동을 정한 설계도 | 세 칸 상자: 이름 / 속성 / 메서드 |
| 속성(Attribute) | 클래스의 데이터 필드 | `가시성 이름: 타입[개수] = 기본값`, 예: `- name: String` |
| 메서드(Method) | 클래스가 할 수 있는 행동 | `가시성 이름(파라미터: 타입): 반환 타입`, 예: `+ getName(): String` |
| 인터페이스 | 구현 클래스가 반드시 제공할 메서드의 계약 | `<<interface>>` 스테레오타입 |
| 열거형(Enumeration) | 이름 붙은 값의 집합(상품 분류, 월) | `<<enumeration>>` 스테레오타입 |
| 접근 제한자 | 공개 범위 | `+` public, `-` private, `#` protected, `~` package |
| 다중성 | 관계 양끝의 개수 | `1` 정확히 하나, `0..1` 없거나 하나, `0..*`·`*` 없거나 여러 개, `1..*` 하나 이상, `n..m` n개에서 m개 |

GoF 패턴 대부분이 클래스 다이어그램으로 설명된다([[gof-design-patterns|GoF 디자인 패턴]]).

### UML로 하는 객체지향 분석·설계

다이어그램을 **어떤 순서로, 무엇에서 무엇을 뽑아** 그리는지가 실제 설계 과정이다.

```text
유스케이스 다이어그램·명세  ──▶  클래스 다이어그램  ──▶  시퀀스·활동·상태 머신
   (요구사항 분석)             (구조 설계)            (동작 설계)
                                   └──▶ 컴포넌트·패키지·배치 (묶음과 물리 구성)
```

화살표는 한 방향이 아니다. 시퀀스 다이어그램을 그리다 클래스에 없던 메서드가 나오면 클래스 다이어그램으로 돌아가 고친다. 모든 단계가 **반복하며 정제**하는 과정이다. 아래 예는 블로그의 「댓글 작성」 유스케이스다(명세는 [[use-case-diagram#유스케이스 명세|유스케이스 명세]]).

**1. 클래스 식별: 명사 추출.** 명세에서 명사를 모두 뽑고(회원, 댓글, 입력창, 내용, 스팸, 목록, 이미지…), 시스템 경계 밖(회원, 스팸 필터 서비스는 액터), 중복(내용은 댓글의 일부), 너무 추상적인 것을 걸러 낸다. 남은 후보를 역할에 따라 세 스테레오타입으로 나눈다.

| 유형 | 맡는 일 | 예 |
| --- | --- | --- |
| 경계(Boundary) | 시스템과 바깥(사용자 화면, 외부 시스템)을 잇는다 | `CommentUI`, `SpamFilterClient` |
| 제어(Control) | 유스케이스의 업무 로직을 처리한다 | `CommentCtrl` |
| 실체(Entity) | 오래 보관하는 데이터를 관리한다 | `Comment`, `Attachment` |

명세에 직접 나오지 않아도 화면과 데이터 사이에서 로직을 맡을 제어 클래스는 **새로 만들어 넣는 경우가 많다.** 이 구분은 MVC나 계층형 아키텍처의 뼈대와 거의 같다. 책임을 나누는 기준은 [[responsibility-driven-design|책임 주도 설계]]에 있다.

**2. 속성과 행위: 명사와 동사.** 속성은 클래스에 남은 명사에서(`Comment`는 내용, 작성자, 작성 시각), 행위는 명세의 동사에서 뽑는다("입력창을 펼친다"는 `CommentUI`, "스팸 여부를 확인한다"는 `CommentCtrl`). 메시지 내용만 다른 같은 동작은 하나로 합친다. "오류 문구를 보여 준다"와 "안내 문구를 보여 준다"는 `showMessage(text)` 하나다.

**3. 시퀀스 다이어그램: 메시지의 시간 순서.** 참여 객체(**생명선**)를 가로로 놓고, 위에서 아래로 시간이 흐르며 주고받는 메시지를 그린다. 객체가 일하는 구간은 긴 사각형(**활성화**)으로 표시하고, 메시지는 동기(채운 화살촉), 비동기(열린 화살촉), 반환(점선)으로 나뉜다.

```text
회원     :CommentUI      :CommentCtrl     :SpamFilterClient    :Comment
 │ 등록 클릭 │                 │                    │                │
 │─────────▶│ register(form)  │                    │                │
 │          │────────────────▶│ check(body)        │                │
 │          │                 │───────────────────▶│                │
 │          │                 │◀ ─ ─ ─ ok ─ ─ ─ ─ ─│                │
 │          │                 │ save()                              │
 │          │                 │────────────────────────────────────▶│
 │          │◀ ─ ─ 목록 ─ ─ ─ │                                     │
```

조건과 반복은 **결합 단편(combined fragment)** 상자로 감싼다. `opt`는 `if`, `alt`는 `if / else`, `loop`는 `for`·`while`, `break`는 조건이 참이면 나머지를 건너뛰고 빠져나가기, `par`는 동시 실행, `strict`는 적힌 순서 강제다. 그리다 보면 "스팸이면?" 같은 빠진 흐름과 새 메서드가 나오고, 이것을 클래스 다이어그램에 돌려 반영한다.

**4. 활동 다이어그램: 실행 흐름.** 업무 프로세스, 유스케이스 흐름, 메서드의 알고리즘을 순서도처럼 그린다.

| 노드 | 의미 |
| --- | --- |
| 행위 노드 | 하나의 동작. 일반 동작 호출, 다른 활동 호출, 특정 클래스 연산 호출, 시간 이벤트 수신 |
| 초기 / 최종 노드 | 시작점. 최종은 **활동 최종**(모든 흐름 종료)과 **흐름 최종**(그 흐름만 종료)으로 나뉜다 |
| 결정 / 병합 | 마름모. 조건(가드)이 참인 한 흐름으로만 간다 / 갈라진 흐름 중 하나라도 오면 통과 |
| 분기 / 결합 | 굵은 막대. 흐름을 복제해 **동시에** 진행 / 모든 흐름이 도착해야 하나로 합친다 |
| 파티션 | 수영 레인. 누가 그 동작을 맡는지 영역으로 나눈다 |

결정·병합은 "둘 중 하나", 분기·결합은 "둘 다 동시에"다. 이 차이를 헷갈리면 병렬 처리를 순차로 그리게 된다.

**5. 상태 머신 다이어그램: 한 객체의 일생.** 상태가 복잡하게 바뀌는 대상(주문, 결제, 장비)을 골라 상태와 전이를 그린다. 전이 라벨은 구조적 방법의 상태 머신과 같은 `이벤트(파라미터) [조건] / 행위`이고, 조건에 따라 여러 전이 중 하나를 고르는 지점은 **선택(choice)** 노드로 그린다.

```text
●──▶ [작성 중] ── 등록(body) [body ≠ ""] / 저장 ──▶ [게시됨]
                                                 │ 신고(n) [n ≥ 5] / 숨김 처리
                                                 ▼
                    [삭제됨] ◀── 삭제() / 기록 ── [숨겨짐]
```

**6. 묶음과 물리 구성.**

| 다이어그램 | 단위 | 작성 순서 | 메모 |
| --- | --- | --- | --- |
| 컴포넌트 | 실행 가능한 단위 | 컴포넌트 식별 → 인터페이스 정의 → 관계 정의 | 제공 인터페이스(롤리팝)와 요구 인터페이스(소켓)로 잇는다. 유스케이스별 클래스 묶음이 컴포넌트 후보가 된다 |
| 패키지 | 유스케이스·클래스 등 요소의 묶음 | 패키지 식별 → 포함·의존 관계 정의 | `<<import>>`는 가져온 요소를 공개로, `<<access>>`는 비공개로 추가한다 |
| 배치 | 물리 노드 | 노드 식별 → 통신 경로 설정 → 아티팩트 배치 | 장치 노드(서버 하드웨어)와 실행 환경(OS, 웹 서버, 컨테이너)을 구분한다. 통신 경로에 HTTP, TCP/IP, RPC 등을 적는다 |

## 프로젝트 관리

프로젝트는 **유일한** 결과물을 만들기 위한 **일시적인** 활동이다. 매일 반복하는 운영 업무나 끝나는 날이 없는 일은 프로젝트가 아니다. 프로젝트 관리는 품질(Quality)·비용(Cost)·일정(Delivery) 목표를 지키려고 지식, 기술, 도구를 적용하는 일이다. Standish Group의 CHAOS 보고서에서 일정·비용·기능을 모두 지킨 "성공" 프로젝트는 1994년 16%에서 2020년 31% 정도로 늘었을 뿐이고, 한 실패 원인 조사에서는 요구사항 정의 부실이 1위, 범위 정의 부실이 2위였다.

```text
착수 ──▶ 계획 ──▶ 실행 ──▶ 종료
          ▲         │
          └─ 통제 ◀─┘  (계획 대비 실적을 보고, 어긋나면 계획을 고친다)
```

| 단계 | 하는 일 |
| --- | --- |
| 착수 | 프로젝트 시작을 공식 승인받는다 |
| 계획 | 목표와 범위를 이룰 활동, 일정, 비용, 인력, 품질 계획을 세운다 |
| 실행 | 인력과 자원을 갖추고 계획대로 수행한다 |
| 통제 | 주기적으로 점검하고, 목표와 차이가 나면 시정 조치를 한다 |
| 종료 | 결과물을 인도하고, 계약 의무를 다했으면 닫는다 |

### 참고하는 틀과 CMMI

| 틀 | 성격 | 내용 |
| --- | --- | --- |
| PMBOK (PMI) | 모든 산업의 프로젝트 관리 지침 | 통합, 범위, 일정, 원가, 품질, 자원, 의사소통, 리스크, 조달, 이해관계자 관리의 10개 지식 영역 (6판 기준. 7판은 원칙 중심으로 개편) |
| ISO/IEC/IEEE 12207 | 소프트웨어 생명주기 프로세스 국제 표준 | 계약, 조직 지원, 기술 관리, 기술 프로세스로 획득부터 폐기까지 규정 |
| CMMI | 조직 프로세스 개선을 위한 사실상의 업계 표준 | 프로세스 성숙도를 5단계로 평가 |

| CMMI 단계 | 이름 | 모습 |
| --- | --- | --- |
| 1 | 초기 (Initial) | 그때그때 즉흥적으로 일한다. 결과가 사람에 따라 다르다 |
| 2 | 관리 (Managed) | 프로젝트 단위로 기본적인 계획·추적을 한다 |
| 3 | 정의 (Defined) | 조직 표준 프로세스가 있고 프로젝트가 그것을 맞춰 쓴다 |
| 4 | 정량적 관리 (Quantitatively Managed) | 프로세스를 수치로 측정하고 통제한다 |
| 5 | 최적화 (Optimizing) | 측정 결과로 프로세스를 계속 개선한다 |

성숙도가 낮은 조직은 일정·비용을 근거 없이 잡고 납기를 맞추려고 품질을 희생한다. 높은 조직은 이전 프로젝트 실적으로 일정을 잡고 품질을 객관적인 수치로 판단한다.

### WBS: 범위를 쪼갠다

**WBS(Work Breakdown Structure)** 는 목표를 이루는 데 필요한 작업을 계층으로 쪼갠 것이다. 맨 아래 단위인 **작업 패키지**는 보통 2~3주 안에 끝낼 수 있을 만큼 작게 나누고, 담당자·공수·비용·일정을 붙일 수 있어야 한다.

```text
쇼핑몰 개발
├─ 요구사항: 요구사항 정의서, 기능 명세서
├─ 설계: 아키텍처 설계, 화면 설계, DB 설계
├─ 구현: 회원, 상품 검색, 주문, 결제
├─ 테스트: 단위, 통합·시스템, 인수
└─ 배포: 운영 이관, 사용자 매뉴얼
```

가까운 단계는 상세하게, 먼 단계는 굵게 잡았다가 다가올 때 상세화하는 방식을 **롤링 웨이브(Rolling Wave)** 계획이라 한다. 애자일의 백로그 정제와 같은 발상이다([[backlog-and-estimation|백로그와 추정]]).

### 소프트웨어 비용 산정

비용을 너무 높게 잡으면 예산 낭비, 너무 낮게 잡으면 개발자 부담과 품질 저하가 생긴다. 결정 요소는 프로젝트(복잡도, 규모, 신뢰도), 자원(인적·하드웨어·소프트웨어), 생산성(개발자 능력, 기간)이다.

| 구분 | 기법 | 설명 |
| --- | --- | --- |
| 하향식 | 전문가 감정 | 경험 많은 전문가 2명 이상에게 의뢰. 빠르지만 주관적 |
| 하향식 | 델파이 | 조정자 1명이 같은 질문을 여러 전문가에게 익명으로 묻고, 결과를 공유한 뒤 다시 묻기를 반복해 편견을 보완한다 |
| 상향식 | LOC | 모듈별 낙관·기대·비관 라인 수로 예측치 = (낙관치 + 4 × 기대치 + 비관치) / 6 |
| 상향식 | 개발 단계별 인월수 | 생명주기 단계별로 노력 산정 |
| 수학적 | COCOMO | LOC 기반, 조직형·반분리형·내장형별 공식 (보헴) |
| 수학적 | Putnam | Rayleigh-Norden 곡선으로 노력 분포 예측, 대형 프로젝트 |
| 수학적 | FP(기능 점수) | 사용자가 식별할 수 있는 입력·출력·질의·파일·인터페이스 수로 점수 산정 (알브레히트). 공공 SW 사업 대가 산정에 쓴다 |

LOC 계산 예: 총 30,000라인, 개발자 5명, 1인당 월 300라인이면 `30000 / (5 × 300) = 20개월`.

**COCOMO 기본형**은 공수 `E = a × (KLOC)^b`(인월), 기간 `D = c × E^d`(월)로 계산한다.

| 유형 | 규모 | 예 | a | b | c | d |
| --- | --- | --- | --- | --- | --- | --- |
| 조직형 (Organic) | 5만 라인 이하, 기관 내부의 중소 규모 | 사무 처리·업무용·과학 계산용 응용 프로그램 | 2.4 | 1.05 | 2.5 | 0.38 |
| 반분리형 (Semi-detached) | 30만 라인 이하, 조직형과 내장형의 중간 | 트랜잭션 처리 시스템, 운영체제, DBMS | 3.0 | 1.12 | 2.5 | 0.35 |
| 내장형 (Embedded) | 30만 라인 이상, 초대형·엄격한 제약 | 신호기 제어, 미사일 유도, 실시간 처리 시스템 | 3.6 | 1.20 | 2.5 | 0.32 |

사내 업무 시스템 12 KLOC를 조직형으로 보면 E = 2.4 × 12^1.05 ≈ 32.6 인월, D = 2.5 × 32.6^0.38 ≈ 9.4개월, 평균 인원 ≈ 3.5명이다. LOC 기반 산정은 언어와 코딩 스타일에 따라 크게 흔들리므로 나온 숫자는 출발점으로만 쓴다.

### 일정: PERT와 주 경로

**PERT** 차트는 작업 사이의 선후 관계를 네트워크로 그리고, 작업마다 ES/EF(가장 빨리 시작·끝낼 수 있는 날), LS/LF(전체 일정을 늦추지 않고 가장 늦게 시작·끝내도 되는 날), **여유**(LS − ES)를 계산한다.

| 작업 | 기간(일) | 선행 | ES | EF | LS | LF | 여유 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A 요구사항 정의 | 3 | - | 0 | 3 | 0 | 3 | 0 |
| B 화면 설계 | 4 | A | 3 | 7 | 3 | 7 | 0 |
| C API 설계 | 2 | A | 3 | 5 | 5 | 7 | 2 |
| D 프론트엔드 구현 | 6 | B, C | 7 | 13 | 7 | 13 | 0 |
| E 백엔드 구현 | 5 | C | 5 | 10 | 8 | 13 | 3 |
| F 통합 테스트 | 3 | D, E | 13 | 16 | 13 | 16 | 0 |

- **앞으로 계산(ES·EF)**: 선행 작업의 EF 중 가장 큰 값이 ES다. D는 B(7)와 C(5) 중 7에 시작한다.
- **뒤로 계산(LS·LF)**: 후행 작업의 LS 중 가장 작은 값이 LF다. C는 D(7)와 E(8) 중 7까지 끝나야 한다.
- 여유가 0인 작업을 이은 **A → B → D → F(16일)** 가 **주 경로(Critical Path)** 다. 이 경로의 작업이 하루 밀리면 전체가 하루 밀리고, E는 3일까지 늦어도 괜찮다.

일정을 줄이려면 주 경로의 작업을 줄여야 한다. 여유가 있는 작업에 인력을 더 넣어도 완료일은 그대로다. 계산 자체는 위상 정렬 위의 최장 경로 DP다([[topological-sort|위상 정렬]]). **간트 차트**는 달력 위에 작업마다 막대를 그려 언제 무엇을 하는지, 오늘 기준으로 무엇이 늦었는지 보여 주지만 의존 관계는 덜 드러난다. 그래서 의존 관계는 PERT로 계산하고 공유는 간트 차트로 하는 경우가 많다.

### 통제: EVM

측정하지 않으면 관리할 수 없다. 일정·비용·공수·품질을 계획과 실적으로 나란히 놓고, 차이가 조직의 기준(예: 일정 차이 10% 초과)을 넘으면 이슈로 등록해 Jira, Redmine 같은 이슈 관리 시스템에서 시정 조치까지 추적한다. **EVM(Earned Value Management)** 은 일정과 비용을 **같은 단위(돈)** 로 바꿔 한 번에 비교한다.

| 용어 | 다른 이름 | 뜻 |
| --- | --- | --- |
| PV | BCWS | 지금까지 **하기로 계획한** 일의 예산 |
| EV | BCWP | 지금까지 **실제로 해낸** 일의 예산상 가치 |
| AC | ACWP | 지금까지 해낸 일에 **실제로 쓴** 돈 |
| BAC | - | 전체 일의 총예산 |

| 지표 | 식 | 해석 |
| --- | --- | --- |
| 일정 차이 SV | EV − PV | 음수면 일정 지연 |
| 비용 차이 CV | EV − AC | 음수면 비용 초과 |
| 일정 성과 지수 SPI | EV ÷ PV | 1보다 작으면 지연 |
| 비용 성과 지수 CPI | EV ÷ AC | 1보다 작으면 초과 |
| 완료 시 예상 비용 EAC | AC + (BAC − EV) ÷ CPI | 지금 효율이 이어진다고 가정한 최종 비용 |
| 완료 시 차이 VAC | BAC − EAC | 음수면 최종적으로 예산 초과 |

**예**: 총예산 1억 원, 8개월 프로젝트의 4개월 시점에 PV 5,000만 원, EV 4,000만 원, AC 4,500만 원이면 SV = −1,000만 원(계획한 일 중 1,000만 원어치를 못 했다), CV = −500만 원(해낸 일에 비해 500만 원을 더 썼다), SPI = 0.80, CPI ≈ 0.89, EAC ≈ 1억 1,250만 원, VAC ≈ −1,250만 원이다. 진척률만 보면 "절반쯤 했다"로 끝나지만, EVM은 늦은 정도와 돈이 새는 정도를 따로 보여 주고 결말까지 예측한다.

### 위험 관리

위험은 품질·비용·일정 목표 중 적어도 하나에 영향을 **줄 수도 있는**, 아직 일어나지 않은 사건이나 상태다. **이미 일어난** 문제는 이슈라 부른다. 위험 관리는 위험이 이슈가 되기 전에 다루는 일이다.

```text
위험 식별 ──▶ 분석·평가 ──▶ 대응 계획 ──▶ 모니터링·문서화
    ▲                                        │
    └──────────── 새 위험, 상태 변화 ────────┘
```

- **식별**: 체크리스트와 과거 위험 DB로 찾는다. "고객과의 소통 채널이 충분한가?", "핵심 인력이 다른 업무를 겸하고 있지 않은가?", "처음 써 보는 기술이 있는가?"
- **분석**: 발생 확률과 영향도를 등급(예: 1~5)으로 매기고 곱해서 우선순위를 정한다.
- **대응**: 네 가지 중 고른다.

| 대응 | 뜻 | 예 |
| --- | --- | --- |
| 회피 | 위험의 원인 자체를 없앤다 | 검증 안 된 신기술 도입을 다음 버전으로 미룬다 |
| 완화 | 확률이나 영향을 허용 가능한 수준까지 낮춘다 | 핵심 기능에 테스트를 더 배정한다 |
| 전가 | 피해를 외부로 넘긴다 | 보험, 외주 계약의 책임 조항 |
| 수용 | 허용 가능한 수준이면 받아들인다 | 사용 빈도가 낮은 관리자 화면의 사소한 오류 |

소프트웨어 프로젝트에서 자주 나오는 위험은 문서화되지 않았거나 계속 바뀌는 요구사항과 불분명한 인수 기준, 비현실적인 예산·일정과 계약 중의 기간 단축, 훈련받지 않은 인력과 불명확한 역할, 발주 측 담당자의 잦은 교체와 이해관계자의 참여 부족, 협력 업체 간 갈등과 통합 지연, 맞지 않는 도구·낯선 언어의 선택, 과도한 문서·검토 절차다. 같은 확률 × 영향도 계산으로 테스트 강도를 나누는 방법은 [[software-testing#위험 기반 테스트|위험 기반 테스트]]에 있다.

## 형상 관리 (SCM)

**형상(configuration)** 은 요구사항 명세서, 설계서, 소스 코드, 테스트 명세서처럼 개발 과정에서 나온 산출물들의 구성이다. 형상 관리는 이 산출물(형상 항목)을 식별하고 변경을 통제하며 처리 상태를 지켜보는 활동이고, 목표는 산출물의 **무결성**(승인된 것만 들어 있다)과 **추적성**(누가 언제 왜 바꿨는지 안다)이다. 형상 관리가 없으면 실수로 덮어쓴 작업을 되살리기 어렵고, 복사본 중 무엇이 최신인지, 버그가 어느 버전에 있는지, 고객이 어떤 수정이 들어간 버전을 가졌는지 알 수 없다.

### 베이스라인

**베이스라인(baseline, 기준선)** 은 공식 검토와 합의를 거쳐 개발의 기초가 된 상태로, 이후에는 **형상 통제 절차로만** 바꿀 수 있다. 보통 개발 단계나 마일스톤마다 잡는다. 요구 분석이 끝나면 요구사항 명세서가, 설계가 끝나면 아키텍처·상세 설계서가 더해지는 식으로 단계마다 베이스라인에 들어가는 항목이 늘어난다.

### 형상 관리 활동

| 활동 | 하는 일 |
| --- | --- |
| 형상 식별 | 관리할 항목(산출물뿐 아니라 컴파일러 같은 개발 도구까지)을 고르고, 유일한 식별자 체계를 정하고(`프로젝트_문서종류_버전_초안` 식 파일 이름), 베이스라인 시점을 정한다 |
| 형상 통제 | 변경 요청을 **형상 통제 위원회(CCB)** 가 심사해 승인된 것만 베이스라인에 반영한다. 심사 기준은 난이도, 다른 산출물에 미치는 영향, 일정·비용 안에서 가능한지다 |
| 형상 상태 보고 | CCB 활동, 베이스라인 상태와 변경 내역, 변경 요청 처리 현황(요청·승인·기각 건수)을 보고해 개발 상태를 보이게 한다 |
| 형상 감사 | 형상 관리 계획을 지켰는지, 베이스라인 설정과 변경 통제가 적절했는지 독립적으로 점검한다 |

정보처리기사는 여기에 **버전 제어**(여러 버전의 형상 항목 관리)를 따로 세고, 상태 보고를 **형상 기록**(식별·통제·감사 결과를 기록·보고)이라고 부르기도 한다. 변경 요청부터 확인까지의 흐름은 위 「변경 관리와 추적」의 요구사항 변경 절차와 같다. 실무에서는 Git·SVN 저장소로 항목과 버전을, Jira·Redmine 같은 이슈 시스템으로 변경 요청과 심사를 관리한다([[Tools/Git/git-basics|Git 기초]]).

### 버전 관리의 기본 동작

| 동작 | 뜻 |
| --- | --- |
| 저장소(repository) | 코드와 모든 변경 이력을 보관하는 곳 |
| 체크아웃(checkout) | 저장소의 코드를 내 작업 공간으로 가져온다 |
| 커밋(commit) | 확인을 마친 변경을 저장소에 기록해 다른 사람이 쓰게 한다 |
| 되돌리기(revert, rollback) | 버그가 들어오면 전체나 일부를 이전의 안정 버전으로 되돌린다 |
| 이력 추적 | 누가 언제 무엇을 바꿨는지 남긴다(`git log`, `git blame`) |

동시 수정을 다루는 방식은 둘이다. 옛 중앙 집중식 도구는 파일을 체크아웃한 사람만 고치도록 **잠근다**(lock-modify-unlock). Git과 SVN의 기본 방식은 각자 고친 뒤 **병합한다**(copy-modify-merge). 어느 쪽이든 공유하는 주 브랜치는 늘 빌드되고 돌아가야 하므로 깨진 코드를 커밋하지 않는다.

## 정리

- 생명주기 모델은 빅뱅(폭포수·V)과 진화적(원형·나선형·UP·애자일)으로 나뉜다.
- 요구공학은 추출 → 분석 → 명세 → 검증으로 만들고, 베이스라인 이후의 변경은 영향 분석과 심사, 추적 매트릭스로 지킨다. 비기능 요구는 숫자로, 자연어 명세는 EARS 틀로 쓴다.
- 구조적 방법은 문맥도 → DFD → 태스크·모듈 → 구조 차트로, 객체지향 방법은 유스케이스 명세 → 클래스(명사·동사, 경계·제어·실체) → 시퀀스·활동·상태 머신으로 내려간다.
- 모듈은 결합도를 낮추고 응집도를 높이며, 정보 은닉이 그 수단이다.
- 프로젝트는 WBS로 쪼개고, COCOMO·FP로 산정하고, PERT 주 경로로 일정을 잡고, EVM으로 통제하고, 위험은 확률 × 영향도로 다룬다.
