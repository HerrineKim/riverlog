좋은 소프트웨어 설계의 핵심은 "고치기 쉽고 다시 쓰기 쉬운 구조"다. 시험에서는 이를 모듈 독립성, 디자인 패턴, 모델링 도구, 그리고 개발 과정을 관리하는 기법(비용 산정, 형상 관리)으로 나눠 묻는다.

## 모듈과 모듈 독립성

**모듈**은 성능 향상과 수정·재사용 편의를 위해 기능 단위로 나눈 부분이다. 모듈 독립성은 **결합도는 약하게, 응집도는 강하게**, 크기는 작게 할수록 높아진다.

### 결합도 (Coupling) — 모듈 간 의존 정도, 약할수록 좋음

| 순서 | 종류 | 설명 |
| --- | --- | --- |
| 1 (약함) | 자료 | 필요한 데이터 값만 매개변수로 주고받음 |
| 2 | 스탬프 | 배열·구조체·객체 같은 **자료구조**를 통째로 전달 |
| 3 | 제어 | 값이 아니라 처리 방식을 지시하는 **제어 요소(flag)** 를 전달 |
| 4 | 외부 | 외부에서 정의한 데이터 형식·통신 프로토콜 등을 공유 |
| 5 | 공통 | **전역 변수**를 여러 모듈이 참조·갱신 |
| 6 (강함) | 내용 | 다른 모듈의 내부 데이터나 지역 변수를 **직접 참조** |

외우기: **자스제외공내**.

### 응집도 (Cohesion) — 모듈 내부 요소의 관련 정도, 강할수록 좋음

| 순서 | 종류 | 설명 |
| --- | --- | --- |
| 1 (강함) | 기능적 | 모든 요소가 하나의 기능을 위해 수행됨 |
| 2 | 순차적 | 한 활동의 출력이 다음 활동의 입력으로 쓰임 |
| 3 | 교환적(통신적) | 같은 입력·출력을 사용해 서로 다른 기능을 수행 |
| 4 | 절차적 | 입출력 연관은 없지만 정해진 순서대로 수행해야 함 |
| 5 | 시간적 | 특정 시점에 함께 처리되는 기능을 모음 (예: 초기화) |
| 6 | 논리적 | 유사한 성격의 처리를 한 모듈에 모음 |
| 7 (약함) | 우연적 | 서로 관련 없는 요소들 |

외우기: **기순교절시논우**.

### Fan-in / Fan-out

- **Fan-in**: 어떤 모듈을 호출하는 상위 모듈의 수 (높으면 재사용성이 좋음)
- **Fan-out**: 어떤 모듈이 호출하는 하위 모듈의 수

## 디자인 패턴 (GoF)

| 분류 | 목적 | 대표 패턴 |
| --- | --- | --- |
| 생성 | 객체 생성 방식 | Singleton, Factory Method, Abstract Factory, Builder, Prototype |
| 구조 | 클래스·객체 조합 | Adapter, Bridge, Composite, Decorator, Facade, Proxy |
| 행위 | 객체 간 상호작용·책임 분배 | Observer, Strategy, Command, Iterator, Template Method, Interpreter |

자주 나오는 패턴

- **Singleton**: 인스턴스를 하나만 만들고 어디서든 같은 인스턴스를 쓰게 함. `getInstance()`를 여러 번 호출해도 같은 객체가 반환되므로 상태가 공유된다.
- **Factory Method**: 상위 클래스는 객체 생성 인터페이스만 정의하고, 실제 생성은 서브 클래스가 결정.
- **Observer**: 한 객체의 상태가 바뀌면 의존하는 객체들에 자동으로 알림이 가는 일대다 의존 관계.

## UML

| 분류 | 다이어그램 |
| --- | --- |
| 구조(정적) | 클래스(속성·메서드), 객체, 컴포넌트, 배치, 복합체 구조, 패키지(`<<import>>` 의존) |
| 행위(동적) | 유스케이스, 시퀀스, 커뮤니케이션, 상태, 활동, 상호작용 개요, 타이밍 |

### 구조 다이어그램

| 다이어그램 | 표현하는 것 |
| --- | --- |
| 클래스 | 클래스의 속성·연산과 클래스 사이 관계. 시스템 구조를 파악하고 문제점을 찾는다 |
| 객체 | 특정 시점의 인스턴스(객체)들과 그 관계 |
| 컴포넌트 | 실제 구현 모듈(컴포넌트) 사이의 관계와 인터페이스. 구현 단계 |
| 배치 | 결과물·프로세스·컴포넌트가 놓이는 물리적 노드와 통신 경로. 구현 단계 |
| 복합체 구조 | 클래스·컴포넌트가 복합 구조일 때 그 내부 구조 |
| 패키지 | 유스케이스·클래스 같은 요소를 묶은 패키지 사이의 관계 |

### 행위 다이어그램

| 다이어그램 | 표현하는 것 |
| --- | --- |
| 유스케이스 | 사용자(Actor) 관점의 요구 기능(Use Case). 기능 모델링 |
| 시퀀스 | 객체들이 주고받는 메시지를 **시간 순서**로 |
| 커뮤니케이션 | 메시지와 함께 객체 간 **연관 관계**까지 |
| 상태 | 한 객체의 상태가 이벤트에 따라 어떻게 바뀌는지 |
| 활동 | 처리 로직이나 조건에 따른 흐름을 순서대로. 기능 모델링 |
| 상호작용 개요 | 여러 상호작용 다이어그램 사이의 제어 흐름 |
| 타이밍 | 객체 상태 변화와 **시간 제약** |

관계

- **연관(Association)**: 서로 관련이 있음
- **집합(Aggregation)**: 부분-전체지만 부분이 독립적으로 존재 가능 (빈 마름모)
- **합성(Composition)**: 부분이 전체에 종속 (채운 마름모)
- **일반화(Generalization)**: 상속 관계
- **의존(Dependency)**: 짧은 시간 동안 사용하는 관계 (점선)
- **실체화(Realization)**: 인터페이스 구현

## 객체지향

- 구성 요소: **객체**(데이터 + 메서드), **클래스**(공통 속성·연산을 가진 객체의 틀, 객체는 클래스의 인스턴스), **메시지**(객체 간 상호작용 수단)
- 기본 원칙: 캡슐화, 정보 은닉, 상속, 추상화, 다형성
- **럼바우(OMT) 분석 기법**: 객체 → 동적 → 기능 모델링 순서
  - 객체(정보) 모델링: 객체 다이어그램, ERD — 구조
  - 동적 모델링: 상태 다이어그램 — 시간에 따른 변화
  - 기능 모델링: 자료 흐름도(DFD) — 입력이 출력으로 바뀌는 과정

## 요구사항

- **기능적 요구사항**: 시스템이 제공해야 하는 기능·서비스
- **비기능적 요구사항**: 성능, 보안, 신뢰성 등 기능에 대한 제약과 품질 속성

## 개발 방법론

- **폭포수(Waterfall)**: 단계를 순차적으로 진행
- **애자일(Agile)**: 짧은 주기를 반복하며 요구사항 변화에 유연하게 대응 (스크럼, XP 등)
  - **스프린트 회고(Sprint Retrospective)**: 스크럼에서 스프린트가 끝날 때(또는 일정 주기마다) 지난 주기를 돌아보며 정한 규칙을 잘 지켰는지, 무엇을 개선할지 확인하고 기록하는 활동
- **리팩토링**: 기능(결과)은 바꾸지 않고 코드 구조를 개선해 가독성과 유지보수성을 높이는 것

## 소프트웨어 비용 산정

비용을 너무 높게 잡으면 예산 낭비, 너무 낮게 잡으면 개발자 부담과 품질 저하가 생긴다. 결정 요소는 프로젝트(복잡도, 규모, 신뢰도), 자원(인적·하드웨어·소프트웨어), 생산성(개발자 능력, 기간)이다.

| 구분 | 기법 | 설명 |
| --- | --- | --- |
| 하향식 | 전문가 감정 | 경험 많은 전문가 2명 이상에게 의뢰. 빠르지만 주관적 |
| 하향식 | 델파이 | 조정자 1명 + 여러 전문가 의견을 종합해 편견 보완 |
| 상향식 | LOC | 예측치 = (낙관치 + 4 × 기대치 + 비관치) / 6 |
| 상향식 | 개발 단계별 인월수 | 생명주기 단계별로 노력 산정 |
| 수학적 | COCOMO | LOC 기반, 조직형·반분리형·내장형별 공식 (보헴) |
| 수학적 | Putnam | Rayleigh-Norden 곡선으로 노력 분포 예측, 대형 프로젝트 |
| 수학적 | FP(기능 점수) | 입력·출력·질의·파일·인터페이스 수로 점수 산정 (알브레히트) |

LOC 계산 예: 총 30,000라인, 개발자 5명, 1인당 월 300라인이면 `30000 / (5 × 300) = 20개월`.

### COCOMO 개발 유형

| 유형 | 규모 | 예 |
| --- | --- | --- |
| 조직형 (Organic) | 5만 라인 이하, 기관 내부의 중소 규모 | 사무 처리·업무용·과학 계산용 응용 프로그램 |
| 반분리형 (Semi-detached) | 30만 라인 이하, 조직형과 내장형의 중간 | 트랜잭션 처리 시스템, 운영체제, DBMS |
| 내장형 (Embedded) | 30만 라인 이상, 초대형·엄격한 제약 | 신호기 제어, 미사일 유도, 실시간 처리 시스템 |

### 비용 산정 자동화 도구

| 도구 | 기반 |
| --- | --- |
| SLIM | Rayleigh-Norden 곡선과 Putnam 예측 모델 |
| ESTIMACS | FP(기능 점수) 모형. 다양한 프로젝트·개인 요소를 반영 |

## 형상 관리 (SCM)

개발 전 과정과 유지보수에서 산출물의 **변경 사항을 관리**하는 활동. 도구로 Git, SVN, CVS가 있다.

| 기능 | 설명 |
| --- | --- |
| 형상 식별 | 관리 대상에 이름·번호를 붙이고 계층 구조로 구분 |
| 버전 제어 | 여러 버전의 형상 항목을 관리 |
| 형상 통제 | 변경 요구를 검토·승인해 기준선(baseline)에 반영 |
| 형상 감사 | 기준선의 무결성을 검증하고 공식 승인 |
| 형상 기록 | 식별·통제·감사 결과를 기록하고 보고 |

## 릴리즈 노트

작성 순서: 모듈 식별 → 릴리즈 정보 확인 → 개요 작성 → 영향도 체크 → 정식 릴리즈 노트 작성 → 추가 개선 항목 식별.
문서 이름, 제품 이름, 버전, 릴리즈 날짜, 노트 버전 등은 **헤더(Header)** 에 적는다.

## UI 설계 원칙과 UX

| 원칙 | 의미 |
| --- | --- |
| 직관성 | 누구나 쉽게 이해하고 사용 |
| 유효성 | 사용자의 목표를 정확하고 완벽하게 달성 |
| 학습성 | 누구나 쉽게 배우고 익힘 |
| 유연성 | 사용자의 요구를 최대한 수용하고 실수를 최소화 |

- **UI**: 사용자와 시스템이 만나는 접점 (CLI, GUI, NUI 등)
- **UX**: 사용자가 제품을 쓰며 느끼는 경험과 감정 전체
