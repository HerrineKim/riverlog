> 고려사이버대학교 「소프트웨어 분석설계」(2023-2학기) 강의 내용을 바탕으로 정리했다.

UML 다이어그램의 종류와 표기는 [[software-engineering#UML|소프트웨어 설계와 공학]], 유스케이스 다이어그램 그리는 법은 [[use-case-diagram|유스케이스 다이어그램]]에 있다. 이 노트는 다이어그램을 **어떤 순서로, 무엇에서 무엇을 뽑아** 그리는지에 집중한다.

```text
유스케이스 다이어그램·명세  ──▶  클래스 다이어그램  ──▶  시퀀스·활동·상태 머신
   (요구사항 분석)             (구조 설계)            (동작 설계)
                                   └──▶ 컴포넌트·패키지·배치 (묶음과 물리 구성)
```

화살표는 한 방향이 아니다. 시퀀스 다이어그램을 그리다 클래스에 없던 메서드가 나오면 클래스 다이어그램으로 돌아가 고친다. 모든 단계가 **반복하며 정제**하는 과정이다.

## 1. 유스케이스 명세

다이어그램은 기능 목록일 뿐이고, 각 기능이 어떻게 진행되는지는 **유스케이스 명세(Use Case Description)** 에 글로 쓴다. 예로 블로그의 「댓글 작성」을 쓴다.

| 항목 | 내용 |
| --- | --- |
| 유스케이스 | 댓글 작성 |
| 설명 | 회원이 글에 댓글을 남긴다 |
| 주 액터 / 보조 액터 | 회원 / 스팸 필터 서비스 |
| 사전 조건 | 회원이 로그인해 있고 글 상세 화면을 보고 있다 |
| 사후 조건 | 댓글이 저장되고 목록 맨 아래에 보인다 |

| 흐름 | 단계 |
| --- | --- |
| 정상 흐름 | 1. 회원이 댓글 입력창을 누른다. 2. 시스템이 입력창을 펼친다. 3. 회원이 내용을 입력한다. 4. 회원이 등록을 요청한다. 5. 시스템이 스팸 여부를 확인한다. 6. 시스템이 댓글을 저장한다. 7. 시스템이 갱신된 목록을 보여 준다. |
| 대안 흐름 | 3a.1 회원이 이미지를 첨부하면, 3a.1.1 시스템이 파일 선택 창을 띄우고, 3a.1.2 첨부 미리보기를 보여 준다. |
| 예외 흐름 | 4e.1 내용이 비어 있으면, 4e.1.1 시스템이 "내용을 입력하세요"를 보여 주고, 4e.1.2 입력창으로 돌아간다. |
| 시나리오 | S1: 1-2-3-4-5-6-7 / S2: 1-2-3-3a.1-3a.1.1-3a.1.2-4-5-6-7 / S3: 1-2-3-4-4e.1-4e.1.1-4e.1.2 |

번호 규칙이 쓸모 있다. `3a`는 "3단계에서 갈라지는 대안", `4e`는 "4단계에서 생기는 예외"라서, 흐름의 조합인 **시나리오가 곧 테스트 케이스 목록**이 된다([[test-design-techniques#시나리오 테스팅|시나리오 테스팅]]).

## 2. 클래스 다이어그램: 명세에서 클래스 뽑기

### 클래스 식별: 명사 추출

1. 명세에서 **명사**를 모두 뽑는다: 회원, 댓글, 입력창, 내용, 등록, 스팸, 목록, 이미지, 파일, 메시지…
2. **걸러 낸다**: 시스템 경계 밖(회원, 스팸 필터 서비스는 액터), 중복(내용은 댓글의 일부), 너무 추상적인 것을 뺀다.
3. 남은 후보에서 클래스를 고르고, 역할에 따라 세 가지 스테레오타입으로 나눈다.

| 유형 | 맡는 일 | 예 |
| --- | --- | --- |
| 경계(Boundary) | 시스템과 바깥(사용자 화면, 외부 시스템)을 잇는다 | `CommentUI`, `SpamFilterClient` |
| 제어(Control) | 유스케이스의 업무 로직을 처리한다 | `CommentCtrl` |
| 실체(Entity) | 오래 보관하는 데이터를 관리한다 | `Comment`, `Attachment` |

명세에 직접 나오지 않아도, 화면과 데이터 사이에서 로직을 맡을 제어 클래스는 **새로 만들어 넣는 경우가 많다.** 이 구분은 MVC나 계층형 아키텍처의 뼈대와 거의 같다.

### 속성과 행위: 명사와 동사

- **속성**은 클래스에 남은 명사에서: `Comment`는 내용, 작성자, 작성 시각.
- **행위**는 명세의 **동사**에서: "입력창을 펼친다", "목록을 보여 준다"는 `CommentUI`, "스팸 여부를 확인한다", "저장한다"는 `CommentCtrl`.
- 같은 동작이 메시지 내용만 다르면 하나로 합친다. "오류 문구를 보여 준다"와 "안내 문구를 보여 준다"는 `showMessage(text)` 하나다.
- 속성마다 읽고 쓰는 접근자(get/set)를 둔다.

표기 형식은 `가시성 이름: 타입[개수] = 기본값`, 연산은 `가시성 이름(파라미터: 타입): 반환 타입`이다.

```text
┌──────────────────────────────┐
│ Comment                      │
├──────────────────────────────┤
│ - id: Long                   │
│ - body: String               │
│ - attachments: Attachment[0..3] │
├──────────────────────────────┤
│ + edit(body: String): void   │
│ + isEmpty(): Boolean         │
└──────────────────────────────┘
```

### 다중성

| 표기 | 뜻 |
| --- | --- |
| `1` | 정확히 하나 |
| `0..1` | 없거나 하나 |
| `0..*` 또는 `*` | 없거나 여러 개 |
| `1..*` | 하나 이상 |
| `n..m` | n개에서 m개 |

### 관계를 코드로 읽기

관계 기호는 결국 코드 모양의 차이다.

| 관계 | 코드에서의 모습 |
| --- | --- |
| 연관 | 상대를 필드로 계속 참조한다 |
| 합성 | 전체가 부분을 **직접 생성**해서 갖는다. 전체가 사라지면 부분도 사라진다 |
| 집합 | 부분을 **밖에서 받아** 갖는다. 다른 객체와 공유할 수 있다 |
| 일반화 | 상속(`extends`) |
| 실체화 | 인터페이스 구현(`implements`) |
| 의존 | 메서드 파라미터나 지역 변수로 **잠깐** 쓴다 |

```ts
class Post {
  private comments: Comment[] = [];          // 연관 (Post 1 ── 0..* Comment)
}

class Comment {
  private meta = new CommentMeta();          // 합성: 직접 생성
  constructor(private author: Member) {}     // 집합: 밖에서 받은 Member를 공유
}

class CommentCtrl {
  register(form: CommentForm) { /* ... */ }  // 의존: 파라미터로만 사용
}
```

## 3. 시퀀스 다이어그램: 메시지의 시간 순서

참여 객체(**생명선**)를 가로로 놓고, 위에서 아래로 시간이 흐르며 주고받는 메시지를 그린다. 객체가 일하는 구간은 긴 사각형(**활성화**)으로 표시한다. 메시지는 동기(채운 화살촉), 비동기(열린 화살촉), 반환(점선)으로 나뉜다.

```text
회원     :CommentUI      :CommentCtrl     :SpamFilterClient    :Comment
 │ 등록 클릭 │                 │                    │                │
 │─────────▶│ register(form)  │                    │                │
 │          │────────────────▶│ check(body)        │                │
 │          │                 │───────────────────▶│                │
 │          │                 │◀ ─ ─ ─ ok ─ ─ ─ ─ ─│                │
 │          │                 │ save()                              │
 │          │                 │────────────────────────────────────▶│
 │          │◀ ─ ─ 목록 ─ ─ ─ │                                     │
```

조건과 반복은 **결합 단편(combined fragment)** 상자로 감싼다.

| 연산자 | 코드로 치면 |
| --- | --- |
| `opt` | `if` (조건이 맞을 때만) |
| `alt` | `if / else` (대안 중 하나만) |
| `loop` | `for`, `while` (최소·최대 횟수 지정 가능) |
| `break` | 조건이 참이면 나머지를 건너뛰고 빠져나간다 |
| `par` | 여러 상호작용을 동시에 |
| `strict` | 적힌 순서를 반드시 지킨다 |

작성 순서는 유스케이스 하나를 고르고, 클래스 다이어그램에서 참여 객체를 가져오고, 메시지를 시간 순으로 잇는 것이다. 그리다 보면 "스팸이면?" 같은 빠진 흐름과 새 메서드가 나오고, 이것을 클래스 다이어그램에 돌려 반영한다.

## 4. 활동 다이어그램: 실행 흐름

업무 프로세스, 유스케이스 흐름, 메서드의 알고리즘을 순서도처럼 그린다.

| 노드 | 의미 |
| --- | --- |
| 행위 노드 | 하나의 동작. 일반 동작 호출, 다른 활동 호출, 특정 클래스 연산 호출, 시간 이벤트 수신 |
| 초기 / 최종 노드 | 시작점. 최종은 **활동 최종**(모든 흐름 종료)과 **흐름 최종**(그 흐름만 종료)으로 나뉜다 |
| 결정 / 병합 | 마름모. 조건(가드)이 참인 한 흐름으로만 간다 / 갈라진 흐름 중 하나라도 오면 통과 |
| 분기 / 결합 | 굵은 막대. 흐름을 복제해 **동시에** 진행 / 모든 흐름이 도착해야 하나로 합친다 |
| 파티션 | 수영 레인. 누가 그 동작을 맡는지 영역으로 나눈다 |

결정·병합은 "둘 중 하나", 분기·결합은 "둘 다 동시에"다. 이 차이를 헷갈리면 병렬 처리를 순차로 그리게 된다.

## 5. 상태 머신 다이어그램: 한 객체의 일생

상태가 복잡하게 바뀌는 대상(주문, 결제, 장비)을 골라 상태와 전이를 그린다. 전이 라벨은 `이벤트(파라미터) [조건] / 행위`다.

```text
●──▶ [작성 중] ── 등록(body) [body ≠ ""] / 저장 ──▶ [게시됨]
                                                 │ 신고(n) [n ≥ 5] / 숨김 처리
                                                 ▼
                    [삭제됨] ◀── 삭제() / 기록 ── [숨겨짐]
```

조건에 따라 여러 전이 중 하나를 고르는 지점은 **선택(choice)** 노드로 그린다.

## 6. 묶음과 물리 구성

| 다이어그램 | 단위 | 작성 순서 | 메모 |
| --- | --- | --- | --- |
| 컴포넌트 | 실행 가능한 단위 | 컴포넌트 식별 → 인터페이스 정의 → 관계 정의 | 제공 인터페이스(롤리팝)와 요구 인터페이스(소켓)로 잇는다. 유스케이스별 클래스 묶음이 컴포넌트 후보가 된다 |
| 패키지 | 유스케이스·클래스 등 요소의 묶음 | 패키지 식별 → 포함·의존 관계 정의 | `<<import>>`는 가져온 요소를 공개로, `<<access>>`는 비공개로 추가한다 |
| 배치 | 물리 노드 | 노드 식별 → 통신 경로 설정 → 아티팩트 배치 | 장치 노드(서버 하드웨어)와 실행 환경(OS, 웹 서버, 컨테이너)을 구분한다. 통신 경로에 HTTP, TCP/IP, RPC 등을 적는다 |

## 정리

- 유스케이스 명세의 흐름 번호를 체계적으로 붙이면 시나리오와 테스트 케이스가 함께 나온다.
- 명사에서 클래스와 속성을, 동사에서 행위를 뽑고, 경계·제어·실체로 역할을 나눈다.
- 클래스 관계는 필드 참조, 직접 생성, 외부 주입, 상속, 파라미터 사용 같은 코드 모양으로 읽는다.
- 시퀀스는 시간 순서, 활동은 실행 흐름, 상태 머신은 한 객체의 상태 변화를 그린다. 그리면서 발견한 것을 다시 클래스에 반영한다.
