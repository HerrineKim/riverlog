> 고려사이버대학교 「소프트웨어 분석설계」(2023-2학기) 강의 내용을 바탕으로 정리했다.

구조적 방법론은 **데이터가 어디서 들어와 어떻게 바뀌어 어디로 나가는지**를 기준으로 시스템을 위에서 아래로 쪼갠다. 객체지향이 "무엇이 책임을 지는가"에서 출발한다면, 구조적 방법은 "어떤 처리가 일어나는가"에서 출발한다. 지금은 웹 서비스보다 C로 짜는 임베디드·실시간 시스템에서 주로 쓰지만, 데이터 흐름으로 범위를 정하는 사고방식은 어디서나 쓸모가 있다.

## 세 가지 설계 원리

| 원리 | 뜻 | 예 (만년 달력) |
| --- | --- | --- |
| 추상화 | 세부를 정하기 전에 상위 수준에서 먼저 설계한다 | 과정: "입력 → 윤년 판정 → 요일 계산 → 출력" 흐름만 먼저 정한다. 데이터: 연·월·일을 "날짜" 하나로 본다. 제어: "윤년이면 A, 아니면 B"를 "요일 계산" 한 단계로 묶는다 |
| 단계적 상세화 | 상위 설계를 점점 구체적인 설계로 나눠 내려간다 (Niklaus Wirth) | "처리"를 "입력 검증, 총 날짜 계산, 윤년 판정, 요일 결정"으로 나눈다 |
| 모듈화 | 함수와 데이터로 이루어진 독립 단위로 나눈다 | 각 단위가 이름을 갖고, 따로 컴파일되고, 다른 곳에서 재사용될 수 있어야 모듈이다 |

좋은 모듈은 **정보 은닉**(내부는 감추고 인터페이스로만 소통), **높은 응집도**, **낮은 결합도**를 갖는다. 단계별 설명은 [[code-cohesion|응집도]], [[code-coupling|결합도]]에 있다.

## 산출물 흐름

| 단계 | 하는 일 | 산출물 |
| --- | --- | --- |
| 요구사항 분석 | 데이터 흐름을 중심으로 기능을 분석한다 | 시스템 문맥도, 데이터 흐름도(DFD), 데이터 사전, 프로세스 명세 |
| 아키텍처 설계 | 기능을 구현할 실행 단위와 모듈을 정한다 | 태스크 모델(동적 관점), 모듈 구조(정적 관점) |
| 상세 설계 | 모듈 안의 함수 구조를 정한다 | 구조 차트 |

아래에서는 **주차장 차단기 제어 소프트웨어**를 예로 단계를 따라간다.

## 1. 시스템 문맥도: 경계를 긋는다

만들 소프트웨어 전체를 **프로세스 하나(번호 0)** 로 두고, 주고받는 외부 개체(**터미네이터**)와 정보 흐름만 그린다. 목적은 **범위 확정**이다. 무엇이 안이고 무엇이 밖인지가 여기서 정해진다.

```text
 [차량 감지 센서] ──차량 진입──▶ ┌─────────────┐ ──개폐 명령──▶ [차단기 모터]
 [번호판 카메라] ──번호판 정보──▶ │ 차단기 제어 0 │ ──안내 문구──▶ [전광판]
 [타이머]  ═══주기 신호═══▶       └─────────────┘
 ──▶ 데이터 흐름   ═══▶ 제어 흐름
```

정보 흐름은 두 종류다.

| 흐름 | 언제 쓰나 | 예 |
| --- | --- | --- |
| 데이터 흐름 | 값이 중요하고 도착 시점은 덜 중요하다 | 번호판 문자열 |
| 제어 흐름 | **언제 일어났는지**가 중요한 이벤트 | 타이머 인터럽트, 차량 진입 신호 |

문맥도 옆에는 흐름마다 의미와 값의 형태, 주기를 표로 적는다(예: "차량 진입: True/False, 센서 인터럽트로 입력").

## 2. 데이터 흐름도: 개발자가 이해할 때까지 쪼갠다

문맥도의 프로세스 0을 1, 2, 3으로, 다시 1.1, 1.2로 나눈다. 기호는 데이터 프로세스, 제어 프로세스, 데이터 흐름, 제어 흐름, **데이터 저장소**다. 한 프로세스가 출력을 여러 개 내보내면 아직 덜 쪼갠 것으로 보고 더 나눈다.

```text
번호판 정보 ──▶ (1.1 번호판 인식) ──차량 번호──▶ (1.3 출입 판정) ──개폐──▶ (2.1 모터 제어)
차량 진입   ──▶ (1.2 센서 입력)  ──진입 여부──▶      │
                                          [등록 차량 목록] (데이터 저장소)
```

최하위 프로세스에는 두 가지 유형 표시를 붙인다.

| 역할 유형 | 뜻 | 표현 |
| --- | --- | --- |
| Device | 센서·디스플레이 같은 장치를 다룬다 | 데이터 프로세스 |
| Control | 상태를 제어한다 | 제어 프로세스(상태 머신으로 명세) |
| Function | 특정 알고리즘을 처리한다 (상태 제어는 아님) | 데이터 프로세스 |

| 실행 유형 | 뜻 | 예 |
| --- | --- | --- |
| Synchronous | 다른 프로세스와 맞물려 데이터를 주고받는다 | 일반 함수 호출 |
| Asynchronous | 독립적으로 돌며 이벤트에 반응한다 | 인터럽트 처리 |
| Periodic | 주기적으로 실행된다 | 타이머로 5ms마다 센서 읽기 |

## 3. 데이터 사전과 프로세스 명세

**데이터 사전**은 DFD에 나온 데이터의 이름, 설명, 값의 범위를 정의한다.

| 데이터 | 설명 | 값의 범위 |
| --- | --- | --- |
| 차량 번호 | 인식한 번호판 문자열 | 7~8자, 한글 1자 포함 |
| 진입 여부 | 차단기 앞 차량 유무 | True / False |
| 개폐 명령 | 모터에 보내는 명령 | Open / Close |

**프로세스 명세**는 최하위 프로세스마다 쓴다. 데이터 프로세스는 자연어로, 제어 프로세스는 상태 머신으로 쓴다.

```text
프로세스 ID  1.2 센서 입력
유형        Periodic Device
입력        센서 값, 타이머 신호
출력        진입 여부 (→ 1.3 출입 판정)
처리        1. 10ms마다 센서 값을 읽는다.
            2. 세 번 연속 감지되면 진입 여부를 True로 보낸다.
```

상태 머신의 전이는 `이벤트(파라미터) [조건] / 행위`로 쓴다.

```text
[닫힘] ── 판정(결과) [결과 = 허가] / "모터 열기" ──▶ [열림]
[열림] ── 진입 여부(값) [값 = False] / "모터 닫기" ──▶ [닫힘]
```

## 4. 태스크 모델: 동시에 도는 단위를 정한다

태스크는 운영체제가 따로 스케줄하는 실행 단위(스레드)다. DFD의 프로세스를 그대로 태스크로 만들면 너무 많아지므로 세 단계로 줄인다.

1. **태스크 후보 식별**: 혼자 돌아야 하는 프로세스(Asynchronous, Periodic, Control)를 후보로 뽑는다.
2. **잔여 프로세스 할당**: 후보가 되지 못한 프로세스(Synchronous, Function)를 관련 깊은 후보에 붙인다. 앞뒤로 이어서 실행되는 관계(절차적 응집)가 기준이 된다.
3. **태스크 통합**: 시간 제약을 어기지 않는 선에서 합친다. 같은 타이머로 깨어나는 태스크끼리(시간적 응집) 합치는 것이 전형적이다.

태스크 사이에 메시지를 보낼 때, 입력이 연달아 들어와도 잃으면 안 되는 곳에는 **비동기 메시지(큐)** 를 쓴다. 태스크 수가 DFD 프로세스 수보다 적어도, 각 태스크가 어느 프로세스를 품고 있는지 추적 관계로 남겨 둔다.

## 5. 모듈 구조: 파일 단위로 나눈다

모듈은 **구현 단위**다. C라면 `.c`/`.h` 파일 하나이거나 그 묶음인 디렉터리다.

1. **모듈 식별**: 태스크를 모듈로 옮기고, 여러 모듈이 같이 쓰는 기능은 **라이브러리 모듈**로 뽑는다.
2. **관계 정의**: 함수 호출 관계를 보고 모듈 간 의존을 그린다.
3. **모듈 명세**: 모듈 ID, 이름, 설명, 인터페이스(다른 모듈이 부르는 함수)를 적는다.

```text
모듈 ID   PK_001        모듈명  출입 판정
설명      번호판과 센서 입력을 종합해 출입 허가 여부를 정한다
인터페이스 Decide_Entry(): 허가 여부를 반환한다
```

공통 기능을 라이브러리로 뽑으면 재사용은 좋아지지만 의존하는 모듈이 늘어 결합도가 올라갈 수 있다. 태스크 단계에서 합쳤던 프로세스를 모듈 단계에서 다시 떼어 내는 일도 생긴다. 어느 쪽이 나은지는 매번 저울질한다.

## 6. 구조 차트: 함수 호출 구조를 그린다

구조 차트는 모듈 안의 **함수 호출 관계와 파라미터 이동**을 계층으로 그린다. 위의 상자가 아래 상자를 호출하고, 화살표 옆에 넘기는 데이터를 적는다. 일반 호출, 비동기 호출, 반복, 조건 같은 기호가 있다.

```text
              Decide_Entry()
            ↙ 차량 번호   ↘ 진입 여부
   Read_Plate()          Read_Sensor()
     ↓                        ↓
 Normalize_Plate()       Debounce_Signal()
```

1. **초기 구조 차트**: 모듈 구조를 바탕으로 DFD의 흐름을 호출 구조로 옮긴다.
2. **상세화**: 기능을 더 쪼개고 공통 기능을 뽑아 최종 구조 차트를 만든다.

구조 차트까지 오면 함수 이름과 시그니처가 거의 정해져서 바로 코딩으로 넘어갈 수 있다.

## 객체지향 방법과 비교

| 관점 | 구조적 | 객체지향 |
| --- | --- | --- |
| 출발점 | 데이터 흐름과 처리 | 사용자 시나리오와 책임 |
| 분석 산출물 | 문맥도, DFD | 유스케이스 다이어그램·명세 |
| 설계 단위 | 태스크, 모듈, 함수 | 컴포넌트, 클래스, 메서드 |
| 잘 맞는 곳 | 센서·주기 처리가 많은 임베디드·실시간 시스템 | 도메인 개념이 풍부한 업무 시스템 |
