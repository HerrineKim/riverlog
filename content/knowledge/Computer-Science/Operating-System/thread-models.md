> 고려사이버대학교 「운영체제이론 및 실습」(2024-1학기) 강의 내용을 바탕으로 정리했다.

스레드는 프로세스에서 **실행 흐름(제어)만 떼어 낸 단위**다. 코드·전역 데이터·힙·열린 파일은 프로세스의 것을 함께 쓰고, PC·레지스터·스택만 스레드마다 따로 둔다. 스레드 자체의 구조와 장점은 [[process-and-thread|프로세스와 스레드]]에 있고, 이 노트는 "그 스레드를 누가 관리하느냐"를 다룬다.

## 누가 스레드를 아는가

스레드를 만드는 방법은 두 가지다. 사용자 공간의 라이브러리가 스레드 표(TCB 목록)를 들고 직접 전환하거나, 커널이 스레드를 스케줄링 대상으로 등록해 관리한다. 사용자 스레드와 커널 스레드를 몇 대 몇으로 잇느냐가 스레드 모델이다.

```text
사용자 수준 (N:1)        커널 수준 (1:1)         혼합형 (M:N)
 u u u u                  u   u   u              u u u u u
  \ | | /                 |   |   |               \ | X | /
    k                     k   k   k                 k   k
커널은 프로세스 하나만 봄  스레드마다 커널 스레드   여러 사용자 스레드를 더 적은
                                                커널 스레드에 나눠 올림
```

## 사용자 수준 스레드 (N:1)

스레드 생성·전환·스케줄링을 모두 라이브러리가 사용자 공간에서 한다. 커널 입장에서는 스레드가 몇 개든 프로세스 하나다.

| 장점 | 단점 |
| --- | --- |
| 전환이 함수 호출 수준이라 빠르다. 모드 전환이 없다 | 한 스레드가 `read()` 같은 블로킹 시스템 콜을 부르면 커널은 **프로세스 전체**를 재운다 |
| 커널 지원 없이 어느 OS에서나 돌아간다(이식성) | 커널이 CPU를 프로세스 단위로 주므로 코어가 여럿이어도 한 번에 한 스레드만 돈다 |
| 응용에 맞는 스케줄링 정책을 라이브러리가 고를 수 있다 | 타이머 인터럽트는 커널이 받으므로, 스레드가 스스로 양보하지 않으면 다른 스레드가 못 돈다 |
| 커널 메모리를 쓰지 않아 스레드를 많이 만들 수 있다 | 스레드 사이의 보호나 시그널 전달 대상 같은 문제를 라이브러리가 떠안는다 |

블로킹 문제를 피하려면 라이브러리가 블로킹 호출을 논블로킹 호출로 바꿔 감싸야 한다(`select`로 준비됐는지 확인한 뒤 읽기). 초창기 JVM의 그린 스레드가 이 방식이었다.

## 커널 수준 스레드 (1:1)

사용자 스레드 하나마다 커널 스레드 하나를 붙인다. 커널이 스레드마다 TCB를 두고 직접 스케줄링한다.

| 장점 | 단점 |
| --- | --- |
| 한 스레드가 블로킹돼도 같은 프로세스의 다른 스레드는 계속 돈다 | 생성·전환마다 시스템 콜과 모드 전환이 든다 |
| 스레드를 여러 코어에 동시에 올릴 수 있다 | 스레드마다 커널 스택과 자료구조가 필요해 수십만 개를 만들기는 부담스럽다 |
| 선점·우선순위·시그널을 커널이 일관되게 처리한다 | 스케줄링 정책을 응용이 바꾸기 어렵다 |

Linux(NPTL), Windows, macOS가 모두 이 모델이다. Linux에서는 스레드도 `task_struct` 하나를 갖는 태스크라서, 같은 프로세스의 스레드는 주소 공간과 파일 테이블을 공유하는 태스크들일 뿐이다.

```bash
ps -eLf | grep my_server     # LWP 열에 스레드마다 다른 ID가 보인다
ls /proc/<pid>/task           # 스레드마다 디렉터리가 하나씩
top -H -p <pid>               # 스레드별 CPU 사용률
```

## 혼합형 (M:N)

사용자 스레드 M개를 커널 스레드 N개(보통 M > N)에 나눠 올린다. 전환은 사용자 공간에서 싸게 하고, 블로킹이나 멀티코어는 커널 스레드 여러 개로 해결하려는 절충이다. 이론상으로는 둘의 장점을 다 갖지만, 사용자 스레드가 블로킹되려는 순간을 라이브러리가 알아야 다른 스레드를 그 자리에 올릴 수 있다. 이를 위해 커널이 라이브러리에 "이 커널 스레드가 곧 블로킹된다"고 알려 주는 **scheduler activation**(upcall) 같은 장치가 제안됐지만, 커널과 라이브러리가 함께 상태를 맞추는 코드가 복잡하고 디버깅이 어렵다.

## 운영체제는 1:1로, M:N은 런타임으로

Solaris는 M:N을 쓰다가 Solaris 9에서 1:1로 바꿨고, 다른 Unix 계열도 같은 길을 갔다. 커널 스레드 생성과 전환이 충분히 싸지자 M:N의 복잡도를 감수할 이유가 줄었기 때문이다.

대신 M:N은 **언어 런타임**에서 되살아났다. 런타임은 자기 언어의 블로킹 지점(채널 대기, 네트워크 I/O)을 모두 알기 때문에, OS가 하기 어려웠던 "블로킹 직전에 갈아 끼우기"를 정확히 할 수 있다.

| 런타임 | 구조 |
| --- | --- |
| Go 고루틴 | 코어 수만큼의 OS 스레드 위에 고루틴 수십만 개를 올린다([[go-language\|Go 언어]]) |
| Java 가상 스레드(21+) | 블로킹 I/O를 만나면 가상 스레드를 OS 스레드에서 내리고 다른 것을 올린다 |
| Erlang/BEAM | 코어마다 스케줄러를 두고 가벼운 프로세스를 선점식으로 돌린다 |

이 런타임들이 어떻게 스케줄링하는지는 [[concurrency-models|동시성·병렬·비동기·논블로킹과 동시성 모델]]에 있다.

## 비교

| 기준 | 사용자 수준 (N:1) | 커널 수준 (1:1) | 혼합형 (M:N) |
| --- | --- | --- | --- |
| 전환 비용 | 가장 싸다 | 시스템 콜 수준 | 대부분 사용자 공간 |
| 블로킹 시스템 콜 | 프로세스 전체가 멈춤 | 그 스레드만 멈춤 | 런타임이 처리하면 그 스레드만 |
| 멀티코어 활용 | 불가 | 가능 | 가능 |
| 구현 난이도 | 낮음 | 커널이 부담 | 가장 높음 |
| 대표 | 초기 그린 스레드 | Linux NPTL, Windows | Go, Java 가상 스레드 |

## 핵심 정리

- 스레드 모델은 사용자 스레드와 커널 스레드를 잇는 비율이다. N:1, 1:1, M:N.
- N:1은 빠르지만 블로킹 호출 하나에 전체가 멈추고 멀티코어를 못 쓴다.
- 1:1은 커널이 모든 스레드를 알아서 안정적이지만 생성·전환 비용이 있다. 현대 OS의 표준이다.
- M:N은 OS 수준에서는 복잡도 때문에 사라졌고, 블로킹 지점을 모두 아는 언어 런타임(Go, Java 가상 스레드)에서 쓰인다.
