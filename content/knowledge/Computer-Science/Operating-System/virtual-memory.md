가상 메모리는 물리 메모리 크기의 한계를 넘기 위한 기법이다. 예를 들어 100MB 메모리에서 200MB짜리 프로세스를 실행할 수 있게 해 준다. 프로세스의 주소 공간 전체를 올리지 않고 **당장 필요한 부분만** 메모리에 두고, 나머지는 디스크(backing store, swap area)에 둔다. 대부분의 시스템이 페이징을 쓰므로 여기서도 페이징을 전제로 정리한다. 페이징의 기본 구조는 [[memory-management|메모리 관리]]를, 같은 내용을 하드웨어(MMU·연관 메모리) 쪽에서 본 정리는 [[cache-and-virtual-memory|캐시와 가상 메모리]]를 참고한다.

## 요구 페이징 (Demand Paging)

프로그램이 실행될 때 모든 페이지를 올리는 대신, **페이지가 요청될 때(demand) 비로소 메모리에 올린다.** 프로그램에서 실제로 자주 쓰이는 부분은 매우 제한적이다. 좋은 소프트웨어일수록 예외 처리 같은 방어 코드가 많고, 이런 코드는 거의 실행되지 않는다.

효과:

- I/O 양 감소
- 물리 메모리 사용량 감소 — 멀티프로그래밍 환경에서 더 효과적
- 빠른 응답 시간 — 한정된 메모리에 정말 자주 쓰는 정보만 올릴 수 있다
- 더 많은 사용자(프로세스) 수용

### valid / invalid 비트

페이지 테이블의 각 엔트리에는 valid/invalid 비트가 있다.

- 처음에는 모든 엔트리가 **invalid**로 초기화된다(사용하지 않는 페이지도 엔트리는 만들어진다).
- invalid의 의미: ① 프로그램이 사용하지 않는 주소 영역이거나 ② 페이지가 물리 메모리에 없음(backing store에 있음)
- 페이지가 메모리에 올라오면 엔트리에 프레임 번호를 기록하고 valid로 바꾼다.
- 주소 변환 시 invalid 비트가 세트되어 있으면 **페이지 폴트(page fault)** 가 발생한다.

## 페이지 폴트 처리

invalid 페이지에 접근하면 주소 변환 하드웨어(MMU)가 **page fault trap**을 발생시키고, CPU 제어권이 운영체제로 넘어가 page fault handler가 실행된다.

1. 잘못된 요청(없는 주소, 접근 권한 위반)이면 프로세스를 강제 종료(abort)한다.
2. 정상 요청인데 빈 프레임이 없으면, 메모리에서 페이지 하나를 빼앗는다(**페이지 교체**).
3. 빈 프레임에 해당 페이지를 디스크에서 읽어 온다. 디스크 I/O는 매우 느리므로
   - 그동안 이 프로세스는 CPU를 반납하고 blocked 된다(다른 프로세스가 CPU 사용).
   - 읽기가 끝나면 페이지 테이블 엔트리에 프레임 번호를 기록하고 valid로 바꾼다.
   - 프로세스를 ready 큐에 넣는다.
4. 프로세스가 다시 CPU를 받으면, 중단되었던 명령어를 **처음부터 다시** 실행한다.

## 페이지 교체 (Page Replacement)

빈 프레임이 없을 때 어떤 페이지를 쫓아낼지(victim) 정한다. 곧바로 다시 쓰이지 않을 페이지를 내보내는 것이 좋다. 같은 페이지가 여러 번 쫓겨났다 들어올 수도 있다.

1. victim을 고른다. victim이 메모리에 올라온 뒤 **내용이 바뀌었다면** 디스크(backing store)에 기록한 뒤 내보내고, 바뀌지 않았다면 그냥 버린다.
2. 쫓겨난 페이지의 엔트리를 invalid로 바꾼다.
3. 새 페이지를 그 프레임에 올리고, 엔트리에 프레임 번호와 valid를 기록한다.

교체 알고리즘의 목표는 **페이지 폴트 비율 최소화**다. 시간 순서대로 참조된 페이지 번호를 나열한 **참조열(reference string)** 에 대해 페이지 폴트가 몇 번 나는지로 평가한다. 예: `1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5`

### OPT (Optimal, MIN)

**가장 먼 미래에 참조될 페이지**를 내보낸다.

- 페이지 폴트가 가장 적은 최적 알고리즘이다. 위 참조열을 프레임 4개로 실행하면 페이지 폴트 6번이며, 어떤 알고리즘도 이보다 적을 수 없다.
- 미래의 참조를 모두 안다고 가정하는 **오프라인 알고리즘**이라 실제로는 쓸 수 없다. 다른 알고리즘 성능의 **상한(upper bound)** 을 재는 기준으로 쓴다.

아래부터는 미래를 모르는 상태에서 쓰는 알고리즘이다.

### FIFO (First In First Out)

**가장 먼저 들어온** 페이지를 내보낸다.

- **FIFO Anomaly(Belady's Anomaly)**: 보통은 프레임을 늘리면 페이지 폴트가 줄지만, FIFO는 프레임을 늘렸는데 오히려 **페이지 폴트가 늘어날 수 있다.**

### LRU (Least Recently Used)

**가장 오래전에 참조된** 페이지를 내보낸다. 최근에 참조된 페이지일수록 가까운 미래에 다시 참조될 가능성이 높다는 성질을 이용하며, 가장 많이 쓰이는 알고리즘이다.

### LFU (Least Frequently Used)

**참조 횟수가 가장 적은** 페이지를 내보낸다. 최저 참조 횟수인 페이지가 여럿이면 구현에 따라 아무거나, 혹은 그중 가장 오래전에 참조된 것을 내보낸다.

### LRU와 LFU 비교

참조 기록이 `1 1 1 1 2 2 3 3 2 4` 순서이고 이제 5를 올려야 한다면:

- **LRU**는 마지막 참조가 가장 오래된 **1**을 내보낸다. 하지만 1은 네 번이나 참조된 인기 페이지였다 — LRU는 **마지막 참조 시점만** 보고 그 이전 기록은 무시한다.
- **LFU**는 한 번만 참조된 **4**를 내보낸다. 하지만 4는 방금 참조되기 시작해 앞으로 많이 쓰일 페이지일 수도 있다 — LFU는 **최근의 흐름**을 반영하지 못한다.

### LRU와 LFU의 구현

| 알고리즘 | 자료구조 | 시간 복잡도 |
| --- | --- | --- |
| LRU | 참조 시간 순으로 줄 세운 **이중 연결 리스트**. 참조된 페이지를 맨 아래로 옮기고, 맨 위를 내보낸다 | O(1) |
| LFU | 참조 횟수 기준 **힙(완전 이진 트리)**. 참조되면 자식과 비교하며 자리를 내려가고, 루트를 내보낸다 | O(log n) |

LFU를 리스트로 구현하면 참조될 때마다 자리를 찾느라 O(n)이 걸리므로 힙을 쓴다.

## 다양한 캐싱 환경

교체 알고리즘은 가상 메모리뿐 아니라 **캐싱 기법** 전반에 쓰인다. 캐싱은 한정된 빠른 공간(캐시)에 요청된 데이터를 저장해 두고, 다음 요청 때 느린 공간까지 가지 않고 캐시에서 바로 서비스하는 방식이다.

| 환경 | 빠른 공간 | 느린 공간 |
| --- | --- | --- |
| 페이징 시스템 | 물리 메모리 | 스왑 영역 |
| 캐시 메모리 | CPU와 메인 메모리 사이의 캐시 | 메인 메모리 |
| 버퍼 캐싱 | 메모리의 버퍼 캐시 | 디스크의 파일 시스템 |
| 웹 캐싱 | 로컬(브라우저·프록시) 캐시 | 멀리 떨어진 웹 서버 |

교체 알고리즘에 너무 많은 시간을 쓸 수는 없으므로, 버퍼 캐싱이나 웹 캐싱에서도 O(1)~O(log n) 정도까지만 허용된다.

### 페이징 시스템에서 LRU·LFU를 못 쓰는 이유

프로세스 A가 실행 중일 때 주소 변환은 하드웨어가 한다.

- 페이지가 이미 메모리에 있으면 하드웨어가 바로 변환하므로 **운영체제는 참조 사실을 모른다.**
- 페이지 폴트가 날 때만 운영체제가 개입하므로, 운영체제는 **페이지가 메모리에 올라온 시점**만 알 수 있다.

즉 페이징 시스템에서 OS가 가진 정보는 반쪽이라, 참조 시각·횟수가 필요한 LRU·LFU를 그대로 구현할 수 없다. 반면 버퍼 캐시·웹 캐시는 모든 요청이 시스템 콜·소프트웨어를 거치므로 LRU·LFU를 자유롭게 쓸 수 있다([[file-system-implementation|파일 시스템 구현]]).

## Clock 알고리즘

FIFO에 참조 비트를 더해 "오래 머물렀어도 최근에 한 번 쓰인 페이지는 한 번 더 기회를 주는" 알고리즘이라 **2차 기회(Second Chance) 페이지 교체**라고도 한다.

= Second Chance 알고리즘, NUR(Not Used Recently), NRU(Not Recently Used)

LRU를 근사한 알고리즘으로, **하드웨어의 도움**을 받아 실제 페이징 시스템에서 쓴다.

- 페이지들을 원형 연결 리스트로 둔다.
- 페이지가 참조되면 **하드웨어가 그 페이지의 reference bit를 1로** 세팅한다.
- 페이지 폴트가 나면 포인터가 시계 방향으로 돌며 reference bit를 확인한다.
  - 1이면 0으로 바꾸고 다음 페이지로 넘어간다(두 번째 기회).
  - 0이면 그 페이지를 내보낸다.
- 한 바퀴를 도는 동안 한 번도 참조되지 않은 페이지를 내보내는 셈이다. "가장 오래전에 참조된" 페이지가 아니라 "**오랫동안 참조되지 않은**" 페이지를 내보낸다.

### 개선: modified bit 함께 쓰기

| 비트 | 1의 의미 |
| --- | --- |
| reference bit | 최근에 참조된 페이지 |
| modified bit (dirty bit) | 메모리에 올라온 뒤 내용이 바뀐(write된) 페이지 |

modified bit가 0이면 backing store에 같은 내용이 있으므로 그냥 버리면 되지만, 1이면 쫓아내기 전에 디스크에 기록해야 해서 I/O가 생긴다. 그래서 가능하면 **modified bit가 0인 페이지를 우선** 내보낸다.

## 페이지 프레임 할당 (Allocation)

각 프로세스에 프레임을 몇 개씩 줄 것인가의 문제다.

- 명령어 하나를 실행하는 데도 명령어·데이터 등 여러 페이지를 동시에 참조하므로, 최소한 할당되어야 하는 프레임 수가 있다.
- 예를 들어 반복문을 구성하는 페이지들이 한꺼번에 올라와 있지 않으면 반복마다 페이지 폴트가 난다. 그렇다고 반복문에 페이지가 10000개 필요하다고 다 줄 수도 없다.

| 할당 방식 | 기준 |
| --- | --- |
| Equal allocation | 모든 프로세스에 똑같은 개수 |
| Proportional allocation | 프로세스 크기에 비례 |
| Priority allocation | 프로세스의 CPU 우선순위에 따라 다르게 |

### 전역 교체 vs 지역 교체

| 방식 | 설명 |
| --- | --- |
| Global replacement | 프로세스별로 미리 할당하지 않는다. 교체할 때 어느 프로세스의 페이지인지 따지지 않고 알고리즘(FIFO, LRU 등)대로 내보낸다. Working Set, PFF 알고리즘을 쓰면 할당량이 자동으로 조절된다 |
| Local replacement | 프로세스별로 프레임을 미리 할당하고, **자기에게 할당된 프레임 안에서만** 교체한다. 교체 알고리즘을 프로세스마다 운영한다 |

현대 시스템은 두 방식을 적절히 섞어 쓴다.

## 스래싱 (Thrashing)

메모리에 올라간 프로세스 수(멀티프로그래밍 정도, degree of multiprogramming)에 따른 CPU 이용률을 보면:

1. 처음에는 프로세스가 늘수록 CPU 이용률이 오른다. 한 프로세스가 I/O를 하러 가도 다른 프로세스가 CPU를 쓰기 때문이다.
2. 어느 지점을 넘으면 각 프로세스가 받는 프레임이 너무 적어져, 모든 프로세스에서 **페이지 폴트가 계속 발생**한다.
3. 모두 디스크 I/O를 기다리느라 CPU 이용률이 **급격히 떨어진다.**
4. 운영체제는 CPU가 놀고 있으니 프로세스를 더 올리고, 상황은 더 나빠진다. 프로세스들이 swap in/out만 반복하며 실제 일은 거의 못 한다.

이것이 스래싱이다. 해결하려면 **멀티프로그래밍 정도를 조절**해야 한다.

### Working-Set 알고리즘

- **참조 지역성(locality of reference)**: 프로세스는 특정 시간에는 특정 메모리 영역만 집중적으로 참조한다. 예: 한 함수가 실행 중이면 그 함수를 이루는 페이지만 집중 참조. 이렇게 집중 참조되는 페이지 집합을 locality set, Working-Set 모델에서는 **working set**이라고 한다.
- 프로세스의 working set 전체가 한꺼번에 메모리에 올라와 있어야 페이지 폴트가 줄어든다. 올라갈 수 없다면(예: 5개 필요한데 3개만 남음) 그 프로세스의 메모리를 **모두 반납하고 swap out** 한다.
- working set은 미리 알 수 없으므로 **과거 Δ시간(window) 동안 참조된 페이지들**을 working set으로 간주해 메모리에 유지하고, 나머지는 버린다.

예: window 크기가 10이면 최근 10번의 참조에서 중복을 뺀 페이지들, 예컨대 `{1, 2, 5, 6, 7}`이 working set이다. 5개 프레임을 줄 수 있으면 이들을 올리고, 줄 수 없으면 프로세스를 swap out 한다. working set은 시간에 따라 변한다(t1에는 `{1, 2, 5, 6, 7}`, t2에는 `{3, 4}`).

- 모든 프로세스의 working set 크기 합이 프레임 수보다 크면, 일부 프로세스를 swap out 해 남은 프로세스의 working set을 우선 보장한다.
- working set을 다 주고도 프레임이 남으면, swap out 되었던 프로세스에게 working set을 할당한다.

### PFF (Page-Fault Frequency)

현재 시점의 **페이지 폴트율을 직접 측정**해 프레임 수를 조절한다.

- 페이지 폴트율의 상한과 하한을 정한다.
- 상한을 넘으면 프레임을 더 할당하고, 하한보다 낮으면 할당 프레임을 줄인다.
- 빈 프레임이 없으면 일부 프로세스를 통째로 swap out 한다.

## 페이지 크기의 결정

페이지 크기를 **줄이면**:

- 같은 메모리에 페이지 수가 늘어 페이지 테이블 엔트리가 많아지고, 테이블에 쓰는 메모리가 커진다.
- 페이지 안에서 쓰이지 않는 부분이 줄어 **꼭 필요한 정보만** 올라가므로 메모리 이용은 효율적이다. 페이지가 크면 아주 작은 부분만 필요해도 큰 페이지를 통째로 올려야 한다.
- **디스크 전송 효율은 떨어진다.** 디스크는 헤드를 옮기는 탐색(seek) 시간이 대부분이라, 한 번 이동해서 많이 읽어 오는 편이 유리하다.

요즘 추세는 **페이지 크기를 키우는** 쪽이다. 기본 페이지는 여전히 4KB인 경우가 많지만, 메모리를 많이 쓰는 프로그램을 위해 x86-64의 2MB·1GB 같은 **huge page**를 함께 쓰면 TLB 하나로 더 넓은 영역을 커버할 수 있다.

## 핵심 정리

- 요구 페이징: 필요한 페이지만 올리고, invalid 페이지 접근 시 페이지 폴트 → OS가 디스크에서 읽어 옴.
- OPT는 최적이지만 오프라인, FIFO는 Belady's anomaly, LRU는 최근성, LFU는 빈도 기준.
- 페이징 시스템의 OS는 참조 정보를 반쪽만 알아서 LRU 대신 Clock 알고리즘(reference bit)을 쓴다.
- 스래싱은 프로세스가 너무 많아 프레임이 부족할 때 생기며, Working Set·PFF로 멀티프로그래밍 정도를 조절해 막는다.
