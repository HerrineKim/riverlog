여러 실행 주체가 같은 데이터를 동시에 읽고 쓰면, 실행 순서에 따라 결과가 달라지는 문제가 생긴다. 프로세스 동기화는 이런 **공유 데이터의 일관성**을 지키기 위해 협력하는 프로세스들의 실행 순서를 정해 주는 메커니즘이다.

## 데이터 접근의 기본 구조

컴퓨터의 모든 연산은 "저장된 곳에서 데이터를 읽어 → 연산하고 → 다시 저장"하는 흐름이다.

| 연산하는 곳 (Execution Box) | 데이터가 저장된 곳 (Storage Box) |
| --- | --- |
| CPU | 메모리 |
| 컴퓨터 내부 | 디스크 |
| 프로세스 | 그 프로세스의 주소 공간 |

하나의 Storage Box를 여러 Execution Box가 공유하면, 누가 언제 읽고 썼는지에 따라 결과가 달라질 수 있다.

## 경쟁 상태 (Race Condition)

여러 프로세스(또는 스레드)가 공유 데이터에 **동시에 접근**하고, 최종 결과가 **마지막으로 데이터를 다룬 쪽**에 따라 달라지는 상황이다.

예를 들어 `count++`는 한 줄이지만 실제로는 "메모리에서 읽기 → 레지스터에서 1 더하기 → 메모리에 쓰기" 세 단계다. 한쪽이 `count++`, 다른 쪽이 `count--`를 하는 도중에 끼어들면, 원래 값으로 돌아와야 할 `count`가 한쪽 결과만 반영된 값이 될 수 있다.

## 운영체제에서 경쟁 상태가 생기는 경우

사용자 프로세스는 각자 주소 공간이 분리되어 있지만, **커널의 데이터는 공유**되기 때문에 문제가 생긴다.

### 1. 커널 수행 중 인터럽트 발생

커널이 `count++`를 하던 중(값을 레지스터로 읽은 직후) 인터럽트가 들어와 인터럽트 핸들러가 `count--`를 수행하고 돌아오면, 커널은 이미 읽어 둔 옛 값에 1을 더해 저장하므로 `count--`가 사라진다.

- 해결: 중요한 공유 변수를 건드리는 동안에는 **인터럽트를 막아 두었다가** 끝난 뒤 처리한다. 다만 너무 오래·자주 막으면 시스템 응답성이 떨어진다.

### 2. 시스템 콜 수행 중 문맥 교환

프로세스 A가 시스템 콜로 커널 모드에서 커널 데이터를 수정하던 중 할당 시간이 끝나 B로 문맥 교환되고, B도 시스템 콜로 같은 데이터를 건드리면 A의 수정이 꼬인다.

- 해결: **커널 모드에서 실행 중일 때는 CPU를 선점하지 않고**, 사용자 모드로 돌아갈 때 선점한다.

### 3. 멀티프로세서에서 공유 메모리의 커널 데이터

CPU가 여러 개면 인터럽트를 막는 것으로는 해결되지 않는다. 다른 CPU가 동시에 같은 커널 데이터에 접근할 수 있기 때문이다.

- 해결: 커널 전체를 한 번에 하나의 CPU만 들어가게 하거나(비효율적), 공유 데이터마다 **lock**을 걸어 그 데이터에 접근할 수 있는 CPU를 매 순간 하나로 제한한다.

## 임계 구역 문제 (Critical-Section Problem)

**임계 구역(critical section)** 은 각 프로세스의 코드 중 공유 데이터에 접근하는 부분이다. 목표는 **한 프로세스가 임계 구역에 있을 때 다른 프로세스는 임계 구역에 들어갈 수 없게** 하는 것이다.

```text
do {
    entry section        // 들어가도 되는지 확인하고 잠금
    critical section     // 공유 데이터 접근
    exit section         // 잠금 해제
    remainder section
} while (1);
```

### 해결책이 만족해야 할 조건

| 조건 | 의미 |
| --- | --- |
| 상호 배제 (Mutual Exclusion) | 한 프로세스가 임계 구역에 있으면 다른 프로세스는 들어갈 수 없다 |
| 진행 (Progress) | 임계 구역에 아무도 없으면, 들어가려는 프로세스는 들어갈 수 있어야 한다 |
| 유한 대기 (Bounded Waiting) | 들어가려고 요청한 프로세스가 무한정 기다리지 않도록, 다른 프로세스가 먼저 들어가는 횟수에 한계가 있어야 한다 |

## 세마포어 (Semaphore)

세마포어 `S`는 정수 변수 하나와, 그것에 접근하는 두 가지 **원자적(atomic)** 연산으로 이루어진 추상 자료형이다. `S`의 값은 **사용 가능한 자원의 개수**를 뜻한다.

- **P(S)**: 자원을 획득한다. 자원이 없으면(`S <= 0`) 기다린다.
- **V(S)**: 자원을 반납한다.

```text
P(S):  while (S <= 0) ;   // 자원이 생길 때까지 대기
       S--;

V(S):  S++;
```

임계 구역에 적용하면 `S = 1`로 두고 `P(mutex); 임계 구역; V(mutex);` 형태로 쓴다.

### Busy-wait vs Block/Wakeup

위 구현은 기다리는 동안 계속 반복문을 돌며 CPU를 낭비한다(**busy-wait**, spin lock). 이를 피하려면 기다리는 프로세스를 재운다.

```text
typedef struct {
    int value;            // 세마포어 값
    struct process *L;    // 대기 중인 프로세스 리스트
} semaphore;

P(S):  S.value--;
       if (S.value < 0) {
           이 프로세스를 S.L에 넣고 block();
       }

V(S):  S.value++;
       if (S.value <= 0) {
           S.L에서 프로세스 P를 꺼내 wakeup(P);
       }
```

- P 연산에서 자원이 없으면 프로세스를 대기 리스트에 넣고 blocked 상태로 만든다.
- V 연산은 자원을 반납하면서, **잠든 프로세스가 있으면 깨워 준다.** 이것이 busy-wait 방식과의 차이다.
- `value`가 음수이면 그 절댓값이 기다리는 프로세스 수다.

일반적으로 block/wakeup이 효율적이지만, 임계 구역이 매우 짧으면 재우고 깨우는 오버헤드가 busy-wait보다 클 수도 있다.

### 세마포어의 두 종류

| 종류 | 값의 범위 | 용도 |
| --- | --- | --- |
| Counting semaphore | 0 이상의 임의의 정수 | 여러 개인 자원의 개수 관리 |
| Binary semaphore (mutex) | 0 또는 1 | 상호 배제(lock) |

### 교착 상태와 기아

세마포어를 잘못 쓰면 문제가 생긴다.

- **교착 상태**: 두 프로세스가 서로 상대가 가진 세마포어를 기다리며 영원히 멈춘다. 예: P0는 `P(S); P(Q);`, P1은 `P(Q); P(S);` 순서로 획득하려는 경우. 획득 순서를 통일하면 피할 수 있다. 자세한 내용은 [[deadlock|교착 상태]].
- **기아(starvation)**: 특정 프로세스가 대기 리스트에서 영원히 깨어나지 못한다.

## 고전적인 동기화 문제

| 문제 | 상황 |
| --- | --- |
| Bounded-Buffer (생산자-소비자) | 크기가 정해진 버퍼에 생산자는 데이터를 넣고 소비자는 꺼낸다. 버퍼가 가득 차거나 비었을 때의 대기, 버퍼 접근의 상호 배제가 필요하다 |
| Readers-Writers | 읽기는 여럿이 동시에 해도 되지만, 쓰기는 혼자 해야 한다 |
| Dining-Philosophers (식사하는 철학자) | 원탁의 철학자들이 양옆의 젓가락 두 개를 집어야 식사할 수 있다. 모두 왼쪽 젓가락을 동시에 집으면 교착 상태가 된다 |

## 모니터 (Monitor)

세마포어는 P·V 순서를 한 번만 잘못 써도 오류가 나고 찾기도 어렵다. **모니터**는 공유 데이터와 그 데이터에 접근하는 프로시저를 하나로 묶은 고수준 동기화 구조다. 모니터 안에서는 한 번에 하나의 프로세스만 활동하도록 언어 차원에서 보장하므로, 프로그래머가 직접 lock을 걸 필요가 없다. 특정 조건을 기다려야 할 때는 조건 변수(condition variable)의 `wait()`·`signal()`을 쓴다.

## 핵심 정리

- 경쟁 상태 = 공유 데이터에 동시 접근해 실행 순서에 따라 결과가 달라지는 것.
- OS에서는 인터럽트, 시스템 콜 중 선점, 멀티프로세서 때문에 커널 데이터에서 경쟁 상태가 생긴다.
- 임계 구역 해결 조건: 상호 배제, 진행, 유한 대기.
- 세마포어 P는 획득(없으면 대기), V는 반납(대기자가 있으면 깨움). Busy-wait 대신 block/wakeup으로 CPU 낭비를 줄인다.
