메모리는 주소로 접근하는 바이트들의 배열이다(C에서 주소를 직접 다루는 모습은 [[pointers-and-memory|포인터와 메모리]]). 여러 프로세스가 한정된 물리 메모리를 나눠 쓰려면, 프로세스가 보는 주소를 실제 메모리 위치로 바꿔 주고 서로의 영역을 보호해야 한다. 이 노트는 프로세스 전체 또는 일부를 **어떻게 메모리에 배치하는지**를 다룬다. 필요한 부분만 올리는 방법은 [[virtual-memory|가상 메모리]]에서 이어진다.

## 논리 주소와 물리 주소

| 주소 | 설명 |
| --- | --- |
| 논리 주소 (logical / virtual address) | 프로세스마다 독립적으로 갖는 주소 공간의 주소. 각 프로세스는 0번지부터 시작한다. **CPU가 보는 주소**는 논리 주소다 |
| 물리 주소 (physical address) | 실제 메모리에 올라간 위치 |

### 주소 바인딩 (Address Binding)

주소가 `심볼릭 주소(변수·함수 이름) → 논리 주소 → 물리 주소`로 결정되는 과정이다. 논리 주소가 물리 주소로 정해지는 시점에 따라 세 가지로 나뉜다.

| 시점 | 설명 |
| --- | --- |
| 컴파일 타임 바인딩 | 컴파일할 때 물리 주소가 정해진다. 컴파일러가 **절대 코드(absolute code)** 를 만들고, 시작 위치를 바꾸려면 다시 컴파일해야 한다 |
| 로드 타임 바인딩 | 프로그램을 메모리에 올릴 때 로더가 물리 주소를 정한다. 컴파일러가 **재배치 가능 코드(relocatable code)** 를 만들어야 한다 |
| 실행 타임 바인딩 | 실행 도중에도 프로세스의 위치를 옮길 수 있다. CPU가 주소를 참조할 때마다 변환 정보를 확인하므로 **하드웨어 지원**(base·limit 레지스터, MMU)이 필요하다 |

앞의 두 방식은 한 번 정해지면 바뀌지 않고, 현대 컴퓨터는 실행 타임 바인딩을 쓴다.

## MMU (Memory-Management Unit)

논리 주소를 물리 주소로 바꿔 주는 하드웨어 장치다. 가장 단순한 방식은 레지스터 두 개를 쓴다.

- **relocation(base) 레지스터**: 프로세스가 올라간 물리 메모리의 시작 주소
- **limit 레지스터**: 프로세스 주소 공간의 크기

```text
논리 주소 < limit ?
  ├─ 아니오 → trap(addressing error): 운영체제가 원인을 확인
  └─ 예     → 물리 주소 = 논리 주소 + relocation 레지스터
```

예: 논리 주소 공간이 0~3000인 프로세스가 물리 메모리 14000번지에 올라가 있다면, 논리 주소 346은 14346이 된다. 사용자 프로그램은 논리 주소만 다루고 실제 물리 주소는 볼 수도, 알 필요도 없다.

## 관련 기법

| 기법 | 설명 | 누가 구현하나 |
| --- | --- | --- |
| 동적 로딩 (Dynamic Loading) | 프로세스 전체를 미리 올리지 않고, 해당 루틴이 **호출될 때** 메모리에 올린다. 오류 처리 루틴처럼 가끔 쓰는 코드가 많을 때 메모리 이용률이 좋아진다 | 프로그램 자체(OS는 라이브러리로 지원 가능) |
| 오버레이 (Overlays) | 프로세스에서 실제 필요한 부분만 올린다. 프로세스가 메모리보다 클 때 쓰던 초창기 방식 | 프로그래머가 수작업(manual overlay), 매우 복잡 |
| 스와핑 (Swapping) | 프로세스를 통째로 메모리에서 **backing store(swap area)** 로 쫓아냈다가 나중에 다시 올린다 | 운영체제(중기 스케줄러) |
| 동적 링킹 (Dynamic Linking) | 라이브러리 연결(linking)을 실행 시간까지 미룬다 | 운영체제 지원 필요 |

### 스와핑

- backing store는 많은 프로세스 이미지를 담을 만큼 빠르고 큰 디스크 공간이다.
- 보통 중기 스케줄러(swapper)가 swap out 할 프로세스를 고른다. 우선순위 기반이라면 우선순위가 낮은 프로세스를 내보내고 높은 프로세스를 올린다.
- 컴파일·로드 타임 바인딩이면 **원래 위치로** swap in 해야 하지만, 실행 타임 바인딩이면 빈 곳 어디에나 올릴 수 있어 스와핑에 적합하다.
- 스왑 시간의 대부분은 데이터 양에 비례하는 **전송 시간(transfer time)** 이다.

### 정적 링킹과 동적 링킹

**링킹**은 따로 컴파일된 파일들을 묶어 하나의 실행 파일로 만드는 것이다.

| 구분 | 정적 링킹 (Static) | 동적 링킹 (Dynamic) |
| --- | --- | --- |
| 라이브러리 위치 | 실행 파일 안에 포함 | 실행 시 연결 |
| 실행 파일 크기 | 커짐 | 작음 |
| 메모리 | 같은 라이브러리(예: `printf`)를 프로세스마다 따로 올려 낭비 | 메모리에 하나만 올려 공유 |
| 동작 | — | 호출 위치에 라이브러리 루틴을 찾는 작은 코드(**stub**)를 두고, 이미 메모리에 있으면 그 주소로, 없으면 디스크에서 읽어 옴 |

동적 링킹에 쓰는 라이브러리를 공유 라이브러리라고 하며, 리눅스에서는 Shared Object(`.so`), 윈도우에서는 DLL(Dynamic Link Library)이다.

## 물리 메모리 할당

메모리는 보통 **낮은 주소의 OS 상주 영역**(인터럽트 벡터 포함)과 **높은 주소의 사용자 프로세스 영역**으로 나뉜다. 사용자 영역을 프로세스에 나눠 주는 방법은 두 가지다.

- **연속 할당(Contiguous)**: 각 프로세스를 메모리의 연속된 공간에 올린다. — 고정 분할, 가변 분할
- **불연속 할당(Noncontiguous)**: 한 프로세스를 여러 영역에 나눠 올린다. — 페이징, 세그멘테이션, 페이지드 세그멘테이션. **오늘날 쓰는 방식**

## 연속 할당

| 방식 | 설명 | 단편화 |
| --- | --- | --- |
| 고정 분할 (Fixed partition) | 물리 메모리를 미리 몇 개의 분할로 나누고(크기 동일 또는 다름) 분할마다 프로그램 하나를 적재. 동시에 올릴 수 있는 프로그램 수와 최대 크기가 고정되어 융통성이 없다 | 내부·외부 단편화 모두 발생 |
| 가변 분할 (Variable partition) | 미리 나누지 않고 프로그램 크기에 맞게 할당. 분할의 크기·개수가 동적으로 변한다 | 외부 단편화 발생 |

### 단편화

| 종류 | 상황 | 의미 |
| --- | --- | --- |
| 외부 단편화 (External) | 분할 크기 < 프로그램 크기 | 아무도 쓰지 않는 빈 공간인데 너무 작아서 프로그램이 들어갈 수 없는 조각 |
| 내부 단편화 (Internal) | 분할 크기 > 프로그램 크기 | 특정 프로그램에 배정되었지만 그 안에서 쓰이지 않는 공간 |

### Hole과 동적 메모리 할당 문제

**hole**은 가용 메모리 공간이다. 가변 분할에서는 다양한 크기의 hole이 여기저기 흩어지고, 운영체제는 할당 공간과 hole 정보를 유지한다. 크기 n인 요청을 어느 hole에 넣을지 정하는 방법은 다음과 같다.

| 방법 | 선택하는 hole | 특징 |
| --- | --- | --- |
| First-fit | 크기가 n 이상인 것 중 **처음 찾은** hole | 빠름 |
| Best-fit | 크기가 n 이상인 것 중 **가장 작은** hole | 정렬되어 있지 않으면 전체 탐색 필요, 아주 작은 hole이 많이 생김 |
| Worst-fit | **가장 큰** hole | 전체 탐색 필요, 상대적으로 큰 hole이 생김 |

실험적으로 **First-fit과 Best-fit이 Worst-fit보다** 속도와 공간 이용률 면에서 낫다.

### 컴팩션 (Compaction)

외부 단편화를 해결하는 한 가지 방법으로, 사용 중인 메모리를 한쪽으로 몰고 hole들을 다른 쪽으로 모아 큰 블록을 만든다.

- 모든 프로세스의 주소가 바뀌므로 **실행 타임 바인딩**이 지원될 때만 가능하다.
- 비용이 매우 크고, 최소한의 이동으로 컴팩션하는 것도 복잡한 문제다.

## 페이징 (Paging)

프로세스의 논리 주소 공간을 **같은 크기의 페이지(page)** 로 자르고, 물리 메모리도 같은 크기의 **프레임(page frame)** 으로 나눈 뒤 페이지를 아무 빈 프레임에나 올린다. 외부 단편화가 생기지 않는다(마지막 페이지에 약간의 내부 단편화는 생길 수 있다).

```text
논리 주소 = [ 페이지 번호 p | 오프셋 d ]
                  │ 페이지 테이블[p] = 프레임 번호 f
물리 주소 = [ 프레임 번호 f | 오프셋 d ]
```

- 프로세스마다 별도의 **페이지 테이블**이 있고, 엔트리 수는 논리 주소 공간의 페이지 수와 같다(배열의 인덱스 = 페이지 번호).
- 페이지 크기는 보통 **4KB**이고, 페이지 테이블은 메인 메모리에 있다.

### 페이지 테이블 구현과 TLB

- **PTBR(Page-Table Base Register)**: 페이지 테이블의 시작 위치
- **PTLR(Page-Table Length Register)**: 페이지 테이블의 크기
- 페이지 테이블이 메모리에 있으므로 모든 메모리 접근에 **두 번의 메모리 접근**(페이지 테이블 1번 + 실제 데이터 1번)이 필요하다.

이를 줄이려고 **TLB(Translation Look-aside Buffer)** 라는 고속의 주소 변환용 캐시(associative register)를 둔다.

- TLB에는 자주 참조되는 페이지 테이블 엔트리 **일부**만 들어 있고, 병렬 검색(parallel search)이 가능하다.
- 페이지 번호가 TLB에 있으면 바로 프레임 번호를 얻고, 없으면 메모리의 페이지 테이블에서 찾는다.
- 프로세스마다 주소 변환 정보가 다르므로, 기본적으로는 **문맥 교환 때 TLB를 비운다(flush).** 다만 현대 CPU는 TLB 엔트리에 주소 공간 식별자(ARM의 ASID, x86의 PCID)를 붙여 여러 프로세스의 엔트리를 함께 담아 둘 수 있어, 매번 전체를 비우지 않아도 된다.

TLB 접근 시간을 ε, 메모리 접근 시간을 1, TLB에서 찾을 확률(hit ratio)을 α라고 하면 실질 접근 시간(EAT)은 다음과 같다.

```text
EAT = (1 + ε)α + (2 + ε)(1 - α) = 2 + ε - α
```

α가 1에 가까울수록 페이지 테이블만 쓸 때(2)보다 훨씬 빠르다.

### 2단계 페이지 테이블

32비트 주소면 주소 공간이 2³² B = 4GB다. 페이지가 4KB면 페이지가 1M(2²⁰)개, 엔트리 하나가 4B면 페이지 테이블 하나에 **4MB**가 필요하다. 프로세스마다 이만큼을 연속으로 잡는 것은 낭비인데, 실제 프로그램은 주소 공간의 일부만 쓴다.

**2단계 페이지 테이블**은 페이지 테이블 자체를 페이지로 나누고, 바깥 페이지 테이블이 안쪽 페이지 테이블을 가리킨다. 사용하지 않는 주소 영역에 대한 바깥 테이블 엔트리는 NULL로 두어 안쪽 테이블을 만들지 않는다. 공간은 줄지만 주소 변환 시간은 늘어난다.

```text
32비트 논리 주소 = [ p1 (10비트) | p2 (10비트) | d (12비트) ]
```

- **d (12비트)**: 페이지 크기 4KB = 2¹²
- **p2 (10비트)**: 안쪽 페이지 테이블 하나도 페이지 크기(4KB)이고 엔트리가 4B이므로 엔트리 1K = 2¹⁰개
- **p1 (10비트)**: 나머지 32 - 12 - 10 = 10비트

단계가 늘수록 메모리 접근이 많아지지만, TLB 덕분에 다단계 페이지 테이블도 실제 오버헤드는 크지 않다. 64비트 시스템은 더 많은 단계를 쓴다. 예를 들어 x86-64는 가상 주소 48비트에 4단계 페이지 테이블을 쓰고, 이를 57비트·5단계로 늘린 방식도 지원한다.

### 페이지 테이블 엔트리의 비트

- **valid / invalid 비트**: valid는 해당 페이지가 실제 프레임에 올라가 있음, invalid는 프로그램이 쓰지 않는 주소이거나 현재 메모리에 없음(스왑 영역에 있음)을 뜻한다.
- **protection 비트**: 페이지에 대한 접근 권한(read / read-write / read-only 등)

### 역 페이지 테이블 (Inverted Page Table)

프로세스마다 페이지 테이블을 두는 대신, **물리 프레임마다 엔트리를 하나씩** 두는 시스템 전체 테이블이다. 엔트리에는 `(프로세스 ID, 페이지 번호)`를 저장한다.

- 테이블 공간을 크게 줄일 수 있다.
- 대신 주소 변환 시 테이블 전체를 검색해야 하므로 시간 오버헤드가 크다. 그래서 associative register에 넣어 병렬 검색한다.

### 공유 페이지 (Shared Pages)

여러 프로세스가 같은 코드(예: 에디터, 컴파일러)를 쓰면 코드를 한 번만 올리고 각자의 페이지 테이블이 같은 프레임을 가리키게 할 수 있다.

- 공유 코드는 **재진입 가능 코드(re-entrant code, pure code)** 여야 하고 **read-only**로 설정한다.
- 모든 프로세스의 논리 주소 공간에서 **같은 위치**에 있어야 한다.
- 통신을 위해 데이터를 공유하는 shared memory IPC와는 목적이 다르다.

## 세그멘테이션 (Segmentation)

프로세스의 주소 공간을 **의미 단위(segment)** 로 나눈다. 작게는 함수 하나, 크게는 프로그램 전체가 하나의 세그먼트가 될 수 있고, 보통 code·data·stack을 각각 하나의 세그먼트로 둔다. 예: `main()`, 함수, 전역 변수, 스택, 심볼 테이블, 배열. 의미 단위이므로 세그먼트 크기는 제각각이다.

```text
논리 주소 = [ 세그먼트 번호 s | 오프셋 d ]
세그먼트 테이블[s] = (base: 시작 물리 주소, limit: 세그먼트 길이)
```

- **STBR(Segment-Table Base Register)**: 물리 메모리에서 세그먼트 테이블의 위치
- **STLR(Segment-Table Length Register)**: 프로그램이 쓰는 세그먼트 수
- `s < STLR`이고 `d < limit`이어야 유효하며, 아니면 trap이 발생한다. 통과하면 물리 주소 = base + d.

| 항목 | 내용 |
| --- | --- |
| 보호 | 세그먼트마다 protection 비트(valid 비트, read/write/execute 권한)를 둔다 |
| 공유 | 공유 세그먼트는 프로세스들이 **같은 세그먼트 번호**로 접근해야 한다 |
| 할당 | 크기가 제각각이라 가변 분할과 같은 문제(first-fit/best-fit, 외부 단편화)가 생긴다 |

- **장점**: 의미 단위라서 공유와 보안 처리가 페이징보다 훨씬 자연스럽다. 세그먼트 수가 적어 테이블 낭비도 적다.
- **단점**: 외부 단편화 등 가변 분할의 문제를 그대로 가진다.

## 페이지드 세그멘테이션 (Paged Segmentation)

세그멘테이션과 페이징을 합친 방식이다. 세그먼트 하나를 여러 페이지로 구성한다.

- 세그먼트 테이블 엔트리가 세그먼트의 시작 주소 대신 **그 세그먼트의 페이지 테이블 시작 주소**를 가진다. 즉 세그먼트마다 페이지 테이블이 있다.
- 메모리에는 페이지 단위로 올라가므로 **할당(외부 단편화) 문제가 사라진다.**
- 공유·보안처럼 의미 단위로 해야 하는 일은 세그먼트 테이블에서 처리한다.

주소 변환은 모두 하드웨어(MMU)가 하며, 이 과정에 운영체제는 관여하지 않는다. 운영체제는 페이지 폴트처럼 메모리에 없는 페이지를 참조할 때 개입한다([[virtual-memory|가상 메모리]]). 하드웨어 관점의 정리는 [[cache-and-virtual-memory|캐시와 가상 메모리]]에도 있다.

## 핵심 정리

- CPU는 논리 주소를 보고, MMU가 실행 시간에 물리 주소로 바꾼다(base + offset, limit으로 보호).
- 연속 할당은 단편화가 문제다. 외부 단편화는 컴팩션으로 해결할 수 있지만 비싸다.
- 페이징은 같은 크기로 잘라 외부 단편화를 없애고, TLB로 주소 변환을 빠르게, 다단계 테이블로 테이블 공간을 줄인다.
- 세그멘테이션은 의미 단위라 공유·보호에 유리하지만 외부 단편화가 생기고, 페이지드 세그멘테이션이 둘의 장점을 합친다.
