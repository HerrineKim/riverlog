여러 프로세스가 하나의 CPU를 나눠 쓰려면 "지금 누구에게 CPU를 줄 것인가"를 정하는 규칙이 필요하다. 이것이 CPU 스케줄링이며, 프로세스의 상태 변화를 이해해야 스케줄링이 언제 일어나는지도 이해할 수 있다. 프로세스의 구조와 PCB, 스레드는 [[process-and-thread|프로세스와 스레드]]에 따로 정리했다.

## 프로세스 상태

| 상태 | 의미 |
| --- | --- |
| 생성(new) | 프로세스가 만들어지는 중 |
| 준비(ready) | CPU 할당을 기다림 |
| 실행(running) | CPU를 차지하고 실행 중 |
| 대기(blocked, waiting) | I/O 등 이벤트를 기다림 |
| 보류(suspended) | 일시 중지되어 디스크로 내려간 상태 |
| 완료(terminated) | 실행을 마치고 PCB까지 제거됨 |

### 상태 전이

생성 → 준비 → 실행 → 완료를 기본 흐름으로, 실행 중에는 다음 전이가 일어난다.

- **Dispatch**: 준비 → 실행 (스케줄러가 CPU 할당)
- **Timeout**: 실행 → 준비 (할당 시간 만료)
- **Block / I/O**: 실행 → 대기
- **Wake up**: 대기 → 준비 (I/O 완료)

> 교착 상태(deadlock)는 별도의 상태라기보다, 프로세스들이 서로가 가진 자원을 기다리며 영원히 대기하는 상황이다. 자세한 내용은 [[deadlock|교착 상태]] 참고.

## 왜 CPU 스케줄링이 필요한가

모든 프로그램은 실행되는 동안 **CPU burst**(CPU로 명령을 실행하는 구간)와 **I/O burst**(I/O를 요청하고 기다리는 구간)를 번갈아 반복한다. 그 비율은 프로그램마다 다르다.

| 유형 | 특징 | 예 |
| --- | --- | --- |
| I/O-bound 프로세스 | 짧은 CPU burst가 자주 나타남. 계산보다 I/O에 시간을 많이 씀 | 사용자와 상호작용이 많은 프로그램 |
| CPU-bound 프로세스 | 긴 CPU burst가 드물게 나타남. 계산 위주 | 과학 계산 |

이런 작업들이 섞여 있으므로, 대화형(I/O-bound) 작업에 빠르게 응답하면서도 CPU를 놀리지 않도록 **공평하면서 효율적으로** CPU를 나눠 주는 규칙이 필요하다.

### CPU 스케줄러와 디스패처

- **CPU 스케줄러**: ready 상태의 프로세스 중 CPU를 줄 프로세스를 **고르는** 운영체제 코드
- **디스패처**: 고른 프로세스에게 CPU 제어권을 **넘기는** 운영체제 코드. 이 과정이 문맥 교환이다.

CPU 스케줄링이 필요해지는 경우:

| 상황 | 방식 |
| --- | --- |
| running → blocked (I/O 요청 등) | 비선점 (스스로 반납) |
| 프로세스 종료 | 비선점 |
| running → ready (타이머 인터럽트로 할당 시간 만료) | 선점 (강제로 빼앗음) |
| blocked → ready (I/O 완료 후 더 높은 우선순위 등장) | 선점 |

## 스케줄링의 종류

- **장기 스케줄링**: 어떤 작업을 메모리에 올려 준비 큐에 넣을지
- **중기 스케줄링**: 메모리가 부족할 때 어떤 프로세스를 디스크로 내릴지(swap)
- **단기 스케줄링**: 준비 큐의 어떤 프로세스에 CPU를 줄지 — 보통 "CPU 스케줄링"이라 하면 이것

## 성능 척도

| 관점 | 척도 | 의미 |
| --- | --- | --- |
| 시스템 | CPU 이용률(utilization) | 전체 시간 중 CPU가 일한 시간의 비율 |
| 시스템 | 처리량(throughput) | 주어진 시간 동안 완료한 작업 수 |
| 프로세스 | 소요 시간(turnaround time) | ready 큐에 들어와서 CPU burst를 마치고 나갈 때까지 걸린 총 시간 |
| 프로세스 | 대기 시간(waiting time) | ready 큐에서 기다린 시간의 합. 선점형이면 여러 번 기다린 시간을 모두 더함 |
| 프로세스 | 응답 시간(response time) | ready 큐에 들어와 **처음으로** CPU를 얻기까지의 시간 |

여기서 시간은 프로그램 전체의 시작~종료가 아니라 **CPU burst 하나** 단위로 잰다.

## 비선점 스케줄링 (Non-preemptive)

한 번 CPU를 받은 프로세스는 스스로 반납할 때까지 계속 사용한다. 응답 시간 예측이 쉽고 일괄 처리에 적합하지만, 덜 중요한 작업 때문에 중요한 작업이 기다릴 수 있다.

| 알고리즘 | 규칙 | 특징 |
| --- | --- | --- |
| FCFS (FIFO) | 도착 순서대로 | 단순·공평하지만 긴 작업 뒤의 짧은 작업이 오래 기다림 |
| SJF | 실행 시간이 가장 짧은 작업부터 | 평균 대기 시간 최소, 긴 작업은 기아(starvation) 위험 |
| HRN | 응답 비율이 높은 작업부터 | SJF의 긴 작업 불리함을 보완 |

HRN의 우선순위 계산식:

```text
우선순위 = (대기 시간 + 서비스 시간) / 서비스 시간
```

오래 기다릴수록 값이 커져 결국 순서가 돌아온다.

### FCFS와 호위 효과

FCFS는 **어떤 프로세스가 먼저 도착하느냐**에 따라 평균 대기 시간이 크게 달라진다. CPU를 오래 쓰는 프로세스가 먼저 도착하면 뒤의 짧은 프로세스들이 모두 오래 기다리는데, 이를 **호위 효과(Convoy effect)** 라고 한다.

### SJF의 두 가지 방식과 한계

- **비선점형 SJF**: 일단 CPU를 주면 더 짧은 프로세스가 도착해도 빼앗지 않는다.
- **선점형 SJF = SRTF(Shortest-Remaining-Time-First)**: 새 프로세스의 CPU burst가 현재 프로세스의 **남은** burst보다 짧으면 CPU를 빼앗는다. 주어진 프로세스들에 대해 **평균 대기 시간이 최소**임이 보장된다.

SJF의 한계:

1. **기아(starvation)**: 짧은 작업만 계속 선호하므로 긴 작업은 영원히 CPU를 못 받을 수 있다.
2. **CPU 사용 시간을 미리 알 수 없다**: 입력이나 분기에 따라 burst 길이가 달라진다. 과거 burst 기록을 지수 평균(exponential averaging)해 다음 burst를 **추정**할 뿐이다.

### 우선순위 스케줄링

우선순위가 가장 높은 프로세스에게 먼저 CPU를 준다. 선점형·비선점형 모두 가능하며, SJF도 "CPU burst가 짧을수록 우선순위가 높은" 우선순위 스케줄링의 일종이다. 마찬가지로 기아 문제가 생길 수 있는데, 오래 기다린 프로세스의 우선순위를 점점 높여 주는 **에이징(aging)** 으로 해결한다.

## 선점 스케줄링 (Preemptive)

우선순위가 더 높은 프로세스가 실행 중인 프로세스의 CPU를 빼앗을 수 있다. 빠른 응답이 필요한 대화형·시분할 시스템에 쓰이며, 타이머 인터럽트가 필요하고 문맥 교환 오버헤드가 크다.

| 알고리즘 | 규칙 |
| --- | --- |
| RR (Round Robin) | FCFS + 시간 할당량(time quantum). 시간이 다 되면 큐의 맨 뒤로 |
| SRT | SJF의 선점형. 남은 실행 시간이 가장 짧은 프로세스 우선 |
| MLQ (다단계 큐) | 프로세스 그룹별로 별도의 준비 큐 사용 |
| MLFQ (다단계 피드백 큐) | 다단계 큐 + 큐 간 이동 허용(오래 쓰면 낮은 큐로) |

### Round Robin

현대 시스템이 쓰는 스케줄링의 기반이다.

- 각 프로세스는 같은 크기의 할당 시간(time quantum, 보통 10~100ms)을 받고, 다 쓰면 타이머 인터럽트로 CPU를 빼앗겨 ready 큐 맨 뒤로 간다.
- ready 큐에 n개의 프로세스가 있고 할당 시간이 q라면, 어떤 프로세스도 **(n-1)q 이상 기다리지 않는다.** 그래서 응답 시간이 빠르다.
- 대기 시간이 프로세스가 쓰려는 CPU 시간에 비례한다 — 짧은 작업은 빨리 끝나고 긴 작업은 오래 기다린다.
- q가 너무 크면 FCFS와 같아지고, 너무 작으면 문맥 교환이 잦아져 오버헤드가 커진다.
- 일반적으로 SJF보다 평균 소요·대기 시간은 길지만 **응답 시간은 짧다.** CPU 사용 시간이 짧은 작업과 긴 작업이 섞여 있을 때 효과적이다.

### 다단계 큐 (Multilevel Queue)

ready 큐를 여러 줄로 나누고, 프로세스 종류에 따라 줄을 고정한다.

| 큐 | 대상 | 큐 안의 알고리즘 |
| --- | --- | --- |
| foreground | 대화형(interactive) 작업 — 응답이 빨라야 함 | RR |
| background | 일괄 처리(batch) 작업 — 사람과 상호작용 없음 | FCFS |

큐끼리도 스케줄링이 필요하다.

- **고정 우선순위**: foreground를 모두 처리한 뒤 background 처리. 낮은 큐는 기아가 생길 수 있다.
- **타임 슬라이스**: 큐마다 CPU 시간을 나눠 줌. 예: foreground 80%(RR), background 20%(FCFS)

### 다단계 피드백 큐 (Multilevel Feedback Queue)

다단계 큐의 "한 번 정해지면 못 바꾸는" 차별을 없애, **프로세스가 큐 사이를 이동**할 수 있게 한다. 정의할 파라미터는 큐의 개수, 큐별 알고리즘, 승격·강등 기준, 처음 들어갈 큐다.

보편적인 구성:

1. 새 프로세스는 우선순위가 가장 높은 큐에 들어간다.
2. 위쪽 큐일수록 RR 할당 시간이 짧고, 아래로 갈수록 길어진다. 마지막 큐는 FCFS.
3. 할당 시간을 다 쓰고도 끝나지 않으면 한 단계 아래 큐로 강등된다.

결과적으로 CPU burst가 짧은 작업은 빨리 끝나고, 긴 작업은 점점 아래로 내려간다. 실행 시간을 미리 몰라도 SJF와 비슷한 효과를 낸다.

## 특수한 환경의 스케줄링

### 다중 프로세서 스케줄링

- **동종(homogeneous) 프로세서**: 큐 하나에 줄 세우고 각 프로세서가 알아서 꺼내 가게 할 수 있다. 단, 특정 CPU에서만 실행되어야 하는 작업이 있으면 문제가 복잡해진다.
- **부하 분산(load sharing)**: 일부 프로세서에 작업이 몰리지 않도록 공유 큐나 프로세서별 큐를 조정하는 메커니즘이 필요하다.
- **대칭형 다중 처리(SMP)**: 모든 프로세서가 대등하며, 각자 스스로 스케줄링한다.
- **비대칭형 다중 처리**: 한 프로세서가 데이터 접근·공유 등 전체를 제어하고 나머지가 따른다.

### 실시간 스케줄링

정해진 시간(deadline) 안에 반드시 끝나야 하는 작업을 다룬다.

- **Hard real-time**: deadline을 반드시 지켜야 한다. 그때그때 정하기보다 미리 스케줄을 짜서 마감을 보장한다.
- **Soft real-time**: deadline을 어겨도 치명적이지는 않다. 일반 프로세스보다 우선순위를 높여 CPU를 먼저 받게 한다.

### 스레드 스케줄링

- **Local scheduling**: 사용자 수준 스레드는 커널이 존재를 모르므로, 사용자 프로세스(스레드 라이브러리)가 어느 스레드를 실행할지 정한다.
- **Global scheduling**: 커널 수준 스레드는 커널이 일반 프로세스처럼 직접 스케줄링한다.

## 알고리즘 평가 방법

| 방법 | 설명 |
| --- | --- |
| 큐잉 모델 | 도착률(arrival rate)과 처리율(service rate)을 확률 분포로 주고 성능 척도를 계산하는 이론적 방법 |
| 구현·측정 | 실제 시스템에 구현해 실행하고 성능을 잰다 |
| 시뮬레이션 | 알고리즘을 모의 프로그램으로 작성하고 trace(입력 데이터)를 넣어 결과를 비교한다. 구현·측정이 어려울 때 사용 |

## 문맥 교환 (Context Switching)

CPU를 한 프로세스에서 다른 프로세스로 넘길 때, 현재 프로세스의 레지스터·PC 등 상태를 PCB에 저장하고 다음 프로세스의 상태를 복원하는 과정이다. 이 시간 동안은 실제 일을 하지 않으므로 OS 오버헤드의 주요 원인이 된다.

## 프로세스 간 통신 (IPC)

프로세스는 서로의 메모리에 직접 접근할 수 없으므로, 데이터를 주고받으려면 OS가 제공하는 통신 수단을 써야 한다.

| 방법 | 설명 |
| --- | --- |
| Shared Memory | 여러 프로세스가 함께 접근하는 메모리 영역을 만들어 통신 |
| Socket | 네트워크 소켓으로 통신 (다른 컴퓨터의 프로세스와도 가능) |
| Semaphore | 공유 자원 접근을 제어해 동기화 |
| Pipe / Named Pipe | FIFO 형태의 버퍼를 공유해 한 방향으로 데이터 전달 |
| Message Queue | 메시지 단위로 큐에 넣고 꺼내 전달 |

## 핵심 정리

- 준비 ↔ 실행 ↔ 대기 사이의 전이(dispatch, timeout, block, wake up)를 기억한다.
- 비선점: FCFS, SJF, HRN / 선점: RR, SRT, MLQ, MLFQ.
- SJF(SRTF)는 평균 대기 시간 최소지만 기아와 burst 예측 문제가 있고, 에이징으로 기아를 완화한다.
- RR은 응답 시간이 짧고 (n-1)q 이상 기다리지 않는다. MLFQ는 실행 시간을 몰라도 짧은 작업을 우대한다.
- 문맥 교환은 피할 수 없는 오버헤드이므로, 스케줄링 정책은 응답성과 오버헤드 사이의 균형이다.
