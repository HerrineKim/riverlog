## 레거시 인프라에서 클라우드로

예전 방식(온프레미스, 레거시 인프라)은 서버를 사서 데이터센터에 들이는 데서 시작한다. 견적, 구매 품의, 입고, 설치, 네트워크 연결까지 몇 주에서 몇 달이 걸린다. 그래서 몇 년 뒤의 최대 수요를 예상해 미리 크게 산다. 예상보다 덜 쓰면 장비가 놀고, 더 몰리면 그때부터 사도 늦는다.

클라우드는 그 자원을 빌려 쓰고 쓴 만큼 낸다. 큰 차이는 두 가지다.

| | 레거시 | 클라우드 |
| --- | --- | --- |
| 돈 | 장비 구매(자본 지출, CAPEX). 감가상각 | 사용료(운영 지출, OPEX). 매달 청구서 |
| 시간 | 주·월 단위로 조달 | 분 단위로 만들고 지운다 |
| 용량 | 최대치에 맞춰 미리 확보 | 필요할 때 늘리고 줄인다 |
| 조작 | 사람이 장비를 만진다 | API로 만든다. 코드로 관리할 수 있다 |

이 변화의 바탕은 **가상화**다. 물리 장비를 소프트웨어로 쪼개고 묶을 수 있게 되면서 자원을 잘게 나눠 팔 수 있게 됐다. 다만 가상화는 기술이고 클라우드는 그 기술로 만든 운영 방식이다. 가상화만 했다고 클라우드가 되지는 않는다.

## 클라우드의 다섯 가지 특징

미국 국립표준기술연구소(NIST)의 정의가 가장 널리 인용된다.

| 특징 | 뜻 | 없으면 |
| --- | --- | --- |
| 주문형 셀프서비스 | 사람에게 요청하지 않고 콘솔·API로 직접 자원을 만든다 | 티켓 넣고 담당자를 기다리는 사내 가상화 |
| 광범위한 네트워크 접근 | 표준 프로토콜로 어디서나 접근한다 | |
| 자원 풀링 | 여러 고객이 물리 자원을 나눠 쓴다(멀티테넌시). 고객은 정확한 위치를 모른다 | 고객마다 전용 장비 |
| 빠른 탄력성 | 수요에 맞춰 금방 늘고 준다. 사용자 눈에는 무한해 보인다 | |
| 측정되는 서비스 | 사용량을 재고 그만큼 과금한다 | 정액 임대 |

배포 모델은 자원을 누가 쓰느냐로 나눈다.

| 모델 | 뜻 |
| --- | --- |
| 퍼블릭 | 여러 고객이 사업자의 자원을 공유한다. AWS, Azure, GCP, 네이버 클라우드 등 |
| 프라이빗 | 한 조직만 쓰는 클라우드. 자체 데이터센터에 OpenStack 같은 것으로 짓거나, 사업자 안에 전용 구역을 받는다 |
| 하이브리드 | 온프레미스·프라이빗과 퍼블릭을 연결해 함께 쓴다. 민감한 데이터는 안에, 변동 큰 부하는 밖에 |
| 커뮤니티 | 같은 요구(규제, 보안 등급)를 가진 조직들이 공유한다. 공공·금융 전용 클라우드 |
| 멀티 클라우드 | 퍼블릭 사업자 여럿을 함께 쓴다 |

## 세 가지 서비스 모델

클라우드는 **제공자가 어디까지 관리해 주느냐**로 나뉜다.

```text
                온프레미스   IaaS       PaaS       SaaS
애플리케이션      사용자     사용자     사용자     제공자
데이터            사용자     사용자     사용자     (사용자)*
런타임·미들웨어    사용자     사용자     제공자     제공자
운영체제          사용자     사용자     제공자     제공자
가상화            사용자     제공자     제공자     제공자
서버·스토리지·네트워크 사용자  제공자     제공자     제공자
```

\* SaaS에서도 데이터의 소유와 그 데이터에 누가 접근하는지에 대한 책임은 사용자에게 남는다. 보안 책임을 어떻게 나누는지는 [[cloud-governance-security|클라우드 거버넌스와 보안]]에 있다.

| 모델 | 빌리는 것 | 사용자가 하는 일 | 예 |
| --- | --- | --- | --- |
| IaaS (Infrastructure) | 가상 서버, 스토리지, 네트워크 | OS 설치·패치, 미들웨어, 앱, 확장 설정 | EC2, Compute Engine, Azure VM |
| PaaS (Platform) | 앱을 올릴 실행 환경, 관리형 DB | 코드와 설정, 데이터 | Elastic Beanstalk, Heroku, App Service, RDS 같은 관리형 DB |
| SaaS (Software) | 완성된 소프트웨어 | 계정과 데이터 관리, 설정 | Google Workspace, Slack, Notion, Salesforce |

아래로 갈수록(IaaS → SaaS) 운영 부담이 줄고 시작이 빠르지만, 바꿀 수 있는 것도 줄고 그 서비스에 묶인다(종속, lock-in). 서버리스와 컨테이너 서버리스는 PaaS와 SaaS 사이 어딘가에 있다([[serverless-architecture|서버리스 아키텍처]]). 이 밖에도 DaaS(가상 데스크톱), BPaaS(업무 프로세스 아웃소싱)처럼 "무엇이든 서비스로(XaaS)" 이름이 붙는다.

### 어떤 경우에 맞나

| 모델 | 맞는 경우 |
| --- | --- |
| IaaS | 하드웨어 살 돈과 시간이 아까운 스타트업·중소기업, 요구가 빨리 바뀌어 특정 장비에 묶이기 싫을 때, OS나 미들웨어를 직접 통제해야 할 때, 기존 시스템을 거의 그대로 옮길 때(리프트 앤 시프트) |
| PaaS | 인프라보다 개발에 집중하고 싶을 때, 여러 개발자·업체가 같은 환경에서 빠르게 만들고 배포해야 할 때 |
| SaaS | 대부분의 업무 도구. 협업이 필요한 짧은 프로젝트, 모바일 접근이 필요할 때. 다만 민감 정보를 다루면 데이터 위치와 보안 수준을 먼저 확인한다 |

실무에서는 섞어 쓴다. 앱은 컨테이너(IaaS나 관리형 쿠버네티스)에, DB는 관리형(PaaS)에, 메일과 문서는 SaaS로.

## IaaS를 받치는 기술

### 서버 가상화

물리 서버 하나를 여러 대처럼 나눠, 각자 OS와 앱을 돌린다. 놀던 서버 자원을 모아 쓰고, 여러 OS 버전이 필요한 테스트 환경을 쉽게 만든다.

| 방식 | 구조 | 특징 | 예 |
| --- | --- | --- | --- |
| 하이퍼바이저형(1형, 네이티브) | 하드웨어 위에 바로 하이퍼바이저 | 호스트 OS가 없어 오버헤드가 적다. 클라우드 데이터센터의 기본 | Xen, KVM, Hyper-V, ESXi |
| 호스트형(2형) | 호스트 OS 위의 프로그램으로 | 설치가 쉽고 노트북에서도 돈다. 한 단계 더 거쳐 느리다 | VirtualBox, VMware Workstation |
| 컨테이너형 | 호스트 OS 커널을 공유하고 프로세스만 격리 | 게스트 OS가 없어 가볍고 빨리 뜬다. 이미지로 어디서나 같게 실행된다 | Docker |

하이퍼바이저가 특권 명령을 어떻게 처리하는지(전가상화·반가상화)는 [[virtualization|가상화]], VM과 컨테이너의 비교는 [[vm-vs-container|VM과 컨테이너]]에 있다.

### 네트워크 가상화

| 기술 | 하는 일 |
| --- | --- |
| VLAN | 물리 스위치 하나를 여러 논리 네트워크로 나눈다. 배선을 바꾸지 않고 망을 분리한다 |
| VPN | 인터넷 같은 공용망 위에 암호화된 전용선처럼 쓰는 사설 통로를 만든다 |
| SDN (Software Defined Networking) | 패킷을 전달하는 기능(데이터 평면)과 경로를 정하는 기능(제어 평면)을 떼어, 중앙 컨트롤러가 소프트웨어로 네트워크 전체를 설정한다 |
| NFV (Network Functions Virtualization) | 방화벽·로드 밸런서·라우터 같은 전용 장비 기능을 일반 서버 위의 소프트웨어로 돌린다 |

클라우드에서 콘솔 클릭 몇 번으로 VPC, 서브넷, 보안 그룹, 로드 밸런서가 생기는 건 SDN과 NFV 덕분이다. AWS에서 이것들이 어떻게 보이는지는 [[aws-vpc-networking|AWS VPC 네트워크 구성]]에 있다.

### 스토리지

블록(디스크처럼, DB용), 파일(폴더 계층으로, 공유 파일용), 오브젝트(키로 접근, HTTP API, 백업·미디어·아카이브용)의 세 가지를 용도에 따라 고른다. 자세한 비교는 [[block-file-object-storage|블록·파일·오브젝트 스토리지]]에 있다.

## PaaS를 받치는 기술

### 관리형 데이터베이스

PaaS의 대표 상품이다. 설치, 패치, 백업, 복제, 장애 조치를 사업자가 맡는다. 관계형(RDB)과 NoSQL(키-값, 문서, 와이드 컬럼, 그래프)을 용도에 맞게 고른다. NoSQL은 데이터를 여러 노드에 나눠 처리하도록 설계된 경우가 많아 클라우드의 수평 확장과 잘 맞는다([[database-selection|용도별 데이터베이스와 고르는 법]]).

### 분산 처리

예전에는 큰 데이터를 처리하려면 비싼 고성능 서버 한 대가 필요했다. 지금은 평범한 서버 여러 대를 묶어(클러스터링) 일을 나눠 처리하고, 몇 대가 고장 나도 다른 서버가 이어받는다.

| | Hadoop (MapReduce) | Spark |
| --- | --- | --- |
| 중간 결과 | 단계마다 디스크에 쓰고 읽는다 | 가능하면 메모리에 둔다 |
| 속도 | 상대적으로 느리다 | 반복 연산에서 훨씬 빠르다 |
| 맞는 일 | 한 번 훑는 대용량 일괄 처리 | 같은 데이터를 여러 번 도는 기계 학습, 대화형 분석 |

Hadoop은 마스터가 작업을 나누고 워커들이 계산하는 구조라, 워커를 늘리면 처리량이 거의 비례해 늘어난다. 클라우드는 이런 클러스터를 필요할 때만 띄웠다가 끌 수 있어서 잘 맞는다(EMR, Dataproc 등).

## SaaS를 받치는 기술

SaaS는 웹 브라우저로 바로 쓰고 설치가 없다. 사업자는 한 소프트웨어를 여러 고객이 함께 쓰게 하면서(멀티테넌시) 데이터는 섞이지 않게 분리해야 한다.

SaaS와 클라우드 전반을 묶는 기술이 **API**다. 자원을 API로 만들 수 있다는 것은 사람 손 대신 프로그램이 인프라를 조작할 수 있다는 뜻이고, 이것이 자동화와 코드형 인프라의 출발점이다([[cloud-native|클라우드 네이티브와 코드형 인프라]]). 이 맥락에서 자주 섞이는 세 용어는 이렇게 구분한다.

| 용어 | 뜻 |
| --- | --- |
| 라이브러리 | 내 코드가 필요할 때 가져다 부르는 함수 묶음. 흐름은 내가 쥔다 |
| 프레임워크 | 전체 흐름을 쥐고, 정해진 자리에서 내 코드를 불러 준다(제어의 역전) |
| API | 다른 프로그램의 기능을 부르기 위한 약속(요청 형식, 응답 형식) |

## 정리

- 클라우드는 장비 구매를 사용료로, 몇 주 조달을 몇 분으로 바꾼다. 바탕은 가상화와 API다.
- 다섯 가지 특징: 셀프서비스, 네트워크 접근, 자원 풀링, 빠른 탄력성, 측정되는 서비스.
- IaaS → PaaS → SaaS로 갈수록 제공자가 더 많이 관리한다. 편해지는 만큼 통제와 이식성을 내준다.
- IaaS는 서버·네트워크 가상화와 스토리지, PaaS는 관리형 DB와 분산 처리, SaaS는 멀티테넌시와 API가 받친다.
