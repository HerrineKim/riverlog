서비스를 서버에 올리는 방식은 물리 서버 → 가상 머신(VM) → 컨테이너로 발전해 왔다. 컨테이너는 가볍고 빠르게 늘리고 줄일 수 있어, MSA·오토 스케일링과 함께 쓰이는 현재의 기본 배포 단위가 되었다.

## VM vs 컨테이너

| | VM(가상 머신) | 컨테이너(Docker) |
| --- | --- | --- |
| 가상화 대상 | 하드웨어. VM마다 **게스트 OS + 앱** | OS 커널을 공유하고 **앱과 의존성만** 격리 |
| 크기 | 수~수십 GB | 수십~수백 MB |
| 시작 속도 | 분 단위 | 초 단위 |
| 비용·밀도 | 무겁고 비싸서 한 서버에 많이 못 올림 | 가벼워서 같은 자원에 훨씬 많이 실행 |
| 격리 수준 | 강함 (OS까지 분리) | 상대적으로 약함 (커널 공유) |

- 보안이 중요한 회사는 직원마다 VM을 나눠 주고 그 안에서만 개발하게 하기도 한다. 강한 격리가 필요할 때는 여전히 VM이 쓰인다.
- 실무에서는 둘을 함께 쓴다. 클라우드 VM(예: AWS EC2) 위에 여러 컨테이너를 올리는 식이다.

## 오토 스케일링

트래픽이 몰릴 것 같을 때 실행 단위를 자동으로 늘리고, 한가해지면 줄이는 것이다.

- 컨테이너 수준: VM 하나당 컨테이너를 예컨대 5개씩 늘리도록 설정
- 인스턴스 수준: EC2 같은 VM 자체도 Auto Scaling Group으로 자동 증감

## 컨테이너 오케스트레이션

관리할 컨테이너가 많아지면 사람이 일일이 배치·재시작·네트워크 연결을 할 수 없다. **오케스트레이션 도구**가 여러 서버에 걸친 컨테이너의 배포, 스케일링, 장애 시 재시작, 서비스 디스커버리를 자동으로 관리한다. 대표적으로 Kubernetes, Docker Swarm, AWS ECS가 있다.

## MSA와의 관계

MSA(Micro Service Architecture)는 모놀리식과 반대로 기능을 여러 서비스(서버)로 분산하는 구조다. 서비스마다 컨테이너로 포장해 독립적으로 배포·확장할 수 있어 컨테이너와 궁합이 좋다. 다만 운영 복잡도가 커서, 실제로는 과장되거나 불완전하게 도입되는 경우도 많다. ([Data Flow 아키텍처](Backend/Architecture/data-flow))

## 핵심 정리

- VM은 OS째로, 컨테이너는 앱 단위로 격리한다. 컨테이너가 훨씬 가볍고 빠르다.
- 오토 스케일링으로 부하에 맞춰 컨테이너·인스턴스 수를 조절하고, 많아지면 오케스트레이션 도구로 관리한다.
