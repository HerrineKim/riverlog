> 고려사이버대학교 「클라우드 컴퓨팅」(2023-2학기) 강의 내용을 바탕으로 정리했다.

클라우드 사업자는 "99.99% 가용성"을 내세우지만, 그 숫자가 무엇을 재는지, 못 지키면 무엇을 받는지는 계약서에 있다. 대형 클라우드 장애가 나면 피해는 이용 기업이 입고, 돌려받는 건 대개 요금 일부의 크레딧이다. 그래서 숫자를 읽는 법과 계약 전에 스스로 준비할 것을 함께 알아야 한다. 법이 정한 이용자 권리는 [[korea-cloud-computing-act|클라우드컴퓨팅법]]에 있다.

## 품질을 재는 세 가지

### 가용성

**가용성(availability)** 은 서비스가 장애 없이 정상적으로 요청을 받는 능력이다. 숫자로는 **가용률**로 잰다.

```text
가용률 = 실제 가동 시간 ÷ 예정된 가동 시간 × 100
```

"예정된 가동 시간"에서 사전 공지한 점검 시간을 빼는 계약이 많다. 점검을 자주 공지하면 가용률이 높게 나오는 셈이라, 점검을 어떻게 공지하고(언제, 무엇을, 어떻게 대처하고, 얼마나 걸리는지) 이용자의 업무 시간을 피하는지도 함께 정해 둔다.

| 가용률 | 30일 기준 허용 중단 시간 |
| --- | --- |
| 99% | 약 7시간 12분 |
| 99.5% | 약 3시간 36분 |
| 99.9% | 약 43분 |
| 99.95% | 약 22분 |
| 99.99% | 약 4분 20초 |

9가 하나 늘 때마다 허용 시간은 10분의 1로 준다. 99.99%는 사람이 알림을 받고 노트북을 여는 사이에 다 써 버리는 시간이라, 자동 복구 없이는 지킬 수 없다.

점검할 것:

- 서비스 인스턴스의 접속 주소(IP와 포트)로 꾸준히 접속해 보고, 프로세스가 떠 있는 것만이 아니라 실제로 요청을 받는 상태인지 확인한다.
- 측정한 가용률이 SLA 목표를 만족하는가.
- 운영 상태 대시보드, 장애 알림, 모니터링 로그가 제공되는가. 자동 복구 기능이 있다면 실제로 복구되는가.

### 응답성

**응답성(responsiveness)** 은 요청에 얼마나 빨리 반응하느냐다. 응답 시간은 요청한 순간부터 처리가 끝날 때까지 걸린 시간이고, 어떤 사양에서 잰 값인지 함께 적어야 의미가 있다.

| 점검 항목 | 재는 것 |
| --- | --- |
| 프로비저닝 시간 | 서버를 요청하고 쓸 수 있을 때까지. 예: 생성 15분 이내, 재시작 5분 이내 |
| 애플리케이션 배포 시간 | 배포 요청부터 실제로 접속해 실행되는 시점까지 |
| 서비스 응답 시간 | 시간대마다 부하가 다르므로 하루 중 여러 번 주기적으로. 사용자 위치(데이터센터와 같은 지역인지)도 영향을 준다 |
| 동시 접속과 처리량 | 동시 접속자 수, TPS(초당 트랜잭션 수)가 목표를 넘는가. JMeter, ab(Apache Bench) 같은 부하 도구로 잰다 |

평균만 보면 느린 요청이 가려지므로 p95·p99 같은 백분위로 보는 게 좋다([[observability|관측 가능성]]).

### 확장성

**확장성(scalability)** 은 요청에 따라 자원 양을 늘리고 줄이는 능력이다.

| 점검 항목 | 확인할 것 |
| --- | --- |
| 수평 확장(scale-out) | 예약한 시간에, 또는 CPU 같은 지표가 임계치를 넘을 때 설정대로 인스턴스가 늘어나는가. 수동으로 같은 환경의 인스턴스를 더할 수 있는가. 확장 이력과 알림이 남는가 |
| 수직 확장(scale-up) | 사양을 바꾼 뒤 OS에서 실제로 CPU·메모리가 늘었는가. 재부팅이 필요한지 미리 안다 |
| 로드 밸런서 연동 | 늘어난 인스턴스가 실제로 요청을 나눠 받는가 |
| 확장 요청 처리 시간 | 확장이 시작된 순간(알람, 스케줄, 클릭)부터 새 인스턴스가 요청을 받기까지 |

마지막 항목이 실전에서 중요하다. 새 서버가 "생성됨"이 된 시점과 사용자가 체감하는 "쓸 수 있음" 시점 사이에는 부팅, 앱 기동, 헬스 체크 통과까지의 간격이 있다. 트래픽이 몇 초 만에 몰리는 서비스라면 자동 확장만 믿을 수 없고 미리 늘려 둬야 한다.

## SLA와 서비스 크레딧

**SLA(Service Level Agreement)** 는 사업자가 약속하는 서비스 수준과, 못 지켰을 때의 보상을 적은 계약이다. 보상은 보통 구간별 **서비스 크레딧**(다음 달 요금 할인)이다.

```text
예시) 월 가용률 99.9% 미만   → 해당 서비스 월 요금의 10%
      99.5% 미만             → 20%
      99.0% 미만             → 30%
```

읽을 때 볼 것:

- **무엇을 재나**: 리전 전체인지, 인스턴스 하나인지. 단일 가용 영역에만 배포하면 SLA 적용 대상이 아닌 경우가 많다.
- **무엇이 빠지나**: 사전 공지 점검, 이용자 설정 오류, 천재지변 같은 면책 사유.
- **누가 증명하나**: 크레딧은 대개 이용자가 기한 안에 신청해야 한다.
- **보상의 한계**: 크레딧은 요금의 일부일 뿐, 매출 손실은 보상하지 않는다. SLA는 사업자의 목표이지 내 서비스의 가용성 보증이 아니다.

결국 내 서비스의 가용성은 내가 설계한다. 여러 가용 영역에 나눠 두고, 의존하는 서비스들의 SLA를 곱해 보면(99.9% 서비스 세 개에 직렬로 기대면 약 99.7%) 목표가 현실적인지 알 수 있다([[disaster-recovery|고가용성과 재해 복구 설계]]).

사업자 쪽에서는 가용률을 지키기 위한 정책(장애 관리 절차, 이중화, 증설·유지보수 계획), 담당 조직과 책임, 서버·VM 단위 모니터링, 가용률 분석과 예측을 갖춰야 한다. 이용자는 계약 전에 이걸 갖췄는지 묻는다.

## 무엇을 클라우드로 옮길까

### 현재 수준부터 평가

목표는 "클라우드 도입" 자체가 아니라 현재 IT 수준을 어디까지 끌어올리느냐다. 네 가지 관점에서 지금을 진단한다.

| 관점 | 보는 것 | 지향점 |
| --- | --- | --- |
| 기술 | 하드웨어·DB·소프트웨어·네트워크 현황, 가상화·자동화 가능성 | 목적별로 흩어진 자원을 모으고 자동으로 제공 |
| 관리 | IT 운영 수준, 현업에 자원을 내주는 절차 | 프로젝트마다 다른 절차를 전사 표준으로 |
| 조직 | IT 조직 구조, 역할, 역량, 훈련 | 기술별 조직에서 서비스 지향 조직으로 |
| 거버넌스 | 현업 수요에 IT가 어떻게 응하는가 | 쓴 만큼 예산을 배분하는 모델 |

### 클라우드가 유리한 경우

- AI·빅데이터처럼 짧은 기간에 큰 계산 자원이 필요하다
- 신규·시범 서비스라 사용량을 미리 알 수 없다
- 사용량 변동이 크다(월말 정산, 이벤트)
- 빨리 만들어야 하거나 기술 변화에 민첩하게 대응해야 한다
- 테스트처럼 잠깐 큰 시스템이 필요하다
- 전환 비용보다 운영비 절감이 더 크다
- 자체 시스템을 안전하게 운영할 역량은 부족하지만, 클라우드를 다룰 역량은 있다

반대로 사용량이 일정하고 오래 돌 시스템은 자체 운영이 더 쌀 수 있다. 핵심 업무는 효율만이 아니라 업무 중요도, 다루는 정보의 민감도, 경영 전략까지 함께 따진다.

### 대상 시스템 고르기

1. 현업에서 IT를 많이 쓰는 사람들에게 요구사항을 모은다(VOC). "외부에서 결재하고 싶다", "테스트 서버를 받는 데 2주 걸린다", "월말 분석용 저장 공간이 부족하다" 같은 것.
2. 요구사항을 관련 시스템별로 분류하고, 자주 언급되는 시스템의 현황을 파악한다.
3. 선정 기준(유지 관리 부담 감소, 대용량 처리, 개발·테스트 효율, 비정기 이벤트 대응)으로 평가표를 만들어 점수가 높은 것부터 옮긴다.

### 중요도 평가

옮기기 전에 업무마다 중요도를 매긴다. 고유식별정보(주민등록번호, 여권번호 등)나 개인신용정보를 처리하면 중요 업무로 본다. 직접 다루지 않더라도 다음을 따져 중요 업무로 분류할 수 있다.

- 정보가 위·변조·유출되면 회사와 고객에게 미칠 영향
- 업무가 멈추면 생기는 운영·법적·평판 리스크와 수익 손실
- 다른 시스템과의 연계(장애가 번지는 정도)
- 목표 복구 시간, 운영·개발·테스트 중 어떤 용도인지, 이용자 수

중요도가 높을수록 아래의 준비를 더 촘촘하게 한다.

## 계약 전에 준비할 것

### 업무 연속성 계획

사업자 쪽 재해나 사고가 내 업무를 얼마나 멈추게 할지 파악하고 대비한다.

- **백업**: 백업할 데이터를 고르고, 중요도에 따라 이중화나 다른 장소 보관(소산)을 한다. 복원 테스트와 무결성 검사를 정기적으로 하고, 백업에도 접근 통제와 암호화를 건다.
- **재해 복구 훈련**: 비상 대응 매뉴얼을 만들고 정기적으로 훈련한다. 필요하면 사업자와 합동으로 한다. 사업자의 자체 훈련 계획도 확인한다.
- **역할과 연락**: 사고 시 사업자와 우리의 역할 분담과 절차를 문서로 남기고, 핫라인을 미리 확보한다. 업무별 RTO(복구 목표 시간)와 RPO(복구 목표 시점)를 정해 사업자와 합의한다.

### 출구 전략

사업자의 파산, 서비스 종료, 품질 저하, 규제 변화, 단순한 사정 변경. 언젠가 나올 수도 있다고 보고 미리 정해 둔다.

| 정할 것 | 내용 |
| --- | --- |
| 발동 조건 | 어떤 상황에서 나갈지, 그걸 판단할 지표와 모니터링 |
| 성공 기준 | 서비스 연속성과 품질, 규제 준수에 지장 없이 계약을 끝내는 것 |
| 방법 | 다른 사업자로 이전, 다른 솔루션으로 대체, 재개발 중 무엇으로 |
| 절차 | 데이터 이전 방법, 기존 사업자 쪽 데이터를 복구할 수 없게 파기하는 방법, 시점과 기간, 인력과 비용, 조직별 역할 |

나가기 쉬우려면 처음부터 특정 사업자 전용 기능에 덜 기대는 게 유리하다. 표준 SQL을 쓰는 관리형 DB는 옮기기 쉽고, 사업자 고유의 메시징·워크플로 서비스에 깊이 묶이면 어렵다. 이건 편의와 이식성의 교환이다. 중요한 시스템일수록 출구 전략을 촘촘히 세우고, 계약서에 사업자의 협조 의무를 넣는다.

### 안전성 확보 조치

| 영역 | 핵심 |
| --- | --- |
| 계정 관리 | 사람마다 개별 계정, 역할별 그룹과 권한, 관리자 같은 특권 계정은 따로 집중 관리 |
| 접근 통제 | 같은 클라우드를 쓰는 다른 기관의 망과 분리. 내부망 시스템은 인터넷과도 분리. 원격 접근 절차를 문서화하고 정기 검토 |
| 내부 시스템 연계 | 사내망과 잇는 구간은 전용선이나 그와 같은 수준의 가상 전용선. 외부 시스템과는 암호화된 채널 |
| 암호화와 키 관리 | 민감 데이터 암호화, 키의 생성부터 폐기까지의 정책, 필요하면 HSM. 사업자 직원이나 다른 고객이 키에 접근할 수 없게 |
| 로깅 | 접근·가동·보안 로그를 남겨 사고 조사(포렌식)에 쓴다. 보안 로그는 독립된 시스템에 보관해 무결성을 지킨다 |
| 가상 환경 보안 | 하이퍼바이저·가상 이미지·컨테이너의 취약점 점검. 표준 이미지와 서비스별 보안 설정 관리 |
| 보안 모니터링 | 중요 로그 실시간 감시, 침입 탐지·방지, 웹 방화벽, DDoS 대응 |
| 인적 보안 | 이용자·관리자 정기 교육. 사업자 직원의 보안 교육 결과도 공유받는다 |

위협과 대응은 [[cloud-governance-security|클라우드 거버넌스와 보안]]에서 더 다룬다.

| 항목 | 내용 |
| --- | --- |
| 서비스 범위와 위치 | 클라우드를 쓰는 업무, 처리하는 데이터, 데이터가 처리되는 **물리적 위치(시·군 단위까지)**. 해외라면 그 나라의 법적 의무를 미리 알리게 한다 |
| 감사 접근권 | 내·외부 감사인이 관련 장치·시스템·네트워크·데이터에 접근할 수 있고, 제3자 인증서나 내부 감사 보고서를 요구할 수 있다 |
| 재위탁 | 사업자가 일부를 다른 업체에 다시 맡기면 범위와 업체를 알리고, 새 재위탁이나 중요 변경은 사전 동의를 받는다. 재위탁 계약에도 원계약의 필수 조항이 들어가게 한다. 동의하지 않으면 해지할 수 있다 |
| 서비스 수준 | 점검 등으로 멈출 때는 사전 협의, 예상 못 한 중단은 지체 없이 통지, 일정 시간 이상 장애가 이어지면 원인 분석과 재발 방지 대책 제출. 구체적인 SLA와 손해배상 규정 |
| 정보 소유와 보호 | 처리하는 모든 정보는 이용 회사 소유이고, 언제든 조회·수정·삭제할 수 있다. 사업자는 위탁 범위 안에서만 처리하고 권리를 주장할 수 없다. 전송 구간은 암호화 |
| 출구 | 전환·종료 시 서비스 중단 없이 데이터를 돌려주도록 이전을 지원하고, 이전이 끝나면 복구할 수 없게 파기하고 **파기 확인서**를 준다 |
| 책임 관계 | 사업자의 위반으로 고객에게 손해가 나면 이용 회사가 함께 배상 책임을 지고, 사업자 귀책이면 이용 회사가 사업자에게 구상권을 행사한다 |

정부가 공개한 클라우드 표준계약서(B2B, B2C)를 출발점으로 삼아 빠진 항목을 더하는 것이 현실적이다.

## 정리

- 품질은 가용성(가용률), 응답성(프로비저닝·응답 시간·TPS), 확장성(확장 기능과 처리 시간)으로 잰다.
- SLA의 숫자는 측정 범위와 면책 사유까지 읽는다. 크레딧은 손실을 메우지 못한다. 내 가용성은 내 설계가 정한다.
- 옮길 대상은 현재 수준 진단과 요구사항, 평가표로 고르고, 업무마다 중요도를 매긴다.
- 계약 전에 업무 연속성 계획, 출구 전략, 여덟 가지 보안 통제를 준비하고, 계약서에 위치·감사권·재위탁·정보 소유·파기를 넣는다.
