> 사내 서버와 개발 환경을 다른 장비·사업장으로 옮기는 실무 절차를 일반화해 정리한 노트다.

## 서버 이전이란

**서버 이전(server migration)** 은 돌아가던 애플리케이션 서버(WAS)와 DB, 그 주변 설정을 다른 장비나 환경으로 옮기는 일이다. 코드는 그대로여도 OS, 런타임 버전, 네트워크, 환경 변수, 파일 경로가 바뀌므로 **새 환경에서 똑같이 동작한다는 보장이 없다.** 그래서 옮기기 전에 무엇이 바뀌는지를 먼저 목록으로 만들고, 리허설로 확인하고, 되돌릴 길을 마련한 뒤 전환한다.

## 단계

| 단계 | 할 일 | 산출물 |
| --- | --- | --- |
| 1. 조사 | OS, 런타임(JDK 등), 프레임워크 버전(예: Spring과 Spring Boot 혼재 여부), 컨테이너 사용 여부, DB 종류·버전, 외부 연동, 배치·크론, 인증서를 파악한다 | 구성 목록 |
| 2. 영향도 평가 | 새 환경의 버전·옵션 차이, 호환성, 바뀌는 IP·포트·방화벽, 영향을 받는 사용자와 연동 시스템을 정리한다 | 변경점·위험 목록 |
| 3. 백업 | 애플리케이션 배포본, 설정 파일, DB 덤프를 받아 두고 복원이 실제로 되는지 확인한다 | 검증된 백업 |
| 4. 리허설 | 테스트 서버에서 설치·설정·데이터 이관을 직접 해 보고 실행한 명령을 셸 스크립트로 정리한다 | 이전 스크립트, 작업 계획서 |
| 5. 전환 | 다운타임을 최소화하는 시간대와 순서로 진행한다. 쓰기를 멈추고 마지막 데이터를 동기화한 뒤 트래픽을 넘긴다 | 전환 기록 |
| 6. 사후 점검 | 기능·성능·로그·배치·연동을 확인하고 옛 환경은 일정 기간 남겨 둔다 | 점검 결과 |

## 설정은 누가 옮기나

- **서버 자체 설정은 직접 옮기는 것이 기본이다.** 네트워크, 환경 변수, 계정·권한, 커널 파라미터, 크론처럼 서버에 흩어진 설정은 자동으로 따라오지 않는다. 리허설에서 빠진 항목을 찾아 목록과 스크립트에 넣는다.
- **널리 쓰이는 제품은 전용 도구가 있다.** DB의 덤프·복원과 복제, 컨테이너 이미지와 Compose 파일, 구성 관리 도구처럼 제품이 제공하는 이관 방법을 먼저 찾는다.
- **컨테이너 환경이면 범위가 줄어든다.** 이미지와 설정 파일, 볼륨 데이터를 옮기면 되므로 호스트에 남는 설정만 따로 챙기면 된다. 옮기는 방법은 [[docker-container-operations|Docker 컨테이너 운영]]과 [[docker-compose|Docker Compose]]를 참고한다.

## 롤백 절차

**전환 전에 되돌리는 방법을 먼저 적는다.** 언제 되돌릴지(판단 기준과 시한), 무엇을 되돌릴지(트래픽 경로, DB, 설정), 전환 중 새 환경에 쓰인 데이터를 어떻게 처리할지를 정해 둔다. 옛 환경을 바로 지우지 않고 남겨 두는 것이 가장 단순한 롤백 수단이다. 트래픽을 넘기는 방식의 선택지는 [[deployment-strategies|배포 전략]]의 블루-그린 전환과 같다.

## 정리

- 옮기기 전에 구성 목록과 변경점 목록부터 만든다.
- 백업은 복원해 봐야 백업이다.
- 테스트 서버 리허설에서 명령을 스크립트로 남기면 본 작업이 반복 가능한 절차가 된다.
- 다운타임 계획과 롤백 절차 없이 전환하지 않는다.
- 전환 뒤 사후 점검까지가 이전 작업이다.
