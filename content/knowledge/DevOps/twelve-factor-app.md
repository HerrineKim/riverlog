> ByteByteGo의 System Design 101 가이드 「[The 12-Factor App](https://bytebytego.com/guides/the-12-factor-app)」을 바탕으로, 원 문서 「[The Twelve-Factor App](https://12factor.net/)」으로 확인해 재구성한 노트다.

## 12요소 앱이란

12요소 앱(The Twelve-Factor App)은 **SaaS 애플리케이션을 이식성 있고, 수평 확장하기 쉽고, 지속적으로 배포할 수 있게 만드는 열두 가지 원칙**이다. Heroku 개발자들이 PaaS에서 수많은 앱을 운영하며 정리했고, 컨테이너·Kubernetes 시대의 [[cloud-native|클라우드 네이티브]] 앱 설계에도 거의 그대로 들어맞는다. 2024년 오픈소스로 전환되어 커뮤니티가 개정을 이어 가고 있다.

열두 원칙에 깔린 생각은 **앱은 자기가 돌아가는 서버에 대해 아무것도 가정하지 않는다**는 것이다. 그래야 어느 서버든 지우고 새로 띄울 수 있다.

## 열두 가지 원칙

| # | 원칙 | 규칙 | 어기면 생기는 일 | 지금의 구현 |
| --- | --- | --- | --- | --- |
| I | 코드베이스(Codebase) | 앱 하나 = 버전 관리되는 코드베이스 하나, 배포는 여러 개 | 환경마다 코드가 갈라진다 | Git 저장소 하나에서 개발·스테이징·운영으로 배포 |
| II | 의존성(Dependencies) | 의존성을 명시적으로 선언하고 격리한다. 시스템에 깔린 도구를 암묵적으로 쓰지 않는다 | 「내 컴퓨터에서는 되는데」 | lock 파일, 컨테이너 이미지 |
| III | 설정(Config) | 배포마다 달라지는 설정(DB 주소, 자격 증명)은 코드가 아니라 **환경 변수**에 둔다 | 비밀 값이 저장소에 커밋된다. 환경 추가 때 코드를 고친다 | 환경 변수, Kubernetes ConfigMap·Secret, 비밀 관리 서비스 |
| IV | 백엔드 서비스(Backing services) | DB·큐·캐시·외부 API를 **붙였다 뗄 수 있는 자원**으로 다룬다. 로컬이든 외부든 URL만 바꾸면 교체된다 | 특정 서버에 묶여 교체가 어렵다 | 연결 문자열을 설정으로 주입 |
| V | 빌드·릴리스·실행(Build, release, run) | 빌드(코드 → 실행 파일), 릴리스(빌드 + 설정), 실행을 엄격히 나눈다. 실행 중인 코드를 고치지 않는다 | 운영 서버에서 직접 고친 코드가 어디에도 남지 않는다 | CI가 이미지를 빌드, 릴리스마다 고유 버전, 롤백은 이전 릴리스로 |
| VI | 프로세스(Processes) | 앱은 **무상태** 프로세스로 돈다. 남겨야 할 상태는 백엔드 서비스에 둔다 | 서버 메모리의 세션 때문에 늘리거나 죽일 수 없다 | 세션은 Redis·DB에, 파일은 객체 스토리지에 |
| VII | 포트 바인딩(Port binding) | 앱이 스스로 HTTP 서버를 품고 포트에 바인딩해 서비스를 내보낸다. 외부 웹 서버에 끼워 넣지 않는다 | 실행 환경의 웹 서버 설정에 의존한다 | 앱이 `PORT` 환경 변수를 읽어 리슨 |
| VIII | 동시성(Concurrency) | 같은 프로세스를 **여러 개 띄워** 수평으로 늘린다. 작업 종류별로 프로세스 유형(web, worker)을 나눈다 | 한 프로세스를 키우는 수직 확장에 갇힌다 | 레플리카 수 조정, 오토스케일링 |
| IX | 폐기 가능성(Disposability) | 빨리 뜨고, 종료 신호(SIGTERM)를 받으면 하던 일을 마무리하고 우아하게 내려간다 | 배포·스케일 축소 때 요청이 끊긴다 | 그레이스풀 셧다운, 헬스 체크, 작업을 멱등하게 |
| X | 개발·운영 일치(Dev/prod parity) | 개발·스테이징·운영의 시간·사람·도구 차이를 최소로 줄인다 | 운영에서만 나는 버그 | 같은 컨테이너 이미지, 로컬에서도 같은 종류의 DB |
| XI | 로그(Logs) | 로그를 파일로 관리하지 않고 표준 출력에 **이벤트 스트림**으로 흘린다. 수집·보관은 실행 환경이 맡는다 | 서버가 사라지면 로그도 사라진다 | stdout → 로그 수집기(Fluent Bit 등) → 중앙 저장소 |
| XII | 관리 프로세스(Admin processes) | 마이그레이션·일회성 스크립트는 같은 코드·설정으로 **별도의 일회성 프로세스**로 돌린다 | 운영 서버에 접속해 손으로 고친다 | Kubernetes Job, 배포 파이프라인의 마이그레이션 단계 |

## 원칙끼리의 관계

```text
III 설정 분리 + IV 백엔드 서비스  →  같은 빌드를 어느 환경에나 배포
            │
            ▼
V 빌드·릴리스·실행 분리  →  릴리스 = 빌드 + 설정, 롤백이 쉬움
            │
            ▼
VI 무상태 + VII 포트 바인딩  →  어느 서버에서든 띄울 수 있음
            │
            ▼
VIII 동시성 + IX 폐기 가능성  →  마음대로 늘리고 죽일 수 있음 = 수평 확장
```

수평 확장은 무상태(VI)와 폐기 가능성(IX)에 달려 있다. 상태가 없고 언제든 죽여도 되는 프로세스만이 개수를 자유롭게 바꿀 수 있다.

## 정리

- 앱은 실행 환경에 대해 아무것도 가정하지 않는다. 설정은 환경 변수, 상태는 백엔드 서비스, 로그는 표준 출력.
- 빌드는 한 번, 설정을 입혀 릴리스하고, 실행 중인 코드는 고치지 않는다.
- 무상태 프로세스를 여러 개 띄워 확장하고, 빨리 뜨고 우아하게 죽게 만든다.
- 개발과 운영의 차이를 줄이고, 관리 작업도 같은 코드로 별도 프로세스에서 돌린다.
