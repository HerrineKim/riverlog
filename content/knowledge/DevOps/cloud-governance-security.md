> 고려사이버대학교 「클라우드 컴퓨팅」(2023-2학기) 강의 내용을 바탕으로 정리했다.

클라우드 도입에서 가장 어려운 건 기술이 아니라는 말이 많다. 서버를 사는 데 익숙한 재무팀은 매달 바뀌는 청구서가 낯설고, 결재를 거쳐 장비를 받던 개발자는 누구나 버튼 하나로 서버를 만들 수 있게 되면서 비용과 보안 사고를 만든다. 클라우드 보안 사고의 대부분이 해커보다 이용자·운영자의 실수와 설정 오류에서 나온다는 조사가 반복해서 나오는 것도 같은 이유다. 이 노트는 그 "사람과 규칙" 쪽을 다룬다.

## 조직: 누가 클라우드를 맡나

클라우드의 장점은 하루에도 여러 번 바꾸고 배포할 수 있다는 데 있다. 몇 달에 한 번 모아서 반영하던 조직 구조로는 이 장점을 못 쓴다.

전담 조직을 꾸릴 때 고려할 것:

- 독립 전담팀을 두거나 IT 부서 안에 전담 인력을 둔다. 의사 결정권자의 확실한 지원이 있어야 한다.
- 설계 단계부터 클라우드 아키텍트와 운영 인력을 한 팀에 둔다(DevOps). 앱 개발팀과 현업을 고객처럼 대한다.
- 서버·스토리지·네트워크 부서를 통합해 관리하고, 외부 전문가를 영입해 다양성을 확보한다.
- 처음부터 비용 관리 방안을 마련한다.

**클라우드 아키텍트**가 구심점이다. 사업자를 고르고 관계를 정의하고, 표준 아키텍처와 DevOps 프로세스를 만들고, 비용·거버넌스·접근 관리·규정 준수 절차를 세운다.

### 운영 조직 모델

| 모델 | 구조 | 장점 | 단점 |
| --- | --- | --- | --- |
| 중앙 집중(centralized) | 중앙 그룹이 전략과 운영을 함께 맡고 모든 결정을 승인 | 일관성, 책임 추적 | 획일적이라 변화가 느리다 |
| 분산(decentralized) | 사업 조직마다 각자 전략과 운영(상향식) | 각자 맞는 결정을 빠르게 | 조직 간 일관성이 없고 확장이 어렵다 |
| 공유 서비스(shared service) | 전략은 각자, 운영은 IT 자회사 같은 전문 조직이 공유 | 확장성이 높다 | 조직 간 간극 조율과 소통이 어렵다 |
| CCoE(Cloud Center of Excellence) | 여러 직무가 모인 중앙 전문 조직이 전략·표준·모범 사례를 만들고 교육·기술 지원을 한다. 실행은 사업 조직이 | 중앙 관리와 전문 인력 | 큰 조직에서나 가능하다 |

플랫폼 엔지니어링 팀은 CCoE의 표준을 셀프서비스 도구로 만들어 내놓는, 비슷한 발상의 요즘 형태다([[devops-sre-platform-engineering|DevOps, SRE, 플랫폼 엔지니어링]]).

전 조직을 한 번에 바꾸기는 어렵다. 단순하고 효과가 분명한 서비스부터 옮겨 성공 경험을 만들고 넓힌다. 계획은 (1) 목표 조직과 직무 정의 → (2) 현재 구조·역량·문화 진단 → (3) 구조·규모·역할·역량 재설계 → (4) 단계별 이행 과제 순서로 세운다.

## 거버넌스: 통제가 아니라 가드레일

거버넌스는 공동의 목표를 위해 이해관계자들이 책임감을 갖고 투명하게 결정하도록 하는 장치다. 클라우드에서 거버넌스가 필요한 이유는 네 가지다.

1. **사용량이 계속 는다.** 워크로드가 늘수록 비용과 인력을 최적화할 기준이 필요하다.
2. **비용이 빠르게 새어 나간다.** 자동 확장과 셀프서비스는 민첩함을 주는 대신, 꺼지지 않은 자원이 과지출을 만든다. 비용을 보이게 하고 예산을 통제해야 한다.
3. **자원이 흩어져 보안이 약해진다.** 클라우드에 둔 데이터를 지킬 책임은 사업자가 아니라 이용 기업에 있다.
4. **생산성을 해치지 않으면서** 클라우드를 합리적으로 쓰는 방법이어야 한다. 감시가 목적이 되면 다들 우회한다.

목표는 "허락받고 쓰기"가 아니라 **"정해진 울타리 안에서는 마음대로 쓰기"** 다. 울타리를 넘는 행동(공개 버킷, 허용 안 된 리전, 너무 큰 인스턴스)은 자동으로 막거나 알린다.

### 해야 할 일

| 할 일 | 내용 |
| --- | --- |
| 필요한 사람을 참여시킨다 | 누가 규칙을 정하느냐가 중요하다. 아키텍트는 계정 정책에 맞는 표준 아키텍처를, 보안 관리자는 보안 문제와 해법을 가져온다 |
| 비용과 청구를 통합한다 | 서비스별로 쪼개진 청구서를 해석해 사업 단위로 배분하고(태그), 쓰지 않는 자원을 찾아 줄인다([[cloud-cost-optimization\|클라우드 비용 최적화]]) |
| 전환을 지원한다 | 온프레미스에 맞던 구조가 클라우드에서도 맞는다는 보장은 없다. 옮긴 워크로드가 적절히 보호받고 클라우드 방식으로 동작하게 돕는다. 접근은 최소 권한 원칙으로, 역할별로 세분화한다 |
| 위협 탐지를 자동화한다 | 인스턴스·스토리지·네트워크·컨테이너, 클라우드 사이의 데이터 이동에서 이상 징후를 찾는다. 악성 파일은 격리하고 중요 데이터의 외부 전송은 막는다 |
| 프로비저닝을 자동화한다 | 손으로 만들면 실수가 나고 느리다. 코드형 인프라와 CI/CD로 자원을 만들면 현황이 바로 보이고 정책 검사도 자동이 된다([[terraform-workflow\|Terraform]]) |
| 교육으로 퍼뜨린다 | 지식 전달보다 왜 필요한지 체감하게 하는 교육. 성공 사례를 공유하고 사전 점검을 자동화한다 |

### 문화 전환

새 방식에는 늘 저항이 따른다. 지금 업무, 오래 쌓은 직책과 경험, 영향력이 줄어든다고 느낄 때 커진다. 배울 기회를 넉넉히 주고 단계적으로 바꾼다. 바뀌어야 하는 사고방식은 다섯 가지로 요약된다.

| 예전 | 클라우드 |
| --- | --- |
| 인프라는 직접 짓는 것 | 빌려 쓰는 것 |
| 단계별 승인 | 표준(거버넌스) 안에서 스스로 결정하는 셀프서비스 |
| 정적인 자원을 손으로 관리 | 동적인 앱에 맞춰 자동으로 늘고 준다 |
| 결재 중심의 접근 제어 | API 중심의 즉시 접근 제어 |
| 하드웨어 중심 | 정책과 변경까지 코드로 다루는 소프트웨어 중심 |

## 보안 책임은 나뉜다

클라우드 보안은 **공동 책임 모델**을 따른다. 물리 시설, 하드웨어, 가상화 계층은 사업자가 맡고, 그 위는 서비스 모델에 따라 이용자 몫이 달라진다([[cloud-service-models|클라우드 서비스 모델]]). IaaS라면 OS 패치, 네트워크 설정, 계정과 권한, 데이터 암호화가 모두 이용자 책임이다. SaaS에서도 누가 데이터에 접근할 수 있는지(계정, 공유 설정)는 이용자 책임으로 남는다.

## 관리적 위협

여러 이용자가 큰 인프라와 중앙의 데이터를 나눠 쓰는 멀티테넌트 환경이라 관리 측면의 위협이 크다.

| 위협 | 내용 | 대응 |
| --- | --- | --- |
| 클라우드 남용 | 누구나 큰 계산 자원을 쉽게 빌릴 수 있어 공격자도 비밀번호 크래킹·채굴·공격 기지로 쓴다. 같은 호스트의 VM 간 트래픽은 기존 네트워크 장비가 못 보는 경우가 많다 | 가입 시 신원 검증, 이용 행태 모니터링 |
| 악의적인 내부자 | 퇴사자 계정이 남아 있거나, 부서를 옮겼는데 예전 권한이 살아 있는 것이 전형. 협력사 사용자도 있다 | 계정·권한의 지속적인 검토와 감사, 한 사람에게 권한이 몰리지 않게 분산 |
| 드러나지 않은 위협 | 클라우드 환경의 잠재 위협이 다 알려지지 않았고, 사업자의 내부가 이용자에게 투명하지 않다 | 로그·인프라 정보 공개 요구, 모니터링과 경고 보완 |
| 이해 부족 | 서버 기반에서 가상화 기반으로 옮기면서 생기는 구조 차이를 모른 채 같은 방식으로 운영 | 교육, 표준 아키텍처 |
| 부실한 식별·권한 관리 | 기업이 쓰는 SaaS가 많아져 담당자도 일부만 안다(섀도 IT). 외부로 공유된 문서 속 기밀이 관리 사각지대에 남는다(섀도 데이터) | 통합 인증(SSO), 최소 권한, SaaS 목록 관리 |
| APT(지능형 지속 위협) | 오래 잠복하며 여러 기법을 섞는 표적 공격. 원격 접속과 데이터 집중으로 침투 경로가 많다 | 기술적 탐지와 관리적 대응을 함께 |

알려지지 않은 취약점 공격은 시점에 따라 이렇게 부른다.

| 이름 | 언제 | 특징 |
| --- | --- | --- |
| 제로데이 | 아직 공개·패치되지 않은 취약점 | 공격 비용이 크고 드물지만 막기 어렵다 |
| 원데이 | 벤더가 공개한 직후, 패치가 퍼지기 전 | 공개된 정보로 빠르게 공격 |
| 올드데이 | 패치가 나온 지 한참 지났는데 적용 안 한 시스템 | 비용이 싸서 가장 흔하다 |

가장 흔한 건 올드데이다. 패치를 제때 하는 것만으로 상당수를 막는다.

## 기술적 위협

| 위협 | 내용 | 대응 |
| --- | --- | --- |
| 안전하지 않은 API | 클라우드는 모든 것을 API로 조작한다. 인증을 우회하거나 권한 밖 데이터에 닿는 API 취약점은 곧 데이터 유출과 시스템 장악이다 | 안전한 API 설계, 앞단에 웹 방화벽([[api-security\|API 보안]]) |
| 가상화 취약점 | 하이퍼바이저나 가상 네트워크의 취약점이 그 위 모든 VM으로 번진다. 가상 스위치에서 이웃 VM 패킷 엿보기(ARP 스푸핑), 게스트에서 호스트·하이퍼바이저로 탈출해 다른 VM 장악 | 하이퍼바이저 패치, 테넌트 격리, 가상 네트워크 모니터링 |
| 계정·서비스·트래픽 탈취 | 계정 정보가 털리면 기밀을 보고, 관리자라면 다른 계정을 만들거나 지우고 계약까지 바꾼다. XSS 같은 웹 취약점이 통로가 된다 | 입출력 검증, 보안 라이브러리, 2단계 인증 |
| 데이터 유출 | 네트워크 접근성이 넓은 만큼 경로가 많다. 퍼블릭 클라우드는 다들 비슷하게 쓰므로 한 회사에 통한 공격이 다른 회사에도 통한다 | 암호화, 접근 통제 |
| 데이터 손실 | 동시 편집 같은 편리함의 반대편. 악의든 실수든 지우거나 덮어쓰면 사라진다. 유출이 주로 **읽기**에서 생긴다면 손실은 **쓰기**에서 생긴다 | 수정·삭제 권한 관리, 버전 관리와 백업 |
| 서비스 거부(DoS) | 자원을 소진시켜 가용성을 무너뜨린다. 클라우드에서도 여전히 통한다. 자동 확장이 켜져 있으면 비용 폭탄이 되기도 한다 | DDoS 방어 서비스, 확장 상한과 비용 알림 |
| 시스템 취약점 | OpenStack 같은 오픈소스 플랫폼과 Xen·KVM·QEMU 같은 하이퍼바이저의 알려진 취약점(CVE), 그리고 설정 미흡(CCE) | 아래 두 가지 점검 |

시스템 취약점은 두 종류로 나눠 점검한다.

| | CVE 점검 | CCE 점검 |
| --- | --- | --- |
| 대상 | 소프트웨어 자체의 알려진 결함 | 설정 미흡(약한 비밀번호 정책, 과한 파일 권한, 필요 없는 서비스 활성화) |
| 누가 만들고 고치나 | 벤더가 만들고 벤더가 패치 | 이용자가 만들고 이용자가 고친다 |
| 관점 | 공격자 관점으로 알려진 취약 버전이 돌고 있는지 | 내부 정책과 규제를 지키는지 |
| 예 | 취약점이 알려진 버전의 서비스가 열려 있다 | 비밀번호 최소 길이가 8자 이상으로 설정됐는가 |

규모가 크고 정책 적용이 복잡한 클라우드는 CCE 쪽에 특히 취약하다. 공개된 버킷, 0.0.0.0/0으로 열린 보안 그룹, 로깅 꺼짐 같은 설정 오류를 계속 검사하는 도구(CSPM)를 쓰는 이유다.

## 대응: 보안 솔루션을 배치할 때

클라우드에서 보안 솔루션을 고를 때는 **서비스와 함께 늘어날 수 있는지**를 먼저 본다. 보안 장비가 확장을 막으면 결국 교체하거나 구조를 다시 짜야 한다.

| 방식 | 구조 | 주의 |
| --- | --- | --- |
| 네트워크 기반 | 구간마다 보안 장비(가상 어플라이언스)를 두고 트래픽을 통과시킨다 | 대량 트래픽에 여러 대가 필요하고, 영역(Zone)마다 따로 둬야 한다. 자동 확장·HA가 안 되는 제품이 많아 미리 확인한다 |
| 호스트 기반 | 서버마다 에이전트를 설치한다 | 서버가 늘면 함께 는다. 확장성이 중요하면 이쪽이 맞다. OS 호환성과 최신 OS 지원은 확인한다 |

웹 서비스의 전형적인 배치는 이렇다.

```text
사용자 ─ HTTPS ─▶ [WAF / DDoS 방어] ─▶ 로드 밸런서
                                         │
           퍼블릭 서브넷   웹 서버들 (보안 그룹, 호스트 IPS)
                                         │
           프라이빗 서브넷  앱 서버들 (보안 그룹)
                                         │
           프라이빗 서브넷  DB (보안 그룹: 앱 서버에서만)
   사무실 ─ VPN·전용선 ─▶ 관리 접근 (접근 제어, 디렉터리 인증)
   모든 계층 ─ 로그 ─▶ 모니터링·탐지
```

온프레미스는 경계 방화벽 장비로 접근을 막았다면, 클라우드는 보안 그룹처럼 **API로 설정하는 접근 제어**가 기본이다. 자원마다 붙고 코드로 관리할 수 있어 더 세밀하고 유연하다. 망 구성 자체는 [[aws-vpc-networking|AWS VPC 네트워크 구성]], 보안을 개발 과정에 넣는 법은 [[devsecops|DevSecOps]]에 있다.

## 정리

- 클라우드의 속도를 쓰려면 조직도 바뀌어야 한다. 중앙·분산·공유 서비스·CCoE 중 규모에 맞게 고르고, 작은 성공부터 넓힌다.
- 거버넌스의 목적은 감시가 아니라 가드레일이다. 비용 가시성, 최소 권한, 자동화된 프로비저닝과 탐지, 교육.
- 보안은 공동 책임이다. 사고 대부분은 설정 오류와 권한 관리 실수에서 나온다.
- 관리적 위협(남용, 내부자, 섀도 IT, APT)과 기술적 위협(API, 가상화, 계정 탈취, 유출·손실, DoS, CVE·CCE)을 나눠 대응한다. 솔루션은 확장성을 먼저 본다.
