## 고가용성과 재해 복구

| 개념 | 대비하는 장애 | 수단 |
| --- | --- | --- |
| 고가용성(HA, High Availability) | 서버·디스크·랙 하나의 고장 | 같은 데이터센터(또는 같은 리전의 여러 AZ) 안의 이중화, 자동 페일오버 |
| 재해 복구(DR, Disaster Recovery) | 화재·정전·지진·대규모 오조작으로 **사이트 전체**가 사라지는 일 | 물리적으로 떨어진 다른 데이터센터·리전에 데이터와 실행 환경을 둔다 |
| 사업 연속성 계획(BCP) | 사람·조직·고객 대응까지 포함한 사업 중단 | DR을 포함하는 상위 계획. 누가 무엇을 결정하는지까지 정한다 |

**한 데이터센터 안에서 완벽하게 이중화해도, 그 건물이 멈추면 아무 소용이 없다.** HA와 DR은 따로 설계해야 한다.

## 목표부터 정한다: RTO와 RPO

| 지표 | 뜻 | 결정하는 것 |
| --- | --- | --- |
| RTO(Recovery Time Objective) | 장애 후 서비스가 돌아오기까지 **허용하는 시간** | 대기 환경을 얼마나 켜 둘지 |
| RPO(Recovery Point Objective) | 잃어도 되는 **데이터의 시간 범위** | 백업 주기, 복제를 동기로 할지 비동기로 할지 |

RTO·RPO가 0에 가까울수록 비용과 복잡도는 가파르게 오른다. 그래서 **모든 기능에 같은 목표를 주지 않는다.** 메시지 전송·로그인·결제처럼 멈추면 안 되는 핵심 기능은 완전 다중화하고, 나머지는 기능별 목표 트래픽과 목표 복구 시간을 따로 정한다.

## DR 전략 네 가지

```text
비용·복잡도 낮음 ─────────────────────────────▶ 높음
복구 시간    김   ─────────────────────────────▶ 0에 가까움

백업·복원 ─▶ 파일럿 라이트 ─▶ 웜 스탠바이 ─▶ 멀티 사이트 액티브-액티브
```

| 전략 | 대기 사이트 상태 | 전환할 때 할 일 |
| --- | --- | --- |
| 백업·복원(Backup & Restore) | 백업만 있다 | 인프라를 새로 띄우고 데이터를 복원한다. 수 시간 이상 |
| 파일럿 라이트(Pilot Light) | DB 복제본 같은 핵심 데이터 계층만 켜져 있고 앱 서버는 꺼져 있다 | 앱 서버를 띄우고 늘린다 |
| 웜 스탠바이(Warm Standby) | 작은 규모로 전체가 돌고 있다 | 용량만 늘린다. 축소판이라도 즉시 트래픽을 받을 수 있다 |
| 액티브-액티브(Multi-site Active/Active) | 모든 사이트가 평소에도 트래픽을 나눠 받는다 | 죽은 사이트로 가는 트래픽만 뺀다. 전환이라는 단계가 거의 없다 |

앞의 셋은 **액티브-스탠바이(active/passive)** 계열이다. 평소에는 주 사이트만 일하고, 장애 때 대기 사이트를 **승격(promote)** 한다. 대기 사이트를 운영 규모 그대로 켜 두되 트래픽은 주지 않는 형태는 **핫 스탠바이**라 부른다.

| 비교 | 액티브-스탠바이 | 액티브-액티브 |
| --- | --- | --- |
| 평소 자원 활용 | 대기 사이트가 놀고 있다 | 모든 사이트가 일한다 |
| 전환 위험 | 승격 절차가 실제로 도는지 평소에 알 수 없다 | 평소 운영이 곧 검증이다 |
| 데이터 쓰기 | 주 사이트 한 곳에서만 쓴다 | 여러 곳에서 쓰면 충돌 처리가 필요하다 |
| 어려운 점 | 승격이 예상보다 오래 걸린다 | 정합성 설계, 한 사이트가 빠졌을 때 남은 곳이 전체 트래픽을 감당할 용량 |

액티브-액티브에서 쓰기를 다루는 방법은 셋이다. 쓰기를 한 곳으로 모으는 **write global**, 가장 가까운 곳에 쓰고 마지막 쓰기가 이기게 하는 **write local**, 사용자 ID 같은 키로 쓰기 사이트를 나누는 **write partitioned**다. 어느 쪽이든 **복제는 실수로 지운 데이터도 그대로 복제한다.** 시점 복구(point-in-time) 백업은 따로 둔다.

## 모든 계층을 다중화한다

장애 범위를 키우는 것은 대개 **아무도 다중화를 챙기지 않은 한 계층**이다.

| 계층 | 챙길 것 |
| --- | --- |
| 설비 | 전원 계통·UPS·배터리실 분리, 소방 설비 이중화. 배터리 화재가 UPS까지 번지면 정상 계통까지 같이 꺼진다 |
| 네트워크 | 백본과 외부 회선을 여러 센터에 나누고 동적 라우팅으로 자동 우회한다 |
| 데이터 | DB·NoSQL·검색 엔진·메시지 큐 클러스터의 노드를 **센터 단위로** 나눈다. 복제본이 셋이어도 두 센터에만 있으면 한 센터가 죽을 때 과반을 잃는다 |
| 캐시·세션 저장소 | 「한 센터 안의 HA」로 끝내지 않는다. 상태 정보를 담은 캐시가 한 센터에만 있으면 앱이 다중화돼 있어도 기능이 멈춘다 |
| 플랫폼·운영 도구 | 사내 인증(LDAP)·VPN·코드 저장소·빌드 산출물 저장소·배포 도구·모니터링·로그 수집 |
| 애플리케이션 | 다른 센터로 넘어갔을 때 외부 의존성까지 같이 넘어가는지 확인한다 |

### 운영 도구가 가장 자주 빠진다

서비스는 다중화하면서 **서비스를 복구하는 데 쓰는 도구**는 한 곳에 두기 쉽다. 그러면 장애 때 이런 일이 생긴다.

- 모니터링·로그 시스템이 같이 죽어 무엇이 망가졌는지 보이지 않는다. 장애 구간 로그도 사라진다.
- VPN·사내 인증이 막혀 엔지니어가 서버에 들어가지 못한다.
- 배포 도구와 빌드 산출물 저장소가 없어 다른 센터에 서비스를 다시 띄우지 못한다.
- 클러스터 관리 도구가 없어 수백 대를 손으로 점검한다.

**복구 경로에 있는 모든 것은 서비스와 같은 수준으로 다중화한다.** 장애 중에는 고장 난 시스템을 고치는 것보다 다른 곳에 새로 구성하는 편이 빠른 경우가 많으므로, 재구성 도구와 IaC 코드가 어느 센터에서든 돌아야 한다. 클라우드에서는 같은 이유로 전환 절차를 설정을 바꾸는 **컨트롤 플레인**이 아니라 실제 트래픽을 처리하는 **데이터 플레인** 동작(헬스 체크 기반 DNS 전환 등)에 의존하게 만든다.

## 전환을 자동화하고 훈련한다

- **전환은 버튼 하나가 되게** 만든다. 승격, DNS·GSLB 전환, 연결 문자열 변경을 스크립트로 묶는다. 수동으로 연결을 옮기는 플랫폼은 장애 때 가장 늦게 돌아온다.
- **자동 전환은 신중히** 쓴다. 오탐으로 넘어가도 RTO·RPO만큼의 손실이 생기므로, 판단은 사람이 하고 실행은 자동으로 하는 구성이 흔하다.
- **실환경을 가정한 모의 훈련**을 정기적으로 한다. 액티브-스탠바이의 승격은 해 보기 전까지 몇 분이 걸릴지 아무도 모른다. 전사 단위 시나리오(센터 하나 전체 차단)로 해 봐야 계층 간 빈틈이 드러난다.
- **백업은 복원해 봐야 백업이다.** 복원을 주기적으로 실행해 시간을 잰다.
- **조직마다 다른 기준을 통일한다.** 계층을 맡은 팀이 각자 다른 일정과 전략으로 이중화하면, 한 팀이 「센터 내 HA」에서 멈춘 곳이 전체의 약점이 된다. 공통 설계 기준을 거버넌스로 강제한다.

## 정리

- HA는 장비 고장, DR은 사이트 소멸에 대비한다. 둘은 따로 설계한다.
- RTO·RPO를 기능별로 정하고, 그에 맞춰 백업·파일럿 라이트·웜 스탠바이·액티브-액티브 중에서 고른다.
- 데이터 복제본은 **센터 단위로** 나눈다. 복제본 수보다 배치가 중요하다.
- 모니터링·인증·VPN·배포 도구처럼 **복구에 쓰는 도구**를 서비스와 같은 수준으로 다중화한다.
- 전환은 자동화하고, 실제처럼 훈련해서 검증한다. 해 보지 않은 전환은 동작하지 않는다고 가정한다.
