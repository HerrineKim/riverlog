## 프론트엔드 면접의 특징

프론트엔드 면접은 일반 소프트웨어 엔지니어 면접보다 **알고리즘 비중이 낮고 도메인 지식 비중이 높다.** HTML, CSS, JavaScript를 실제 상황에 적용하는 능력을 본다. LeetCode만으로는 부족하지만, 기본 자료구조·알고리즘은 여전히 나온다. 유형은 업계 표준이 없고 회사마다 조합이 다르므로 지원 회사의 후기를 찾아 맞춰 준비한다.

어느 유형이든 공통 바탕은 **기본기**다. 면접 내내 기본기를 드러내야 한다.

| 영역 | 확실히 알아야 할 것 |
| --- | --- |
| CSS | 명시도(specificity), 박스 모델, 레이아웃, 포지셔닝 |
| JavaScript | `this`, 프로토타입, 클로저, 비동기 코드, Promise, 타이머 |
| 패턴 | 옵저버 패턴, 모듈 패턴 |
| DOM | 이벤트 위임(거의 모든 면접에 쓸모 있다), DOM 탐색·조작, 폼 검증·제출 |

React를 못 쓰게 하는 면접도 있다. 프레임워크 없이 Vanilla JS로 DOM을 다룰 수 있어야 한다.

## 다섯 가지 유형

| 유형 | 내용 | 대표 문제 |
| --- | --- | --- |
| JavaScript 코딩 | 유틸 함수나 내장 API 폴리필 구현. 프론트엔드판 LeetCode | `debounce`, `throttle`, `Promise.all`, `Array.prototype.filter`, `getElementsByClassName` |
| UI 코딩 | HTML·CSS·JS로 컴포넌트·앱·게임 만들기 | 자동완성, 이미지 캐러셀, 툴팁, 별점, 틱택토 |
| 알고리즘 | 일반 LeetCode 문제를 JavaScript로 | 트리 탐색, 해시맵 활용 |
| 퀴즈 | 짧고 정답이 분명한 지식 질문. 리크루터도 묻는다 | 클로저란? Promise와 콜백 차이? 박스 모델? |
| 시스템 디자인 | UI 컴포넌트나 앱의 구조를 설계하고 토론 | 이미지 캐러셀 설계, 이메일 클라이언트 설계 |

### JavaScript 코딩

- 기본 문제는 **10~15분** 안에 끝낸다. 대개 한 문제를 더 받으므로 시간을 다 쓰지 않는다.
- 고급 문제(템플릿 엔진, `JSON.stringify` 구현, HTML에서 목차 생성)는 시니어에게 나오고 25~30분을 준다.
- lodash 구현처럼 옛 브라우저용 예외까지 처리할 필요는 없다. 대신 **시간 복잡도**는 신경 쓴다. 해시맵으로 O(n)이 되면 O(n²)로 쓰지 않는다.
- 순수 함수로 쓴다. 재귀라면 최대 스택 깊이를, 중첩 객체라면 순환 참조 처리 여부를 먼저 묻는다.
- 직접 구현하고 테스트 케이스를 써 보는 것이 가장 좋은 준비다.

### UI 코딩

진행 환경은 미리보기가 있는 온라인 에디터(CodePen, CodeSandbox), 미리보기 없는 에디터(CoderPad), 자기 노트북(BYOE), 화이트보드 중 하나다. 자기 환경이면 Vite 같은 스캐폴딩으로 바로 시작해 설정에 시간을 쓰지 않는다.

구현 전후로 아래를 짚는다. 다 구현할 필요는 없지만 **범위를 면접관과 먼저 확인**하고, 못 한 것은 말로 언급한다.

| 관점 | 확인할 것 |
| --- | --- |
| 독립성 | 전역 변수가 없나? 한 페이지에 여러 인스턴스를 둬도 서로 영향이 없나? 옵션을 받는 API가 있나? |
| 극단적 입력 | 문자열이 아주 길면(`word-break`)? 이미지가 크면? 항목이 0개면(빈 상태 표시) 또는 수천 개면(최대 높이, 페이지네이션, 가상 리스트)? |
| 네트워크 | 앞 요청 응답 전에 새 요청이 나가는 **경쟁 상태**? 타임아웃·에러 복구? 캐싱·지연 로딩·프리페치? |
| UX | 모바일 대응, i18n과 RTL, 접근성(대비, 포커스 순서, `aria-label`) |
| 보안 | 사용자 입력을 `innerHTML`로 넣지 않는다(XSS). `textContent`를 쓴다. URL에 넣는 값은 인코딩한다 |

마무리로 「시간이 더 있으면 프로덕션에선 이렇게 하겠다」(테스트, 키보드 단축키, 반응형 검증 등)를 말한다.

### 알고리즘

프론트엔드 지원자에게는 대체로 쉬운 문제가 나온다. 배열·Set·Map 다음으로 **트리**를 우선한다. DOM이 트리이기 때문이다. BFS, DFS, 레벨 순회를 익혀 둔다. 답을 외우지 말고 문제 **패턴**을 익힌다.

### 퀴즈

전형 초반에 많이 나온다. 정답이 분명해 비개발자도 채점할 수 있기 때문이다. 시니어에게는 「React는 어떻게 동작하나, 가상 DOM은 무엇을 푸나」, 「왜 X 대신 Y 라이브러리를 골랐나」처럼 정답이 없는 질문이 나온다. 암기보다 **개념 이해와 실제 적용 경험**으로 준비한다.

자주 나오는 퀴즈 주제는 다음과 같다.

| 영역 | 주제 |
| --- | --- |
| JavaScript | 호이스팅과 실행 컨텍스트, 클로저, `this` 바인딩, 프로토타입, 이벤트 루프, `async`/`await` |
| 브라우저·DOM | `<!DOCTYPE>`의 역할, `meta` 태그, `script` 위치와 `defer`·`async`, 이벤트 버블링·캡처링, 렌더링 과정 |
| CSS | 박스 모델, 레이아웃(Flexbox·Grid), CSS 애니메이션과 JS 애니메이션의 차이 |
| 네트워크 | CORS가 생기는 이유와 해결 방법, 캐시, HTTP 메서드와 상태 코드 |
| 라우팅 | SPA에서 해시(`#`) 라우팅과 History API의 차이 |

`float` 해제나 JSONP 같은 질문도 나오지만, 각각 Flexbox·Grid와 CORS로 대체된 레거시 기법이라 왜 대체됐는지까지 설명할 수 있으면 된다.

## 프론트엔드 시스템 디자인과 RADIO

프론트엔드 시스템 디자인은 분산 시스템 설계가 아니라 **클라이언트 쪽 구조**를 설계한다. UI 코딩보다 범위가 넓고, 1시간 이내 면접이면 코드보다 설계 트레이드오프를 말로 다룬다. DB 스키마, SQL vs NoSQL, 샤딩, 서버 가용성은 보통 다루지 않는다.

질문은 일부러 모호하게 주어진다. **지원자가 대화를 이끈다.** 화이트보드에 RADIO를 적어 두고 하나씩 다룬다.

| 단계 | 컴포넌트 문제 | 앱 문제 |
| --- | --- | --- |
| **R**equirements | 지원 기기·브라우저, i18n, 스타일 커스터마이즈 범위를 질문으로 확정한다. **요구사항이 분명해지기 전에 그리지 않는다** | 같은 질문 + 오프라인 지원 여부 |
| **A**rchitecture | 하위 컴포넌트와 그 사이 데이터 흐름. 예: 캐러셀 = 메인 이미지, 썸네일, 이미지 캐시 | MVC, MVVM, Flux 같은 클라이언트 구조 |
| **D**ata model | 컴포넌트 상태 | 서버 상태 + 클라이언트 전용 상태 |
| **I**nterface | props, 기본값, 이벤트 훅(`onChange` 등) | HTTP API 파라미터와 응답 형태 |
| **O**ptimizations | UX, 성능, 접근성, i18n, 멀티 디바이스, 보안 중 관련 있는 것을 깊게 | 같다 |

### 설계 원칙

- **상태는 최소로.** 다른 상태에서 계산되는 값(`items.length`로 알 수 있는 `isEmpty`)은 상태에 넣지 않는다. 상태는 최상위에 모으고 하위 컴포넌트는 순수하게 둔다.
- **API는 개방-폐쇄 원칙.** 수정 없이 확장되게 한다. 외형 커스터마이즈는 컴포지션, 렌더 props, `className`·`style` 주입으로 연다.
- **성능**은 로딩 속도(JS 양, 모듈 분리), 상호작용 응답성(메인 스레드 작업 줄이기), 메모리다. 화면에 보이는 것만 렌더링(가상화), 필요한 것만 지연 로딩, 다음 것을 미리 로딩(캐러셀의 다음 N장)이 핵심 기법이다.
- **UX 기본기**: 로딩·에러 상태를 보여 준다. 빈 목록엔 빈 상태를 둔다. 되돌릴 수 없는 동작엔 확인 단계를 둔다. 비동기 요청 중엔 버튼을 비활성화한다. 검색은 키 입력마다 요청하지 않는다([[debounce-throttle|디바운스]]).
- **모바일**: 메모리를 아끼고 터치 영역을 키운다.
- **보안**: XSS(`dangerouslySetInnerHTML`), CSRF, 클릭재킹, 새 창 링크의 `rel="noopener"`.

**성능·접근성·i18n을 먼저 꺼내 깊게 말하는 것이 시니어와 주니어를 가른다.** RADIO는 면접 밖에서도 기술 설계 문서의 뼈대로 쓸 수 있다.

## 레주메와 비헤이비어럴

- 레주메가 ATS에서 제대로 파싱되는지 확인한다. 내용을 **일반 텍스트 파일에 붙여 넣어** 빠진 항목, 깨진 글자, 뒤섞인 섹션이 없는지 보거나, OpenResume 같은 무료 파서로 검사한다. 쓰는 법은 [[resume-writing|합격하는 영문 레주메 작성법]]에 있다.
- 코딩·설계를 잘하고도 **비헤이비어럴에서 떨어지는** 경우가 있다. 시니어일수록 중요하다. 이력서의 모든 내용을 설명하고, 내가 한 일과 결과를 구체적 사례로 말하고, 과거를 스스로 비판해 배운 점을 말하고, 이직 이유를 정리해 둔다([[behavioral-interview-questions|영어 면접 단골 질문 12가지]]).

## 정리

- 프론트엔드 면접은 도메인 지식과 실전 구현 중심이다. 기본기가 전부의 바탕이다.
- 유형은 JS 코딩, UI 코딩, 알고리즘, 퀴즈, 시스템 디자인 다섯 가지이고 회사마다 조합이 다르다.
- UI 코딩은 범위를 먼저 합의하고, 극단적 입력·네트워크·접근성·보안을 짚는다.
- 시스템 디자인은 RADIO로 대화를 이끌고, 최적화 단계에서 깊이를 보여 준다.
