## 코딩 인터뷰 평가 기준이란

코딩 인터뷰 평가 기준(rubric)은 면접관이 지원자의 행동에서 **채용 신호**(hire signal)를 읽어 점수로 바꾸는 틀이다. Google, Amazon, Meta 같은 빅테크는 용어와 가중치만 다를 뿐 거의 같은 네 축을 쓴다. 지원자에게는 「무엇을 보여 줘야 하나」의 목록이고, 면접관에게는 판단을 일관되게 만드는 장치다. 면접 중 지원자가 할 행동은 [[tech-interview-prep#코딩 인터뷰 진행 원칙|기술 면접 준비]]에, 인성 면접의 평가 기준은 [[behavioral-interview-rubrics|인성 면접 평가 기준]]에 있다.

## 네 가지 평가 축

| 축 | 묻는 것 |
| --- | --- |
| 소통(communication) | 질문을 명확히 하고, 접근과 근거·트레이드오프를 말하고, 코딩하면서도 계속 설명하는가 |
| 문제 해결(problem solving) | 문제를 이해하고 체계적으로 접근해, 트레이드오프를 따지고 최적화하는가 |
| 기술 역량(technical competency) | 논의한 풀이를 빠르고 정확하게 코드로 옮기는가. 문법 오류는 없는가 |
| 테스트(testing) | 일반 사례와 경계 사례로 검증하고, 버그를 스스로 찾아 고치는가 |

### 축별 신호

| 축 | 기본 신호 | 고급 신호 |
| --- | --- | --- |
| 소통 | 알맞은 명확화 질문, 접근·근거·트레이드오프 설명, 코딩 중에도 끊기지 않는 설명, 짜임새 있고 간결한 말 | - |
| 문제 해결 | 좋은 질문으로 문제를 빨리 이해한다. 체계적·논리적으로 접근한다. 최적화된 풀이에 이른다. 시간·공간 복잡도를 정확히 낸다. 큰 힌트 없이 푼다 | 풀이를 여러 개 낸다. 각각의 트레이드오프를 설명하고 지금 상황에 맞는 것을 고른다. 후속 문제·확장까지 다룰 시간이 남는다 |
| 기술 역량 | 버그가 거의 없는 동작하는 코드. 문법 오류와 불필요한 코드 없이 깔끔하고, 중복을 줄이고(DRY) 추상화를 알맞게 쓴다. 들여쓰기·간격·이름이 깔끔하다 | 여러 구현 방식을 비교한다. 언어의 구문과 패러다임을 깊이 안다 |
| 테스트 | 일반 사례를 더 만들어 검증한다. 경계 사례를 찾아 처리한다. 버그를 스스로 찾아 고친다. 디버거처럼 한 줄씩 상태를 갱신하며 체계적으로 따라간다 | - |

### 구간별 판정

| 축 | Strong hire | Leaning hire | Leaning no hire | Strong no hire |
| --- | --- | --- | --- | --- |
| 소통 | 이해, 접근, 트레이드오프까지 사고 과정이 철저하고 간결해 면접관이 따라가는 데 전혀 어려움이 없다 | 충분하고 분명하지만, 접근이나 사고 과정을 이해하려고 면접관이 되물어야 했다 | 설명 없이 코딩부터 하거나 말이 어수선해 따라가기 어렵다 | 거의 소통하지 못하거나 말을 걸어도 침묵한다 |
| 문제 해결 | 기본 신호를 모두 쉽게 보이고, 남은 시간에 고급 신호도 대부분 보인다 | 기본 신호는 모두 보였지만 고급 신호까지 갈 시간이 없었다 | 기본 신호 일부만 보였다 | 풀지 못했거나 사고 과정 설명 없이 풀었다. 접근이 어수선하고 틀렸다 |
| 기술 역량 | 기본·고급 신호를 힘들이지 않고 보인다 | 기본 신호만 보였고, 접근을 코드로 옮기는 데 다소 애먹었다. 언어 패러다임 활용이 아쉽다 | 동작하는 코드를 내는 데 고전했다. 문법 오류가 여럿이다 | 동작하는 코드를 내지 못했다. 큰 문법 오류가 있다 |
| 테스트 | 테스트 신호를 쉽게 보인다 | 관련 경계 사례를 다 찾지 못하는 등 다소 애먹었다 | 테스트는 했지만 경계 사례를 처리하지 못했고 버그를 찾거나 고치지 못했다 | 일반 사례로도 테스트하지 않았고, 눈에 띄는 버그를 두고 끝났다고 했다 |

## 점수를 매기는 방식

점수 내는 법은 두 가지다.

| 방식 | 내용 |
| --- | --- |
| 축별 합산 | 축마다 점수(예: 1~4)를 매기고 더해 총점을 낸다 |
| 종합 점수 | 네 축을 두루 보고 전체 점수(예: 1~4) 하나를 낸다 |

어느 방식이든 구간은 **Strong hire, Hire, No hire, Strong no hire**의 네 단계가 기본이다. 판단을 미루고 추가 평가가 필요하다는 중간 구간을 두는 회사도 있다. 최종 판단은 **수학적 커트라인이 아니라 축 전체에 걸친 종합 인상**으로 한다.

## 점수가 결과로 이어지는 방식

| 단계 | 결정 방식 |
| --- | --- |
| 전화 면접 | 면접관이 보통 한 명이라, 그 사람이 Leaning hire 이상을 주지 않으면 온사이트로 가지 못한다. 신호가 불분명하면 전화 면접을 한 번 더 본다 |
| 온사이트 | 대부분의 빅테크는 모든 라운드를 끝까지 보게 한 뒤 전체 결과(패킷)로 결정한다. 라운드마다 결과가 엇갈리면 면접관들이 모여 드러난 신호를 두고 논의한다(debrief). 그래서 한 라운드를 망쳐도 나머지 라운드가 중요하다 |
| 추가 라운드 | 두 코딩 라운드가 비슷한 문제를 내 평가가 빠진 영역이 있거나, 특정 영역 신호가 엇갈려 더 확실한 신호가 필요할 때 추가 라운드를 잡는다 |

- 라운드별 점수와 피드백은 보통 모든 면접관이 볼 수 있다. 같은 회사의 **과거 면접 피드백**까지 보이기도 해서 같은 질문을 피하고, 그때보다 성장했는지를 본다.

## 면접관 체크리스트

알고리즘 면접을 진행하는 면접관이 지킬 것이다. 지원자도 면접관이 무엇을 챙기는지 알면 흐름을 예상할 수 있다.

| 시점 | 할 것 | 하지 않을 것 |
| --- | --- | --- |
| 면접 전 | 밝고 조용하며 인터넷이 안정된 곳, 카메라·마이크·화상 앱 점검. 질문 2~3개를 준비하고 풀이별 트레이드오프를 익혀 둔다. **풀이가 여러 개이고 각각 대가가 다른 질문**이 좋다. 지식의 빈틈을 찾을 수 있게 서로 다른 주제에서 고른다. 코딩 환경(CoderPad·CodePen) 단축키·자동 완성을 설정해 둔다 | - |
| 도입 | 화장실이나 휴식이 필요한지 묻는다. 형식(소개, 시간, 쓸 수 있는 언어, 끝 5분 질의응답)을 안내한다. 서로 소개한다. 문제가 여러 개면 다 못 풀어도 되고 중간에 끊을 수 있다고 미리 말한다 | 지원자 자기소개를 길게 두기 |
| 문제를 낼 때 | 본 적 있는 문제인지 묻는다. 작은 예제와 기대 출력을 준다. 코딩 전에 풀이를 말로 설명하게 한다. 필요하면 힌트를 준다. 힌트 뒤에도 막혀 있으면 풀이를 알려 주고 코딩으로 넘어가 코딩 신호라도 얻는다 | - |
| 코딩 중 | 화이트보드라면 멀찍이 앉지 말고 곁에 서되 공간은 준다. 긍정·부정 신호를 모두 적는다. 문제가 여럿이면, 특히 첫 문제가 쉬우면 한 문제에 오래 머물지 않게 한다 | 시계를 대놓고 보기 |
| 코딩 후 | 테스트 케이스를 내게 하고 함께 따라간다. 놓친 경계 사례는 직접 지적하지 않고 「X가 입력이면 어떻게 되나요?」로 묻는다. 시간·공간 복잡도를 묻는다. 문제별 걸린 시간을 피드백용으로 적는다. 코드를 사진이나 복사로 남긴다. 5분 남으면 「여기서 멈추고 다음으로 넘어가겠다」며 끊는다 | - |
| 마무리 | 지원자 질문에 성실히 답하고 감사 인사를 한다 | - |
| 면접 후 | 세부를 잊기 전에 **최대한 빨리 피드백을 쓴다** | - |

## 정리

- 코딩 인터뷰는 소통, 문제 해결, 기술 역량, 테스트 네 축으로 평가한다.
- 기본 신호만 다 보이면 Leaning hire, 시간 안에 고급 신호(여러 풀이와 트레이드오프, 후속 문제)까지 보이면 Strong hire다.
- 최종 결과는 커트라인이 아니라 라운드 전체 신호의 종합이고, 엇갈리면 면접관 논의로 정한다.
- 면접관은 풀이가 여럿인 질문을 고르고, 힌트로 막힘을 풀어 주며, 신호를 기록하고 바로 피드백을 쓴다.
