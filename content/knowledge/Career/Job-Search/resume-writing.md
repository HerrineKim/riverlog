> 마차카피(matchacopy)와 Flitto의 웨비나 「합격하는 레주메 & 커버레터의 모든 것」을 바탕으로 재구성한 노트다. 「개발자 이력서에 공통으로 통하는 원칙」은 팔만코딩경(42Seoul 커뮤니티 위키)의 「[목요특강] Interviewees are from Mars, Interviewers are from Venus」 강연 정리로 보강했고, 「제출 전 감점 체크」는 김태곤의 「[개발자 이력서, 사소한 체크리스트](https://taegon.kim/blog/developer-resume-checklist/)」(2023.08)로, 「미국 레주메 섹션별 요령」은 resume.guide의 「[미국 개발자 Resume 작성 가이드](https://www.resume.guide/ko/intro)」 공개 파트로 보강했다.

레주메·커버레터 템플릿: [[resume_cover_letter_template.docx|resume_cover_letter_template.docx]] (Word)

국문 이력서와 가장 큰 차이는 **직무 설명과 성과를 함께** 써야 한다는 점이다. "무슨 일을 했다"에서 끝내지 않고 "그래서 어떤 결과가 나왔다"까지 쓴다.

## 1. 무조건 한 장으로 끝낸다

- 인사 담당자는 이력서 한 장을 몇 초 안에 훑고 판단한다.
- **Experience**에는 인턴십, 교내 활동, 봉사, 리서치까지 적는다. 재학생·최근 졸업생은 교내 활동도 괜찮고, 리더십 포지션이었다면 더 좋다.
- 하단 **Skills**에는 지원 포지션이 요구하는 스킬 중 **이미 가진 것**만 넣는다.
- 포맷과 디테일은 지원하는 포지션과 업계 관행에 맞춘다.

## 2. 실무 경험과 학교 정보, 무엇을 먼저 쓸까

| 먼저 쓰는 것 | 이런 경우 |
| --- | --- |
| **Experience** | 지원 직무와 관련된 경험이 있다 / 교내외 활동 경험이 다양하다 |
| **Education** | 학위가 실무 경험보다 더 매력적이다 (전공과 지원 분야가 밀접하다, 석사 과정이다, 교내외 활동이 매우 적다) |

학교 정보에는 **전공, 학점, 장학금, 교내 수상, 관련 수강 과목(Course Highlights)** 을 넣는다.

```text
EDUCATION   Seoul National University, Seoul, Korea      Mar 2022 – Feb 2026 (Expected)
            Bachelor of Science in Computer Science      GPA: 3.50/4.00
```

날짜는 **월 + 연도**(`Mar 2022`)로 쓰고, 학교·회사 이름 옆에 **도시**를 적는다. 재학 중이면 졸업 예정일 뒤에 `(Expected)`를 붙인다.

## 3. Summary는 간략하게

레주메가 이력을 한 장으로 요약한 서류라면, **Summary는 그 한 장을 2~3문장으로 요약한 것**이다. **과거(경험) – 현재(강점) – 미래(커리어 목표)** 를 한 번에 보여 준다.

```text
Frontend engineer with 3 years of experience building React and TypeScript web apps
for 1M+ monthly users. Strong in performance tuning and design-system collaboration.
Aiming to grow into a product engineer on a global team.
```

## 4. 성과 중심으로 경력 쓰기

각 경력 아래에 불릿(•)으로 2~4줄씩, **액션 동사 + 한 일 + 결과(숫자)** 순서로 쓴다.

```text
• Reduced checkout page load time by 40% by code-splitting routes and lazy-loading
  images, raising conversion by 5%
```

- **시제**: 끝난 경험은 과거형(*managed*), 진행 중인 경험은 현재형(*manage*)으로 쓴다.
- **문장은 동사로 시작**한다. 주어 *I*는 생략한다.
- 같은 동사를 반복하지 않도록 **액션 동사 목록(Action Verbs for Resumes)** 을 참고한다.

| 역량 | 액션 동사 예시 |
| --- | --- |
| 관리·리더십 | administered, analyzed, assigned, coordinated, delegated, developed, directed, supervised |
| 커뮤니케이션 | addressed, articulated, authored, clarified, collaborated, communicated, convinced, negotiated |
| 리서치 | analyzed, clarified, collected, conducted, critiqued, evaluated, investigated |

## 커버레터

템플릿의 커버레터는 한 장, 네 덩어리로 되어 있다.

1. **머리글**: 내 이름·주소·연락처 → 날짜 → 회사 이름·주소 → `Dear Hiring Manager:`
2. **자기소개 + 지원 포지션**: "[근무 회사]에서 [직책]을 맡고 있는 / [대학]에서 [전공]을 전공한 [이름]입니다. [지원 회사]의 [포지션]에 필요한 역량을 갖췄다고 확신해 지원했습니다."
3. **지원 동기 + 성과 사례**
   - 회사의 **미션**과 나의 **커리어 목표**가 어떻게 맞닿는지 구체적으로 쓴다.
   - 성과를 낸 경험 하나를 **기승전결**로 풀어 쓴다.
   - Job Description에 적힌 요구 조건을 내 경험·능력과 **하나씩 연결**한다.
   - 성과는 **수치화**한다.
4. **마무리**: 내 경험이 회사에 자산이 될 것이라는 말, 인터뷰에서 더 이야기 나누고 싶다는 요청, 감사 인사 → `Best Regards,` + 이름

## 개발자 이력서에 공통으로 통하는 원칙

영문·국문을 가리지 않고 개발 직군 이력서에 통하는 원칙이다. 기준은 하나다. **채용 담당자의 시간과 수고를 줄여 주는가.**

| 원칙 | 이유 |
| --- | --- |
| 파일은 PDF로 낸다 | 링크를 타고 들어가야 하는 노션 페이지는 번거롭고, 한글(.hwp)은 운영체제에 따라 안 열린다 |
| 최근 것이 위로 온다 | 읽는 사람은 지금의 나를 먼저 알고 싶다 |
| 기술 스택은 잘하는 몇 가지만 | 길게 나열하면 신뢰가 떨어지고, 면접에서 하나하나 깊게 검증받는다. 신입이 다 잘한다고 쓰면 오히려 위험하다 |
| 직무와 관련된 것만 쓴다 | 사진, MBTI, 취미는 채용 판단에 쓰이지 않는다. 교육 과정·부트캠프 경험도 1~2줄로 압축한다 |
| 수식어 대신 사실을 쓴다 | "포기를 모르는 개발자" 같은 문구는 없느니만 못하다. 무엇을 했고 어떤 결과가 났는지로 보여 준다 |
| 블로그·GitHub는 꾸준할 때만 | 없는 것보단 낫지만, 읽을 만한 글과 코드가 쌓여 있어야 효과가 있다 |
| 숙련도 그래프·상중하 표기는 피한다 | 근거 없는 자기 평가로 읽힌다. 「상」은 면접관의 검증 욕구를 부르고, 「중」은 애매하고, 「하」는 그대로 약점이 된다. 점수 대신 쓴 기간·프로젝트·성과로 보여 준다 |
| 지원 직무의 기술을 앞에 둔다 | 프론트엔드에 지원하면서 `Java, Spring, MySQL, React` 순으로 쓰면 주력이 백엔드로 읽힌다. React·TypeScript처럼 직무에 맞는 것을 먼저 쓴다 |

신입 이력서에 빈칸이 많은 것은 당연하다. 억지로 채우지 말고 1페이지 안에서 지원 직무에 맞는 강점만 추린다.

## 제출 전 감점 체크

지원자가 많으면 서류 검토는 **「안 될 이유」부터 찾아** 걸러 내는 방식이 된다. 실력과 무관한 사소한 흠이 그 이유가 되지 않게 한다.

| 항목 | 감점되는 모습 | 이렇게 |
| --- | --- | --- |
| 용어 표기 | `Typescript`와 `TypeScript`가 섞여 있다, `Jquery` | 공식 표기(`TypeScript`, `jQuery`, `Next.js`)로 통일한다 |
| 용어 오용 | Vanilla JavaScript를 「라이브러리」라고 쓴다 | 개념을 정확히 쓴다. 틀린 용어는 이해 부족으로 읽힌다 |
| 정보량 | 경력직인데 「프론트엔드 개발 경험 있음」 한 줄 | 비공개 프로젝트라도 맡은 범위와 한 일을 쓴다. 예: 「사내 관리자 페이지 리뉴얼에서 React 컴포넌트 설계와 API 연동 담당」 |
| 깨진 링크 | 포트폴리오 링크가 404 | 제출 직전에 모든 링크를 직접 열어 본다. 사라진 사이트는 다른 근거로 바꾼다 |
| 커밋 로그 | 개인 프로젝트 커밋이 `update`, `Fix bugs`, `임시 저장`, `.` | 변경 의도가 보이게 쓴다. 검토자는 최종 코드보다 **변경 이력에서 습관**을 본다. 형식보다 의미가 중요하다([[commit-convention\|커밋 컨벤션]]) |
| 경력 공백 | 근무 기간 사이가 설명 없이 비어 있다 | 이유를 한두 줄로 적는다. 서류만 보는 사람은 사정을 알 수 없다 |

## 미국 레주메 섹션별 요령

미국 레주메는 `Name → Contact Info → Summary(선택) → Work Experience → Skills(선택) → Education → Projects` 순서가 흔하다. 이름은 `First Last` 순서로 쓰고, 비자 스폰서십이 필요 없으면 Contact Info에 Visa Status를 적기도 한다. 평가자가 레주메를 어떻게 훑는지는 [[us-hiring-process|미국 개발자 채용 프로세스와 ATS]]에 정리했다.

### Work Experience: XYZ 공식

불릿 하나를 **「Accomplished [X] as measured by [Y], by doing [Z]」** 로 짠다. X는 성과, Y는 숫자, Z는 구체적인 기여다.

```text
Before: Built a pub-sub message brokering system for news content delivery.
After:  Led development of a pub-sub message brokering system for reliable news delivery,
        reducing message loss rate from 8% to 0% by introducing AmazonMQ virtual topics.
```

면접에서 같은 경험을 말할 때는 XYZ 대신 **STAR**(Situation, Task, Action, Result)로 풀어 말한다. XYZ는 글에는 간결하지만 말로 하면 어색하다.

| 규칙 | 이유 |
| --- | --- |
| 직함은 **실제 한 역할** 기준의 일반 직함으로 쓴다 (`Software Engineer`, `Senior Software Engineer`) | 미국 직함은 연차가 아니라 역할을 나타낸다. 사원·대리·과장을 `Associate`·`Assistant Manager`로 직역하면 오해를 산다. 단, 직급 체계가 알려진 빅테크·대기업 경력은 공식 직함을 쓴다 |
| 사내 용어(제품명, 프로젝트명, 직급명)를 쓰지 않는다 | 외부 평가자는 알 수 없다 |
| 불릿은 `•`나 `-`로, 하위 불릿은 피한다 | 줄글보다 읽기 쉽고, 하위 불릿은 복잡해 보인다. 꼭 필요하면 1단계까지만 |
| 날짜는 `Jan 2025 – Dec 2027`. 5년 이상이면 `2020 – 2025`도 된다 | `09/10`은 연·월이 헷갈린다 |
| Git으로 협업했다 같은 일상 업무는 빼고, 남는 공간은 여백으로 둔다 | 평범한 줄 하나가 먼저 보이면 나머지를 안 읽고 넘긴다 |

### Education

- 필수는 학교명, 재학 기간, 전공, 학위명이다. GPA는 평균 이상일 때만, TA 경험은 CS·공학 수업일 때만 넣는다.
- **신입**은 인턴 경험과 CS 전공 여부가 가장 중요하다. 이름 있는 학교의 CS 학위라면 Education을 맨 위로 올린다.
- **경력 5년 이상**이면 필수 네 항목만 남긴다. Summa cum laude 같은 특별한 성과는 둬도 된다.
- 학위명은 정확히 쓴다. 최종 합격 뒤 **백그라운드 체크**에서 한국 학교에까지 직접 확인한다.

### Projects

- 경력자는 최대 3개만 쓴다. 지원 직무와 관련이 깊거나, 지원 포지션의 기술 스택을 썼거나, 사용자가 많은 오픈소스에 기여했거나, 직무를 전환하려 할 때 넣는다.
- 인턴 경험도 없는 신입은 Projects를 Work Experience처럼 쓴다.
- 짧은 설명, 맡은 역할, 주요 기술 스택, 서비스·저장소 링크를 넣는다. 평가자는 코드보다 **README**를 본다.
- 비공개 저장소는 NDA 제약이 없으면 GitFront 같은 링크 공유 서비스로 보여 준다.
- 답이 정해진 학교 과제는 넣지 않는다. 자유 주제 과제나 학교의 불편을 푼 실제 서비스는 좋은 재료다.

### Awards & Certifications

| 내용 | 섹션 이름 | 요령 |
| --- | --- | --- |
| 수상, 리더십 | Awards / Leadership and Awards | 수상자가 많은 흔한 상은 뺀다 |
| 자격증·수료증 | Certifications | Udemy·Coursera 수료증은 큰 의미가 없다. 경력이 부족할 때 학습 의지를 보이는 용도로만 쓴다. 직무 필수 자격증이면 눈에 띄게 둔다 |
| 논문·연구 | Research Experience / Publications | 석사 이상으로 연구직에 지원할 때 쓴다. 제목·학회·날짜·링크를 적고, 국제 학회 논문은 위로 올린다 |
| 특허 | Patents | 특허명·번호·출원일. 지원 직무와 관련이 깊으면 위로 올린다 |

## 체크리스트

- [ ] 한 장인가?
- [ ] 경력마다 숫자로 된 성과가 있는가?
- [ ] 모든 불릿이 액션 동사로 시작하는가? 시제가 맞는가?
- [ ] 날짜는 `월 연도`, 장소는 도시까지 적었는가?
- [ ] Skills는 지원 포지션과 관련된 것만 남겼는가?
- [ ] 직함이 연차 직역이 아니라 실제 역할을 나타내는가?
- [ ] Summary가 2~3문장 안에 과거·현재·미래를 담고 있는가?
- [ ] 기술 이름 표기가 공식 표기로 통일됐는가?
- [ ] 모든 링크를 제출 직전에 열어 봤는가?
- [ ] 링크한 저장소의 커밋 메시지가 변경 의도를 설명하는가?
- [ ] 경력 공백에 한 줄 설명이 있는가?
