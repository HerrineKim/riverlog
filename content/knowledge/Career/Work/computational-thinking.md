## 컴퓨팅 사고란

**컴퓨팅 사고(Computational Thinking)** 는 문제를 컴퓨터가 효과적으로 수행할 수 있는 형태로 정의하고 답을 기술하는 사고 과정이다. 구성 요소는 문제 분해(decomposition), 자료 표현(data representation), 일반화(generalization), 모형화(modeling), 알고리즘이다.

컴퓨터는 0과 1, 곧 숫자만 다룬다. 그래서 **컴퓨터의 관점으로 본다는 것은 데이터의 관점으로 세상을 보는 것**이다. 개발은 사람의 요구사항을 계속 변하는 값, 즉 데이터의 형태로 바꾸는 일이다.

```typescript
// "불을 켜고 끈다" → 상태 하나와 그 상태를 바꾸는 두 함수
let isLight = false
const turnOn = () => { isLight = true }
const turnOff = () => { isLight = false }
```

사람은 불을 켜면 켜진 것을 당연히 안다. 컴퓨터는 켜짐을 직접 인식하지 못하므로 반드시 값으로 표현해야 한다. 이 번역을 **의식하면서** 하는 것이 컴퓨팅 사고의 출발이다.

## 데이터 → 구조 → 알고리즘 → 추상화

| 단계 | 하는 일 | 할 일 앱 예시 |
| --- | --- | --- |
| 데이터로 보기 | 요구사항에서 상태를 찾아 값으로 표현한다 | "체크한다" = `completed: boolean` |
| 구조 고르기 | 0과 1보다 사람에게 가까운 구조를 고른다. 숫자 → 문자 → 배열 → 트리·그래프로 쌓아 온 것이 **자료구조**다 | 추가·삭제·목록 = 객체의 배열 |
| 알고리즘 | 구조를 활용해 원하는 결과를 얻는 절차 | "완료한 일만 보기" = 조건으로 거르기 |
| 추상화 | 절차를 함수로 감싸 세부를 숨기고 재사용한다 | `todos.filter(t => t.completed)` |

`filter`의 본질은 "조건에 맞는 요소만 거른다"이다. 반복문과 `push` 같은 세부는 밖으로 드러낼 필요가 없다. 자동차를 운전할 때 엔진 구조를 몰라도 핸들과 페달만 알면 되는 것과 같다. 데이터로 보는 것이 출발이라면, **추상화를 이해하고 쓰는 것**이 다음 단계다.

결국 프로그래밍의 핵심 요소는 언어가 바뀌어도 같다. **변수, 타입, 조건, 반복, 함수**로 데이터의 구조와 알고리즘을 표현한다.

## 알고리즘 공부가 필요한 이유

알고리즘은 자료구조를 바탕으로 문제를 푸는 절차이고, 알고리즘을 배운다는 것은 **지금까지 찾아낸 가장 효율적인 풀이를 배우는 것**이다. 기준은 기계 성능이 아니라 입력이 늘 때 시간이 얼마나 늘어나는지, 즉 시간 복잡도(Big-O)다.

| 배울 것 | 핵심 |
| --- | --- |
| 시간 복잡도 | 입력 대비 시간 함수가 가파를수록 나쁜 알고리즘이다 |
| 선형 검색 vs 이진 검색 | 정렬돼 있으면 **반씩 줄이는 전략**으로 100개를 7번 만에 찾는다. 이후 배우는 많은 알고리즘의 근간이다 |
| 선택 정렬 vs 퀵 정렬 | 사람이 책을 정리하듯 하면 O(n²), 사람에게 낯선 "컴퓨터스러운" 방식이면 O(n log n) |

현실의 방식을 그대로 본뜬 풀이가 비싸면, **더 컴퓨터스럽게 생각해 최적화**하는 법을 배우는 것이 알고리즘 공부다.

### 프론트엔드 개발자에게는

실무에서 프론트엔드가 알고리즘을 직접 짤 일은 드물다. 그래프보다 복잡한 자료구조를 쓰는 경우도 많지 않다. 디자이너가 포토샵 내부 구현을 몰라도 되듯, `Array.prototype.sort()`의 내부를 몰라도 쓸 수 있다. 프론트엔드는 오히려 최적화보다 **가독성과 사람에 가까운 코드**를 중시한다. 그래도 공부가 필요한 이유는 둘이다.

1. **요구사항을 String·Array·Object로 만드는 감각**이 길러진다. 문제를 이미 알려진 자료구조의 세계로 끌고 오면, 그 세계의 문법으로 보고 이미 해결된 방법으로 풀 수 있다. 자료구조와 알고리즘은 컴퓨터와 소통하는 언어다.
2. 프론트엔드에도 최적화가 필요한 순간이 있다. 이때는 알고리즘 목록보다 **최적화 원리**(분할 정복, 동적 계획법, 탐욕법)가 쓸모 있다. React의 `useMemo`도 동적 계획법의 메모이제이션이다.

어디까지 깊게 팔지는 전략적으로 정한다. 사전처럼 알고리즘을 외우기보다 "현실 문제를 어떻게 데이터로 보고 어떻게 최적화하는가"를 익힌다고 생각한다.

### 코딩 테스트의 의미

코딩 테스트 문제는 특정 언어·라이브러리에 묶이지 않는다. 실무 능력이 아니라 **지문을 읽고 알맞은 자료구조와 알고리즘을 찾는 능력**, 즉 컴퓨팅 사고를 보기 때문이다. 취업 준비 때 제대로 공부해 두면 좋다. 입사 후에는 동기가 잘 안 생긴다. 다만 시간 제약이 있는 평가 도구라, 실무에 필요한 디자인·일정·협업·보안·유지 보수는 다루지 않는다. 실력을 키우는 주 훈련으로 삼기에는 부족하다. 코딩 테스트 준비법은 [[coding-test|코딩 테스트 접근법]]에 있다.

## 개발은 학문이 아니라 운동이다

축구 교재와 경기 영상만 봐서는 공을 잘 찰 수 없다. 개발도 **직접 해 봐야** 늘고, 한 번에 늘 수 있는 폭에 한계가 있어 꾸준함이 중요하다. 무작정 실전만 하면 나쁜 습관이 붙으니 공부와 훈련을 병행하되, **처음에는 실전 비중이 훨씬 커야** 한다. 실력이 오르면 다양한 경험과 넓은 시야가 중요해진다. 팀 스포츠처럼 협업과 내 포지션에 대한 이해도 실력이다.

- **도구 숙련도와 본질은 다르다.** React를 잘하면 Vue도 금방 한다. 잘하는 개발자는 무엇을 해도 잘한다.
- **많이 아는 것과 잘하는 것은 다르다.** 면접에서 잘 대답한 사람이 실무에서 못하는 일이 생기는 이유다.

### 훈련 방법: 베끼고, 돌리고, 고치고, 합친다

```text
목표 정하기 ─ 가장 비슷한 남의 코드 찾기 ─ 일단 내 환경에서 돌리기
   ─ 숫자·문자를 바꿔 가며 내 것으로 고치기 ─ 다른 코드와 결합하기 ─ 반복해서 완성
```

1. **만들고 싶은 것부터 정한다.** 개발은 기술로 가치를 만드는 일이라 만들지 않으면 의미가 없다. 모르겠으면 책의 예제라도 "만든다"를 목표로 삼는다.
2. **돌아가는 남의 코드를 가져와 일단 돌린다.** 분석은 나중이다. 에러는 검색이나 AI에 물어 해결한다.
3. **고쳐서 내 것으로 만든다.** 보이는 값을 바꿔 가며 변화를 느끼면 맥락이 잡힌다. 목적이 있을 때 공부한 것은 빨리 내 지식이 된다. **처음부터 다 이해해야 넘어가겠다는 생각이 가장 큰 방해물**이다. 띄엄띄엄 배워도 된다.
4. **결합한다.** 원하는 코드가 100% 있을 리 없다. 서로 다른 코드를 합치는 과정에서 대부분의 문제가 생기고, 그때 얻는 지식이 오래 남는다. 바퀴를 다시 발명하지 말고 필요한 부분만 이해해 조립하는 것, 이것이 추상화이자 개발의 공유 문화다.
5. **반복해서 완성한다.** 위태롭게 쌓은 코드도 조금씩 안정된다.

### 의식적으로 생각하며 훈련한다

run & fix만 반복하며 직관에 기대면 어느 지점에서 성장이 멈춘다. 의식적으로 연습하면 나중에는 실전에서 직관에 맡겨도 컴퓨팅 사고가 자동으로 작동한다.

| 연습 | 효과 |
| --- | --- |
| 요구사항을 데이터 관점으로 **나눠 적어 보기** | 어떤 데이터를 다루는지와 방향이 정해진다 |
| 코드보다 **데이터 구조를 먼저 기술하기** | 이름과 타입을 먼저 생각하는 습관이 든다 |
| 문제에 맞는 알고리즘 고르기 | 많이 풀고 다양한 알고리즘을 겪어야 는다 |
| 기존 데이터와 알고리즘을 **연결해 새 데이터 만들기** | 데이터 처리와 알고리즘 적용을 잇는 능력이 생긴다 |

## 정리

- 컴퓨팅 사고는 사람의 요구사항을 **데이터의 관점**으로 다시 정의하고, 변수·타입·조건·반복·함수로 표현하는 것이다.
- 알고리즘 공부의 가치는 알고리즘 목록이 아니라 **데이터로 사고하고 최적화하는 법**을 익히는 데 있다. 프론트엔드 개발자에게도 그렇다.
- 개발은 운동처럼 훈련으로 는다. 목표를 정하고, 남의 코드를 돌리고, 고치고, 합치는 과정을 반복한다.
- "일단 뭐든 만들어 보되, 생각은 하면서."
