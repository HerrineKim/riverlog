## 보안 직무란

「보안 일」이라고 하면 관제 센터에서 화면을 보는 모습을 먼저 떠올리기 쉽지만, 실제로는 **무엇을 지키느냐(제품, 조직, 코드)와 누구를 상대하느냐(내부, 고객사, 심사 기관)**에 따라 직무가 갈린다. 개발 경력이 어느 갈래에서 강점이 되는지도 다르다.

## 주요 갈래

| 직무 | 하는 일 | 개발 경험이 쓰이는 곳 |
| --- | --- | --- |
| 보안관제 | 보안 장비와 로그를 지켜보며 공격 징후를 탐지하고 초동 대응한다. 교대 근무가 많다 | 로그 분석 자동화, 탐지 규칙 작성 |
| 보안 솔루션 엔지니어 | 방화벽·접근 제어·DLP 같은 보안 제품을 고객사에 구축하고, 고객 요구에 맞게 설정·커스터마이징한다 | 연동 개발, 고객사 시스템 이해. 해외 제품을 국내 금융권의 결재 라인 같은 업무 규칙에 맞춰 고치는 일은 규모가 커서 사업 단가 차이도 크다 |
| 보안 컨설팅 | 조직의 관리 체계를 진단하고 정책을 세우며, ISMS-P 같은 인증 심사를 준비·대응한다 | 시스템 구조를 알아야 통제 항목을 현실적으로 설계한다 |
| 소스코드 진단 | 애플리케이션 코드에서 보안 약점(입력 검증 누락, 인증 우회 등)을 찾아 고치게 한다 | 코드를 읽고 고치는 능력이 그대로 쓰인다 → [[secure-system-design\|보안 시스템 설계]] |
| 모의해킹 | 허가받은 범위에서 공격자처럼 시스템을 시험해 취약점을 찾고 보고한다 | 웹·네트워크 동작 이해 → [[api-security\|API 보안 체크리스트]] |

개발 조직 안에서 보안을 파이프라인에 넣는 일은 직무가 아니라 방식에 가깝다 → [[devsecops|DevSecOps]].

## 개발자가 보안으로 옮길 때

- **고객 대면 직무는 대체가 늦다.** 고객사 환경에 맞춰 구축하고, 요구를 조율하고, 문제가 생기면 현장에서 책임지는 일은 AI가 코드 작성보다 늦게 가져간다. 보안 솔루션 엔지니어로 옮기는 개발자가 드는 이유다.
- **엔지니어 수요가 꾸준하다.** 보안 제품은 팔린 뒤에도 구축·운영·업그레이드 인력이 계속 필요하다.
- **사내 전환이 가장 쉽다.** 다니는 회사가 보안 회사라면 제품과 고객을 이미 알아 직무 전환의 문턱이 낮다.

## 인맥 넓히기

교육이나 컨퍼런스에 회사 단위로 가면 결국 같은 팀끼리 이야기하다 돌아오기 쉽다. **같은 직무 사람들이 모인 커뮤니티**에 들어가 질문하고 답하는 편이 직무 정보와 인맥을 얻는 데 효과적이다. 평판을 쌓는 방법은 [[reputation-building|명성 쌓기와 커뮤니티 기여]]에 있다.

## 정리

- 보안 직무는 관제, 솔루션 엔지니어, 컨설팅, 소스코드 진단, 모의해킹으로 갈리고 상대하는 대상과 필요한 역량이 다르다.
- 개발 경력은 소스코드 진단과 솔루션 엔지니어(연동·커스터마이징)에서 바로 쓰인다.
- 고객 대면이 필요한 직무는 수요가 꾸준하고, 보안 회사 안에서의 전환이 가장 쉽다.
- 인맥은 행사보다 같은 직무 커뮤니티에서 넓어진다.
