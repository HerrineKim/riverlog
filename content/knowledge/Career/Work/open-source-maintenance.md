## 오픈소스를 쓰는 쪽에서

직접 만들기보다 검증된 오픈소스를 쓰면 업데이트, 안정성, 문서를 함께 얻는다.

| 고를 때 보는 것 | 이유 |
| --- | --- |
| 사용자 수와 활동성 | 버그가 빨리 드러나고 고쳐진다. 최근 커밋·릴리스·이슈 응답 속도를 본다 |
| 문서와 예제 | 학습 비용과 장애 대응 시간을 좌우한다 |
| 인터페이스의 단순함 | 나중에 갈아 끼우기 쉽다 |
| 멈췄을 때의 대안 | 메인테이너가 떠나면 포크해서 유지할 수 있는가(라이선스, 코드 이해도) |

## 포크와 메인테이너 신뢰

원 프로젝트가 멈추면 포크가 선택지가 된다.

1. **먼저 기여한다.** PR을 보내고 이슈에 답하며 활동 이력을 만든다.
2. **공개적으로 묻는다.** 비공개 연락에 응답이 없으면 공개 이슈로 유지 계획을 묻는다.
3. **당위와 계획을 설명한다.** 사용자는 포크가 있다는 이유만으로 옮겨 오지 않는다. 왜 포크하는지, 앞으로 어떻게 유지할지를 밝혀 메인테이너로서 신뢰를 얻는다.
4. **이주 비용을 낮춘다.** 호환성이 깨지는 메이저 버전 전환에는 마이그레이션 가이드를 낸다.

## 문서와 예제

**문서가 프로젝트의 성패를 가른다.**

- README는 무엇을 하는지, 어떻게 시작하는지를 첫 화면에서 보여 준다.
- API 문서는 동작이 바뀔 때마다 함께 고친다. 한 번 쓰고 끝나는 문서는 없다.
- 다양한 예제는 「이걸로 무엇을 할 수 있나」를 보여 준다. 온라인 플레이그라운드는 설치 없이 시험해 보게 해 진입 장벽을 낮춘다.

## 이름 짓기

- 기존 패키지 이름과 겹치지 않는지, 상위·원 프로젝트와 혼동되지 않는지 패키지 레지스트리에서 확인한다.
- 코드 안의 이름은 언어 관례를 따른다. 인기 Java 프로젝트들을 보면 클래스는 명사형 UpperCamelCase, 함수는 동사로 시작하는 lowerCamelCase, 변수는 가장 짧고, 상수는 UPPER_SNAKE_CASE이며, 대개 3단어 안팎으로 조합한다.

## 알리기

공개만으로는 아무도 오지 않는다. 개발자 커뮤니티, 뉴스레터, 큐레이션 목록에 소개를 요청하고 등록한다. 다른 개발자가 연동 프로젝트(래퍼, 플러그인)를 만들기 시작하면 생태계가 자라는 신호다.

## 공개 이후

| 할 일 | 이유 |
| --- | --- |
| 이슈·버그에 빠르게 대응 | 스타 수는 시작점일 뿐, 신뢰는 응답 속도에서 생긴다 |
| 로드맵 공개 | 사용자와 기여자가 방향을 보고 판단한다 |
| 메인테이너의 지속 가능성 관리 | 오픈소스는 대부분 무상 기여다. 악성 비판에 휘둘리지 않고, 감당할 수 있는 범위로 일을 줄이고, 공동 메인테이너를 늘린다 |

## 정리

- 쓸 때는 활동성·문서·인터페이스와 「멈췄을 때의 대안」을 본다.
- 포크는 코드가 아니라 신뢰로 성공한다.
- 문서와 예제가 사용자를 데려온다.
- 공개 후의 응답 속도와 메인테이너의 지속 가능성이 프로젝트의 수명이다.
