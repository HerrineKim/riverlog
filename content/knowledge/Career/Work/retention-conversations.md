## 왜 퇴사 통보는 늘 갑작스러운가

관리자는 엔지니어의 불만을 **퇴사 통보 때 처음** 듣는 일이 많다. 그때는 이미 마음이 떠났고 되돌리기 어렵다. 원인은 정보 흐름에 있다. 관리 계층을 하나 지날 때마다 세부와 긴급도가 깎여, 경영진은 「잘 처리하고 있다」만 듣고 위기나 사직서가 나와야 문제를 안다.

**후회되는 이탈(regrettable attrition)**은 회사가 붙잡고 싶었던 사람의 이탈이다. 저성과자의 이탈과 섞어 세면 지표가 문제를 가린다. 시니어 엔지니어의 이탈이 특히 비싼 이유는 사람과 함께 **문서에 없는 시스템 지식과 설계 판단**이 나가기 때문이다.

## 엔지니어가 실제로 떠나는 이유

| 이유 | 모습 |
| --- | --- |
| **판단이 무시된다** | 기술적 판단을 물어 놓고 기술 외 이유로 뒤집는다. 반대했던 자체 인증 시스템을 만들게 했다가 보안 취약점이 나는 식이다 |
| **갚을 수 없는 기술 부채** | 핵심 인프라 작업이 신기능 일정에 계속 밀린다. 장애를 예측한 엔지니어는 탓을 듣기 전에 떠난다 |
| **의미 없는 일** | 가치 낮은 시스템 유지, 아무것도 바꾸지 않는 추정 의식과 아키텍처 리뷰 같은 프로세스 연극에 시니어를 배치한다 |
| **보상(표면 이유)** | 보상이 진짜 이유인 경우도 있지만, 더 깊은 불만을 말하기 쉬운 형태로 바꾼 설명인 경우가 많다 |

**20% 인상 테스트**: 「연봉을 20% 올려 주면 남을까」라고 물어 아니라면 돈은 진짜 이유가 아니다. 원인을 그대로 두고 보상만 올리는 대응은 실패한다.

한 명의 이탈은 다음 이탈을 부른다. 남은 사람은 「떠난 사람이 뭘 알았을까」를 생각하고, 리크루터는 그 팀을 노린다. 지식이 빠진 자리에서는 문서에 없던 예외 처리를 몰라 비싼 사고가 난다.

## 레벨별 이탈 신호

| 누가 | 무엇을 보나 |
| --- | --- |
| 주니어·미들 | 가장 먼저 알아챈다. 시니어 이탈 6~12개월 전에 시니어가 더는 논쟁하지 않고, 리뷰가 형식적인 승인으로 바뀌는 것을 본다 |
| 시니어 | 같은 패턴이 반복되는 것을 알아보고, 옳은 일을 못 하는 도덕적 상처(moral injury)를 겪은 뒤 발을 뺀다. 경영진은 이를 「성숙해졌다」고 오해한다 |
| 매니저 | 1:1 태도 변화, 문서화가 갑자기 늘어남, 업계 활동(발표, 밋업, 프로필 갱신)이 늘어남을 본다. 이탈이 자기 평가에 반영되니 위로 잘 올리지 않는다 |
| 경영진 | 사직서만 본다 |

배우고 싶은 것을 더는 말하지 않는 것도 신호다. 성장 이야기가 사라졌다면 이미 다른 곳을 보고 있을 수 있다.

## 정보가 위로 닿게 만든다

| 장치 | 내용 |
| --- | --- |
| **스킵 레벨 대화** | 경영진이 중간 관리자를 거치지 않고 여러 레벨의 엔지니어와 직접 정기적으로 대화한다. 중간 관리자의 권위를 깎지 않게 목적을 미리 공유한다 |
| **외부 진단** | 외부 자문이나 파트타임 CTO처럼 불이익 걱정이 덜한 사람이 들으면 더 솔직한 이야기가 나온다 |
| **하나라도 실제로 고친다** | 들은 문제 중 하나라도 눈에 보이게 고치면 「말하면 바뀐다」는 신호가 된다. 테스트 스위트 개선처럼 작은 비용으로 끝나는 일이 많다. 듣기만 하고 아무것도 안 바뀌면 오히려 신뢰가 깎인다 |
| **나쁜 소식 에스컬레이션** | 기술적 우려를 시각과 함께 기록하고, 정한 기간 안에 처리되지 않으면 위로 자동으로 올라가게 한다 |
| **기술 부채 예산** | 엔지니어링 용량의 일정 비율을 알려진 인프라 문제에 고정으로 떼어 둔다 |

## 스테이 인터뷰: 떠나기 전에 묻는다

퇴사 면담(exit interview)은 이미 늦다. **스테이 인터뷰(stay interview)**는 남아 있는 사람에게 남는 이유를 묻는 대화다.

- 핵심 질문: 「왜 계속 여기서 일하나?」, 「더 오래 머물게 하려면 내가 무엇을 하면 되나?」, 「일을 더 낫게 하려면 무엇이 바뀌어야 하나?」
- 한 번에 질문 5~7개로 짧게 하고, 1:1에 나눠 돌아가며 묻는다.
- 퇴사 면담처럼 떠날 이유만 캐는 분위기가 되지 않게 한다.
- 들은 것은 기록하고, 다음 대화에서 무엇이 바뀌었는지 먼저 말한다.

### 1:1 의제에 넣을 것

1:1을 고정 일정으로 두는 법은 [[tech-lead-transition|개발자에서 리더로]]에 있다. 이탈을 막는 관점에서는 다음을 정기적으로 다룬다.

| 의제 | 묻는 것 |
| --- | --- |
| 판단 | 최근에 당신 의견이 무시됐다고 느낀 결정이 있었나 |
| 기술 부채 | 지금 가장 불안한 시스템은 어디인가, 그 일은 언제 할 수 있나 |
| 일의 의미 | 지금 하는 일 중 가장 의미 없다고 느끼는 것은 |
| 성장 | 다음 6개월에 배우고 싶은 것, 맡고 싶은 범위 |
| 경로 | 매니저가 아니어도 올라갈 수 있는 길이 보이는가 |

## 정보만으로 부족할 때: 경제적 개입

정보 흐름은 필요조건이지 충분조건이 아니다. 문제를 들은 경영진이 고칠 **동기**가 없으면 바뀌지 않는다. 그래서 인센티브 구조를 바꾼다.

| 개입 | 방법 |
| --- | --- |
| **이탈 비용 회계** | 시니어 한 명이 떠날 때의 비용(채용 수수료, 완전한 생산성까지 약 6개월, 프로젝트 지연, 잃은 설계 판단)을 계산해 매달 고객 획득 비용·매출과 나란히 보고한다 |
| **무시된 경고 추적** | 포스트모템에 「사전 경고」 항목을 필수로 둔다. Jira, Slack, 아키텍처 리뷰, 이메일에서 누가 언제 경고했고, 무슨 해법을 냈고, 왜 미뤄졌는지 기록한다 |
| **경영진 온콜** | 임원도 분기에 한 주 호출기를 든다. 알림이 미뤄진 수정에서 왔다면 그 결정을 내린 사람에게 에스컬레이션한다 |
| **유지 지표 연동 보상** | 임원 변동 보상의 일부를 시니어 엔지니어 유지율에 묶는다(예: 변동 보상의 25%, 연간 유지율 목표 90%). 시니어는 근속 2년 이상, 기대 이상 성과, 핵심 시스템 소유 중 하나로 정의한다 |
| **거부권 있는 기술 자문단** | 엔지니어링 조직이 뽑은 시니어 엔지니어 5명이 분기마다 경영진과 만나고, 분기에 한 번 경영 결정에 거부권을 쓴다. 거부할 때는 대안, 비용 추정, 위험 분석을 글로 낸다. 뒤집으려면 CEO 승인과 기록된 이유가 필요하다 |
| **경영진급 보상의 IC 트랙** | Staff·Principal·Distinguished를 Director·VP·SVP 보상 밴드에 맞추고, 팀 크기가 아니라 기술 영향과 승수 효과로 승진시킨다([[engineering-levels\|엔지니어 레벨]]) |

최소한으로 시작한다면 **이탈 비용 회계 + 유지 지표 연동 보상** 둘이다.

### 통하지 않는 조건

- 이직률 20~40%를 전제로 하는 컨설팅·외주형 사업
- 제품-시장 적합성을 찾기 전이라 이탈이 필요한 방향 전환의 결과일 수 있는 스타트업
- 실제 거부권 없는 자문단, 근본 원인을 고칠 권한 없는 온콜 같은 **보여 주기식 도입**. 아무것도 안 하는 것보다 나쁘다
- 「임원 보상 25%를 유지율에 묶자」는 제안에 바로 반발하는 경영진. 개혁이 실패할 신호다

## 정리

- 엔지니어는 돈보다 무시된 판단, 쌓이는 기술 부채, 의미 없는 일 때문에 떠난다. 20% 인상 테스트로 진짜 이유를 가린다.
- 이탈 신호는 아래 레벨이 먼저 본다. 경영진은 스킵 레벨 대화와 외부 진단으로 걸러지지 않은 이야기를 듣는다.
- 남아 있을 때 「왜 남아 있나」를 묻고, 들은 것 중 하나라도 실제로 고친다.
- 들어도 안 바뀌면 인센티브를 바꾼다. 이탈 비용을 숫자로 보이게 하고, 그 숫자를 결정하는 사람의 보상에 묶는다.
