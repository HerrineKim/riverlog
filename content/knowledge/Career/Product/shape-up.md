> 「[Shape Up: 스타트업 소프트웨어 제품 개발 및 관리 프로세스](https://www.relate.kr/blog/shape-up-relate/)」를 바탕으로 재구성한 노트다. 원 자료는 Basecamp가 공개한 책 「[Shape Up](https://basecamp.com/shapeup)」이다.

## Shape Up이란

Shape Up은 Basecamp가 자기 팀의 제품 개발 방식을 정리해 공개한 방법론이다. 스크럼처럼 백로그를 쌓고 스프린트마다 꺼내 쓰는 대신, **일정을 고정하고 범위를 조절한다.**

```text
Shaping (사이클과 별도로 진행)
  └─ 피치 작성 ──▶ Betting table ──▶ 6주 Building ──▶ 2주 Cool-down ──▶ 다음 베팅
                    (무엇에 걸까)      (팀이 알아서)    (버그·리팩터링·정리)
```

| 비교 | 스크럼 | Shape Up |
| --- | --- | --- |
| 고정하는 것 | 범위를 추정해 스프린트에 맞춘다 | **시간**을 고정하고 범위를 줄인다 |
| 일의 출처 | 백로그 | 매 사이클 새로 올라오는 피치 |
| 주기 | 1~4주 스프린트 | 6주 개발 + 2주 쿨다운 |
| 작업 분해 | 계획 단계에서 | 팀이 개발하면서 |

## 핵심 개념

| 개념 | 뜻 |
| --- | --- |
| **Appetite** | 이 문제에 쓸 가치가 있는 시간의 **상한**. 「얼마나 걸리나(견적)」가 아니라 「얼마까지 쓸 건가」를 묻는다. 팀은 이 안에서 기능을 줄이거나 더 단순하게 다시 설계한다 |
| **Shape** | 세부 명세 대신 적당히 추상적인 해결 방향. 아래 세 조건을 만족해야 한다 |
| **Pitch** | 다듬어진 안건 문서. 문제, appetite, 해결안, rabbit hole(빠질 수 있는 함정), no-go(하지 않을 것) 다섯 가지를 담는다 |
| **Betting table** | 의사결정자들이 피치를 보고 다음 사이클에 걸 일을 고르는 자리 |
| **Bets, not backlogs** | 백로그가 없다. 이번에 뽑히지 않은 피치는 우선순위를 쌓지 못하고 다음에 새 안건과 다시 겨룬다 |
| **Cool-down** | 6주 뒤 2주. 버그 수정, 리팩터링, 다음 shaping을 하며 사이클을 완결한다 |

### 잘 다듬은 Shape의 세 조건

| 조건 | 뜻 | 표현 도구 |
| --- | --- | --- |
| **Rough** | 세부 디자인이 없어 팀이 채울 여지가 있다 | 화면·이동만 그린 breadboard, 굵은 펜 스케치(fat marker sketch) |
| **Solved** | 새 기술, 팀이 혼자 결정하기 어려운 사항 같은 **큰 위험을 미리 제거**했다 | 기술 검토, 전문가 확인 |
| **Bounded** | 하지 않을 일이 명시돼 범위가 무한히 늘지 않는다 | no-go 목록 |

## 6주 동안 팀이 일하는 법

베팅이 끝나면 작업 분해, 구현, 테스트, 배포 결정은 **팀이 책임진다.**

- **한 조각을 먼저 끝까지.** 디자인은 세부보다 기본 UI 요소(affordance)를 먼저 내놓고, 백엔드는 권한 같은 세부보다 데이터 모델을 먼저 만들어 화면이 실제 데이터로 돌게 한다.
- **가운데부터 시작한다.** 핵심이고, 작고, 처음 해 보는(core · small · novel) 부분부터 만들어 모르는 것을 빨리 드러낸다.
- **스코프 지도를 그린다.** 할 일을 서로 관련된 묶음(scope)으로 나누고, 위험이 큰 묶음부터 진행한다.
- **힐 차트(Hill chart)로 진척을 보인다.** 언덕을 오르는 구간은 아직 방법을 찾는 중(불확실성), 내려가는 구간은 할 일만 남은 상태다. 남은 작업 개수가 아니라 불확실성이 얼마나 걷혔는지를 보여 준다.
- **언제 멈출지 정한다.** 시간이 다 되면 견적을 늘리지 않고, 핵심 문제를 푸는 한 일부 scope를 뺀다. 뺀 것은 다음 shaping 후보가 된다.

## 한계

- shaping을 잘하는 사람(제품·디자인·기술을 함께 보는 시니어)이 없으면 피치 품질이 떨어지고 6주가 위험해진다.
- 6주 단위로 끊기 어려운 일(운영 대응, 긴급 요청)은 따로 흡수할 체계가 필요하다.
- 백로그가 없으므로 「언젠가 할 일」을 기억하는 책임이 각 담당자에게 넘어간다.

## 정리

- 견적 대신 appetite: 얼마나 걸리나가 아니라 얼마까지 쓸지를 정한다.
- shape는 거칠되 위험이 제거되고 경계가 있어야 한다.
- 백로그 대신 베팅: 매 사이클 새로 고른다.
- 시간은 고정, 범위는 조절. 쿨다운으로 사이클을 닫는다.
