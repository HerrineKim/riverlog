## 사용자 리서치가 필요한 이유

제품 팀은 "이 제품이 무엇을 해야 하나"부터 "이 버튼에 뭐라고 쓰나"까지 끝없이 결정한다. 결정마다 위험이 있고, 그 위험을 줄이는 가장 중요한 근거가 **사용자에 대한 이해**다. 직관과 시장 이해만으로는 부족하다.

무시한 대가는 숫자로 돌아온다. 업계 조사(HDI)에서 북미 고객지원 통화 한 건의 비용은 평균 15달러 남짓이다. 디자인 결함으로 문의가 늘면 그대로 비용이 된다.

## 단계마다 맞는 방법: 더블 다이아몬드

영국 디자인 카운슬의 더블 다이아몬드는 **문제를 넓게 탐색한 뒤 좁히고, 해결책을 넓게 시도한 뒤 좁히는** 두 번의 발산·수렴이다.

```text
  다이아몬드 1: 올바른 문제 찾기      다이아몬드 2: 올바른 해결책 만들기
  ◇ 탐색(발산) → 정의(수렴)  ──→   ◇ 개발(발산) → 전달(수렴)  ──→ 출시 후
```

| 단계 | 알고 싶은 것 | 맞는 방법 | 이유 |
| --- | --- | --- | --- |
| 문제 탐색 | 사람들이 실제로 어떻게 행동하고 어디서 막히나 | 에스노그래피, 관찰, 일기 연구 | 한 번의 인터뷰에선 기억나지 않는 문제를 드러낸다 |
| 문제 정의 | 그 문제가 얼마나 크고 흔한가 | 설문조사 | 정성 조사로 찾은 행동의 대표성과 우선순위를 잰다 |
| 해결책 검증 | 이 해결책이 왜 통하거나 안 통하나 | 진행자가 있는 사용성 테스트 (원격 가능) | "지금 무슨 생각을 하세요?"를 물을 수 있다 |
| 해결책 다듬기 | UI·문구 같은 작은 질문의 답 | 진행자 없는 원격 테스트 (UserTesting, Maze 같은 플랫폼) | 빠르고 싸다. 대신 상시 테스터 패널은 일반 사용자와 달라지는 **표본 편향**이 있어 후반부 작은 결정에만 쓴다 |
| 출시 후 | 사람들이 무엇을, 왜 하나 | 분석 데이터 + 진행자 있는 테스트 | 분석은 "무엇"만 보여 준다. "왜"는 정성 조사로 채운다 |

일기 연구는 피트니스 트래커처럼 **시간에 걸쳐 일어나는 사용**을 볼 때, 단일 세션 관찰은 온라인 쇼핑처럼 한 번에 끝나는 과제에 맞다. 진행자가 있는 심층 세션 하나가 진행자 없는 여러 세션보다 많은 것을 알려 줄 때가 많다.

## 사용자를 직접 만날 수 없을 때

직접 조사를 대체할 수는 없지만, 이미 쌓인 사용자 목소리로 정성 데이터를 빠르게 모을 수 있다.

| 출처 | 볼 것 | 주의 |
| --- | --- | --- |
| 앱 리뷰 | 별점이 아니라 본문. 누락 기능, UI 혼란, 버그·성능, 의외로 사랑받는 기능, 튜토리얼 필요성 | 감정이 강한 사람이 쓰므로 양극단에 치우친다. iOS 리뷰가 안드로이드·웹에 그대로 맞지 않을 수 있다 |
| 고객 상담 기록 | 반복되는 문제와 불만. 기록이 없으면 상담 직원을 인터뷰한다 | 대부분 부정적이다. 화면 밖의 정책·업무 관행 문제까지 드러난다 |
| 문의 양식 메일 | 사이트에 대한 불만, 찾지 못한 기능 | 양식을 만들면 누군가 답해야 한다 |
| 업계 포럼·커뮤니티 | 사용자의 동기와 관심사, 특정 제품 스레드 | 산업마다 맞는 포럼이 다르다 |
| 경쟁사 리뷰 | 새 서비스라 데이터가 없을 때 경쟁 제품에 대한 불만 | 잠재 고객의 기대를 짐작하는 용도 |

## 페르소나와 UX 시나리오: 조사 결과를 이야기로

조사 결과는 **조사 → 분석 → 전략 도출** 중 분석 단계에서 페르소나와 시나리오로 정리한다. 기능 목록만 보면 "있으면 좋은 기능"이 끝없이 늘어나지만, 누가 어떤 상황에서 어떤 문제를 안고 서비스를 쓰는지 이야기로 그리면 **어떤 순간에 무엇이 가장 가치 있는지**와 없어도 되는 기능이 보인다.

### 페르소나

**페르소나**는 리서치에서 찾은 사용자 유형을 한 명의 가상 인물로 구체화한 것이다. 수많은 사용자의 동기·욕구·행동 패턴을 한 장으로 요약하고, 회의에서 각자의 짐작 대신 "민지라면 이 버튼을 찾을까?"로 대화하게 한다. 개발자는 사용자의 기술 수준을 과대평가하고 영업은 과소평가하기 쉬운데, 그 시각차도 좁힌다.

| 영역 | 예 |
| --- | --- |
| 기본 정보 | 이름, 연령대, 직업, 거주지, 가족 |
| 생활 방식 | 여가를 어떻게 보내나, 어디에 돈을 쓰나, 정보를 어디서 얻나 |
| 디지털 습관 | 주로 쓰는 앱, SNS 활동 정도, 새 기술에 대한 태도 |
| 목표(Goal) · 니즈(Needs) | 이루고 싶은 것, 그것을 위해 필요한 것 |
| 불편(Pain point) | 지금 방식에서 막히는 지점 |
| 가치관 | 무엇에서 만족과 행복을 느끼나 |

| 흔한 실수 | 고치는 법 |
| --- | --- |
| 리서치 없이 회의실에서 만든다 | 팀의 고정관념을 포장할 뿐이다. 인터뷰·관찰에서 반복된 패턴을 근거로 만든다 |
| 인구통계만 있다 ("35세 남성, 서울 거주") | 설계 결정에 쓸 수 없다. 행동, 목표, 불편이 핵심이다 |
| 다섯 명이 넘는다 | 아무도 기억하지 못한다. 주 페르소나 하나, 부 페르소나 한두 명이면 충분하다 |

### UX 시나리오

**UX 시나리오**는 페르소나가 서비스를 쓰는 과정을 **사용 전, 사용 중, 사용 후**로 나눠 이야기로 쓴 것이다. 사용자(성격·가치관), 니즈와 문제, 사용 맥락(언제·어디서·무엇이 계기인가), 핵심 기능, 과업 흐름, 사용자 가치를 한 흐름에 엮는다. 경험은 동기에서 시작해 행동을 낳고, 결과를 기대와 비교해 평가하고, 그 평가가 기억과 태도로 남는다. 시나리오는 이 흐름 전체를 따라간다.

| 단계 | 쓸 것 |
| --- | --- |
| 사용 전 | 지금 상황은 어떤가, 서비스를 알기 전 어떤 정보를 갖고 있나, 무엇이 계기가 되나 |
| 사용 중 | 서비스를 어떻게 쓰나, 어디서 문제가 생길 수 있나, 그 원인은 무엇인가 |
| 사용 후 | 무엇이 달라졌나, 다음에 무엇을 하나 |

짧은 예: *"퇴근길 지하철에서 지민(29, 직장인 3년 차)은 주말에 갈 북카페를 찾는다. 인스타그램에 저장해 둔 곳은 많지만 다시 찾기 어렵고, 가 보면 자리가 없던 적이 많다. 앱에서 저장한 카페를 지도로 모아 보고, 오늘 저녁 좌석 혼잡도를 확인한 뒤 독서 모임이 있는 곳을 예약한다. 모임이 끝나면 좋았던 문장을 사진으로 남기고 다음 모임 알림을 켠다."* 이 한 단락에서 저장 목록, 지도 보기, 실시간 혼잡도, 모임 예약, 기록, 알림이라는 기능 후보와 우선순위가 나온다.

시나리오는 정보 구조와 화면 흐름을 정하는 근거가 되고, 같은 시나리오를 경쟁 서비스로 따라가면 단계별 강점과 빈틈이 보이며, 완성된 화면이 시나리오를 끝까지 따라갈 수 있는지가 곧 검증 기준이 된다. 시나리오의 장면이 사용자 동선대로 끊김 없이 이어져야 하고 단계별 기능이 순서대로 들어 있어야 한다. 힘든 상황의 사용자까지 시나리오에 넣는 관점은 [[practical-empathy|공감하는 제품 만들기]]의 스트레스 케이스에 있다.

"유저 스토리"라는 말은 두 맥락에서 쓰인다. **UX의 유저 스토리(유저 시나리오)** 는 장면별 스케치와 매트릭스(시나리오, 니즈, 사용자 행동, 필요한 기능)로 리서치 결과를 이해관계자에게 전하고 기능을 도출하는 기획 초기 산출물이다. **애자일의 사용자 스토리**는 "~로서, ~을 위해, ~을 원한다" 한 문장과 인수 조건으로 된 개발 백로그의 작업 단위다([[backlog-and-estimation|백로그와 추정]]).

### UX 전략으로 잇기

분석 결과는 포지셔닝, 차별화, 디자인 방향으로 정리한다.

| 항목 | 내용 |
| --- | --- |
| 포지셔닝 | **주 사용자**(경험 설계의 중심, 예: 단순한 인터페이스·빠른 검색·얕은 메뉴)의 기능적 만족을 먼저 확보하고, **부 사용자**(특정 니즈가 잘 드러나지 않는 그룹, 예: 공유·다시 보기 같은 배려 기능)의 정서적 만족을 그 위에 더한다 |
| 차별화 | 비즈니스(경험을 서비스 품질과 경쟁 우위로 잇고 계속 개선할 팀을 꾸리나), 기술(구현·경제성·확장성·호환성), 사용자(조사에서 찾은 가치에 맞는 디자인 원칙) 세 방향에서 점검한다 |
| 디자인 방향 | 상호작용(한눈에 알 수 있는 조작, 짧은 동선, 즉각적 피드백), 정보(멘탈 모델에 맞는 분류, 길잡이가 되는 내비게이션, 모호한 아이콘엔 레이블), 시각(단순한 레이아웃, 충분한 글자 크기·대비, 목적과 브랜드에 맞는 색) |

이 방향이 이후 와이어프레임과 목업([[wireframe-mockup-prototype|와이어프레임, 목업, 프로토타입]])의 판단 기준이 되고, 완성된 화면은 아래 사용성 평가로 검증한다.

## 사용성 평가

**사용성(usability)** 은 사용자가 특정 상황에서 목표를 이루려고 시스템을 쓸 때 "쓰기 쉬운가"다. 국제 표준 ISO 9241-11의 세 축과 재는 법은 다음과 같다. 사용성의 심리학적 바탕(지각, 기억, 어포던스)은 [[interface-psychology|인터페이스 심리학]]에 있다.

| 축 | 질문 | 재는 법 |
| --- | --- | --- |
| 효과성(effectiveness) | 원하는 목표를 제대로 이뤘나 | 과업 성공률, 오류 수 |
| 효율성(efficiency) | 얼마나 적은 시간과 노력으로 이뤘나 | 완료 시간, 클릭 수, 최적 경로 대비 이동 |
| 만족도(satisfaction) | 쓰는 경험이 만족스러웠나 | 설문(SUS 등), 인터뷰 |

제이콥 닐슨(Jakob Nielsen)은 이를 실무 속성으로 풀었다. 처음 쓰는 사람이 얼마나 빨리 익히나(**학습 용이성**), 익숙해진 뒤 얼마나 빨리 하나(**효율성**), 한동안 안 쓰다 돌아와도 기억나나(**기억 용이성**), 실수가 적고 쉽게 회복되나(**오류**), 쓰기 즐거운가(**만족도**). 사람은 보기 좋은 화면의 문제에 더 관대하다(**심미적 사용성 효과**). 그래서 "좋아요"라는 말이 나와도 실제로 과업을 해냈는지 따로 보고, 반대로 미관을 위해 사용성을 깎지 않는다(대비 낮은 회색 글자, 레이블 없는 아이콘).

### 휴리스틱 평가

**휴리스틱 평가(heuristic evaluation)** 는 사용자 없이 UX 전문가가 정해진 원칙 목록에 비춰 화면을 점검하는 방법이다. 평가자 한 명은 문제의 일부만 찾으므로 **3~5명**이 각자 따로 평가한 뒤 합친다. 빠르고 싸서 와이어프레임·프로토타입 단계에서 큰 문제를 미리 걸러 낸다. 찾은 문제마다 0(문제 아님)부터 4(출시 전 반드시 고침)까지 **심각도**를 매기고, 빈도·영향·반복성(한 번 겪으면 피할 수 있나)을 함께 본다. 전문가의 판단이라 실제 사용자가 막히는 지점을 놓칠 수 있어 사용성 테스트로 보완한다.

1994년에 정리된 **닐슨의 10가지 휴리스틱**이 지금도 거의 그대로 쓰인다.

| # | 원칙 | 점검 질문 |
| --- | --- | --- |
| 1 | 시스템 상태를 보여 준다 (Visibility of system status) | 누른 뒤 반응이 바로 오나? 지금 무엇이 진행 중이고 어디쯤인지 보이나? |
| 2 | 현실 세계와 맞춘다 (Match between system and the real world) | 사용자가 쓰는 말인가, 개발 용어인가? 아이콘과 순서가 현실의 관습과 맞나? |
| 3 | 사용자에게 통제권과 자유를 준다 (User control and freedom) | 실수로 들어간 곳에서 빠져나갈 비상구가 있나? 실행 취소와 다시 실행이 되나? |
| 4 | 일관성과 표준을 지킨다 (Consistency and standards) | 같은 것을 같은 이름·모양·위치로 부르나? 플랫폼 관례(뒤로 가기, 링크 색)를 따르나? |
| 5 | 오류를 예방한다 (Error prevention) | 지울 수 없는 동작 전에 확인하나? 입력 형식과 예시를 미리 보여 주나? |
| 6 | 기억하게 하지 말고 알아보게 한다 (Recognition rather than recall) | 앞 화면의 정보를 외워야 다음 화면을 쓸 수 있나? 메뉴와 선택지가 보이나? |
| 7 | 유연하고 효율적이게 한다 (Flexibility and efficiency of use) | 숙련자를 위한 단축키·바로 가기가 있나? 시스템이 대신할 수 있는 일을 사용자에게 시키지 않나? |
| 8 | 간결하고 미적인 디자인 (Aesthetic and minimalist design) | 지금 필요 없는 정보가 필요한 정보와 경쟁하지 않나? 입력 항목이 꼭 필요한 것만 있나? |
| 9 | 오류를 알아차리고 진단하고 회복하게 돕는다 (Help users recognize, diagnose, and recover from errors) | 오류 메시지가 쉬운 말로 무엇이 왜 잘못됐는지, 어떻게 고치는지 알려 주나? |
| 10 | 도움말과 문서 (Help and documentation) | 필요할 때 맥락에 맞는 도움을 찾기 쉬운가? 도움말과 작업 화면을 쉽게 오가나? |

이 목록은 출발점이고 제품에 맞게 항목을 고르거나 더한다. 접근성 관점의 휴리스틱은 [[accessible-design-process|디자인 단계의 접근성]]에, 문구 점검 기준은 [[ux-writing|UX 라이팅]]에, 입력 폼 기준은 [[form-usability|폼 사용성]]에 있다.

### 사용성 테스트

**사용성 테스트(UT)** 는 실제 사용자(또는 대표 사용자)에게 과업을 주고 수행하는 모습을 관찰하며 문제와 원인을 찾는 방법이다. 어느 단계에서 왜 막혔는지와, 무엇부터 고칠지의 우선순위를 얻는다.

| 단계 | 할 일 |
| --- | --- |
| 1. 계획 | 이해관계자 인터뷰로 목표를 정하고, 방법(대면·원격, 진행자 유무)을 계획서에 적는다 |
| 2. 참가자 | 대상자 프로필(직업, 사용 경험 유무, 연령대 등)을 정하고 모집한다 |
| 3. 과제 시나리오 | 실제 상황처럼 과제를 쓴다. "장바구니에 담긴 상품 하나를 빼고 주문하세요"처럼 목표만 주고 방법은 알려 주지 않는다 |
| 4. 진행 | 참가자가 생각을 소리 내 말하게 하고(think-aloud), 진행자는 개입을 최소화한다. 시간·성공 여부·오류를 기록한다 |
| 5. 정리 | 기록을 과제별·단계별로 정리하고 사용자 발언(VOC)을 모은다 |
| 6. 분석 | 원인을 휴리스틱에 비춰 분류하고 심각도와 개선안을 낸다 |

닐슨은 정성 테스트에서 **5명** 정도면 주요 문제 대부분이 나오고 그 이상은 같은 문제가 반복된다고 봤다. 20명을 한 번에 하기보다 5명씩 고치고 다시 테스트한다. 성공률이나 시간을 통계적으로 비교하려면 더 많은 인원이 필요하다.

| 범주 | 지표 |
| --- | --- |
| 효과성 | 과업 성공률(%), 오류 수와 유형, 오류에서 회복했는지 |
| 효율성 | 과업 완료 시간, 클릭·탭 수, 최적 경로 대비 실제 경로의 비율 |
| 학습 용이성 | 처음 시도와 반복 시도의 차이, 설명 없이 바로 쓸 수 있는 정도 |
| 일관성 | 비슷한 과업에서 같은 방식으로 조작하는지 |
| 만족도 | 과업 직후 난이도 한 문항(SEQ), 테스트 끝에 SUS(10문항, 0~100점) |

정량 지표는 "어디서" 문제가 생겼는지를, 관찰과 발언은 "왜" 생겼는지를 알려 준다.

| 비교 | 휴리스틱 평가 | 사용성 테스트 |
| --- | --- | --- |
| 누가 | UX 전문가 3~5명 | 실제·대표 사용자 5명 안팎 |
| 언제 | 아주 이른 단계부터 | 동작하는 프로토타입이나 제품이 있을 때 |
| 비용 | 낮다 | 모집·진행·분석에 시간이 든다 |
| 강점 | 원칙 위반을 빠짐없이 훑는다 | 실제로 막히는 지점과 이유를 본다 |
| 약점 | 실제 사용자의 행동과 다를 수 있다 | 과제로 정하지 않은 부분은 못 본다 |

먼저 휴리스틱 평가로 뻔한 문제를 걷어 내고 남은 시간을 사용성 테스트에 쓰는 순서가 효율적이다. 접근성 측면의 평가 절차는 [[accessibility-evaluation|접근성 평가]]에 있다.

## 큰 조직에서 학습 문화 만들기

큰 조직은 느리고 예산을 정당화하라고 요구한다. 대신 **사람·도구·업무 관행이라는 자원**이 이미 많다. 새로 들이기보다 있는 것을 활용한다.

| 자원 | 활용법 |
| --- | --- |
| 사람 | 영업·고객지원처럼 사용자와 닿아 있는 부서를 찾는다. 인터뷰가 끝날 때 "다음에도 참여하실래요?", "피드백 줄 만한 분을 소개해 주실래요?"를 물어 참가자 풀을 늘린다 |
| 도구 | 이미 전사에 깔린 화상회의 도구를 리서치에 쓴다. 스크립트·모집 메일을 템플릿으로 쌓아 재사용한다 |
| 업무 관행 | 기존 주간 회의에 결과 공유를 얹는다 |

핵심 기법은 **준비되기 전에 정기 세션 일정을 잡는 것**이다. 매주 화요일 테스트, 수요일 회의 공유처럼 고정해 두면 "언제 테스트하나"를 따로 정할 필요가 없다. 논쟁이 생기면 아이디어를 적어 두고 다음 세션에서 확인한다. 테스트가 주간 리듬이 되면 팀원이 자기 기능의 피드백을 먼저 요청하게 된다.

리서치를 지속하려면 가치를 **비즈니스 언어**로 바꿔야 한다. 검증 안 된 기능을 만드느라 쓴 시간, 기능을 두고 논쟁한 시간을 비용으로 환산해 보여 준다.

## 서두를 때 생기는 디자인 리스크

린·애자일 압박 속에서 리서치를 급히 끝내라는 요구가 많다. 대충 만든 상관관계와 인용문에 기댄 결정이 리스크다.

| 리스크 | 대응 |
| --- | --- |
| 편한 장소에서 조사한다 | **편의보다 맥락.** 시끄러운 현장에서 일하는 사용자를 조용한 회의실로 부르지 않는다. 건설 장비라면 실제 현장에 가야 소음·시야·운전자 체격 차이·염분 부식 같은 문제가 보인다 |
| 분석 전에 결론을 원한다 | **타협한다.** 분석이 끝날 때까지 큰 변경은 미루고, 그 사이 디자인 팀은 제한적으로 진행한다. 타협이 신뢰를 쌓는다 |
| 말만 믿는다 | 사람은 자기 행동을 정확히 말하지 못한다. 설문 답보다 **실제 행동**을 관찰한다 |
| 내 디자인이라서 좋아 보인다 | **보유 효과(endowment effect)**: 내가 가진 것을 과대평가한다. 불리한 관찰 결과를 "특이 케이스"로 치부하게 만든다 |
| 요소가 계속 늘어난다 | **줄인다.** 과제에 필요한 것만 남긴다. 팀에게 복잡한 화면에서 기능을 찾아보게 하거나 과거 테스트 영상을 보여 주면 설득이 쉽다 |

## 리서치 윤리

리서치를 모두가 하게 되면서(리서치 민주화) 훈련받지 않은 사람이 사람을 대상으로 조사하는 일이 늘었다. 인터뷰는 말일 뿐이라 해도 참가자에게 해를 줄 수 있다.

| 위험 | 대응 |
| --- | --- |
| 취약 집단 (아동, 환자, 소수자, 경제적 약자, 판단 능력이 낮은 성인) | 특별한 명분과 보호 장치 없이 모집하지 않는다 |
| 참가자를 오해하게 함 | 목적, 후원사, 보상, 실제 출시 여부를 어디까지 밝힐지 미리 정한다. **중단 요청엔 즉시 멈춘다** |
| 예상 못 한 민감한 주제 | 감정이 격해질 때의 대응을 준비하고 관찰자와 역할극으로 연습한다 |
| 잘못된 기대 | 시작할 때 "오늘 30분 동안 무엇을 할지"를 말하고 기대를 다시 맞춘다 |
| 결과를 해석할 줄 모름 | 연구 질문 → 가설 → 질문 문항 → 데이터 → 분석 방법을 미리 연결해 둔다 |
| 정보 오용 | 개인정보 입력을 사전에 알리고 동의받는다. 데이터 보관 기간·접근 권한을 정한다. 상사 같은 권력 관계의 관찰자가 있으면 반드시 알린다 |

당장 할 수 있는 것은 **참가자 경험 중심의 사전 동의서와 동료의 연구 절차 검토**다. 그다음이 윤리·데이터 분석 교육과 멘토링이고, 학술 발표나 아동·건강 관련 연구라면 학계의 기관윤리위원회(IRB) 검토까지 고려한다.

## 정리

- 단계에 맞는 방법을 고른다. 탐색엔 관찰, 우선순위엔 설문, 검증엔 진행자 있는 테스트, 미세 조정엔 원격 테스트.
- 사용자를 못 만나도 리뷰·상담 기록·포럼에 목소리가 있다.
- 조사 결과는 행동·목표·불편 중심의 페르소나 몇 명과 사용 전·중·후 시나리오로 정리하고, 그 문장에서 기능 후보와 우선순위를 뽑는다.
- 화면은 전문가 3~5명의 휴리스틱 평가로 먼저 훑고, 과제 시나리오로 실제 사용자 5명씩 관찰한다. 예쁜 화면은 문제를 가리니 말보다 행동을 본다.
- 리서치를 이벤트가 아니라 **정기 일정**으로 만들면 문화가 된다.
- 급할수록 맥락, 분석 시간, 내 디자인에 대한 애착을 경계한다.
- 참가자도 사람이다. 동의·투명성·데이터 보호를 절차로 갖춘다.
