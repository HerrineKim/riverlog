> okdevtv의 「개발 프로젝트 진행 순서」 정리와 『오늘도 개발자가 안 된다고 말했다』를 바탕으로 정리한 노트다. 「결정 로그」는 웹액츄얼리가 번역한 Happy Cog의 「내가 하는 일에 대해 바로 알아가기」(2015.10)를 바탕으로 덧붙였다. PoC·프로토타입·MVP 비교는 Asana의 「[애자일 프로젝트 관리 리소스](https://asana.com/ko/resources/agile)」 아티클들을 함께 참고했다. 「[Lv0 에서 Lv2 까지 - 인프런 서비스 리뉴얼](https://www.hyungjoo.me/4%EB%85%84%EC%9D%84-%EA%B8%B0%EB%8B%A4%EB%A6%B0-%EC%9D%B8%ED%94%84%EB%9F%B0-%EC%84%9C%EB%B9%84%EC%8A%A4-%EB%A6%AC%EB%89%B4%EC%96%BC-%EC%98%A4%ED%94%88)」의 내용을 더해 보강했다.

새로운 서비스를 처음부터 만들 때 무엇을 어떤 순서로 준비해야 하는지 **기승전결** 네 단계로 정리한 체크리스트다. 사이드 프로젝트를 시작할 때 빠뜨린 단계가 없는지 점검하는 용도로 쓰기 좋다.

## 기 — 기획

- 구성원 모집
- 서비스 기획: 페르소나와 사용 시나리오 정의
- 화면 설계: 와이어프레임 (Figma 등)
- 데이터 설계: ERD (ERDCloud 등)
- 개발 기술 스택 선택

### 만들기 전에 검증하기: PoC · 프로토타입 · MVP

셋 다 "작게 먼저 만들어 본다"지만, **답하려는 질문**이 다르다.

| | 개념 증명(PoC) | 프로토타입 | MVP |
| --- | --- | --- | --- |
| 질문 | 기술적으로 **가능한가** | 어떻게 **보이고 쓰이는가** | 사용자가 실제로 **원하는가** |
| 대상 | 개발팀·의사결정자 | 팀·이해관계자·소수 사용자 | 실제 사용자 |
| 모양 | 핵심 기술 하나만 검증하는 코드 조각 | 화면 흐름, 클릭되는 목업 | 핵심 가치 하나를 담은, 실제로 쓰이는 제품 |
| 이후 | 대개 버린다 | 디자인·기획 결정에 반영하고 버린다 | 피드백을 받아 계속 키운다 |

- PoC는 **선례가 없는 기술이나 방법**을 쓸 때 필요하다. 이미 검증된 방식이면 조사 자료로 대신한다.
- MVP의 "최소"는 품질이 아니라 **범위**다. 기능은 적어도 쓸 만해야 배울 것이 생긴다.

## 승 — 개발 기반 구축

- 저장소 생성 (GitHub)
- 개발 환경 구축 및 팀 공유
- 기본 폴더 구조 잡기, 코딩 컨벤션 합의
- 기능별 샘플 코드·테스트 케이스 (선택)
- 개발 서버 구축
- CI/CD 구성 (GitHub Actions, Jenkins 등)
- 빌드 결과를 메신저로 받는 웹훅 (Slack 봇 등)

## 전 — 개발 진행

- 스프린트 단위의 점진적 개발
- 기능 테스트, 사이드 이펙트 감지
- 버그·취약점 점검 (SonarQube 같은 정적 분석, OWASP ZAP 같은 보안 스캐너)
- 모니터링 추가 (Sentry 에러 추적, Google Analytics 사용자 분석)

## 결 — 서비스 진화

- 오픈 후 운영
- 운영 데이터 시각화 (ELK 스택 등)
- 데이터를 근거로 개선 기획 → 다시 '기'로

## 진행 내내: 결정 로그 남기기

큰 프로젝트의 작은 결정 수백 개는 이메일과 메신저에 흩어지므로, 끝난 뒤 몰아 쓰지 말고 **진행하는 동안 결정 로그(decision log)를 쓴다.** 첫 방향이 정해진 뒤 시작하고, 내부 초안이니 언제든 고친다.

| 무엇을 | 왜 |
| --- | --- |
| 매일의 작은 결정과 그 이유 | 결정을 설명하기 쉬워지고, 글로 쓰면 논리의 빈틈이 보인다 |
| 지금은 상관없지만 개발 때 문제 될 피드백 | 나중에 이슈가 될 것을 미리 잡아 둔다 |
| 길 찾기(내비게이션)·기능 규칙 | 막힐 때 다시 볼 길잡이가 된다 |
| 쓰는 색·글꼴 계층 | 스타일 가이드와 디자인 시스템의 뼈대가 되고 프런트엔드 개발을 앞당긴다 |

## 대규모 리뉴얼·오픈을 앞두고

기존 서비스를 갈아엎는 리뉴얼은 새 프로젝트보다 변수가 많다.

| 원칙 | 이유 |
| --- | --- |
| 일정은 보수적으로, 범위는 실행 가능한 만큼 먼저 | 일정은 회의와 개발이 진행될수록 늘어난다 |
| 디자인·기획 범위를 개발 일정과 함께 확정 | 개발 중 잦은 디자인 변경이 가장 큰 지연 요인이다. 바꾸려면 비용을 인정하고 합의한다 |
| 기획 문서는 최소한 팀이 공유할 수준으로 | 문서가 부실하면 이후 작업마다 해석이 갈린다 |
| 레거시 데이터 이전은 전담자와 넉넉한 시간 | 이전 스크립트와 정합성 검증에서 시행착오가 가장 많다 |
| 인프라는 아는 사람이 맡는다 | 모르는 채로 떠안으면 시간과 에너지를 크게 잃는다 |
| **베타 테스트 결과가 나오기 전에 오픈일을 확정하지 않는다** | 베타에서 나온 문제를 고칠 시간이 일정에 없으면 품질을 포기하게 된다 |
| 보안 점검은 베타 단계에서 | 오픈 뒤 외부 제보로 발견되는 일을 줄인다 |
| 서비스 중단 작업은 트래픽이 적은 시간에, 사후 수정 시간까지 잡는다 | 전환 직후 버그가 몰린다. 팀 전체가 버그를 찾고 바로 고치는 안정화 기간을 둔다 |
| 기존 서비스 운영 인력을 보호한다 | 긴 리뉴얼 기간에도 매출은 기존 서비스에서 나온다 |

| 단계 | 핵심 산출물 |
| --- | --- |
