# /note — 지식 창고에 노트 넣기

`$ARGUMENTS`로 받은 자료를 riverlog 지식 창고의 노트 한 편(또는 기존 노트 보강)으로 만든다.
형식·문체의 세부 규칙은 [style.md](style.md)에 있다. 노트를 쓰기 전에 반드시 읽는다.

## 0. 입력 파악

`$ARGUMENTS`를 다음 중 하나 이상으로 해석한다. 섞여 있으면 모두 재료로 쓴다.

| 입력 | 처리 |
| --- | --- |
| 붙여 넣은 본문 | 그대로 재료로 쓴다 |
| URL | WebFetch로 본문을 가져온다. 못 가져오면 사용자에게 본문을 붙여 달라고 한다 |
| 로컬 파일 경로 (md, pdf, 이미지) | Read로 읽는다 |
| 짧은 주제어만 있음 | 재료가 없다는 뜻이다. 웹 검색으로 자료를 모을지 AskUserQuestion으로 묻는다 |
| `→ Career/Work` 같은 경로 힌트 | 저장 위치로 우선 사용한다 |
| `--draft` | frontmatter에 `publish: false`를 넣는다 |

재료가 비어 있으면 아무것도 만들지 말고 무엇을 넣을지 묻는다.

## 원칙: 기록이 아니라 주제별 정리

지식 창고는 **나중에 개념·주제로 찾아 읽는 사전**이다. 일기장이나 작업 로그가 아니다. 그리고 **언제 열어도 오늘 기준으로 맞아야 한다.** 원문이 몇 년 전 글이어도 노트는 지금의 사실로 쓴다. 자세한 규칙은 [style.md의 「사전체」](style.md#사전체-늘-지금-기준으로-쓴다)다.

- 노트 하나는 **개념 하나 또는 주제 하나**다. 엄격한 1노트 1개념일 필요는 없다. 「Claude Code 활용 팁」처럼 한 주제 아래 여러 항목을 묶어도 된다.
- 판단 기준은 **글이 시간순으로 짜였나, 주제순으로 짜였나**다. 날짜별 TIL, 「오늘 ~했다」, 프로젝트·회차별 진행 기록, 회고는 노트로 만들지 않는다.
- 재료가 로그 모양이면 **개념만 뽑아** 기존 노트에 보강하거나 새 개념 노트로 쓴다. 남는 개인 회고·경험담은 지식 창고가 아니라 `content/blog`에 어울린다고 사용자에게 알린다.
- 직접 겪은 경험은 「언제 무엇을 했나」가 아니라 「그래서 알게 된 개념·방법」으로 쓴다. 트러블슈팅은 `증상 · 원인 · 해결` 표로 일반화한다.
- **개념 하나의 집은 하나다.** 같은 정의·비교표·"A와 B의 차이" 설명이 두 노트에 있으면 한 노트만 남기고 다른 쪽은 한 줄 요약 + 링크로 바꾼다. 관점이 다르다는 이유로 같은 표를 두 번 두지 않는다.
- **장황한 노트와 기록성 노트는 해체해도 된다.** 강의·책 순서를 그대로 따라간 긴 노트, 문제 풀이를 여러 개 나열한 노트, 제목에 연도가 붙은 노트, 행사 후기·"현장에서 들은 이야기"는 개념만 뽑아 간결한 주제 노트로 병합하고 원 노트는 지운다. 자세한 기준과 절차는 [style.md의 「분량과 해체」](style.md#분량과-해체)와 아래 7번을 따른다.

## 1. 기존 노트와 겹치는지 확인

새 파일부터 만들지 않는다. 같은 내용이 이미 있으면 **보강이 기본**이다.

```bash
ls content/knowledge content/knowledge/*/
grep -ril "<핵심 키워드>" content/knowledge --include=*.md
grep -rh "^concept:\|^title:" content/knowledge | grep -i "<키워드>"
```

- 같은 주제의 노트가 있다 → 그 노트에 섹션을 추가하거나 고친다. 출처 인용을 한 줄 더한다.
- 상위 개념만 겹친다 → 새 노트를 만들고 서로 관련 노트로 링크한다.
- 판단이 애매하다 → AskUserQuestion으로 "새 노트 / 기존 노트 보강" 중 고르게 한다.

## 2. 위치와 파일 이름 정하기

- 분야(1단계 폴더)는 `Frontend · Backend · Computer-Science · Algorithm · DevOps · AI-Data · Tools · Career · Life-and-Learning` 중 하나다. 새 분야 폴더는 만들지 않는다.
- 하위 주제 폴더는 기존 것을 먼저 쓴다. 같은 주제 노트가 3편 이상 쌓일 때만 새 폴더를 제안한다.
- 파일 이름은 영어 kebab-case 슬러그(`loop-engineering.md`). 위키링크가 파일 이름으로 풀리므로 **vault 전체에서 유일**해야 한다:
  `find content -name "<slug>.md"` 결과가 비어 있어야 한다.

## 3. 노트 쓰기

[style.md](style.md)를 따른다. 핵심만 요약하면:

1. **frontmatter**: `title`, `concept`, `summary`, `tags`, `source`, `date`(오늘), 필요하면 `sources`, `publish: false`.
2. **출처 인용 한 줄**: `> 누구의 「제목」(날짜)을 바탕으로 재구성한 노트다.` 시점 경고는 붙이지 않는다.
3. **최신화**: 원문 이후 바뀐 사실(권장 도구, API, 기본값, 지원 범위)을 웹 검색·공식 문서로 확인해 오늘 기준으로 쓴다. 옛 방식은 「과거에는 ~」 한 줄이나 `## 역사`로 내린다.
4. **사전체**: 본문의 주어는 개념이다. 「글쓴이는」, 「테오가 본」, 「현재(2021)」, 「글 작성 시점 기준」 같은 화자·시점 서술을 쓰지 않는다. 경험담·홍보는 빼고 원칙만 남긴다.
5. **본문은 번역이 아니라 재구성**이다. 원문 순서를 따르지 말고 "무엇인가 → 왜 → 어떻게 → 한계 → 정리"처럼 읽는 사람 기준으로 다시 묶는다. 나열된 항목은 표로, 흐름은 코드 블록 다이어그램으로.
6. **끝에 관련 노트**: `관련 노트: [[slug|제목]], ...` — 실제로 있는 노트만 건다.

### 넣지 않는 것

- 돈, 구직 진행 상황, 회사 내부 업무, 개인 생활 같은 사적인 정보 (사이트는 공개된다). 재료에 섞여 있으면 빼고, 뺐다고 보고한다.
- 원문 문단 통째 복사, 근거 없는 수치, 재료에 없는 내용을 사실처럼 덧붙이기.
- 시간에 민감한 사실(버전, 가격, 명령어)은 오늘 기준으로 확인해서 쓴다. 확인할 수 없으면 빼거나 공식 문서 링크로 대신한다. "글 작성 시점 기준"으로 얼버무리지 않는다.
- 원저자를 주어로 한 문장(「~는 ~라고 말한다」), 원문 연도를 「현재」로 쓰는 문장.

## 4. 연결하기

- 상위 인덱스 노트(`content/knowledge/<분야>.md` 또는 `<분야>/<주제>.md`)의 `## 하위 노트` 목록(없으면 표)에 한 줄 추가한다: `- [제목](분야/slug.md): 한 줄 설명`. 기존 줄의 형식을 그대로 따른다.
- 내용상 밀접한 기존 노트 1~3편의 `관련 노트` 줄에 새 노트를 역링크로 추가한다. 억지로 늘리지 않는다.

## 5. 검증

```bash
node .claude/skills/note/scripts/check-note.mjs content/knowledge/<경로>/<slug>.md
```

frontmatter 필수 필드, 파일 이름 중복, 위키링크·상대 링크 대상 존재 여부, 인덱스 등록 여부를 검사한다. 오류가 나오면 고치고 다시 돌린다. 통과 전에는 완료라고 말하지 않는다.

## 7. 기존 노트 병합·해체 (정리 작업일 때)

"창고를 점검해 달라", "겹치는 노트를 합쳐 달라"처럼 새 재료 없이 정리를 요청받으면 이 절차를 따른다. 새 노트를 넣을 때도 1번 단계에서 겹침을 발견하면 같은 절차로 먼저 정리한다.

### 찾기

```bash
grep -rh '^concept:' content/knowledge --include='*.md' | sort | uniq -d          # concept 중복
node .claude/skills/note/scripts/check-note.mjs $(find content/knowledge -mindepth 2 -name '*.md')  # 인덱스 미등록·깨진 링크
grep -rl -E "/<slug>\)|\[\[<slug>[|#\]]|<slug>\.md" content/knowledge             # 어떤 노트로 들어오는 링크
```

같은 소제목(「X와 Y의 차이」, 「~ 비교」, 「RAID」처럼)이 두 파일에 있거나, 제목·소제목에 연도·행사명이 있으면 후보다.

### 판정

| 모양 | 처리 |
| --- | --- |
| 두 노트가 같은 개념을 설명 | **병합**: 더 일반적인 제목·위치의 노트를 살리고, 다른 쪽 고유 내용만 이식한 뒤 삭제 |
| 한 노트의 한 섹션이 다른 노트의 본론 | **쪼개어 병합**: 그 섹션을 본론 노트로 옮기고 원 자리에는 한 줄 + 링크 |
| 비교표·정의가 여러 노트에 반복 | 가장 포괄적인 한 곳만 남기고 나머지는 링크 |
| 긴 노트 안의 문제 풀이·실습 나열 | 패턴 1~2개만 남기고 나머지는 삭제. 풀이 자체는 지식이 아니다 |
| 제목에 연도가 붙은 노트, 행사 후기 | 시간이 지나도 남는 원칙만 뽑아 관련 개념 노트에 보강하고 삭제 |
| 화자·시점 서술이 남은 노트 (「글쓴이는」, 「(2021) 현재」, 「글 작성 시점 기준」, 출처 비평형 「한계」) | 사전체로 다시 쓰고, 원문 이후 바뀐 사실을 확인해 최신화한다. 커밋 메시지는 `Refresh knowledge note: <제목>` |
| 2KB 미만의 조각 노트 | 상위 주제 노트가 있으면 섹션으로 흡수. 독립 개념이면 그대로 둔다 |
| 폴더에 노트가 1편 | 폴더를 풀고 상위 폴더로 올린다 (3편 이상일 때만 폴더) |

### 절차

1. 살릴 노트(B)와 사라질 노트(A)를 정한다. B의 frontmatter(`summary`, `tags`, `sources`, `date`)에 A의 것을 합친다.
2. A의 고유 내용만 B의 알맞은 섹션에 **다시 써서** 넣는다. 통째로 붙이지 않는다. 합친 뒤 겹치는 설명은 하나로 줄인다.
3. A로 들어오는 링크를 모두 B로 바꾼다. 위키링크 `[[A|…]]`, 절대 경로 `/knowledge/dictionary/…/A`, 상대 경로 `…/A.md`, 인덱스 노트의 목록 줄까지 전부다.
4. A를 지우고 인덱스 노트에서 A 줄을 삭제·수정한다. 공개 URL이 바뀌거나 사라지므로 `next.config.ts`의 `movedNotes`에 `옛 URL → 새 URL(병합이면 B의 URL)` 한 줄을 추가한다. 노트를 다른 폴더로 옮길 때도 같다.
5. 영향받은 모든 파일에 `check-note.mjs`를 돌린다. 깨진 링크 0, 인덱스 미등록 0이어야 끝이다.
6. 커밋 메시지: `Merge knowledge notes: A → B`, 쪼개어 옮기면 `Move knowledge section: A#섹션 → B`, 삭제만이면 `Remove knowledge note: A`, 여러 건이면 `Reorganize knowledge notes: <분야>`.

## 6. 보고

짧게 보고한다:

- 만든/고친 파일 경로와 사이트 URL(`/knowledge/dictionary/<분야>/<slug>` — 소문자)
- 노트 구성 한 줄 요약, 뺀 내용(불확실한 사실)이 있으면 그것
- 커밋 여부를 AskUserQuestion으로 묻는다. **푸시는 곧 배포**이므로 사용자가 원할 때만 한다.
  커밋 메시지 형식: `Add knowledge note: <제목>` (보강이면 `Update knowledge note: <제목>`)
- 커밋은 노트마다 하되, **푸시는 노트마다 하지 않는다.** 이번 작업의 노트를 모두 커밋한 뒤 한 번만 푸시한다.
  노트마다 푸시하면 빌드(3~4분)가 쌓여 앞 배포가 취소되고, GitHub에 failure로 남는다.
